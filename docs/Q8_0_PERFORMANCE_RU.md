# Q8_0: измерения скорости на локальном ПК

Дата: 3 октября 2026 года. Это продолжение [настройки Q8_0](Q8_0_LOCAL_SETUP_RU.md)
и [исследования подгрузки экспертов Colibri](COLIBRI_DISK_EXPERTS_PLAN_RU.md).
База: Strata `d9ab8435f654c368c586340d490915f6addf56a3`, движок 0.1.35,
локальная поддержка исходной Q8_0 PLE. Нового загрузчика экспертов из Colibri здесь ещё нет.

**Итог:** после закрытия приложений и перезапуска оставлен RAM-кэш **48 GiB**.
В контрольном русском ответе с reasoning получены **2048 токенов за 63,726 с — 32,1 токена/с**,
после запроса доступно 12,23 GiB RAM. Вариант 56 GiB на том же prompt ранее дал
19,0 токена/с и 0,60 GiB доступной RAM, поэтому его короткое преимущество не принято.
Это результаты конкретных последовательных тестов, а не обещание постоянной скорости.
MTP включён и в финальном запросе принял 69,9% предложенных draft-токенов.

## Условия

- Windows 10 Pro, Ryzen 9 9950X, 16 ядер / 32 потока.
- 128 GiB установленной RAM, Windows видит около 125,55 GiB; два модуля по 64 GiB,
  оба работают на 5600 MT/s по `Win32_PhysicalMemory`.
- RTX 5090, 32607 MiB VRAM, драйвер 581.80, локальная сборка CUDA 13.0 / sm_120.
  Стартовая проверка PCIe: 52,4 GB/s host-to-device.
- Samsung 990 PRO 4 TB, диск H:, модель `H:\Q8_0`.
- Unsloth Qwen3.8-Flash-Next Q8_0: шесть GGUF, 175,30 GiB; эксперты 119,53 GiB,
  PLE 50,66 GiB. Ревизия и проверенные размеры — в документе настройки.
- Контекст 8192, MTP `--spec 4`, словарь `cyrillic`, `--ple-io direct`, vision выключен.
- Исходный бюджет экспертов в RAM — 48 GiB, GPU-кэш — 4024 слота / 19,57 GiB.
  Примерно 51,96 GiB экспертных весов остаются на файловом пути.
- Другие приложения продолжали работать. Глобальный файловый кэш Windows не очищался.

## До изменения условий: RAM почти закончилась

Остановленная пользователем длинная генерация: 2194 токена за 268,839 с,
**8,2 токена/с** по журналу движка. Принято 1105 из 2040 предложенных MTP-токенов.
Попадания decode в GPU-кэш — 78,6%. Это другая нагрузка, чем короткие тесты ниже;
сравнивать её 8,2 токена/с с максимальным результатом короткого теста как «ускорение» нельзя.

При сравнении параметров снято 20 системных снимков через примерно 2,8 с:

| Показатель при активной генерации | Минимум | Медиана | Максимум |
| --- | ---: | ---: | ---: |
| Доступная RAM, MiB | 16 | 474,5 | 1064 |
| Физические чтения H:, MB/s | 140,5 | 343,3 | 659,6 |
| Загрузка CPU, % | 38 | 68 | 85 |
| Page reads/s, вся система | 433 | 2573,5 | 9490 |

Page reads включают обращения к отображённым файлам: это не счётчик чтений только
из pagefile. В отдельном снимке pagefile на C: занимал 3622 MiB из выделенных 18211 MiB.
Private bytes Strata были около 80,8 GiB, хотя бюджет экспертного кэша равен 48 GiB.
Он не ограничивает память GPU-драйвера, других буферов, файловых отображений и всей ОС.

Диск действительно работает во время decode. Высокая загрузка GPU сама по себе не
доказывает, что всё время уходит на математику: в движке есть ожидание CPU/экспертного пути.
PLE читает небольшие строки по запросу; её файл размером 50,66 GiB не загружается целиком.
`--ple-io direct` относится к PLE. Холодные **эксперты** здесь всё ещё читаются через mmap,
PrefetchVirtualMemory и сборку трёх срезов gate/up/down в staging-буфер.

## Методика коротких запросов

Последовательные запросы к `/v1/chat/completions`: `temperature=0`,
`reasoning_effort=none`, `max_tokens=128`. Скорость — `timings.predicted_per_second`,
то есть decode отдельно от чтения prompt и HTTP-задержки. Все эти запросы достигли 128 токенов.
Один prompt просит Python-функцию слияния списков и тесты; второй — объяснить холодильник
по-русски. Повторный prompt использует prefix cache, переключение темы — нет.

Параметры передавались через `strata_tune`; это не меняет сохранённую конфигурацию.
Контекст короткий: тесты не характеризуют всю скорость длинного чата или длинного thinking.
Результаты CPU/GPU и разного verify-окна могут немного различаться при близких логитах;
это не проверка качества квантования.

### PCIe

Первичный проход проверил доли 0; 0,2; 0,35; 0,55; 0,75. Исходная доля 0,55 дала
12,3 токена/с в начале прохода и 20,7 в конце. Прогрев сильнее различия ряда настроек.
Отдельный прогрев перед проходом дал 6,2 токена/с; он не включён в результаты настройки.

Следующие 18 запросов сравнили 0; 0,35; 0,55 на двух prompts. Порядок менялся прямой/обратный,
но нулевая доля всегда оставалась посередине. Это даёт ей преимущество уже прогретого prompt;
по этому набору нельзя объявить победителем PCIe=0. Устойчивого преимущества замены
исходных 0,55 эта проверка не установила.

### Порог MTP

Следующие 18 запросов при PCIe=0,55 проверили пороги 0; 0,5; 0,8. В трёх проходах
порядок циклически сдвигался, поэтому каждый вариант побывал первым, вторым и третьим
для каждого prompt. Значение 0 отключает сокращение MTP-окна по вероятности,
а не сам MTP.

| `spec_min_p` | Код: три decode-скорости, токена/с | Русский: три decode-скорости, токена/с |
| --- | --- | --- |
| 0,5, исходный | 13,7; 22,2; 20,4 | 20,0; 30,8; 28,0 |
| 0 | 19,8; 13,6; 24,3 | 24,5; 14,8; 25,5 |
| 0,8 | 25,4; 19,1; 15,5 | 30,2; 30,4; 20,1 |

Порог 0,8 выглядит лучше на русском prompt, хуже на коде. Разброс большой;
оснований менять исходные 0,5 для всех запросов по этой серии нет.

## После закрытия приложений: сравнение бюджетов

Пользователь закрыл неиспользуемые приложения. Затем выполнены три последовательные
серии с перезапуском движка: 32, 48 и 56 GiB резидентных экспертов. В каждой — один
исключённый из таблицы прогрев и восемь измеряемых запросов: код дважды, русский дважды,
затем повтор всей последовательности. Все ответы — 128 токенов, PCIe=0,55, MTP min-p=0,5.

| RAM-кэш | GPU-слоты | Код: медиана / диапазон, токена/с | Русский: медиана / диапазон, токена/с | Минимум доступной RAM после коротких запросов |
| --- | ---: | --- | --- | ---: |
| 32 GiB | 4111 | 18,3 / 13,4–20,5 | 21,4 / 12,5–24,5 | 24,9 GiB |
| 48 GiB | 4392 | 21,7 / 16,8–27,1 | 26,5 / 15,8–33,4 | 21,7 GiB |
| 56 GiB | 4413 | 23,5 / 20,0–26,3 | 27,7 / 14,9–36,4 | 20,3 GiB |

Четыре наблюдения на ячейку. Это последовательное практическое сравнение конфигураций,
а не изолированная оценка одного RAM-параметра: GPU-кэш пересчитывался при загрузке,
файловый кэш между сериями не сбрасывался, возвратная проверка именно короткой серии не выполнялась.
Особенно небольшой прирост 56 против 48 GiB нельзя считать гарантированным.

После освобождения VRAM и перезапуска GPU вместил 4413 экспертов вместо исходных 4024:
на 389, или 9,7%, больше. Резидентный RAM-кэш вырос с 9868 до 11513 экспертов.
Уменьшение кэша до 32 GiB как оптимизация не подтвердилось. Кандидат 56 GiB дал лучшую
короткую серию, но последующий длинный тест снова показал давление на RAM. После этого
бюджет возвращён к 48 GiB для контрольного длинного прогона.

### Где тратится время

Включены существующие `STRATA_DECODE_TIMING=1` и `STRATA_SPLIT_TIMING=1`.
В первом запросе серии 32 GiB, 44 verify-окна, среднее окно заняло 419,71 мс:
342,50 мс — `jobs`, 51,19 мс — CPU expert kernels, 10,06 мс — GPU-reach wait.
`jobs` включает prefetch, ожидание читателей и сборку списка работ; это не чистый
таймер SSD. Тем не менее именно этот участок, вместе с физическими чтениями,
указывает на загрузку экспертов как основное направление оптимизации.

В прогретом русском запросе при 48 GiB окно занимало 68,48 мс, `jobs` — 28,41 мс,
CPU — 16,58 мс. Разница с первым запросом показывает цену прогрева.

### Длинный запрос

При 56 GiB отдельный русский prompt про устройство ОС, `reasoning_effort=medium`,
`temperature=0`, `max_tokens=1024`: prompt 121 токен за 2,339 с; decode 1024 токена
за 35,549 с — **28,8 токена/с**. Весь HTTP-запрос — 37,890 с. Принято 573 из 836
MTP-предложений; GPU hit rate 81,8%. После запроса доступно 7,10 GiB RAM.
Это один запрос после серии прогревов, а не универсальная скорость модели.
Его нельзя напрямую делить на 8,2 токена/с исходного пользовательского ответа:
текст, состояние кэшей и фоновые приложения различаются.

Следующий запрос того же prompt при 56 GiB, с лимитом 2048, показал **19,0 токена/с**:
2048 токенов за 107,852 с. Доступная RAM снизилась с 7,41 до 0,60 GiB. В 24 снимках
во время генерации — 605–1476 MiB. Физически прочитано с H: 23,59 GiB за весь HTTP-запрос;
это отдельный системный счётчик, не логические mmap bytes. MTP принял 1139 из 1702
draft-токенов (66,9%), GPU hit rate 84,6%. Повторное чтение prompt почти полностью
обслужено prefix cache (116 reused, 5 новых токенов).

Это существенно ограничивает вывод по коротким тестам: закрытие приложений и увеличение
резидентного кэша не устранили просадки при росте рабочего набора. Для Q8_0 нельзя обещать
постоянные 28–36 токенов/с на основании прогретого короткого ответа.

После возврата к **48 GiB** сервер перезапущен. GPU-кэш составил 4383 слота / 21,32 GiB,
то есть на 0,7% меньше, чем в тесте 56 GiB. Сначала тот же длинный prompt с лимитом
1024 дал 28,3 токена/с, после чего выполнен запрос с лимитом 2048:

| RAM-бюджет | Decode 2048 токенов | Время decode | Доступно RAM после ответа | Физические чтения H: за HTTP-запрос |
| --- | ---: | ---: | ---: | ---: |
| 56 GiB | 19,0 токена/с | 107,852 с | 0,60 GiB | 23,59 GiB |
| 48 GiB, возвратная проверка | **32,1 токена/с** | **63,726 с** | **12,23 GiB** | **19,12 GiB** |

В финальном 48 GiB запросе prefix cache повторно использовал 116 токенов, прочитал 5;
prompt занял 177,8 мс, весь HTTP-запрос — 63,906 с. Принято 1152 из 1647 MTP-предложений,
GPU hit rate 83,1%. В 13 системных снимках последних примерно 16 секунд генерации
доступно не менее 12994 MiB RAM. Остальные снимки этой телеметрии сделаны уже после ответа.

48 GiB оставлен как более подходящий вариант для текущего ПК. Сравнение не изолирует
чистый эффект 8 GiB: до длинной серии 56 GiB выполнялись ещё короткие запросы двух тем,
а возвратная серия 48 GiB началась в новом процессе с одного длинного запроса; состояние
файлового и адаптивного GPU-кэшей различается. Поведение после многих часов и смен тем
не проверено. Закрытие приложений дало запас памяти, но не устраняет саму необходимость
подгрузки Q8_0 и не заменяет ограниченный cold cache.

### Сохранённая конфигурация

В `strata-q8_0.json` возвращён `--resident-budget-gib 48`. Сохранены исходные
`--expert-cache auto`, резерв VRAM 1536 MiB, `--spec 4`, `--spec-min-p 0.5`,
контекст 8192 и PLE direct. Доля PCIe остаётся штатной 0,55 на этом PCIe probe.
Диагностические переменные записывают по несколько строк на запрос в существующий журнал.
В итоговом запуске GPU-кэш больше первоначального: 4383 против 4024 экспертов (+8,9%).
Веса, квантование, число выбираемых экспертов и контрольные векторы не менялись.

Конфигурация до исследования сохранена в `build-local/strata-q8-before-perf.json`.
`run-q8_0.bat` использует обновлённую конфигурацию. Повторное открытие тяжёлых приложений
изменит условия. Короткого выигрыша 56 GiB недостаточно для увеличения бюджета по умолчанию.

Исходные измерения и скрипт: [bench/results/2026-10-03-local-q8_0](../bench/results/2026-10-03-local-q8_0/README.md).
JSON содержит времена всех запросов, доступную RAM, физические дисковые счётчики и хеши
ответов; полные тексты тестовых ответов сохранены только в локальном `build-local`.

## Что следует из кода и измерений

Главные направления для Q8_0 — уменьшение физических чтений и ожиданий на пути холодных
экспертов. Предложение из исследования Colibri остаётся актуальным: ограниченный cold LRU,
постоянный I/O-пул, приоритет востребованных чтений, перекрытие загрузки и вычисления.
Для Windows полезно отдельно сравнить mmap с явным чтением крупных диапазонов в ограниченный
пул буферов. Это ещё не реализовано и не имеет измеренного ускорения на данном ПК.

Важное ограничение текущей реализации: `FileExpertSource::prefetch()` создаёт потоки чтения
для слоя и делает `join()` до возврата; внутренний `file_us_` складывает времена параллельных
копирований. Его нельзя выдавать за время ожидания I/O на критическом пути. Счётчик
`file_read_bytes()` тоже логический: mmap может обслужить его из RAM. Нужны оба измерения —
логические bytes движка и физические read bytes диска.

Меньшее квантование уменьшает как объём чтений, так и размер эксперта в GPU/RAM-кэше.
UD-Q4_K_XL уже поддерживается штатным установщиком; Q5/Q6 требуют проверки всех tensor formats,
и поддержка одного dense-ядра не гарантирует поддержку всех expert-слоёв. Q8_0 в этой работе
не реквантизировался и другим checkpoint не заменялся.
