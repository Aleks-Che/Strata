# Настройка DSpark и дальнейшее ускорение

Дата: 3 октября 2026. Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ,
Samsung 990 Pro. Target — DeepSeek V4 Flash 0731 `UD-Q3_K_XL`, DSpark — Q8_0.
Контекст 8192, batch 4096, CPU threads 1, pinned staging 2 × 16 МиБ на контекст.
Под нагрузкой `nvidia-smi` показал PCIe **5.0 ×16** при максимуме 5.0 ×16.

## Где проходит время

В предыдущем прогретом замере двух токенов DSpark (`deepseek4-dspark-cache15-2-4k.log`)
на 128 выходных токенов пришлось 50 проверок target. Сам draft занял 549,60 мс,
проверка target вместе с sampling и инъекцией признаков — 7982,34 мс,
весь decode — 8618 мс. Доля draft — около **6,4%**.
Время target включает вычисления, перенос весов, sampling и инъекцию; текущие
таймеры не позволяют приписать все эти 7982 мс одному копированию.

Даже полное устранение этих 550 мс дало бы только около **+6,8%** к скорости
этого запроса при неизменной остальной работе. Поэтому уменьшение DSpark или
размещение всех его экспертов в VRAM не является главным направлением:
отнятая у target память может стоить больше, чем экономия на draft.

Нужно уменьшать число и стоимость проверок target. Сейчас каждый пропуск
кэша означает чтение матрицы из mmap, копирование в pinned RAM, H2D, затем
копирование из GPU-кэша в рабочий тензор. GPU выполняет математику, но ожидает
подачи весов. Разбивка уже идёт по матрицам gate/up/down. Дальнейшее дробление
без перекрытия копирования и вычислений не уменьшает число необходимых байтов.

## Фильтр обученной уверенности

В локальном sidecar присутствует `conf_proj.weight`. Добавлен параметр
`--draft-min-confidence` от 0 до 1; **0 оставляет прежнее поведение**.
При положительном пороге сохраняется только непрерывный уверенный префикс.
Первый токен ниже порога отбрасывается вместе со всем хвостом. После этого
target проверяет оставшиеся токены обычным способом; принятие без проверки
не добавлено. Если отфильтрован весь черновик, target обрабатывает anchor.

Параметр доступен и в `tools/setup_deepseek4.py`. Загрузчик проверяет наличие
веса confidence head до загрузки модели. INFO и About показывают порог.
`STRATA_SPEC_CONFIDENCE_TRACE=1` добавляет в журнал оценки, предложенную и
проверенную длину, принятие и время каждого раунда; без этой переменной
подробная трассировка выключена. Итоговая строка `STRATA_SPEC` содержит
`proposed` и `filtered`; счётчик `offered` означает реально проверенные токены.

Оценка head обучена для распределений, поэтому её нельзя считать точно
откалиброванной вероятностью совпадения greedy-токенов нашей Q3-модели.
В [статье DSpark, раздел 3.2](https://arxiv.org/html/2607.05147v1#S3.SS2)
описываются калибровка, вероятность выживания всего префикса и выбор длины
по стоимости проверки на конкретном железе. Здесь реализован простой
отключаемый порог; полного планировщика по стоимости ещё нет.

## Результаты подбора

Русский запрос — объяснение кэшей L1/L2/L3, 36 токенов prompt. Везде кэши
target/draft 15/1 ГиБ, кроме явно указанного варианта 16/0,5.

| Режим | Прогретый decode, ток/с | Принято / проверено | Повторов |
|---|---:|---:|---:|
| Два токена, прежний замер | 14,85 | 78 / 98 | 1 |
| Один токен | 13,49 | 56 / 71 | 1 |
| Два токена, кэши 16/0,5 ГиБ | 14,65 | 78 / 98 | 1 |
| Три токена, confidence ≥ 0,7 | 12,30 | 64 / 74 | 3 |
| Два токена, confidence ≥ 0,4 | 14,94 | 78 / 96 | 3 |
| Пять токенов, confidence ≥ 0,4 | 11,80 | 77 / 139 | 3 |
| Два токена, write-combined staging | 14,75 | 78 / 98 | 3 |
| Два токена, заключительный контроль | 13,75 | 78 / 98 | 3 |

При трёх повторах указана медиана. Диапазон для двух токенов с порогом 0,4 —
14,90–15,13 ток/с. Два отфильтрованных кандидата из 98 не изменили количество
принятых токенов и число раундов (50); это слишком малое изменение для
заявления о надёжном ускорении. Порог 0,7 повысил долю принятия до 86,5%, но
потребовал 64 раунда вместо 50 и оказался медленнее.

Заключительный контроль без фильтра дал 15,03 / 13,75 / 13,30 ток/с. Общая
загрузка системы доходила до 29,8% против 13,0% в запуске с порогом 0,4;
изолировать фоновые приложения не пытались. Поэтому небольшую разницу
между базовым режимом, WC и порогом 0,4 считать доказанным выигрышем нельзя.
128 token IDs базового режима, двух токенов с порогом 0,4 и WC совпали.

Для второго запроса, генерации Python LRUCache через OrderedDict с type hints,
docstrings и тремя pytest-тестами, prompt — 81 токен:

| Режим | Медиана, ток/с | Диапазон трёх повторов | Принято / проверено |
|---|---:|---:|---:|
| Два токена без фильтра | 12,84 | 12,63–12,90 | 79 / 95 |
| Пять токенов, confidence ≥ 0,4 | 11,06 | 10,39–11,08 | 92 / 146 |

Больше принятых черновиков не компенсировало более дорогую проверку.
Оба запроса ограничены 128 выходными токенами; это не оценка качества кода
или общего ускорения на всех задачах. Полные тексты и ответы находятся в JSON.

Сырые результаты: `bench/results/deepseek4-dspark-tune-*.json` и соседние `.log`.
Имена вариантов: `n1`, `cache16`, `confidence`, `n2-p4`, `n5-p4`,
`code-baseline`, `code-n5-p4`, `write-combined`, `baseline-final`.
Пики CPU процесса — 3,17–3,27% всех 32 логических CPU; аудит графов —
`cpu_compute_nodes=0`. Небольшая загрузка CPU нужна для memcpy, token sampling
и управления GPU; вычисление слоёв на CPU не включалось.

### Проверка staging

Опция окружения `STRATA_EXPERT_STAGE_WC=1` включает `cudaHostAllocWriteCombined`
вместо обычной pinned-памяти. По умолчанию она выключена. CPU только записывает
эти буферы, затем GPU читает их через H2D; CPU не читает WC-память.
Такой режим предусмотрен [CUDA 13.0](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#write-combining-memory),
но выгоды на нашей модели в этом замере нет. Проверка побайтовой точности
кэша, eviction и staging прошла и с обычными, и с WC-буферами.

В рабочем профиле сохранены **два токена, кэши 15/1 ГиБ, фильтр выключен,
обычная pinned-память**. Экспериментальные параметры не включены автоматически.

## Как воспроизвести сравнение

`tools/benchmark_deepseek4.py` теперь поддерживает `--repeats 3` и
`--generation-prompt FILE.txt`. JSON содержит исходный текст, token IDs всех
повторов и медиану `warm_median_tokens_per_second`. Повторы должны давать
одинаковые token IDs внутри одной конфигурации, иначе тест завершается ошибкой.

```powershell
.venv\Scripts\python.exe tools/benchmark_deepseek4.py --config strata-deepseek4-ud-q3-k-xl-dspark.json --prompt-tokens 256 --tokens 128 --repeats 3 --output bench/results/dspark-repeat.json
```

Сначала отдельный prefill на 256 токенов, затем запрос на 128 выходных токенов
и три повтора с восстановлением prompt из RAM. Temperature 0. Файловый кэш ОС
не очищается. Первый decode нельзя использовать для вывода об ускорении:
между запусками меняется резидентность страниц. Даже прогретые результаты на
разных режимах могут относиться к разным ответам, поэтому ниже нет заявления
о сравнении строго одинаковой последовательности вычислений.

## Что имеет смысл делать дальше

1. **Планировщик длины по времени проверки.** Собирать стоимость target для
   1–6 входных токенов и отдельно для прогретого/холодного чтения. Калибровать
   head под фактическое принятие на Q3 и используемом sampling. Останавливать
   расширение префикса, когда ожидаемые выходные токены за миллисекунду падают.
   Один процент принятия без стоимости прохода недостаточен.
2. **Перекрытие чтения, H2D и вычислений — реализовано отдельным этапом.**
   Добавлены фоновое чтение mmap, кольцо staging, отдельный H2D stream и
   зависимости CUDA events для gate/up/down с известными router IDs.
   Устройство, проверки и замеры:
   [DEEPSEEK4_EXPERT_PIPELINE.md](DEEPSEEK4_EXPERT_PIPELINE.md).
3. **Компактные рабочие тензоры экспертов.** Сейчас рабочий адрес соответствует
   исходному expert ID, даже если выбрано несколько экспертов из 256. Remap
   выбранных ID в плотный набор может уменьшить рабочие буферы и оставить
   больше VRAM для кэша target. Это изменение scheduler и CUDA kernels,
   требующее проверки байтов/чисел и измерения после реализации.
4. **Избежать повторного D2D на попаданиях в кэш.** Kernels могут читать
   неизменные матрицы через таблицу адресов кэша. Для этого потребуются
   закрепление используемых слотов до завершения графа и поддержка такого
   размещения в quantized matmul. Сейчас этого нет.

Это направления работы, а не измеренные проценты будущего ускорения.
DSpark ускоряет decode; проблему загрузки длинного prompt нужно измерять
отдельно. Ограничения воспроизводимости между полным prefill, инкрементальным
decode и DSpark сохраняются: см. [DEEPSEEK4_DSPARK.md](DEEPSEEK4_DSPARK.md).
