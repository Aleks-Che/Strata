# Step-3.7-Flash: удачные оптимизации

Сводка на 2026-10-06, Asia/Yekaterinburg, по результатам STEP-05–17.
Здесь собраны изменения с измеренной пользой для скорости или памяти.
Результаты относятся к Step-3.7-Flash, а не к GLM/Qwen/DeepSeek.

Стенд: Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32607 МиБ,
драйвер 581.80. Модель: локальная UD-Q4_K_S, четыре GGUF, 106,323 ГиБ.

## За счёт чего получен выигрыш

1. **Кэш в VRAM** сохраняет часто используемые экспертные матрицы. На попадании
   веса копируются внутри GPU; перенос из RAM не требуется. В STEP-05 доля
   попаданий повторных запросов составила 55,0–64,1%. Первое заполнение кэша
   увеличивало prefill; это учтено отдельной оптимизацией № 3.
2. **Асинхронный конвейер** использует отдельный reader и кольцо staging buffers.
   Подготовка следующей копии может идти параллельно с другими стадиями доставки.
   Результат +7,6% — финальное сравнение sync/pipeline в порядке ABBA;
   разброс между процессами был существенным.
3. **Prefill admission off** убирает заполнение кэша экспертами, полезность
   которых для последующей генерации ещё не установлена. Попадания в существующий
   кэш и учёт частоты сохраняются. На измеренном 511-token prompt накопленные
   prefill cache-fill D2D сократились с 98,128 ГиБ до нуля. При этом decode после
   этого prompt замедлился с 5,459 до 4,608 токена/с: успех здесь — меньшее время
   полного запроса. Последовательность пяти запросов сократилась на 17,1%.
4. **MTP2** предлагает до двух токенов перед проверкой основной моделью.
   Проверенная конфигурация: Q8_0, depth 2, `p_min=0.6`, все три головы на GPU,
   исходный catch-up, общий embedding. Acceptance в контрольных сериях — 92,55%.
   Встроенных экспертов у этого MTP sidecar нет: его головы плотные.
5. **Общий embedding** использует уже размещённую GPU-матрицу основной модели
   после побайтной проверки равенства. Дублирующая embedding и неиспользуемые
   global output/norm остаются в RAM; собственные output/norm каждой MTP-головы
   сохраняются. Успех № 4 уже включает эту оптимизацию: это не два независимых
   процента, которые можно сложить.
6. **Allocation reuse** передаёт новому эксперту GPU-блок вытесненного эксперта
   подходящего размера. Среднее число новых allocations за decode одного ответа
   уменьшилось с 622 до 24,625 без MTP и с 1385,625 до 51,750 с MTP2. H2D-трафик
   почти не изменился; сокращены вызовы `cudaFree`/`cudaMalloc`.
7. **Batching** убирает поштучные ожидания завершения копий. Число host fences
   на copy stream за decode ответа: 71146 → 8820 без MTP, 55813 → 3402 с MTP2.
   Защита используемых cache entries сохраняется до завершения копий.
8. **Early refill** разрешает заново заполнить host buffer после его H2D,
   сохраняя отдельную защиту GPU slot до завершения потребителя. MTP2/batch+early
   был быстрее MTP2/batch во всех четырёх раундах STEP-13. Без MTP устойчивый
   дополнительный выигрыш не установлен.
9. **AVX2 temporal stores** уменьшают стоимость CPU-копирования в pinned buffers.
   В диагностической серии copy throughput вырос с 20,120 до 30,000 ГиБ/с,
   cycles/byte сократились с 0,19957 до 0,13343. Итоговые +7,06% измерены отдельно,
   с выключенными профилировщиками, во всех четырёх парных MTP-раундах был выигрыш.
   Без MTP повторный контроль дал −0,48% по decode, но на 6,62% меньше CPU-с/ответ.

## Как читать числа

Проценты относятся к контрольному варианту **своей серии**. Складывать или
перемножать их для получения общего ускорения нельзя: между этапами менялись
кэш, конфигурации и фон CPU. Единого замера «все оптимизации off → все on» нет.
Скорости разных строк не образуют последовательную лестницу одного benchmark.

Основные decode-серии используют два коротких P1 prompts, 38/34 входных и
54/88 выходных токенов, включая EOG, с повторениями после прогрева.
STEP-05/06 считают forward steps без первого токена из prefill; STEP-11–17 —
все выходные IDs за generation time. Context 2048, batch 17, F32 KV, FA/TF32 off;
STEP-08 использует context 4096 и отдельный 511-token prompt.

В STEP-11–17 offline cache cap — 16384 МиБ с динамическим ограничением по
общей памяти. Это не фактически занятые 16 ГиБ и не лимит HTTP-профиля.
Фоновая CPU-нагрузка не контролировалась. Во всех сериях, на которые ссылается
таблица, сохранены проверки совпадения IDs; для ранних transport stages —
также полных logits. Короткий greedy MTP не подтверждает работу на длинных
диалогах, stochastic sampling и rollback через SWA512.

## Что уже включено и что ещё переносить

В отдельном экспериментальном HTTP-профиле
`build-local/step35-cuda/step10-http-profile-8g/step37.json` уже заданы:
кэш 8192 МиБ, один pipeline reader и `--expert-cache-prefill off`.
Это отдельный профиль; его наличие не означает замену активного профиля приложения.

**STEP-18:** [START-STEP37-FAST.bat и отдельный профиль](STEP37_FLASH_FAST_LAUNCH.md)
добавляют allocation reuse и batching в native pipe/HTTP. Проверены exact
ответы через оба API, cancel/recovery, unload/reload и запрос511+16 с побитовой
проверкой logits. Профиль использует cap8GiB; проценты STEP-12/13 в таблице
получены на прежних offline cap16GiB и не являются новым HTTP speed benchmark.

Early refill, AVX2 и MTP остаются кандидатами checker. Для MTP нужны
state/rollback/sampling и integration gates. Предельные pressure/OOM проверки
остаются открытыми. Прежний `strata-step35.exe` после STEP-08 не заменялся:
новый запуск использует отдельный `strata-step35-fast.exe`.

Текущие варианты для дальнейших проверок: без MTP — reuse + batch + CRT;
с MTP — Q8_0/shared embedding/depth2 + reuse + batch-early + AVX2.
В обоих случаях reader1/chunk8, cacheable pinned RAM, baseline victim scan,
prefill admission off и выключенные диагностические profilers.
