## Один и два потока чтения

Каждая конфигурация прогрета на двух P1 prompts, затем четыре парных раунда.
Порядок конфигураций меняется на обратный в нечётных раундах.

| Режим | Один поток, токена/с | Два потока, токена/с | Изменение decode | Полная пара, с |
|---|---:|---:|---:|---:|
| Без MTP, batch | 10,224 | 10,188 | −0,35% | 17,916 → 17,914 |
| MTP2, batch + early | 12,203 | 12,572 | +3,03% | 16,009 → 15,435 (−3,58%) |

Без MTP выигрыша не получено. С MTP2 два потока быстрее во всех четырёх
парных раундах: 13,242/12,499/12,310/12,284 против
12,670/12,154/11,780/12,240 токена/с. Один и два потока используют одинаковую
ёмкость ring; это параллелизм подготовки весов, а не увеличение GPU-кэша.

Во время reader/depth серий наблюдалась сторонняя CPU-нагрузка, в том числе
Blender и фоновая загрузка. Эти процессы не останавливались. Поэтому абсолютные
скорости нельзя напрямую сравнивать с STEP-13 (11,364/13,941 токена/с).
Сравнение выше относится к чередующимся конфигурациям внутри каждой серии;
даже такое сравнение не исключает влияние меняющейся нагрузки.

## Размер буфера

MTP2, batch+early, два потока; по два прогревочных запроса на конфигурацию
и два измеряемых раунда с обратным порядком во втором.

| Один slot | Decode, токена/с | Полная пара, с | Pinned RAM / GPU ring |
|---|---:|---:|---:|
| 4 МиБ | 13,215 | 14,781 | 16 /16 МиБ |
| 8 МиБ | 13,325 | 14,556 | 32 /32 МиБ |
| 16 МиБ | 13,384 | 14,525 | 64 /64 МиБ |

16 МиБ дал лишь +0,44% decode и −0,21% времени пары относительно8 МиБ.
Двух раундов недостаточно, чтобы признать такую разницу устойчивой. Для
следующего depth sweep сохранены8 МиБ. Каждая routed матрица имеет размер
2,8125 МиБ плюс не более512 байт tail и помещается в любой из этих slots.
Pipeline дробит отдельные slices, но не объединяет их при увеличении chunk;
сама форма H2D jobs в этих вариантах одинакова. Это проверка ёмкости,
а не эксперимент по укрупнению transfer jobs.

## Повторный выбор глубины MTP

Batch+early, два потока,8 МиБ; по два warmups на depth, четыре парных раунда.

| Глубина | Decode, токена/с | Accepted/proposed |
|---|---:|---:|
| MTP1 | 11,956 | 268/276 =97,10% |
| MTP2 | 12,576 | 348/376 =92,55% |
| MTP3 | 12,986 | 384/440 =87,27% |

MTP3 опередил MTP2 в среднем на3,26%, но не во всех раундах. Более низкий
acceptance сам по себе не исключает ускорение: проверяется больше кандидатов
за один target pass. Эта серия ещё не подтверждает окончательный выбор.

В заключительной серии сравнены четыре сочетания MTP2/3 ×1/2 readers.
Для неё добавлен `cpu_load`: процессорное время системы и model child вокруг
каждого запроса. Проценты от всей CPU-мощности ПК; разность включает другие
приложения, ОС и часть работы драйверов, это оценка сопутствующей нагрузки.
Измерение не останавливает процессы и не устраняет влияние нагрузки.

## Заключительный контроль

По два warmups на конфигурацию и четыре измеряемых раунда, batch+early,8 МиБ.
CPU-проценты усреднены по времени запросов; они относятся ко всему32-поточному ПК.

| Глубина / readers | Decode, токена/с | Полная пара, с | CPU модели | CPU вне model process |
|---|---:|---:|---:|---:|
| MTP2 /1 — текущий кандидат | 13,359 | 14,661 | 4,39% | 7,90% |
| MTP2 /2 | 13,109 | 14,825 | 6,56% | 9,00% |
| MTP3 /1 | 13,434 | 14,610 | 4,44% | 7,78% |
| MTP3 /2 | 13,444 | 14,468 | 6,63% | 8,91% |

Второй поток при MTP2 теперь медленнее на1,88%, вместо первоначальных +3,03%.
При одном потоке переход MTP2 →MTP3 даёт только +0,56% decode и −0,34% времени
пары. Лучшее среднее MTP3/2 превосходит текущий MTP2/1 на0,63% decode и1,31%
полного времени пары. Преимущество по decode не сохраняется во всех раундах.
Такие малые различия при меняющейся нагрузке не дают основания менять default.

H2D за генерацию в этих четырёх вариантах в среднем72,84–73,84 ГиБ на ответ:
сам перенос весов практически не уменьшился. Высокий acceptance или больше
readers не заменяют повторяемый результат по времени.

## Реализация и метод

`check_mtp.cpp` принимает `pipeline_readers` (1/2) и `pipeline_chunk_mib`
(4/8/16) на каждый запрос. Оба значения проверяются и возвращаются в RESULT.
READY описывает начальную конфигурацию. `pipeline_configure_ms` хранит время
переключения отдельно: настройка происходит до таймера запроса. При замене
ring используются существующие drain, budget check и ограниченный cache trim.

`tools/check_step35_mtp.py` добавляет декартов перебор через
`--pipeline-readers` и `--pipeline-chunks`. Значения по умолчанию остаются 1/8.
Runner проверяет подтверждение параметров и все output IDs. Старые сохранённые
probe binaries по-прежнему допускаются для фиксированных 1/8; новые значения
без подтверждения отклоняются. Сам алгоритм общего pipeline не изменён.

Стенд: Windows, Ryzen 9 9950X, RAM128 ГиБ (125,555 ГиБ видимо), RTX5090
32607 МиБ, driver581.80. Наблюдались PCIe5 ×16, GPU P0/2767 МГц,
power limit400W; настройки питания не менялись.

Main — Step-3.7-Flash UD-Q4_K_S, 106,323 ГиБ. MTP — официальный Q8_0 с
проверенным SHA-256, shared embedding, все три головы в VRAM, исходный catch-up.
Context2048, batch17, F32 KV, FA/TF32 off, p_min0.6, prefill admission off,
cache reuse on, cache cap16384MiB с динамическим ограничением по глобальной VRAM.
Без MTP draft не загружается. Свежие KV/speculative state на каждый запрос,
expert cache сохраняется внутри процесса. Модельные файлы открываются для чтения.

Два P1 prompts: 38/34 входных и 54/88 выходных токена, включая EOG.
Decode = сумма output tokens / сумма generation seconds. Полная пара включает
prefill, исключает загрузку и переключение конфигурации. Это короткие repeated
prompts, а не разные задачи или оценка длинного контекста. Все результаты
проверяются против сохранённых native IDs.
