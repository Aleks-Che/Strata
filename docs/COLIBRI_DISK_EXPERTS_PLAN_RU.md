## Вывод

Strata уже умеет запускать Qwen3.8-Flash-Next, когда эксперты не помещаются в выделенную RAM:
для Unsloth UD-Q4_K_XL есть ограниченный резидентный набор и чтение остальных экспертов
из GGUF через отображение файлов в память. Есть предсказание маршрутизации следующего
слоя и предварительное чтение его страниц.

Из Colibri полезнее перенести устройство управляемого дискового пути:

1. Ограниченный долгоживущий RAM-кэш недавно использованных холодных экспертов.
2. Постоянный пул чтения с готовностью каждого эксперта отдельно.
3. Перекрытие чтений с CPU-вычислениями уже готовых экспертов.
4. Планирование полного пика памяти, включая промежуточные буферы и файловый кэш ОС.
5. Сохранение статистики использования экспертов между запусками.
6. Раздельные измерения логических чтений, физических чтений SSD и ожидания данных.

Первый контрольный вариант — уже поддерживаемый UD-Q4_K_XL с ограничением RAM.
Целевой более крупный вариант — Q8_0 той же модели. В исходной версии обнаружен блокер:
его PLE-таблица тоже имеет формат Q8_0, который `PleTable` отклонял. Во время последующей
настройки поддержка Q8 PLE добавлена и проверена; детали — в [отчёте настройки](Q8_0_LOCAL_SETUP_RU.md).

## Этот компьютер

Характеристики прочитаны через Windows CIM/Storage API и `nvidia-smi`. Свободные объёмы
относятся к моменту проверки и изменятся при запуске других программ.

| Ресурс | Результат проверки |
| --- | --- |
| ОС | Windows 10 Pro, 10.0.19045 |
| CPU | AMD Ryzen 9 9950X, 16 ядер / 32 потока |
| RAM | Класс 128 ГБ; Windows видит 125,56 GiB, свободно около 87,57 GiB |
| GPU | NVIDIA GeForce RTX 5090, 32 607 MiB VRAM, свободно 23 978 MiB, около 23,42 GiB |
| Драйвер NVIDIA | 581.80 |
| NVMe | Три Samsung SSD 990 PRO 4TB: тома `C:`, `H:`, `I:` |
| Свободно на NVMe | `C:` 66,26 GB / 61,71 GiB; `H:` 177,48 GB / 165,30 GiB; `I:` 27,57 GB / 25,68 GiB |
| Другие накопители | SATA HDD; не выбраны для первого эксперимента с холодными экспертами |

Здесь и далее GB = 10^9 байт, GiB = 2^30 байт.

UD-Q4_K_XL может разместить всех экспертов в RAM+VRAM этого ПК при достаточном запасе
памяти. Поэтому обычный запуск Q4 сам по себе не доказывает эффективность SSD-пути.
Нужен явный бюджет RAM и измерение фактических чтений: оставшуюся часть модели может
незаметно удерживать файловый кэш ОС.

На `H:` достаточно места для исходных файлов Q4 и обычных подготовительных файлов.
Полный Q8_0, 188,23 GB без pack и MTP, сейчас не помещается целиком ни на одном NVMe.
Суммарно место на NVMe есть, но штатная схема держит GGUF-шарды рядом. Для простого
первого размещения Q8 следует освободить место на одном NVMe; ориентир 220–230 GB
свободного места включает запас, а точный расчёт надо повторить перед загрузкой.
Файлы на дисках в ходе исследования не переносились и не удалялись.

## Что действительно реализовано в Colibri

Colibri ориентирован на GLM-5.2, имеет другие внимание, роутер, размеры экспертов
и контейнер весов. Переносимыми являются принципы хранения и исполнения, а не его
математический forward или собственные int4/int8-контейнеры.

### Ярусы хранения

В `moe()` поиск идёт через закреплённые горячие эксперты, затем RAM LRU конкретного слоя,
затем загрузку с диска во временный слот. После вычисления холодный эксперт может попасть
в LRU обменом буферов, без ещё одного копирования всего эксперта.

Термин pin в Colibri означает прежде всего удержание в hot-store. Это не обязательно
CUDA-pinned или заблокированная физическая память: механизмы `mlock` и загрузки в VRAM
включаются отдельно.

Источники: [`c/glm.c`, `moe`, `pin_load`](../../colibri/c/glm.c),
[`c/tier.h`](../../colibri/c/tier.h).

### Чтение и вычисление

`expert_load()` читает gate/up/down позиционными чтениями в переиспользуемый slab.
Когда три матрицы соседствуют в одном файле, веса читаются одним объединённым запросом;
масштабы квантования читаются отдельно. При раздельном расположении остаются отдельные
чтения. Тензоры становятся представлениями внутри slab.

Опциональный `PIPE=1` создаёт постоянные I/O-потоки. Они загружают экспертов в разные
слоты и выставляют отдельные флаги готовности. Основной поток ждёт только эксперта,
который нужен для следующего вычисления. Generation-теги не позволяют старому заданию
использовать слот нового пакета. Все загрузки слота должны завершиться до его повторного
использования. Это полезный контракт для Strata, но копировать конкретную lock-free
реализацию необязательно.

Важное ограничение для нашего Windows: `posix_fadvise` в Colibri является no-op.
Его WILLNEED/DONTNEED не дадут эффекта при прямом переносе. Strata уже использует
`PrefetchVirtualMemory` на Windows.

Источники: [`c/glm.c`, `expert_load`, `pipe_dispatch`, `pipe_wait`](../../colibri/c/glm.c),
[`c/st.h`](../../colibri/c/st.h), [`c/compat.h`](../../colibri/c/compat.h).

### Планирование и обучение кэша

Colibri считает доступную память, резидентные веса, рабочие слоты, KV и временные буферы.
Отдельно оставляет запас для ОС и page cache. Утилита `coli plan` читает заголовки весов
и показывает раскладку Disk/RAM/VRAM до инференса.

Статистика использования сохраняется в `.coli_usage`, затем используется при старте.
Опциональный `REPIN` меняет горячие эксперты с гистерезисом и ограничением числа замен.
Сами численные константы GLM нельзя переносить на Qwen без расчёта и измерений.

Источники: [`c/resource_plan.py`](../../colibri/c/resource_plan.py),
[`c/glm.c`, `usage_save`, `cap_for_ram`, `repin_pass`](../../colibri/c/glm.c).

## Сравнение с текущей Strata

| Механизм | Что есть в Strata | Что стоит добавить |
| --- | --- | --- |
| SSD как источник экспертов | GGUF in-place через mmap/MapViewOfFile и `--resident-budget-gib` | Сделать этот режим управляемым независимо от одной записи модели в setup |
| Горячие эксперты | GPU-кэш, профиль, RAM complement, адаптивные обмены GPU/RAM | Сохранение пользовательской статистики и отдельная политика удержания холодных экспертов |
| RAM LRU | Есть короткоживущий пул собранных blobs с возрастом/порядком использования | Отдельный кэш с явным бюджетом байт, сохраняющий данные между полными проходами модели |
| Параллельные чтения decode | `prefetch()` создаёт потоки чтения, затем делает `join()` всех | Постоянный пул, отдельная готовность и вычисление готовых групп без ожидания всего слоя |
| Prefill | Уже есть асинхронный `Stager`, кольцо буферов и CUDA events | Переиспользовать его контракты времени жизни, не создавать второй несовместимый механизм |
| Предсказание следующего слоя | Уже есть `RouterLookahead`, отдельный поток и `warm()` | Приоритет обязательных чтений, дедупликация с прогнозом, измерение полезности прогнозов |
| Batch-union | Уже есть группировка повторяющихся экспертов для verify | Сохранить её в новом загрузчике; не читать эксперт отдельно на каждый draft-токен |
| Прямой I/O | Уже есть Windows/Linux `DirectFile` для PLE | Рассмотреть backend для экспертов, сохранив buffered/mmap как вариант A/B |
| Профиль использования | Есть поставляемый профиль, runtime heat, `--dump-routing`, `make_profile.py` | Автоматическое сохранение статистики с привязкой к конкретной модели |
| Выбор speculative window | `DraftPolicy` уже учитывает измеренное время раундов | Дополнить измерениями холодных чтений и разделением cold/warm-состояний |

Основные подтверждения в коде Strata:

- [`FileExpertSource`](../include/strata/core/expert_source.hpp): интерфейсы `blob`, `copy_blob`,
  `prefetch`, `warm`, RAM complement и счётчики.
- [`expert_source.cpp`](../src/core/expert_source.cpp): `open_gguf` около строки 566,
  `claim_stage` 666, `prefetch` 751, `warm` 814, `pin_cache_complement` 988.
- В `prefetch()` после запуска чтений вызываются `join()`. В dispatch около строки 1764
  этот вызов предшествует подготовке и запуску CPU jobs. GPU-работа при этом уже может
  выполняться: речь именно о дополнительном перекрытии SSD и CPU, а не об отсутствии
  любого перекрытия в существующем движке.
- [`prefill.cpp`](../src/prefill/prefill.cpp): `Stager` около строки 159; ветка `stream_all`
  заранее ставит в очередь всех нерезидентных на GPU экспертов диапазона слоёв.
- [`direct_file.hpp`](../include/strata/platform/direct_file.hpp) и
  [`direct_file.cpp`](../src/platform/direct_file.cpp): платформенный асинхронный I/O.
- [`draft_policy.cpp`](../src/spec/draft_policy.cpp): выбор по токенам на миллисекунду.

Текущий stage pool нельзя считать отсутствующим кэшем: он уже дедуплицирует запросы
и переиспользует недавно собранные blobs. Но его возраст примерно в три смены слоя
и эвикция по последовательности сборок не дают управляемой гарантии сохранения эксперта
до следующего токена через все 48 слоёв. При занятости слотов он также может создавать
новые буферы, вместо соблюдения отдельного жёсткого бюджета.

## Какие изменения внедрять

### 1. План памяти и измерения до изменения политики

Ввести единый расчёт в байтах:

```text
RAM процесса = host-веса и служебные данные
             + горячие эксперты RAM
             + LRU холодных экспертов
             + in-flight чтения и сборка blobs
             + prefill staging и буферы обмена GPU/RAM
             + KV/снимки диалогов
             + временные активации и запас
```

Файловый кэш ОС учитывать отдельно через доступную физическую память; не объявлять
`resident-budget` пределом всей памяти процесса. Бюджеты RAM и VRAM рассчитывать по
текущему свободному объёму. На этом ПК свободны не все установленные 128/32 ГБ.

Размеры брать из GGUF/native manifest каждого слоя: у UD-Q4_K_XL форматы слоёв отличаются.
Стоимость преобразованного `dense.bin` считать отдельно от размера исходных dense-тензоров.

Добавить счётчики попаданий VRAM/hot RAM/cold LRU, bytes queued/completed, ожидания данных,
занятых слотов и памяти. Существующий `file_read_bytes` считает логические копирования
из mapping и не доказывает, что эти байты действительно прочитал SSD.
Сумма времени чтения по потокам также не равна задержке запроса.

### 2. Ограниченный кэш холодных экспертов

Начать с простого per-layer LRU с общим пределом байт. Сравнить с базовым вариантом при
одинаковой суммарной памяти экспертов, например:

- baseline: 48 GiB горячей RAM;
- вариант A: 40 GiB горячей RAM + 8 GiB cold LRU;
- вариант B: 32 GiB горячей RAM + 16 GiB cold LRU.

Это точки эксперимента, не утверждение об оптимальных настройках. Память временных
буферов учитывается сверх этих 48 GiB внутри общего плана.

Нужны явные состояния слота `empty/loading/ready/failed`, поколение и удержание слота
потребителем. Указатель должен жить до завершения CPU job, CUDA DMA и адаптивной замены,
которые его используют. Одного возраста в слоях для нового async-пути недостаточно.
Подходящий интерфейс — handle/lease вместо незащищённого долгоживущего raw pointer.

Не дублировать экспертов GPU в RAM без причины. Но сохранить необходимые копии для
prefill lending и существующий протокол обмена complement: это часть корректности,
а не просто политика вытеснения.

### 3. Асинхронное чтение decode

Разделить «поставить чтения» и «дождаться нужного blob». Постоянные I/O-потоки читают
данные, CPU начинает вычислять резидентные или уже готовые группы. Это потребует изменения
не только `prefetch()`, но и dispatch/интерфейса CPU pool: сейчас jobs готовятся после
получения указателей на все нужные blobs.

Обязательные свойства:

- одно чтение для одинакового `(model, layer, expert)` в текущем пакете;
- готовность публикуется только после полной успешной загрузки;
- читающийся или используемый слот нельзя вытеснить;
- generation защищает от позднего завершения предыдущего запроса;
- отмена и выгрузка модели завершают либо отменяют I/O до освобождения буферов;
- ошибки и короткие чтения возвращаются как ошибки, а не как частично готовые веса;
- порядок записи результатов и итогового суммирования не меняется;
- I/O-потоки и CPU-вычисления имеют отдельные лимиты, без бесконтрольного oversubscription.

### 4. Явный backend чтения и расположение весов

Сначала сохранить GGUF in-place и сравнить mmap с явными позиционными чтениями.
На Windows использовать собственные платформенные примитивы Strata. `DirectFile` даёт
основу для NO_BUFFERING/OVERLAPPED, но экспертам нужны выравнивание диапазонов, сборка
трёх ролей, обработка границ файла и управление большим числом живых buffers.

По примеру Colibri можно исследовать отдельный pack с соседними gate/up/down эксперта.
В исходном GGUF они часто разнесены, иногда между шардами, поэтому одно чтение нельзя
получить простой заменой `memcpy` на `pread`. В Strata уже существует опциональный
`experts.bin`, содержащий последовательные blobs: оценить его как отдельную ветку,
а не вводить новый формат без необходимости.

Минус pack — дополнительное место: Q8-эксперты сами занимают 128,35 GB. Для первого
опыта предпочтительнее читать GGUF напрямую. Сохранять квантованные байты без
реквантования и проверять manifest/идентичность источника.

Buffered I/O и direct I/O измерять отдельно. Direct I/O помогает контролировать
расход RAM и проверять реальные холодные чтения, но может потерять полезный cache hit ОС.
Нельзя обещать, что он всегда быстрее.

### 5. Профиль, prefetch и speculation после базовых измерений

Сохранять пользовательскую heat map атомарно и привязывать к ревизии модели, layout
и числу экспертов. Использовать затухание и гистерезис, чтобы кэш не менялся постоянно.
Не ограничиваться доработкой `make_profile.py`: его текущий алгоритм сохраняет порядок
базового профиля, поэтому требуется определить правила смешивания с новой статистикой.

Уже существующий `RouterLookahead` должен использовать очередь с меньшим приоритетом,
чем реальные misses. Измерять, сколько прогнозов потреблено вовремя и сколько лишних
байт прочитано. На насыщенном SSD неверные прогнозы могут задерживать обязательные чтения.

MTP оценивать по конечным токенам в секунду и байтам SSD на принятый токен. Высокая
доля принятых draft-токенов сама по себе не означает ускорения: verify запрашивает
объединение экспертов нескольких позиций. Существующую политику времени раундов
нужно расширять, а не заменять фиксированным правилом «больше draft — лучше».

## Квантование для первого и следующего этапа

### Контрольный вариант: Unsloth UD-Q4_K_XL

Уже документирован и поддерживается установщиком. Эксперты занимают около 71,7 GiB,
исходные четыре GGUF — 111 334 654 784 байта. PLE — IQ4_NL, знакомый движку.
Gate/up используют Q4_K/Q5_K, down — Q5_1/Q8_0 в зависимости от слоя.

Первый опыт: одна RTX 5090, текст, контекст 8K, бюджет экспертов 32/40/48 GiB,
`--expert-cache auto`. Сначала фиксированные GPU residency и размер verify-окна,
потом отдельные прогоны с адаптацией и MTP. Значения являются матрицей проверки,
готовая рабочая конфигурация в ходе исследования не создавалась.

Замер из [UNSLOTH_Q4.md](UNSLOTH_Q4.md): на Windows 10, RTX 5070 12 ГБ,
64 ГБ RAM и AVX-512 CPU при RAM-бюджете 40 GiB — 6,7–8,6 токена/с в шести запусках
короткого greedy-запроса. Это не прогноз для RTX 5090 и не обещание выигрыша от Colibri.

### Целевой более крупный вариант: Q8_0

Проверен каталог Unsloth и GGUF-заголовки на закреплённой ревизии
`38bb39ee97821de2c9009abb7e93950eec396e66`. Для каждого из шести шардов прочитан только
начальный HTTP Range до 1 MiB; модель целиком не скачивалась. Шард 1 содержит метаданные
и не содержит тензоров; таблицы тензоров остальных шардов помещаются в этот диапазон.

| Часть | Размер по каталогу и заголовкам |
| --- | ---: |
| Шесть файлов всего | 188 225 033 248 байт / 175,30 GiB |
| 144 expert-тензора, все Q8_0 | 128 345 702 400 байт / 119,53 GiB |
| Один эксперт: gate + up + down | 5 222 400 байт / 4,98 MiB |
| PLE: `[160, 320001536]`, Q8_0 | 54 400 261 120 байт / 50,66 GiB |
| Остальные данные, включая заголовки | Около 5,10 GiB; это не оценка runtime RAM/VRAM |

Источник файлов: [Unsloth Q8_0 на закреплённой ревизии](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF/tree/38bb39ee97821de2c9009abb7e93950eec396e66/Q8_0).

Q8_0 выбран кандидатом потому, что grouped expert kernels, CPU-путь, dense MMVQ и MMQ
в Strata уже имеют поддержку Q8_0; есть синтетическая проверка пары Q8_0/Q8_0.
Это уменьшает объём работы с экспертными ядрами, но не подтверждает работоспособность
всего checkpoint. Полный prefill/decode и преобразования pack ещё требуют проверки.

**Обнаруженный блокер исходной версии — PLE.** `PleTable::open()` в
[`src/kernels/ngram.cpp`](../src/kernels/ngram.cpp) разрешал IQ4_NL, Q5_0 и специальный FP8,
но отклонял Q8_0. План устранения (пункты 1–5 уже выполнены при локальной настройке):

1. Добавить чтение Q8_0 PLE без реквантования: одна строка — пять блоков по 34 байта,
   то есть 170 байт.
2. Расширить `PLE_ROW_BYTES_MAX` в
   [`include/strata/kernels/ngram.hpp`](../include/strata/kernels/ngram.hpp): исходный максимум 160.
3. Добавить выбор формата и деквантизацию пяти Q8_0-блоков, обновить сообщения и описание формата.
4. Проверить mmap/direct пути, последнюю строку и строку, пересекающую границу 4 KiB.
   Нижний `PleReader` уже принимает переменный `row_bytes` до 4096, но его поддержку
   170-байтовых строк надо подтвердить тестами.
5. Проверить pack с `--compat-bf16`, все шесть шардов и согласованность остальных тензоров.
6. Добавить Q8_0 в setup только после проверок; сейчас таблица моделей и RAM-budget
   в установщике специально выделяют UD-Q4_K_XL.

Подмена PLE на IQ4_NL из другого варианта создала бы смешанный checkpoint. Для честной
валидации Q8_0 использовать его собственную таблицу.

В начальной конфигурации разумно проверить 48 GiB RAM под экспертов и общий целевой
пик процесса около 64 GiB при 8K контексте. Это проектный бюджет, не измеренный расход
и не существующий флаг жёсткого ограничения всего процесса. Перед запуском рассчитать
dense/KV/staging и свободную VRAM заново. Большой файл не обязан целиком помещаться
в RAM: PLE и холодные эксперты должны читаться по запросу.

Другие варианты каталога: UD-Q5_K_XL — 158,29 GB, UD-Q6_K_XL — 169,17 GB.
Их tensor layouts в этом исследовании полностью не проверялись. Поддержка Q6_K в dense
MMVQ не означает поддержку Q6_K в grouped expert kernels: последняя сейчас отсутствует
в списках допустимых expert-форматов. Поэтому выбирать их только по названию квантования нельзя.
Источники: [Q5](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF/tree/38bb39ee97821de2c9009abb7e93950eec396e66/UD-Q5_K_XL),
[Q6](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF/tree/38bb39ee97821de2c9009abb7e93950eec396e66/UD-Q6_K_XL).

## Как оценивать скорость без необоснованных обещаний

Для Q8_0 один обычный decode-токен при отсутствии любых cache hits требует до
`48 × 10 × 5 222 400 = 2 506 752 000` логических байт экспертов, около 2,51 GB.
Это расчёт по геометрии модели, без PLE, выравнивания I/O и speculative verification.

```text
bytes_per_accepted_token = физические байты чтений / число принятых токенов
I/O ceiling tokens/s     = измеренная полоса чтения / bytes_per_accepted_token
```

Например, при измеренной эффективной полосе 3 GB/s и 0,5 GB физических чтений
на принятый токен потолок от диска составит 6 токенов/с. Это арифметический пример,
не результат для Samsung 990 PRO или нашего ПК. CPU/GPU, зависимость слоёв и задержки
чтений могут дополнительно снижать скорость. Скорость диска из рекламной спецификации
не заменяет случайные чтения реальных expert-диапазонов.

## Этапы внедрения и критерии проверки

| Этап | Результат | Условие перехода |
| --- | --- | --- |
| 0. Базовая линия | UD-Q4_K_XL при заданных бюджетах, отдельные cold/warm измерения | Известны пик RAM, физические чтения, prefill/decode и ожидание I/O |
| 1. Учёт памяти и cold LRU | Явные бюджеты, удержание слотов, отдельные счётчики | Соблюдается бюджет; корректность при вытеснении и переменных размерах |
| 2. Async decode | Постоянный I/O-пул и вычисление готовых групп | Нет гонок/зависаний; результаты совпадают при неизменном вычислительном пути |
| 3. Q8 PLE и checkpoint | Поддержка исходного Q8_0, pack и настройка запуска | Проверены PLE, prefill, decode и сравнение с эталоном того же файла |
| 4. Политики | История использования, приоритет prefetch, адаптация окна | Повторяемый выигрыш на нескольких нагрузках при одинаковых бюджетах |
| 5. Prefill и layout | Выбор чтений по фактическому union, сравнение GGUF/pack/direct | Выигрыш оправдывает память, дисковое место и сложность |

Для длинного prefill объединение маршрутов часто охватывает почти всех экспертов слоя.
Поэтому отказ от чтения неиспользуемых экспертов не обязан давать большой выигрыш,
а раннее чтение всех экспертов может лучше скрывать задержку. Это отдельный эксперимент.

Минимальные проверки реализации:

- Полное совпадение байтов blobs нового загрузчика с текущими GGUF slices, включая split роли.
- Переменные размеры Q4-слоёв, повторные запросы одного blob, короткие чтения и ошибки файла.
- Вытеснение занятого слота запрещено; поздние completions, cancel, unload и shutdown безопасны.
- Для фиксированных kernels, residency и verify-окна I/O-политика не меняет токены/логиты.
- Для другого квантования — сравнение с эталонным движком на том же checkpoint;
  не требовать совпадения Q8 с IQ3 или Q4.
- Q8 PLE: 170-байтовые строки, край файла, границы страниц, direct и mmap, деквантизация против ggml.
- Cold LRU не вызывает регрессии обычного режима, где эксперты уже находятся в RAM.

Матрица измерений: короткий чат, код, смена темы, повторный диалог, prefill 4K/16K;
RAM experts 32/40/48 GiB; фиксированные окна без draft и с несколькими размерами draft;
lookahead выключен/включён. После базовых сравнений — адаптивные политики.
Не обязательно выполнять полное декартово произведение: сначала выбрать контрольные
случаи, затем расширять только при обнаружении различий.

Каждый отчёт должен содержать commits, модель и ревизию, команды, бюджеты, число запусков,
медиану и разброс, политику прогрева, фактические GPU/RAM/disk показатели.
Не сбрасывать глобально файловый кэш рабочего ПК ради теста. Для повторяемого cold-I/O
использовать отдельную проверку direct backend или явно описанные первые чтения;
перезапуск процесса сам по себе не делает файловый кэш холодным.

## Что не переносить на первом этапе

- Архитектуру GLM, MLA, его роутер и собственный формат квантования Colibri.
- Уменьшение числа выбранных экспертов ради скорости: это меняет вычисления модели.
- Одновременную переработку multi-GPU, vision и персистентного кэша диалогов.
- Предположение, что «часто используемый» эксперт обязан всегда иметь копию и в RAM, и в VRAM.
- Константы числа потоков, размеров буферов и порогов Colibri без измерений на Qwen.

Colibri распространяется под Apache-2.0, Strata — под MIT. Этот документ переносит идеи
и указывает источники; код из Colibri в Strata не копировался.

## Состояние после исследования

Проверены исходники обоих проектов, характеристики этого ПК, наличие и размеры вариантов
на Hugging Face, типы тензоров Q8_0 по заголовкам. Сформирован план изменений и проверки.
На момент этого исследования скорость Q8_0 ещё не была измерена. Позднее выполнены
[реальные замеры Q8_0](Q8_0_PERFORMANCE_RU.md): они подтвердили большую долю времени
подготовки/подгрузки экспертов и зависимость от прогрева. Новый cold LRU и pipeline
из этого плана ещё не реализованы; их ускорение по-прежнему не измерено.
