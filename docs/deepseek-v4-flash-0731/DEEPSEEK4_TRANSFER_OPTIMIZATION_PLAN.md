# План оптимизации подкачки и CPU lane после этапа 5

13 октября 2026. О0 и О1 выполнены в описанной области:
[измерения по фазам и исправление CUDA Graph](DEEPSEEK4_TRANSFER_O0_O1.md).
Следующий этап — О2. Принятого ускорения относительно рабочего GPU-only пока нет.

Основание — [аудит замедления при нуле CPU-заданий](DEEPSEEK4_ZERO_CPU_QUEUE_AUDIT.md)
и [проверка полной связки](DEEPSEEK4_CPU_STAGE5_COMPARISON.md).
Этот документ задаёт следующий порядок работ. Предыдущий
[план внедрения CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md)
сохраняет историю реализации и её ограничения.

Цель: сначала вернуть эффективную передачу весов и использование GPU-кэша,
затем проверить дополнительный выигрыш от CPU-экспертов. Длинный prefill остаётся
на GPU. CPU lane — опциональный режим для decode и короткой проверки draft.
Сохраняются DSpark, матричный кэш, сессии и отдельная поддержка Qwen.

## Что уже установлено

ПК: Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows.
Target: DeepSeek-V4-Flash-0731 UD-Q3_K_XL; DSpark Q8_0.

| Наблюдение | Следствие для плана |
|---|---|
| При нуле CPU-заданий прежняя подкачка дала 12,71, новая — 5,20 ток/с в A/B/B/A | Начинать с пути передачи, а не с CPU-ядер и числа потоков |
| H2D за четыре запроса вырос с 133 до примерно 229 ГиБ | Исправлять решения кэша; прогрев RAM сам по себе не убирает PCIe-трафик |
| В микротесте 6×4 МиБ DMA — 14,16 ГБ/с, новая очередь со staging — 9,92 ГБ/с | Проверить copy engine вместо копирования весов через SM |
| Новый путь запрашивает gate/up/down по отдельности | Восстановить раннюю подготовку набора; отдельно измерить перекрытие |
| С прежней подкачкой реальные CPU-задания вызывают `consumer missing from graph replay`; без графов контроль проходит | Исправить capture/replay до приёмки гибридного пути |
| При нуле CPU-заданий CPU-service продолжает работать | Сокращать пустые операции и polling после основных потерь |

Первые скорости относятся к двум прогретым запросам после двух прогревочных;
H2D — ко всему процессу из четырёх запросов. Эти величины нельзя смешивать.
Чтение SSD H: на измеренных коротких запросах было нулевым.
14,74 ток/с GPU-only в том же аудите — одиночный предварительный контроль,
не утверждённая цель для любого запроса. Долю потерянного перекрытия пока не измерили.
Наблюдавшийся PCIe Gen3 x16 ограничивает оба пути; изменение BIOS не входит в план.

## Как выполнять и принимать изменения

Проектировать весь порядок зависимостей до изменения транспорта, реализовывать
отдельными проверяемыми шагами. Арифметика экспертов и настройка CPU-пула уже есть;
повторять их разработку для этого плана не требуется.

Каждый этап заканчивается кодом, проверкой корректности, сравнением с контролем
и коротким отчётом. Этап исправления ошибки можно закрыть без ускорения; этап
оптимизации — только с измеренным результатом в его области. Неудачную гипотезу
закрывать как отклонённую с цифрами, не расширять этап бесконечно.
Локально удачную оптимизацию можно сохранить под флагом до общей приёмки.
Менять рабочий профиль только после окончательного сравнения полного запроса.

Ниже 3%, 5% и 10% — выбранные критерии будущих испытаний, не измеренный
или обещанный прирост. Если разброс сравним с порогом, результат не определён:
нужно выяснить источник разброса и повторить затронутую пару.

## О0. Зафиксировать контроль и разделить измерения

Использовать уже сохранённые запросы, конфигурации и сборку из
`build-local/deepseek4/cpu-zero-audit-20261013/`; сохранить их без перезаписи.
Новые серии складывать в отдельные каталоги с датой и названием этапа.

| Обозначение | Режим | Для чего |
|---|---|---|
| W | Рабочий GPU-only | Итоговая пользовательская скорость |
| G | GPU-only с совместимой CPU/GPU арифметикой | Проверка одинакового вычисления и logits |
| L0 | Прежняя подкачка, CPU-инфраструктура включена, фактически 0 CPU-заданий | Контроль транспорта и остаточной цены CPU-инфраструктуры |
| Q0 | Нынешняя GPU fetch queue, фактически 0 CPU-заданий | Воспроизводимость выявленной регрессии |
| N0 | Новый кандидат, фактически 0 CPU-заданий | Цена новой инфраструктуры без CPU-арифметики |
| N+ | Тот же кандидат с реальными CPU-заданиями | Польза CPU-вычислений поверх исправленного пути |

Нулевой CPU-режим проверять счётчиками jobs/rows. В существующей серии бюджет
0,01 мкс дал такой результат; само значение настройки не заменяет проверку.
Калибровку при сравнении инфраструктуры заморозить; автоматическое обновление
включать отдельно после получения воспроизводимого контроля.

- [x] Добавить снимки счётчиков на границах запроса и prefill/decode: H2D,
  D2D, D2H при демоции, GPU hits/misses/admissions, CPU jobs/rows, RAM hits,
  чтение файлов и физическое чтение диска модели. Target и DSpark учитывать отдельно.
- [x] Записывать полное время, TTFT, prefill/decode, output IDs, draft acceptance,
  CPU-seconds, RAM/VRAM и состояние PCIe под нагрузкой. Потоковые CPU-таймеры
  или профиль добавить только для разделения I/O-service, CPU-service и workers.
- [x] Проверить цену самой диагностики: подробные трассы выключить в итоговой серии.
- [x] Повторить короткий G/L0/Q0 контроль на выбранной сборке; архивировать SHA,
  diff, профиль стоимости, настройки памяти и входные IDs.

Завершение: одинаковые данные сравниваются в одинаковых фазах. Таймеры с перекрытием
не суммируются как независимые части времени запроса. Глобальные счётчики процесса
больше не используются как оценка одного позднего decode.

## О1. Исправить смену CPU-плана при CUDA Graph replay

Это первый кодовый этап. Места проверки:
[cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc),
[cpu_expert_lane.cuh](../../backends/deepseek4/cpu_expert_lane.cuh),
[ShortBatchPatches.cmake](../../backends/deepseek4/ShortBatchPatches.cmake).

- [x] Сделать воспроизводимый тест: пустой RAM-снимок → готовые CPU-кандидаты →
  реальные CPU-задания → снова ноль. Отдельно проверить отказ по бюджету,
  разные размеры короткого batch и чередование target/DSpark с общим scratch.
- [x] Установить точный источник пропущенного consumer. Проверить соответствие
  ключа графа фактической структуре CPU-ветки, binding и поколениям контекста.
  Подтверждён пропуск состояния CPU-ветки в проверке свойств графа; также
  исправлено ошибочное отключение графов значением `0` в тестах.
- [x] Выбрать минимальное исправление: корректная инвалидизация/разные варианты
  графов либо стабильная структура с корректным пустым завершением.
  Сравнить цену пустой ветки; не удалять проверку незавершённого consumer.
- [x] Проверить capture/replay, отмену и следующий запрос, release всех leases,
  обновление профиля между запросами. Синтетический тест должен сопровождаться
  исходным модельным сценарием, который падал.

Завершение: прежняя подкачка с реальными CPU-заданиями и включёнными CUDA Graph
проходит повтор сценария, проверку token IDs и полный массив logits на фиксированной
истории относительно G. Известные отдельные ограничения batch/serial учитываются
по О6. Отключение графов остаётся диагностикой, не исправлением.

## О2. Вернуть DMA и раннюю подготовку gate/up/down

Места работы:
[expert_pipeline_sched.inc](../../backends/deepseek4/expert_pipeline_sched.inc),
[gpu_fetch_sched.inc](../../backends/deepseek4/gpu_fetch_sched.inc),
[gpu_fetch_queue.cuh](../../backends/deepseek4/gpu_fetch_queue.cuh),
[gpu_fetch_lane.cuh](../../backends/deepseek4/gpu_fetch_lane.cuh).

Первый кандидат — совместить проверенный прежний pipeline с исправленной
CPU-веткой. Он даст измеримый ориентир для нового протокола. Затем отделить
публикацию маршрута и CPU-маски от транспорта весов: один маршрут позволяет
подготовить все три матрицы, но не разрешает заранее перезаписывать общий scratch.

- [ ] Описать зависимости: готовность маршрута → выбор CPU/GPU → подготовка
  источников → окончание прежних читателей → H2D → потребитель матрицы → возврат
  буфера. Для target/DSpark и каждого staging-буфера должны быть явные владельцы.
- [ ] Публиковать достаточные сведения для раннего чтения gate/up/down за один
  маршрут. Читать следующие веса параллельно вычислению текущих, сохраняя
  существующий ограниченный бюджет pinned RAM.
- [ ] Передавать веса через copy engine. CUDA-команды ставить из безопасного
  контекста владельца; I/O-service готовит данные. Не вставлять CUDA API в текущий
  service, пока GPU ждёт его ответа: существующий протокол допускает deadlock.
- [ ] Если для первого DMA-прототипа нужен один host-read компактного маршрута
  или CPU-маски, измерить его отдельно. Допускать этот вариант как эксперимент;
  требование отсутствия host-read не должно сохранять более дорогую передачу.
- [ ] Сравнить транспорт при одинаковых маршрутах и решениях кэша. Раннюю
  подготовку включать отдельным переключением, чтобы отделить её вклад от DMA.

Проверки: реальная очередь с потребителем, совпадение payload, ожидание при
переполнении, отмена, повторное использование буфера, два backend, capture/replay,
отсутствие зависаний при подготовке/выделении памяти владельцем.
Микротест: [benchmark_gpu_fetch.cu](../../backends/deepseek4/benchmark_gpu_fetch.cu),
1/6 матриц по 2/4/8 МиБ; затем модельный N0 против L0/Q0.

Критерий транспорта: для 6×4 МиБ полезная пропускная способность не ниже 90%
одновременно измеренного DMA-контроля. На модели должны быть видны ранний старт
чтения и уменьшение ожидания весов, без изменения маршрутов и арифметики.
Микротест сам по себе этап модельной оптимизации не закрывает. Если раннее чтение
не выигрывает, сохранить результат отдельно от удачного DMA.

## О3. Исправить замещение GPU-кэша и защиту RAM

Места работы:
[gpu_fetch_cache.inc](../../backends/deepseek4/gpu_fetch_cache.inc),
[cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc),
[host_cache.hpp](../../backends/deepseek4/host_cache.hpp).

- [ ] После фактического маршрута разрешить замещение невыбранных экспертов
  текущего слоя. Защищать выбранные адреса и незавершённых читателей; сохранять
  защиту при передаче владения между target и DSpark. Не снимать её со всего слоя
  до появления маршрута.
- [ ] Учитывать padding и размер слота, поколение публикации и незавершённую
  демоцию. Адрес может быть опубликован только после завершения записи.
- [ ] Устранить лишние предложения слотов и возврат неиспользованных записей,
  ориентируясь на фактические GPU-промахи. Изменение числа slots — отдельная
  настройка после исправления правил, не замена исправлению.
- [ ] Для N0 готовность RAM-тройки не должна сама запрещать GPU admission.
  Для N+ сохранять RAM-защиту по фактическому CPU-использованию/измеренной выгоде,
  с ограниченным сроком и бюджетом; учитывать отказ CPU-плана.
- [ ] Проверить DSpark отдельно: маленький кэш особенно чувствителен к запрету
  замещения внутри текущего слоя. Сначала сравнить target-only, затем полную связку.

Завершение: безопасная смена адресов и logits-проверки пройдены. В N0 H2D за
одинаковые фазы не более чем на 5% выше L0 при тех же лимитах и прогреве; результат
показан отдельно для target и DSpark. Ускорение проверено на полном запросе.
133 ГиБ из аудита — исторический контроль конкретных четырёх запросов, не общий
лимит. Если остаётся лишний трафик, отчёт должен назвать его источник.

## О4. Убрать оставшуюся цену пустых веток

- [ ] Ввести корректное быстрое завершение ветки без CPU-заданий; по возможности
  не выполнять ненужные publish/join/scatter и пробуждение CPU-service.
  Если отсутствие заданий известно только на GPU, не добавлять синхронное
  чтение этого факта на host без измерения его цены.
- [ ] Для подкачки без промахов не запускать обслуживание пустого запроса,
  сохранив готовность pointer table и правильное завершение поколения.
- [ ] Сократить polling: ограниченное активное ожидание и парковка там,
  где есть безопасное пробуждение. Не предполагать, что запись GPU автоматически
  будит CPU condition variable. Измерить CPU-seconds и задержку пробуждения.
- [ ] Повторить переходы О1 после изменения пустых веток.

Промежуточная приёмка перед настройкой CPU: N0 относительно G имеет не более
3% потери полного времени и decode в коротком прогретом сценарии, без регрессии
длинного GPU-prefill сверх разброса. Если порог не достигнут, продолжить локализацию
остатка; не пытаться компенсировать его числом CPU-потоков.
N0 с нулём CPU-заданий всё ещё может расходовать CPU на I/O и управление.

## О5. Повторно оценить пользу CPU-экспертов

Начинать после О1–О4: изменение транспорта делает прежнюю калибровку непригодной
для выводов о новой связке.

- [ ] Пересоздать профиль стоимости для принятого транспорта. Учесть конкуренцию
  CPU с реальным H2D и подготовкой данных, дополнительную стоимость назначения,
  объединения результата и изменение попаданий кэша.
- [ ] Сравнить N+ с N0 на 12 и 16 потоках; 8 потоков оставить контрольной точкой,
  если предварительные измерения показывают влияние конкуренции за RAM.
  Реальные CPU jobs/rows должны быть ненулевыми в проверяемых decode-сценариях.
- [ ] Сначала заморозить профиль, затем отдельно включить его пересоздание между
  запросами. При ошибке/устаревании профиля проверить рабочий GPU fallback.
- [ ] Проверить отказ от CPU там, где он не уменьшает время ветки; одно снижение
  H2D не является достаточным основанием назначения.

Завершение: есть воспроизводимый выигрыш полного запроса относительно N0,
превышающий шум, и выполнено итоговое сравнение с W. Если выигрыша нет, CPU lane
остаётся экспериментальным; полезные улучшения подкачки принимаются независимо.

## О6. Итоговая проверка короткого и длинного контекста

| Сценарий | Что проверять |
|---|---|
| Короткий fresh, 15 входных / 32 выходных токена | Два прогрева и два измерения в процессе; N0/N+, G и W |
| Target-only с фиксированной историей | Полные logits, NaN/Inf, argmax, неизменные входы; исключить влияние acceptance DSpark |
| 4096 и 8152 входных, 32 выходных, лимит 8192 | Fresh/full prefill и restore отдельно; время, I/O, память, CPU jobs в prefill = 0 |
| Target + DSpark | Acceptance, причинность, batch/serial, fallback и общий scratch |
| Сессии A→B→A, продолжение, отмена, повтор | KV restore, очереди, leases и поколения профиля |
| Qwen | Изоляция настроек backend и генерация при наличии файлов модели |

Для итогового кандидата выполнить минимум три независимые A/B/B/A серии коротких
запросов. Сравнения N0/N+ и G/N0 проводят с одинаковой арифметикой; W служит
отдельной проверкой пользовательского результата. При разном ответе/acceptance
не выдавать свободную генерацию за одинаковую вычислительную нагрузку.
Для длинных сценариев повторить пары в обоих порядках, отдельно fresh и restore.

Контролировать фазу прогрева, лимиты RAM/VRAM, физическое чтение модели, фоновые
нагрузки и paging. Новый процесс не означает холодный файловый кэш Windows.
Не смешивать серии с SSD-чтением и без него. Сборка, модельные тесты и транспортные
микротесты выполняются последовательно.

Известное batch/serial расхождение logits уже есть и в G, и в гибриде этапа 5.
Оно не доказывает ошибку нового транспорта, но не позволяет объявить полную
lossless-приёмку DSpark завершённой. Сравнивать кандидат с тем же режимом G,
а проверку lossless закрывать отдельно. Отсутствующий файл Qwen указывать как
непроверенную генерацию, не подменять её успешным `--help`.

Критерий принятия в рабочий профиль: улучшение полного времени запроса против W
не менее 3% и больше наблюдаемого разброса, без регрессии длинного prefill,
с пройденными обязательными проверками корректности/состояния. Если выигрыш
ограничен отдельным сценарием, оставить явный opt-in и описать его область.
