# План оптимизации подкачки и CPU lane после этапа 5

13 октября 2026. О0 и О1 выполнены в описанной области:
[измерения по фазам и исправление CUDA Graph](DEEPSEEK4_TRANSFER_O0_O1.md).
О2 в работе: [owner DMA и раннее чтение](DEEPSEEK4_TRANSFER_O2.md), затем
[окно DMA](DEEPSEEK4_TRANSFER_O2_DMA_WINDOW.md) реализованы под отдельными
флагами и проверены. Окно дало +10,55% decode в модельном A/B/B/A при одинаковой
работе. Прямой pinned RAM достиг 97,8% DMA-контроля, staging — 84,8%; критерий
90% для staging пока не выполнен.
Продолжение — [проверка staging](DEEPSEEK4_TRANSFER_O2_STAGING.md): размеры
8/16 МиБ и альтернативные подтверждения проверены; устойчивого ускорения нет.
На модели 8 МиБ дали +1,07% в пределах разброса, 16 МиБ — −6,86% decode.
Затем [чтение через mmap](DEEPSEEK4_TRANSFER_O2_READER.md) при прежних 4 МиБ
подтвердило локальные +12,81% decode: 9,363 → 10,562 ток/с, полное время −7,49%.
Все счётчики работы совпали после объединения native/mmap bytes; CPU jobs = 0.
Опция остаётся экспериментальной: RSS вырос с 17,52 до 39,73 ГиБ, 90% DMA
не достигнуты, GPU-only контроль той же серии — 15,746 ток/с.
Принятого ускорения относительно рабочего GPU-only пока нет.

Основание — [аудит замедления при нуле CPU-заданий](DEEPSEEK4_ZERO_CPU_QUEUE_AUDIT.md)
и [проверка полной связки](DEEPSEEK4_CPU_STAGE5_COMPARISON.md).
Этот документ задаёт следующий порядок работ. Предыдущий
[план внедрения CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md)
сохраняет историю реализации и её ограничения.

Цель: сначала вернуть эффективную передачу весов и использование GPU-кэша,
затем проверить дополнительный выигрыш от CPU-экспертов. Длинный prefill остаётся
на GPU. CPU lane — опциональный режим для decode и короткой проверки draft.
Сохраняются DSpark, матричный кэш, сессии и отдельная поддержка Qwen.

## Как выполнять и принимать изменения

Проектировать весь порядок зависимостей до изменения транспорта, реализовывать
отдельными проверяемыми шагами. Арифметика экспертов и настройка CPU-пула уже есть;
повторять их разработку для этого плана не требуется.

Каждый этап заканчивается кодом, проверкой корректности, сравнением с контролем
и коротким отчётом. Этап исправления ошибки можно закрыть без ускорения; этап
оптимизации — только с измеренным результатом в его области. Неудачную гипотезу
закрывать как отклонённую с цифрами, не расширять этап бесконечно.
Локально удачную оптимизацию можно сохранить под флагом до общей приёмки.
Менять рабочий профиль только после окончательного сравнения полного запроса.

Ниже 3%, 5% и 10% — выбранные критерии будущих испытаний, не измеренный
или обещанный прирост. Если разброс сравним с порогом, результат не определён:
нужно выяснить источник разброса и повторить затронутую пару.

## О0. Зафиксировать контроль и разделить измерения

Использовать уже сохранённые запросы, конфигурации и сборку из
`build-local/deepseek4/cpu-zero-audit-20261013/`; сохранить их без перезаписи.
Новые серии складывать в отдельные каталоги с датой и названием этапа.

| Обозначение | Режим | Для чего |
|---|---|---|
| W | Рабочий GPU-only | Итоговая пользовательская скорость |
| G | GPU-only с совместимой CPU/GPU арифметикой | Проверка одинакового вычисления и logits |
| L0 | Прежняя подкачка, CPU-инфраструктура включена, фактически 0 CPU-заданий | Контроль транспорта и остаточной цены CPU-инфраструктуры |
| Q0 | Нынешняя GPU fetch queue, фактически 0 CPU-заданий | Воспроизводимость выявленной регрессии |
| N0 | Новый кандидат, фактически 0 CPU-заданий | Цена новой инфраструктуры без CPU-арифметики |
| N+ | Тот же кандидат с реальными CPU-заданиями | Польза CPU-вычислений поверх исправленного пути |

Нулевой CPU-режим проверять счётчиками jobs/rows. В существующей серии бюджет
0,01 мкс дал такой результат; само значение настройки не заменяет проверку.
Калибровку при сравнении инфраструктуры заморозить; автоматическое обновление
включать отдельно после получения воспроизводимого контроля.

- [x] Добавить снимки счётчиков на границах запроса и prefill/decode: H2D,
  D2D, D2H при демоции, GPU hits/misses/admissions, CPU jobs/rows, RAM hits,
  чтение файлов и физическое чтение диска модели. Target и DSpark учитывать отдельно.
- [x] Записывать полное время, TTFT, prefill/decode, output IDs, draft acceptance,
  CPU-seconds, RAM/VRAM и состояние PCIe под нагрузкой. Потоковые CPU-таймеры
  или профиль добавить только для разделения I/O-service, CPU-service и workers.
- [x] Проверить цену самой диагностики: подробные трассы выключить в итоговой серии.
- [x] Повторить короткий G/L0/Q0 контроль на выбранной сборке; архивировать SHA,
  diff, профиль стоимости, настройки памяти и входные IDs.

Завершение: одинаковые данные сравниваются в одинаковых фазах. Таймеры с перекрытием
не суммируются как независимые части времени запроса. Глобальные счётчики процесса
больше не используются как оценка одного позднего decode.

## О2. Вернуть DMA и раннюю подготовку gate/up/down

Места работы:
[expert_pipeline_sched.inc](../../backends/deepseek4/expert_pipeline_sched.inc),
[gpu_fetch_sched.inc](../../backends/deepseek4/gpu_fetch_sched.inc),
[gpu_fetch_queue.cuh](../../backends/deepseek4/gpu_fetch_queue.cuh),
[gpu_fetch_lane.cuh](../../backends/deepseek4/gpu_fetch_lane.cuh).

Первый кандидат — совместить проверенный прежний pipeline с исправленной
CPU-веткой. Он даст измеримый ориентир для нового протокола. Затем отделить
публикацию маршрута и CPU-маски от транспорта весов: один маршрут позволяет
подготовить все три матрицы, но не разрешает заранее перезаписывать общий scratch.

- [x] Описать зависимости: готовность маршрута → выбор CPU/GPU → подготовка
  источников → окончание прежних читателей → H2D → потребитель матрицы → возврат
  буфера. Для target/DSpark и каждого staging-буфера должны быть явные владельцы.
- [x] Публиковать достаточные сведения для раннего чтения gate/up/down за один
  маршрут. Читать следующие веса параллельно вычислению текущих, сохраняя
  существующий ограниченный бюджет pinned RAM.
- [x] Передавать веса через copy engine. CUDA-команды ставить из безопасного
  контекста владельца; I/O-service готовит данные. Не вставлять CUDA API в текущий
  service, пока GPU ждёт его ответа: существующий протокол допускает deadlock.
- [x] Если для первого DMA-прототипа нужен один host-read компактного маршрута
  или CPU-маски, измерить его отдельно. Допускать этот вариант как эксперимент;
  требование отсутствия host-read не должно сохранять более дорогую передачу.
- [x] Сравнить транспорт при одинаковых маршрутах и решениях кэша. Раннюю
  подготовку включать отдельным переключением, чтобы отделить её вклад от DMA.

Первый прототип — [отчёт О2](DEEPSEEK4_TRANSFER_O2.md). Затем реализовано
[окно до восьми DMA](DEEPSEEK4_TRANSFER_O2_DMA_WINDOW.md) с подтверждением
готового префикса и четырьмя staging-сегментами при прежнем payload 4 МиБ.
Host fence на границе матрицы сохранён. Подтверждён локальный модельный прирост;
прямой RAM-путь прошёл критерий транспорта. Остаток О2: цена подготовки и
повторного использования staging — 84,8% контроля. Два сегмента с большим
окном, восемь мелких сегментов и write-combined allocations в этой серии
не улучшили выбранный вариант; эти гипотезы проверены, повторять их без
нового основания не требуется.
Расширенная [серия staging](DEEPSEEK4_TRANSFER_O2_STAGING.md) также не закрыла
порог: более 91% в узких пробах не повторились в полном тесте. Увеличение
буфера до 16 МиБ устранило ожидания его повторного использования, но замедлило
модель; вариант отклонён для рабочего профиля.
Стоимость callback затем проверена [отдельной серией reader](DEEPSEEK4_TRANSFER_O2_READER.md).
Повторное использование Request не помогло; проверка resident дала только
дополнительные запросы к Windows. Прямой mmap сократил суммарное read-время
всего процесса с 11,668 до 7,639 с и дал +12,81% позднего decode в A/B/B/A
при одинаковой работе. Это отдельная опция для достаточной RAM, не новый default.
О2 остаётся открытым по критерию staging 90%; следующие изменения должны
учитывать выросший working set и невозможность отменить page fault в memcpy.
О3 по-прежнему нужен отдельно: в этой серии очередь передавала 44,255 ГиБ
за два поздних decode против 31,680 ГиБ в GPU-only контроле.

Проверки: реальная очередь с потребителем, совпадение payload, ожидание при
переполнении, отмена, повторное использование буфера, два backend, capture/replay,
отсутствие зависаний при подготовке/выделении памяти владельцем.
Микротест: [benchmark_gpu_fetch.cu](../../backends/deepseek4/benchmark_gpu_fetch.cu),
1/6 матриц по 2/4/8 МиБ; затем модельный N0 против L0/Q0.

Критерий транспорта: для 6×4 МиБ полезная пропускная способность не ниже 90%
одновременно измеренного DMA-контроля. На модели должны быть видны ранний старт
чтения и уменьшение ожидания весов, без изменения маршрутов и арифметики.
Микротест сам по себе этап модельной оптимизации не закрывает. Если раннее чтение
не выигрывает, сохранить результат отдельно от удачного DMA.

показан отдельно для target и DSpark. Ускорение проверено на полном запросе.
133 ГиБ из аудита — исторический контроль конкретных четырёх запросов, не общий
лимит. Если остаётся лишний трафик, отчёт должен назвать его источник.

Результаты 14 октября: [кандидаты на замещение](DEEPSEEK4_TRANSFER_O3.md).

−83,95%. У обоих кэшей нет неиспользованных предложений в измеряемом decode.

Общий H2D теперь на 18,94% ниже L0: порог ≤5% выполнен в коротком N0-сценарии.
У DSpark остаётся 0,677 ГиБ лишнего трафика относительно его части L0.
На момент target-серии защита RAM ещё не была закрыта; её продолжение описано ниже.
Длинный контекст этой серии не проверен. GPU-only остаётся быстрее; цена обслуживания очередей и
пустых CPU-веток требует работы в О4. Рабочий профиль не переключён.
О2 с критерием 90% staging остаётся отдельным открытым пунктом.

Продолжение: [защита RAM по фактическому назначению](DEEPSEEK4_TRANSFER_O3_RAM.md).
В N0 KEEP_RAM=2 вернул H2D к уровню отключённого запрета: 28,626 → 25,681 ГиБ.

(+4,98%), wall −3,27%, H2D −4,59%, CPU-seconds −9,89%. Преимущество перед

два дополнительных context-теста, точные logits и lifecycle с реальными CPU jobs.
Локальные критерии О3 для короткого N0 выполнены. Рабочий профиль сохраняется;
следующий этап — О4, длинный контекст и общая приёмка остаются в О6.

## О4. Убрать оставшуюся цену пустых веток

- [x] Ввести корректное быстрое завершение ветки без CPU-заданий; по возможности
  не выполнять ненужные publish/join/scatter и пробуждение CPU-service.
  Если отсутствие заданий известно только на GPU, не добавлять синхронное
  чтение этого факта на host без измерения его цены.
- [x] Проверить обычный GPU-транспорт без дополнительной очереди, когда
  замороженный профиль заранее исключает CPU. Реализовано opt-in;
  ускорение не подтверждено, опция по умолчанию выключена.
- [x] Перенести отбор О3 в обычный GPU-путь и измерить H2D: общий selector,
  порядок обучения частот, возврат слотов при отмене. Короткий N0 ускорен
  на 6,55%, GPU-only на 11,92%; опция остаётся экспериментальной.
- [x] Для подкачки без промахов не запускать обслуживание пустого запроса,
  сохранив готовность pointer table и правильное завершение поколения.
- [x] Измерить раннюю проверку CPU-бюджета и повторную пустую очистку.
  Кэш решения обновляется с поколением; N0 в среднем +1,80%, один повтор
  −0,59%. Устойчивый выигрыш не подтверждён, обе опции остаются opt-in.
- [ ] Сократить polling: ограниченное активное ожидание и парковка там,
  где есть безопасное пробуждение. Не предполагать, что запись GPU автоматически
  будит CPU condition variable. Измерить CPU-seconds и задержку пробуждения.
- [x] Повторить переходы О1 после изменения пустых веток.

Промежуточная приёмка перед настройкой CPU: N0 относительно G имеет не более
3% потери полного времени и decode в коротком прогретом сценарии, без регрессии
длинного GPU-prefill сверх разброса. Если порог не достигнут, продолжить локализацию
остатка; не пытаться компенсировать его числом CPU-потоков.
N0 с нулём CPU-заданий всё ещё может расходовать CPU на I/O и управление.

14 октября: [пустые ветки и очереди](DEEPSEEK4_TRANSFER_O4_EMPTY.md).
Реализованы три opt-in. Лучший предварительный вариант — только
`CPU_EMPTY_FAST=1`: одна короткая A/B/B/A дала 13,408 → 14,059 ток/с
(+4,85%), wall −3,19%, CPU-seconds −25,74%, H2D не изменился.
Все 1622 лишних CPU wakes измеряемого decode устранены. Отложенное
пробуждение CPU-service и пустой fetch на владельце прошли протокольные тесты,
но дополнительного ускорения пока не показали. Активное ожидание во время
реального I/O остаётся; общий пункт polling не закрыт.
Пройдены 35 CTest, два combined-context запуска, точные logits с реальными
CPU jobs и lifecycle с обновлением поколения профиля. Длинная A/B/B/A дала
−3,35% времени decode после restore и для 4096, и для 8152. Полный prefill
8152 отличается на +0,66% при 78–81 ГиБ чтения SSD; отдельный контроль без
чтения не получен. Порог ≤3% от GPU-only и общая приёмка остаются открытыми.

Продолжение: [парковка I/O-service](DEEPSEEK4_TRANSFER_O4_SERVICE.md).
Реализовано ожидание сигнала владельца после существующего DMA-барьера,
с ограниченным spin 0/25/100 мкс. Комбинация с пустым fetch в A/B/B/A дала
14,071 → 14,081 ток/с: ускорения нет, CPU-seconds −6,18%, wall +0,76%.
Фазовые счётчики показывают около 133 мс подготовки CPU-веток против 1,96 с
обслуживания DMA за два поздних decode; интервалы перекрываются.
Парковка остаётся опциональной, задержка пробуждения отдельно не измерена;
активное ожидание живых DMA не менялось, общий пункт polling не закрыт.
Следующий кандидат — обычный GPU-транспорт для ветки, в которой замороженный
профиль исключает CPU-назначение. Перед принятием проверить переходы
GPU/CPU, поколения профиля, кэш и H2D; такой обход в этой серии не реализован.

Следующая серия: [обычный GPU-путь при исключённом CPU](DEEPSEEK4_TRANSFER_O4_GPU_FALLBACK.md).
Обход реализован и проверен. В N0 A/B/B/A дала 14,174 → 13,357 ток/с
(−5,76%), wall +4,95%, CPU-seconds −15,11%; H2D вырос на 23,36%.
В смешанном режиме с реальными CPU jobs: 14,680 → 14,633 ток/с, прироста нет.
Опция выключена. Следующий кандидат — сохранить выбор матриц О3 в обычном
GPU-транспорте и измерить остаток планировщика при отсутствии CPU-назначений.
Пройдены 39 CTest, точные logits с CPU-работой и с полным обходом, lifecycle
со смешанными ветками и отдельная проверка обновления поколения профиля.
Порог ≤3% от G и длинная приёмка остаются открытыми.


Продолжение: [отбор О3 в обычном GPU-пути](DEEPSEEK4_TRANSFER_O4_ORDINARY_CACHE.md).
Три A/B/B/A N0 дали 14,403 → 15,346 ток/с (+6,55%), wall −4,19%,
CPU-seconds −23,09%. H2D 25,681 → 24,448 ГиБ. В отдельной GPU-only
A/B/B/A: 15,787 → 17,669 ток/с (+11,92%), wall −7,55%, H2D
31,680 → 24,448 ГиБ. Пройдены 43 CTest, полные logits с принудительной
CPU-работой, lifecycle с автоматическими заданиями и обновление поколений
на отдельном тестовом профиле.

Длинный N0: restore 8152 ускорен по времени decode на 11,84%, 4096 —
лишь на 0,49%; полный prefill отличается на +0,27/+0,40% при чтении SSD.
Fresh 4096 медленнее по wall на 6,86%, H2D decode немного вырос. Опция
остаётся выключенной по умолчанию; рабочий профиль сервера не изменён.
Короткий порог относительно прежнего G достигнут, но новый GPU-only с О3
быстрее гибридного N0 при одинаковом H2D. Следом измерить ранние CPU-проверки,
повторное завершение веток и RAM bookkeeping без CPU-назначений; отдельно
проверить холодный транспорт и длинный GPU-only с О3. Общий О4 остаётся открыт.

Продолжение: [кэш проверки бюджета и пустая очистка](DEEPSEEK4_TRANSFER_O4_CPU_PROOF.md).
На 64 токена ранняя проверка сократилась с 2,540 до 0,366 мс, пропущено
3468 пустых очисток. Три симметричные серии N0: +1,94%, +4,24%, −0,59% decode;
среднее +1,80%, wall −1,70%, CPU-seconds −2,08%, H2D неизменен. Смешанный режим
не ускорен: −0,35% decode при прежних 50 jobs / 68 rows. Проверены 44 CTest,
точные logits с реальными CPU-заданиями, сессии и живые поколения профиля.
В длинной A/B/B/A H2D совпал побайтно; restore wall −3,23% / −1,16%,
fresh имеет различное физическое чтение. Это не доказательство ускорения
полного prefill. Настройки выключены по умолчанию, рабочий профиль не изменён.
Следом измерить общую подготовку ветки, поиск в планировщике, CPU hooks и
RAM/residency отдельными интервалами. Цена проверки бюджета слишком мала,
чтобы объяснить основной разрыв. Общая приёмка О4 остаётся открыта.

Продолжение: [подготовка ветки и RAM](DEEPSEEK4_TRANSFER_O4_BRANCH_RAM.md).
Подготовка в планировщике сократилась с 401 до 144 мс на 64 токена,
обычный О3 — с 168 до 65 мс, CPU hook — со 182 до 72 мс,
RAM read metadata — с 54 до 36 мс. Интервалы вложены, их нельзя складывать.
Три симметричные серии N0: **15,311 → 16,383 ток/с (+7,00%)**,
wall −4,08%, CPU-seconds −4,73%, H2D неизменен. GPU-only в одной A/B/B/A:
17,346 → 17,945 ток/с (+3,45%), wall −2,15%. Смешанный режим: −0,76%
decode, wall +2,73% при прежних 50 jobs / 68 rows; ускорение не подтверждено.

В длинной серии restore wall −2,44% / −4,29%; IDs, acceptance и H2D по фазам
совпали. Различное физическое чтение fresh не позволяет объявить ускорение
полного prefill. Три новые опции остаются выключенными, рабочий профиль
сервера не изменён. Следом разделить выделение/освобождение pinned RAM и
копирование при публикации; отдельно измерить оставшиеся CPU hooks в N+.
Проверки давления памяти сохранены. Общий О4 и длинная приёмка GPU-only открыты.

Дополнительная проверка финального бинарника после исправления записи
диагностического счётчика: три симметричные серии дали −5,90%, +2,93%, +6,72%
decode. Среднее +1,33%, **wall +0,99%**; выброс не исключён. H2D, IDs и
acceptance сохранены, SSD-чтения нет. Сокращение подготовки подтверждено
повторным профилем, но стабильный выигрыш полного запроса не подтверждён.
48 разных CTest и повторные точные logits с реальными CPU-заданиями прошли.
До продвижения в рабочий профиль нужно объяснить разброс RAM-чтения/передач.

## О5. Повторно оценить пользу CPU-экспертов

Начинать после О1–О4: изменение транспорта делает прежнюю калибровку непригодной
для выводов о новой связке.

- [ ] Пересоздать профиль стоимости для принятого транспорта. Учесть конкуренцию
  CPU с реальным H2D и подготовкой данных, дополнительную стоимость назначения,
  объединения результата и изменение попаданий кэша.
- [ ] Сравнить N+ с N0 на 12 и 16 потоках; 8 потоков оставить контрольной точкой,
  если предварительные измерения показывают влияние конкуренции за RAM.
  Реальные CPU jobs/rows должны быть ненулевыми в проверяемых decode-сценариях.
- [ ] Сначала заморозить профиль, затем отдельно включить его пересоздание между
  запросами. При ошибке/устаревании профиля проверить рабочий GPU fallback.
- [ ] Проверить отказ от CPU там, где он не уменьшает время ветки; одно снижение
  H2D не является достаточным основанием назначения.

Завершение: есть воспроизводимый выигрыш полного запроса относительно N0,
превышающий шум, и выполнено итоговое сравнение с W. Если выигрыша нет, CPU lane
остаётся экспериментальным; полезные улучшения подкачки принимаются независимо.

## О6. Итоговая проверка короткого и длинного контекста

| Сценарий | Что проверять |
|---|---|
| Короткий fresh, 15 входных / 32 выходных токена | Два прогрева и два измерения в процессе; N0/N+, G и W |
| Target-only с фиксированной историей | Полные logits, NaN/Inf, argmax, неизменные входы; исключить влияние acceptance DSpark |
| 4096 и 8152 входных, 32 выходных, лимит 8192 | Fresh/full prefill и restore отдельно; время, I/O, память, CPU jobs в prefill = 0 |
| Target + DSpark | Acceptance, причинность, batch/serial, fallback и общий scratch |
| Сессии A→B→A, продолжение, отмена, повтор | KV restore, очереди, leases и поколения профиля |
| Qwen | Изоляция настроек backend и генерация при наличии файлов модели |

Для итогового кандидата выполнить минимум три независимые A/B/B/A серии коротких
запросов. Сравнения N0/N+ и G/N0 проводят с одинаковой арифметикой; W служит
отдельной проверкой пользовательского результата. При разном ответе/acceptance
не выдавать свободную генерацию за одинаковую вычислительную нагрузку.
Для длинных сценариев повторить пары в обоих порядках, отдельно fresh и restore.

Контролировать фазу прогрева, лимиты RAM/VRAM, физическое чтение модели, фоновые
нагрузки и paging. Новый процесс не означает холодный файловый кэш Windows.
Не смешивать серии с SSD-чтением и без него. Сборка, модельные тесты и транспортные
микротесты выполняются последовательно.

Известное batch/serial расхождение logits уже есть и в G, и в гибриде этапа 5.
Оно не доказывает ошибку нового транспорта, но не позволяет объявить полную
lossless-приёмку DSpark завершённой. Сравнивать кандидат с тем же режимом G,
а проверку lossless закрывать отдельно. Отсутствующий файл Qwen указывать как
непроверенную генерацию, не подменять её успешным `--help`.

Критерий принятия в рабочий профиль: улучшение полного времени запроса против W
не менее 3% и больше наблюдаемого разброса, без регрессии длинного prefill,
с пройденными обязательными проверками корректности/состояния. Если выигрыш
ограничен отдельным сценарием, оставить явный opt-in и описать его область.
