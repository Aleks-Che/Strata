# Калибровка распределения CPU/GPU под AVX2-ядра

13 октября 2026. Реализована первая часть этапа 4
[плана CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md): отдельные измерения
новых ядер, замороженный профиль стоимости и выбор CPU-работы на GPU.
Профиль учитывает совместную обработку нескольких токенов одного эксперта.
Это экспериментальный режим; итоговая приёмка относительно рабочего GPU-only
и оставшиеся части этапа 4 пока открыты.

Этот отчёт описывает первую версию профиля. Продолжение и текущая сборка —
[стоимость GPU и конкуренция CPU/H2D](DEEPSEEK4_CPU_GPU_COST.md): профиль v2,
измеренное перекрытие, новые 8/12/16-поточные пробы и A/B/B/A.

## Что изменилось

Старый auto-план трижды считал один прогретый blob на одном токене и переносил
это время на каждый следующий экспертный выход. Стоимость запуска он измерял
через CUDA host callback. После появления общей распаковки весов и mapped
GPU-очереди такие измерения больше не описывают выбранный путь исполнения.

- [Калибратор](../../backends/deepseek4/cpu_calibrate.cu) загружает сохранённые
  эксперты до измерений, вращает восемь pinned RAM-банков и считает полную работу
  постоянного пула: подготовку, gate/up, SwiGLU/квантование hidden, down.
  Параметры — тройка форматов, размеры, clamp, число токенов и распределение
  повторений экспертов. Отдельно сохраняются времена фаз.
- [Профиль](../../backends/deepseek4/cpu_cost_profile.cpp) привязан к исходникам
  ядер/очереди и параметрам сборки, CPU, GPU UUID/SM/драйверу, числу потоков,
  режиму AVX2 и геометрии. JSON загружается один раз на процесс. Изменение файла
  не меняет активное распределение во время запроса или серии.
- [GPU-план](../../backends/deepseek4/cpu_cost_model.hpp) сравнивает подмножества
  до восьми готовых кандидатов текущего токена. Используются только текущие ID
  и уже зафиксированный префикс, без просмотра будущих draft-токенов.
  Вариант с нулём CPU-экспертов участвует в сравнении.
- Учитываются только уникальные H2D-байты, передачу которых действительно можно
  отменить. Если эксперт уже нужен GPU для другого токена, его назначение CPU
  не приносит повторной экономии. Окончательная маска отменяет передачу только
  при размещении всех использованных вхождений на CPU.
- Профиль измеряет publication/input → постоянный service → join/output →
  scatter через настоящую mapped-очередь. Для этой проверки service выполняет
  пустую работу: время CPU-ядра уже измерено отдельно.
- В TSV добавлены прогнозы CPU, оставшейся передачи GPU, очереди и сэкономленных
  байтов. `STRATA_CPU_COST_OBS` сопоставляет прогноз с фактическим CPU-временем.
  Force может записывать эти прогнозы, сохраняя принудительное назначение.

Формула первой версии:

```text
T = max(CPU_полная_группа, уникальные_оставшиеся_H2D_байты × цена_байта)
    + стоимость_очереди
```

Новый вариант принимается с запасом 3% относительно уже выбранного. CPU и очередь
должны укладываться в 2000 мкс на токен префикса; это бюджет прогнозируемой работы,
а не гарантия задержки ОС. Общая стоимость вызова не делится на число токенов.
Время GPU-арифметики пока не включено: это консервативная оценка передачи,
а не полный прогноз длительности GPU-ветки или всего MoE.

## Включение и границы

Сначала собрать `deepseek4_cpu_calibrate` и `strata-deepseek4` одной сборкой.
Калибратор принимает новый путь JSON, число потоков и пути CPU fixtures,
полученных существующей диагностикой `STRATA_DS4_CPU_CAPTURE_DIR`:

```powershell
$fixtures = (Get-ChildItem -LiteralPath 'путь-к-сохранённым-экспертам' -Filter '*.bin').FullName
& .\build-deepseek4\deepseek4_cpu_calibrate.exe .\cpu-cost-12.json 12 @fixtures
```

Для этих команд нужны DLL CUDA в PATH, как для самого движка. Существующий JSON
не перезаписывается. Калибратор не запускает генерацию модели и не меняет её веса.
На платформе без автоматически определяемого CPU требуется явный устойчивый
`STRATA_DS4_CPU_MACHINE`; без него профиль не принимается.
Затем в отдельной экспериментальной конфигурации процесса:

```text
STRATA_DS4_CPU_MMVQ_FAST=1
STRATA_DS4_CPU_COST_PROFILE=C:\полный\путь\cpu-cost-12.json
STRATA_DS4_CPU_SHARED_RAM=1
STRATA_DS4_CPU_GPU_QUEUE=1
```

Сам CPU lane включается прежним `--expert-cpu-threads 12`; нужны готовые матрицы
общего RAM-кэша. Для auto используется `--expert-cpu-policy auto`.
Необязательный `STRATA_DS4_CPU_BUDGET_US` меняет бюджет микросекунд на токен.
Все условия совместимых ядер из [этапа 3](DEEPSEEK4_CPU_MULTITOKEN.md) сохраняются.
Длинный prefill остаётся на GPU.

При несовпадении профиля или отсутствии измеренного формата auto выбирает GPU,
с записью причины `STRATA_CPU_COST_PROFILE enabled=0`. Старый callback-путь
не использует этот профиль. Без `CPU_COST_PROFILE` остаётся прежний auto;
force отдельно обходит выбор по стоимости. Рабочий pack не изменён.

Измерены 33 распределения на формат: окна 1–4 токена, суммарно 1–4 CPU-строки,
включая разные и повторяющиеся эксперты. Для каждого распределения хранятся
полные времена, без интерполяции. Неизмеренные комбинации, в том числе более
четырёх строк, не добавляются в auto-план. Это покрывает текущий cap=1 на токен.
Профиль и код ограничены восемью CPU-строками; сам транспорт сохраняет прежние
более широкие диагностические возможности.

## Измерения на этом ПК

Ryzen 9 9950X, 128 GiB RAM, RTX 5090 32 GiB, Windows, MSVC 2022, CUDA 13.0.
Восемь fixtures получены на UD-Q3_K_XL; вход 4096, hidden 2048, clamp 10.
Исходные IQ3_XXS/IQ3_XXS/MXFP4 и MXFP4/MXFP4/MXFP4 берутся из GGUF без
переквантования. Для стоимости Q8_0 калибратор преобразует сохранённые веса:
это проба стоимости формата, а не извлечение экспертов из DSpark.

Восемь банков занимают соответственно 83, 102 и 204 MiB — больше совокупного
L3 этого CPU. Содержимое fixtures повторяется по кругу; разные адреса не означают
восемь разных распределений весов. Первый проход прогревает страницы/ядра,
затем берётся медиана трёх средних по восьми банкам. Пул создаётся заранее.
Внутри CPU-замера нет файлового ввода-вывода. Распаковка/DRAM и dot products
считаются вместе: раздельные аппаратные счётчики этих частей ещё не собраны.

Полное CPU-вычисление, мкс:

| Gate/up → down | Потоки | Один токен | Три токена одного эксперта | Три разных эксперта |
|---|---:|---:|---:|---:|
| IQ3_XXS → MXFP4 | 8 | 1525 | 2182 | 4449 |
| IQ3_XXS → MXFP4 | 12 | 1208 | 1706 | 3194 |
| IQ3_XXS → MXFP4 | 16 | 1111 | 1543 | 2833 |
| MXFP4 → MXFP4 | 8 | 672 | 1357 | 1771 |
| MXFP4 → MXFP4 | 12 | 661 | 1173 | 1420 |
| MXFP4 → MXFP4 | 16 | 799 | 1192 | 1418 |
| Q8_0 → Q8_0 | 8 | 765 | 1512 | 2012 |
| Q8_0 → Q8_0 | 12 | 738 | 1340 | 1798 |
| Q8_0 → Q8_0 | 16 | 824 | 1287 | 1825 |

Pinned H2D трёх матриц: около 756, 929 и 1854 мкс соответственно.
Mapped-очередь с тремя токенами/строками: 63–72 мкс в этой серии.
Перед H2D и очередью GPU прогревается вычислением 250 мс. В исходной пробе после
простоя P8 передача Q8 стоила около 3,65 мс; после прогрева — 1,85 мс.
План, построенный по простаивающей GPU, необоснованно переоценивал пользу CPU.
Настройки питания видеокарты не менялись.

## Запросы модели

UD-Q3_K_XL + DSpark Q8_0, max context 8192, draft-max 2, GPU-кэш target 15 GiB,
draft 1 GiB, общий RAM-кэш 2 GiB, демоция 16 MiB, GPU-очереди CPU/fetch,
совместимые AVX2/SwiGLU. Cap=1. Это диагностическая связка CPU lane, а не рабочий
GPU-only pack. Host TSV включён у всех вариантов, CUDA Graphs разрешены.

Серия: old16 → new8 → new12 → new16 → new16 → new12 → new8 → old16.
Каждый процесс сначала генерирует 16 токенов для прогрева; затем два новых
запроса с 372 и 15 входными токенами, по 16 выходных. Новые session ID не дают
restore/reuse префикса. Ниже сумма времени двух измеряемых запросов, без запуска
процесса и прогревочного запроса; decode tokens/s также исключает прогрев.

| Auto-план | Два повтора, с | Медиана, с | Decode, ток/с | CPU-seconds, медиана |
|---|---|---:|---:|---:|
| Старый, 16 потоков | 15,937 / 16,860 | 16,399 | 3,47 | 57,11 |
| Новый, 8 потоков | 16,000 / 16,797 | 16,399 | 3,46 | 56,15 |
| Новый, 12 потоков | 16,031 / 15,500 | 15,765 | 3,61 | 54,14 |
| Новый, 16 потоков | 15,953 / 15,984 | 15,969 | 3,54 | 55,87 |

Все 16 выходных token IDs каждого из трёх запросов совпали между вариантами.
У 12 потоков минимальная медиана, но повторов мало и контроль заметно дрейфует.
Кроме того, old16/new12 одновременно меняет план и число потоков: по этой
таблице нельзя приписывать разницу только новой калибровке.

Дополнительная серия old12 → new12 → new12 → old12 сохраняет 12 потоков:

| Auto-план | Два повтора, с | Медиана, с | Decode, ток/с | CPU-seconds, медиана |
|---|---|---:|---:|---:|
| Старый | 16,422 / 16,797 | 16,610 | 3,424 | 57,81 |
| Новый | 16,359 / 16,796 | 16,578 | 3,424 | 57,56 |

Разница полного времени около 0,2%; decode практически одинаковый.
**Ускорение за счёт новой калибровки в этой серии не подтверждено.** Новый план
обработал 341/352 CPU-строки против 275/317 у старого (включая прогрев), но само
увеличение CPU-работы не означает сокращения критического пути. Token IDs совпали.

Отношение фактического CPU-времени к прогнозу по медиане заданий — 1,26× / 1,28× /
1,33× для 8/12/16 потоков. За пределы 0,5–1,5× вышли 13/336, 25/377 и 39/328
заданий соответственно. Изолированная калибровка недооценивает исполнение внутри
модели: там есть конкуренция за RAM, работа service и освобождение leases.
Автоматического изменения коэффициентов по этим наблюдениям пока нет.

В восьми пробах простоя по одной секунде процесс потратил 0–0,015625 CPU-seconds.
Это короткий снимок с дискретностью счётчика Windows, а не длительный тест сна.
Счётчик process read bytes в сырых результатах не является физическим чтением
SSD; нулевой SSD-трафик этими измерениями не подтверждается.

## Корректность

Пройдены восемь native CTest: cost, gpu_queue, lane, mmvq_fast, numerics,
hybrid_fast, expert_context_combined_g0 и expert_context_cache_g1. Проверяются
бюджет, нулевая CPU-работа, повторения, уникальные H2D-байты, неизмеренные формы,
отказ от устаревшего профиля, неизменность загруженного JSON и реальные GPU-решения
при изменении будущих ID. Численные тесты этапа 3 сохраняют прежние критерии.

На сборке серии полная модель прошла строгие восемь greedy-сценариев относительно
GPU-контроля с той же совместимой арифметикой, lifecycle/restore, cancel и seeded
repeat. Новый auto12 выполнил 250 CPU-заданий / 431 строку; force16 с наблюдением
профиля — 315 / 540. Seeded-запросы по прежней политике выполняются на GPU:
это не проверка seeded CPU-арифметики. Сравнение полного вектора logits в ранней
диагностической пробе выбрало ноль CPU-строк и не считается гибридным покрытием.

После серии усилены проверки профиля и границы scratch калибратора: учтены
дополнительные заголовки/флаги компилятора, обязательный CPU identity, повторные
записи стоимости очереди и буфер прогрева для малых геометрий. Арифметика ядер
и формула выбора не менялись. Для финальной сборки заново измерены 8/12/16
потоков, повторно пройдены cost/gpu_queue/mmvq_fast/numerics и полный validator
auto12: 237 CPU-заданий / 397 строк, строгие 8/8 greedy-сценариев и lifecycle PASS.

Профили `profile-final-*.json` относятся к измеренной серии и сохранённому
`experiment.exe` (SHA-256 `18905af613a50e50c8e4b8d04c5cae600b20d982af507ff139ca20d6f71bfa43`).
Для заключительной сборки этой серии используются `profile-current-*.json` и `current-engine.exe`
(SHA-256 `84136efb19959d6ebfda127f7b00e988c940eae372a0e893f143ce6d7de6aa79`).
Готовая отдельная конфигурация — `current-config-12.json` в каталоге результатов.
Она проверена на корректность; новые коэффициенты не получили отдельной серии
измерений полного времени. Старые профили намеренно не принимаются новой сборкой.

## Что осталось в этапе 4

Стоимость GPU, перекрытие с передачами и CPU под одновременной нагрузкой на RAM
добавлены в [следующей серии](DEEPSEEK4_CPU_GPU_COST.md). Остаётся по устойчивому
расхождению пересоздавать профиль между сериями/запросами, сохраняя неизменность
внутри speculative window.
Сейчас код только сообщает `recalibration_required`, когда после восьми и более
заданий большинство оказалось вне 0,5–1,5×; это сигнал, не автоматический пересчёт.

Остаются подбор разбиения работы пула и spin/sleep, дополнительные геометрии
и настоящие Q8 fixtures DSpark. NUMA/affinity не включались. Эти пункты нужны
до закрытия этапа 4. Полные контрольные варианты, длинный контекст и независимые
серии относительно рабочего GPU-only относятся к этапу 5.

Подбор пула и прерывистая CPU-нагрузка впоследствии проверены в
[серии v3](DEEPSEEK4_CPU_POOL_TUNING.md). Сохранены стандартные настройки пула;
автоматическое пересоздание профиля и дополнительное покрытие остаются открытыми.

Сырые JSON/TSV, конфигурации, исполняемые файлы, тесты и снимок исходников:
`build-local/deepseek4/cpu-calibration-20261013/`.
