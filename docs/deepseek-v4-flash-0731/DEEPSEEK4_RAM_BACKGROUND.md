# Пул RAM-буферов и фоновое заполнение кэша

12 октября 2026. Продолжение [RAM admission после GPU placement](DEEPSEEK4_RAM_ADMISSION.md).

## Реализация

Два независимых экспериментальных механизма, выключенных по умолчанию:

- STRATA_DS4_RAM_POOL_MIB=128 сохраняет освобождённые после GPU promotion буферы для повторного использования. Пул входит в STRATA_DS4_RAM_CACHE_MIB, а не добавляется к нему. В тестах общий лимит RAM 2048 МиБ, из него не более 128 МиБ свободных буферов. Дополнительный предел — 128 allocations.
- STRATA_DS4_RAM_ASYNC_RETAIN=1 переносит сохранение уже прочитанных данных со стороны consumer на отдельный поток. Требует STRATA_DS4_RAM_ON_BYPASS=1. Очередь ограничена двумя заданиями на backend, включая выполняемое. При переполнении пропускается необязательное сохранение в RAM; передача на GPU выполняется как прежде.

Пул использует точное совпадение размера allocation. Перед вытеснением полезных матриц освобождаются свободные буферы других размеров. Давление памяти сначала освобождает пул. GPU promotion может убрать запись из HostCache, но удерживаемый CPU/DMA lease не допускает повторного использования адреса. Только после последнего читателя блок может попасть в пул. Свободный блок не удерживает идентичность старого файла; она назначается заново при публикации следующего payload. Существующее переиспользование при обычном вытеснении сохранено.

Фоновое сохранение использует уже выделенные host-слоты pipeline и не создаёт отдельной копии для очереди. Слот остаётся неизменяемым до конца callback; reader не может его перезаписать. Событие used защищает соответствующий GPU-слот до завершения consumer. Так ограничены и память, и число работ, но занятый host-слот может задержать последующее чтение при обороте кольца. Проверка фактической фазы prefill/decode выполняется на consumer до постановки задания, без обращения к thread-local фазе фонового потока.

На нормальной границе плана принятые задания завершаются. При брошенном остатке плана, ошибке или уничтожении pipeline необязательные заполнения отменяются. Новый план не сбрасывает cancellation и не переиспользует слоты до дренирования очереди. Ошибка worker передаётся в transfer/finish и остаётся sticky. Вычисления экспертов остаются на GPU при CPU threads=0. Qwen и остальные пользователи общего pipeline не создают worker при стандартных настройках.

## Счётчики

STRATA_RAM_POOL сообщает bytes, peak, puts, reuses, frees, allocations. bytes — текущий свободный пул, включённый в STRATA_RAM_CACHE.bytes. frees считает освобождения из пула при освобождении места/давлении, не все освобождения HostCache. allocations — число успешных новых allocations HostCache; обычное переиспользование при вытеснении и взятие из пула не увеличивают его.

gpu_drop_bytes при включённом пуле означает удалённые из кэша payload: часть их allocations остаётся в свободном пуле, поэтому это не объём возвращённой ОС физической памяти. pool_reuses считает взятия готового allocation; последующая отмена ещё может не дать опубликованного payload.

STRATA_RAM_ASYNC сообщает queued, dropped, cancelled, pending_peak и drain_us. cancelled считает задания, пропущенные до callback; выполнявшийся callback также получает cancellation и может не публиковать данные. drain_us — ожидание остатка очереди на границе плана. Время, когда очередь задерживала повторное использование ring-слота, отдельно не выделено. retain_us — суммарное CPU wall time callback, не время запроса и не GPU-время.

Статистика HostCache и пула общая для target/DSpark: строки разных backend нельзя складывать. H2D/retain/async-счётчики относятся к конкретному pipeline, их можно суммировать.

## Методика

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, SSD H: Samsung 990 PRO. DeepSeek-V4-Flash-0731 UD-Q3_K_XL. Context 8192, batch 4096, target GPU-cache 15360 МиБ, draft cache 1024 МиБ при DSpark Q8_0, RAM-cache 2048 МиБ, stage 16 МиБ, два reader, auto I/O, frequency policy. CPU lane выключен во всех замерах этой серии.

Фиксированная история: target-only, одинаковые 68 IDs. Четыре прохода с полным prefill и decode последних 32 токенов после префикса 36 по одному либо по три. KV очищается между фазами, expert caches сохраняются. Сравниваются средние двух последних проходов. Hashes полных logits префикса и каждого шага проверяются относительно GPU при том же batch; это не проверка эквивалентности serial/batch.

Порядок процессов: GPU, синхронный ON_BYPASS, только пул, только очередь, пул+очередь, GPU. Везде одна новая сборка; direct H2D включён во всех RAM-режимах. Файловый кэш ОС не очищался. PhysicalDrive6 учитывает весь диск; для fixed он измерен за все проходы, поэтому холодное чтение не приписывается прогретому decode.

Артефакты: build-local/deepseek4/ram-background-20261012 (игнорируется Git). Профили, скрипты, baseline.exe, experimental.exe и executables.json сохраняют условия сравнения. SHA-256 experimental.exe: 13ec31ea0272826bec2c63bfa80f14edba74129c0cf20227732e7f10f9d677f8.

## DSpark: короткая генерация

Короткий prefill 64 токена, затем запрос 36→64 и четыре повтора с восстановлением KV. В конце каждого процесса выполняется fresh/full-prefill. Порядок: GPU, синхронный ON_BYPASS, пул, пул+очередь. Один процесс на вариант, четыре повтора; это не независимая серия ABBA. Длинный prefill 4096 в этой серии не измерялся.

Пул увеличил медиану относительно синхронного ON_BYPASS на 6.76%, но она ниже GPU-only на 16.45%. Комбинация с очередью по медиане немного медленнее пула отдельно; преимущество одного последнего повтора не подтверждает устойчивый выигрыш очереди.

Во всех четырёх режимах все 64 IDs совпали между процессами и повторами; acceptance везде 38/51, gpu_only=1. CPU process time включает обслуживание и перемещение данных, CPU lane выключен. Все прогретые повторы имели нулевой физический SSD-трафик. Первый GPU prefill-запрос прочитал 9545752576 байт, первая генерация — 4488880128 байт. Следующие процессы использовали уже прогретый файловый кэш, поэтому первые холодные запросы не используются для вывода об ускорении RAM-режимов.

Пул отдельно: allocations 2759 против 3681 у синхронного ON_BYPASS, снижение 25.05%; 970 взятий из пула. Пул+очередь: 2777 allocations, 982 взятия из пула, 46086 принятых заданий и 41 пропущенное. Суммарное ожидание очереди на границах 0,201484 с за весь процесс; это не все задержки, связанные с очередью. Финальные pending=0, retired_bytes=0, pool_bytes=0, OOM=0.

Источники: bench/results/ds4-ram-background-20261012-short-{gpu,bypass,pool,both}.json и .log. short-analysis.json и summary-short-bench.json в каталоге опыта содержат времена, токены и счётчики.

## Решение

Пул подтвердил снижение числа allocations; отдельного преимущества над GPU-only не получено. Обе настройки сохраняются как выключенные экспериментальные возможности. Рабочий профиль остаётся GPU-only без дополнительного RAM-кэша. Очередь этой серии не рекомендуется как ускорение: после переноса работы в другой поток остаются блокировки общего HostCache, удержание слотов и ожидание хвоста плана; их раздельная цена ещё не измерена.

Дальше имеет смысл сначала измерить время lookup/частотной политики/блокировок и ожидания занятых retention-слотов. Увеличивать RAM-бюджет или количество потоков по этим результатам оснований нет. Следующая реализация должна опираться на такой профиль, а не считать перенос на worker устранением всей стоимости.
