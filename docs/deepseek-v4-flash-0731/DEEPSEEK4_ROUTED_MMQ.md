# Routed MoE: входы, ID и короткий MMQ

11 октября 2026. RTX 5090 32 ГиБ, Ryzen 9950X, RAM 128 ГиБ,
Windows, CUDA 13, драйвер 581.80. Модель DeepSeek-V4-Flash-0731
UD-Q3_K_XL на H: (Samsung 990 PRO 4 ТБ, PhysicalDrive6).
Продолжение [shared expert](DEEPSEEK4_SHARED_PROJECTIONS.md).

Кандидат **не принят в рабочий профиль**: замедлил измеренную генерацию
и ухудшил совпадение DSpark с обычным greedy. Полезный результат этапа —
локализация разных форматов активаций и проверенная трассировка экспертов.

## Достоверность наблюдения

В `ActivationProbe` добавлен селектор `@expert:<имя веса>` для
`MUL_MAT_ID`. Он снимает выход, вход активаций и ID экспертов в момент
callback матрицы, когда эти данные ещё доступны. Читается выбранный токен,
а не весь весовой тензор. Сохраняются формы и strides всех входов/выхода.
Для небольшого I32-тензора сохраняются и сами ID; границы чтения остаются
32 МиБ на тензор и 256 МиБ суммарно. Поддержаны имена копий scheduler
вида `CUDA0#blk.0.ffn_gate_exps.weight#0`.

Первый прогон оказался непригоден для численных выводов: наблюдение
промежуточных узлов мешает fusion. Observer изменил logits полного
prefill на 2,9924910, поэтапного — на 2,0377655. Дополнительно селектор
первой версии не распознавал обёртку scheduler. Этот прогон сохранён как
`probe-row371`; его внутренние разницы не используются как доказательство.

После исправления выбора весов baseline и observer запущены с одинаковым
`GGML_CUDA_DISABLE_FUSION=1`. На row 371 и 282 observer, snapshot/restore
и replay дали max Δ = 0. Это отдельный диагностический режим: отключение
fusion само меняет результаты относительно предыдущего этапа.

## Что различается

Прежние 410 token IDs: полный префикс 409 против префикса 371,
одиночных токенов 371–403 и пакета 404–408; последний токен 409 отдельно.
Численные режимы предыдущих этапов одинаковы: MMQ=5/J64/4, FA=4,
HCA=1, HC=3, router sample=3, shared=2, MMVQ=2, TF32 off.

На row 371 выбранные ID в обоих путях:
`107, 85, 126, 215, 44, 129`. Вход FFN, маршруты и их веса совпадают.

| Узел первого слоя | Тип весов | Max Δ |
|---|---|---:|
| Вход gate/up | — | 0 |
| Gate | IQ3_XXS | 0,0003679991 |
| Up | IQ3_XXS | 0,0003404319 |
| SwiGLU / вход down | — | 0,0003254414 |
| Down | MXFP4 | 0,0979425237 |
| Weighted experts | — | 0,0357959382 |
| Routed MoE / сумма FFN | — | 0,0447273813 |
| Выход слоя | — | 0,0223059338 |

На row 282 (два больших пакета) все наблюдаемые узлы первого слоя равны.
Полные конечные logits baseline различаются: max Δ 3,3460645676,
RMS 0,4963074043, argmax 539 / 1.

Размеры gate/up — 4096 × 2048 × 256; их F32-вход транслируется
по шести маршрутам. Down — 2048 × 4096 × 256, с отдельным входом
для каждого маршрута. На Blackwell штатный длинный MXFP4 MMQ квантует
активации в FP4, одиночный MMVQ — в Q8. У IQ3 MMQ и MMVQ также отличаются
scale и порядок редукции. Различие арифметики не доказывает ошибку
копирования экспертов или неправильные ID.

## Эксперимент

`STRATA_DS4_ROUTED_MMQ` доступен только при
`STRATA_DEEPSEEK_PROJECTION_EXPERIMENT=ON`:

- `1`: короткие routed IQ3_XXS матрицы на штатном MMQ;
- `2`: также MXFP4;
- отсутствует / другое значение: прежний путь.

Пакет 1–8 токенов, реальные K/M gate/up/down, шесть маршрутов,
6–256 экспертов, плотные F32-активации, I32 ID, плотные веса без view,
NVIDIA Ampere и новее. Длинный MMQ, квантизация весов и device-ядра
не изменены. Один предикат управляет dispatch и отказом от MMVQ fusion.
Режим MXFP4 меняет точность квантизации активаций короткого пути;
совпадение с prefill само по себе не является доказательством качества.

## Изолированный GPU-тест

`deepseek4_routed_mmq_test`: **54 матричных сценария**, **30 проверок
границ**, **три целые цепочки** gate/up → SwiGLU → down → веса маршрутов.
Размеры K/M настоящие, веса синтетические; восемь экспертов, шесть
выбранных ID. Batch 1/2/3/4/5/8/9/371/409, обе квантизации для каждой
из трёх матриц. Эталон — соответствующие строки штатного MMQ на 409
токенах, без нового dispatch. Это проверка согласованности с существующим
GPU-путём, не FP64-эталон и не оценка качества модели.

MXFP4 совпал с длинным эталоном побитово во всех 27 сценариях.
У IQ3 максимальная разница снизилась с 0,0001695566 до **5,3644180e−7**;
24 из 27 сценариев ещё не побитово равны. Допуск IQ3 в этом тесте — 1e−5.
Неподходящие имена, K, strides и тип Q8_0 сохраняют прежний результат;
режим 1 сохраняет MXFP4, а batch >8 не затрагивается.

В цепях на 1/4/9 токенах, с разными весами gate/up и активным SwiGLU
clamp 0,3, целый граф совпал с пятью отдельными GPU-операциями побитово.
Заполненные NaN промежуточные gate/up после нового целого графа содержат
конечные значения: MMVQ fusion не обходит выбранный путь.

Первая версия fixture превысила лимит 180 с при повторном CPU-квантовании
одинаковых синтетических весов. Добавлено повторное использование уже
подготовленных весов между guards; вычислительная часть теста не менялась.
Результат повторного прогона — `fixture-cached.json`.

Микрозамеры: медиана трёх чередующихся серий по 40 запусков, восемь
разогревающих, CUDA graphs выключены. Только resident GPU-матрицы,
без чтения/копирования весов. Время включает запуск графа.

## Разделение причин на модели

Диагностические profiles `unfused`, `iq3`, `all`, row 371:

| Узел, max Δ | Прежний путь | Только IQ3 MMQ | IQ3 и MXFP4 MMQ |
|---|---:|---:|---:|
| Gate | 0,0003679991 | 0 | 0 |
| Up | 0,0003404319 | 0 | 0 |
| Вход down | 0,0003254414 | 0 | 0 |
| Down | 0,0979425237 | 0,0982584581 | 0 |
| Routed MoE / сумма FFN | 0,0447273813 | 0,0446137972 | 0 |
| Выход слоя | 0,0223059338 | 0,0222492870 | 0 |

Режим IQ3 оставил разный результат down при побитово одинаковом входе
и ID, тем самым выделив независимое расхождение MXFP4. Режим 2 выровнял
все наблюдаемые узлы первого слоя на row 371 и 282. Во всех этих probes
контроли observer/restore/replay равны нулю.

| Режим без fusion | Max Δ конечных logits | RMS | Argmax full / segmented |
|---|---:|---:|---|
| Прежний | 3,346064568 | 0,496307404 | 539 / 1 |
| Только IQ3 | 3,297958374 | 0,535487254 | 539 / 1 |
| IQ3 и MXFP4 | 5,074950218 | 1,000796958 | 539 / 1 |

Полная разница logits выросла. Проверка внутренней трассировки с обычным
fusion (`all-fused-row371`) снова изменила logits: observer full/segmented
3,3286362 / 2,9732342, при нулевых restore/replay. Внутренние совпадения
этого прогона не используются как доказательство. Сравнение модели по
скорости и проверки сессий выполняются без наблюдателя, с обычным fusion.

## Сессии и DSpark

Прошли **33/33 CTest** за 165,85 с. Проверки сессий без DSpark и с ним
прошли: A/B/A, восстановление и продолжение, отмена и следующий запрос,
один токен и повторяемый sampling. **30 проверок причинности** дали
max Δ logits = 0. Эти проверки меняют будущие draft-токены и контролируют
anchor logits; они не доказывают эквивалентность всей последовательности.

В отдельном сравнении token IDs с обычным greedy обнаружена **регрессия**:
совпали только **4 из 8** сценариев, тогда как на предыдущем этапе — все 8.
`session_a`, его восстановление, одиночный токен и ответ после отмены
совпадают. `session_b` расходится с 15-го токена; active extension,
его восстановление и fresh extension — с первого. Для продолжения использован
одинаковый prompt, поскольку исходный ответ `session_a` совпадает.

В обоих запусках `full_prefill_identical=false`: без DSpark первое различие
между полным prefill и продолжением на первом токене, с DSpark — на втором.
Поэтому успешные state/causality-тесты не означают готовности этого режима
для рабочего профиля. Проверки качества ответов не проводились.

## Скорость всей модели

Две последовательные серии A/B/B/A: без DSpark и с ним. Один `candidate.exe`,
одинаковые предыдущие численные режимы, обычный fusion, без трассировки.
A — routed MMQ=0, B — routed MMQ=2. Это сравнение двух исследовательских
профилей; оно не является замером обычного рабочего профиля с экспериментами OFF.
Контекст 8192, batch 4096, один поток управления; target-кэш 15360 МиБ,
staging 16 МиБ, pipeline=1, readers=2, frequency, CRT, early refill=0,
prefill cache hits=1, slabs 16 МиБ. Для DSpark — прежние параметры draft.

В каждом процессе: prefill 4096, decode 32 токенов, четыре закэшированных
повтора и ещё один полный prefill 4096. «Поздние» — медиана третьего и
четвёртого повторов; медиана всех четырёх также сохранена.

| Без DSpark | Поздние повторы, ток/с | Все четыре, ток/с | Прогретый prefill, мс |
|---|---:|---:|---:|
| A1 | 19,744 | 18,827 | 9733,63 |
| B1 | 18,216 | 17,323 | 9663,42 |
| B2 | 18,191 | 17,440 | 9696,26 |
| A2 | 19,762 | 19,027 | 9713,37 |
| Медианы A → B | **19,753 → 18,203** | **18,927 → 17,382** | **9723,50 → 9679,84** |

| С DSpark | Поздние повторы, ток/с | Все четыре, ток/с | Прогретый prefill, мс |
|---|---:|---:|---:|
| A1 | 20,921 | 19,034 | 9664,53 |
| B1 | 17,964 | 16,775 | 9631,60 |
| B2 | 18,065 | 17,095 | 9828,55 |
| A2 | 20,695 | 19,397 | 10043,80 |
| Медианы A → B | **20,808 → 18,015** | **19,215 → 16,935** | **9854,165 → 9730,075** |

Поздние повторы замедлились на **7,84% без DSpark** и **13,42% с ним**.
По всем четырём повторам — −8,17% и −11,87%. На prefill получены
−0,45% / −1,26%; двух измерений каждого режима недостаточно, чтобы считать
такую небольшую разницу устойчивым ускорением. Внутри каждого режима ответы
повторяются; между A/B в обеих сериях различаются с 26-го токена.
В повторе DSpark принимает 18/26 draft-токенов у A и 16/29 у B.
Сравнение включает другие маршруты и принятие черновика, а не только ядра.
Token IDs после prefill между A/B без DSpark также различаются, с DSpark
на этом запросе совпали; сырые последовательности сохранены в сводке.

Во всех **32 прогретых decode и восьми полных прогретых prefill** чтение
PhysicalDrive6 равно **0 байт / 0 операций**. Холодные запросы читают SSD.
CPU процесса: медианы 4,46–4,87% всего 32-поточного CPU, максимум 6,42%;
общий CPU в выборках достигал 11,8%. Пик VRAM — 28757 МиБ без DSpark,
30566 МиБ с ним; NVML опрашивался раз в две секунды, краткие пики возможны.
Во всех **1391** записях аудита моделей `cpu_compute_nodes=0`.

## Следующая проверка

В отдельном probe слоя 1 на row 371 с mode=2 и fusion off совпали все
наблюдаемые узлы: вход из слоя 0, HC, Q/K, attention с видимыми K/V,
wo_a/wo_b, router, ID, routed/shared FFN и выход слоя. Observer, restore
и replay снова дали ноль. Это точное совпадение на выбранной позиции,
не доказательство равенства всей истории или всех слоёв.

Продолжение полного/поэтапного prefill следует искать начиная со слоя 2,
с теми же контролями наблюдения. Отдельная задача — первая разница logits
между DSpark verification и обычным decode на **одинаковых заданных token IDs**:
проверять каждую позицию пакета, а не только anchor с изменённым будущим.
Это необходимо до любых попыток включать новый routed-путь в рабочий профиль.

Продолжение: [stride ID и проверка каждой позиции DSpark](DEEPSEEK4_ROUTED_ID_STRIDE.md).
Регрессия коротких пакетов устранена: причиной была проверка contiguity top-k
view со слоя 3. Все 319 проверенных строк logits и 8/8 greedy-сценариев
совпали; ускорения исправленный вариант также не дал. Следующая граница
полного/поэтапного prefill — исторические K/V слоя 2.
