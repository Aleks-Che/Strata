# Проверка переноса AVX2, early refill и prefill cache hits

6 октября 2026 года. Реализованы три отключаемых варианта из
[анализа GLM/Step](DEEPSEEK4_OPTIMIZATION_TRANSFER_REVIEW.md).
Этот отчёт относится к DeepSeek; результаты исходных моделей на него не перенесены.

**Полезный результат — использование готовых GPU-матриц при повторном prefill.**
Для запроса 256 токенов первая пара дала 4214,62 → 3753,60 мс (−10,94%).
На 4096 токенов ускорение пока не отделено от чтения SSD. AVX2 и early refill
в проверенном режиме ускорения не дали.

## Условия

Windows, Ryzen 9 9950X (32 логических CPU), RAM 128 ГиБ, RTX 5090
32606 МиБ, драйвер 581.80, CUDA 13.0, Release, CUDA architecture 120.
Основные GGUF UD-Q3_K_XL находятся на H: Samsung 990 Pro 4 ТБ
(`PhysicalDrive6`), DSpark — локальный Q8_0 sidecar.

Контекст 8192, batch 4096, один вычислительный host thread, все вычисления
графа на GPU. Target-кэш 15360 МиБ, draft-кэш 1024 МиБ, resident expert
layers 0, stage 16 МиБ, pipeline 1, readers 2, read mode auto
(decode использует одного читателя), frequency + match-size, DSpark2,
общий compute scratch. Кэш сессий — 2048 МиБ / 4 записи.

Файловый кэш ОС не очищался; другие приложения не останавливались.
Фоновая загрузка CPU менялась, поэтому одного небольшого различия недостаточно
для вывода об ускорении. Дисковые счётчики относятся ко всему физическому H:
и включают другие процессы. Они не измеряют чтение sidecar на другом диске.

Все сравнительные замеры выполнены одной сборкой:
`build-local/deepseek4/transfer-trial/candidate/strata-deepseek4.exe`, SHA-256
`662cbae08d0cac55febbf196b24f747c049b7bb54f80c283a8612a88221ffadf`.
Первый контроль использовал идентичный файл с именем `candidate.exe`.

Финальная сборка `build-deepseek4/bin/strata-deepseek4.exe`, SHA-256
`ba1a8f3ea9d3d317518045d65f0faefb78427e8b58ca8f1f6b8d3574db8f4bd6`,
добавляет раннюю проверку поддержки AVX2 до загрузки GGUF; путь передачи
из сравнительной сборки не меняется. В GPU fixture также добавлен skip
для принудительного AVX2 на неподдерживаемом CPU.

## Что изменено

- `--expert-host-copy crt|avx2`: cacheable AVX2 stores для mmap → pinned RAM,
  адаптированные из Step. AVX2 компилируется в отдельном translation unit;
  выбор режима проверяет поддержку CPU/ОС. Режим по умолчанию — CRT.
- `--expert-early-refill 0|1`: общий конвейер может заполнять host slot после
  завершения H2D, пока GPU ещё читает device slot. Ожидание `used` перед
  перезаписью device slot сохранено. По умолчанию выключено.
- `--expert-prefill-cache-hits 0|1`: при batch больше восьми токенов брать
  готовую матрицу из GPU-кэша. Промахи идут через прежнюю передачу, новые
  записи не создаются, frequency/LRU/touched не обновляются. Работает с
  фиксированной ареной и динамическими allocations, с pipeline и без него.
  Общий default выключен.

AVX2 и early refill требуют pipeline. Все три настройки относятся к target
и DSpark. План исключает готовые prefill hits из чтения и защищает их от
вытеснения; признак `slice.cacheable`, управляющий также reader/file mode,
сохранён. В `INFO` видны выбранные параметры, в журнале —
`STRATA_EXPERT_TUNING` и отдельный счётчик `STRATA_EXPERT_PREFILL hits`.
Общий конвейер, сборки Qwen/Step/GLM и закреплённые исходники llama.cpp
этим экспериментом не изменены.

## AVX2 и раннее заполнение: прирост не подтверждён

Одинаковый русский запрос о L1/L2/L3, 128 выходных токенов. Перед ним —
prefill 256 токенов; затем первый decode и три повтора из RAM-сессии.
В таблице только прогретые повторы, без начального чтения модели и весов.

| Режим | Три повтора, ток/с | Медиана, ток/с | Медиана CPU-с / повтор |
|---|---|---:|---:|
| CRT, early=0, контроль до | 18,64 / 20,23 / 20,72 | 20,23 | не записана |
| AVX2, early=0 | 18,32 / 19,42 / 18,53 | 18,53 | 9,19 |
| CRT, early=1 | 18,10 / 18,25 / 20,98 | 18,25 | 9,48 |
| AVX2, early=1 | 17,94 / 19,02 / 17,80 | 17,94 | 9,61 |
| CRT, early=0, контроль после | 17,46 / 20,52 / 21,06 | 20,52 | 8,77 |

CPU-с — сумма user + system процесса движка за запрос, включая prompt/restore,
а ток/с рассчитаны только по `decode_ms`. В первом контроле инструмент ещё
не собирал эти дельты; монитор также не распознал переименованный exe.
Инструмент исправлен до следующих запусков, отсутствующие числа не восстановлены.

Во всех 15 прогретых повторах физические чтения H: равны нулю. Token IDs
совпали между режимами. Совпали также итоговые hits/misses, H2D/D2D:
у target за весь каждый запуск H2D 438500913664 байта,
D2D 1258751176192 байта, у draft H2D 19904777216 байт.
`pipeline_fallbacks=0`.

AVX2, early refill и их сочетание оставлены выключенными в рабочем профиле.
Это ограниченный тест одного запроса при stage 16 МиБ, а не доказательство,
что эти варианты всегда медленнее на других CPU, размерах кольца и моделях.

## Prefill 4096: меньше передач, но влияние SSD не отделено

Свежий session ID для каждого повторного полного prefill, `reused=0`.
GPU-кэш весов сохраняется; KV-сессия не восстанавливается.

| Режим | Время трёх полных prefill, мс | Чтение H: в тех же запросах, ГиБ |
|---|---|---|
| hits=0 | 13465,3 / 12053,5 / 8969,75 | 34,17 / 24,85 / 0 |
| hits=1 | 12578,3 / 12554,3 / 11718,5 | 34,32 / 37,85 / 30,39 |

У target за весь запуск H2D уменьшилось с 622383804928 до 578109822464
байт: на **41,23 ГиБ**, зарегистрировано 12150 prefill hits. D2D одинаков:
в обоих вариантах остаётся копирование в рабочий буфер. Итоговые admissions,
misses и evictions совпали; новые матрицы prefill в кэш не добавлялись.

Однако скорость этой пары нельзя приписать только флагу: физическое чтение
существенно различается. Последний контроль уже находился в файловом кэше,
последний вариант с hits всё ещё читал SSD. Ускорение длинного контекста
по этой серии **не доказано**, а повтор запроса не гарантирует отсутствие SSD.

## Prefill 256: подтверждение на прогретых весах

Четыре запуска в порядке hits=0 / hits=1 / hits=0 / hits=1. В каждом —
тот же начальный prefill, decode 128, один RAM-повтор, затем пять полных
prefill в новых сессиях. Первые два полных повтора отведены на прогрев,
в таблице последние три. `reused=0`, во всех двенадцати зачётных запросах
физическое чтение H: равно **0 байт**.

| Режим | Три prefill, мс | Медиана, мс | Медиана CPU-с / запрос | Средний CPU всей системы, % |
|---|---|---:|---:|---:|
| hits=0, до | 4186,84 / 4264,70 / 4214,62 | 4214,62 | 9,63 | 13,28 |
| hits=1 | 3721,96 / 3823,45 / 3753,60 | 3753,60 | 8,81 | 16,82 |
| hits=0, после | 4720,33 / 5121,53 / 4633,10 | 4720,33 | 10,39 | 38,72 |
| hits=1, подтверждение | 3628,05 / 3680,67 / 3625,91 | 3628,05 | 8,55 | 13,31 |

Первая пара даёт −10,94% времени prefill. Во второй паре разница больше,
но фон CPU контрольного запуска заметно выше; её нельзя целиком объявлять
эффектом флага. Повторное включение снова дало меньшую задержку. Это измерение
повторяющегося короткого контекста с полезными матрицами в GPU-кэше,
не прогноз для произвольного длинного запроса или первого холодного запуска.

За весь каждый запуск target H2D: 606647333376 → 557045199360 байт,
экономия **46,20 ГиБ**. Счётчик prefill hits — 13612; misses 72874,
evictions 5516, target D2D 1057336120320 байт одинаковы. Эти суммы включают
начальные запросы и все пять prefill, не являются объёмом одного запроса.
У draft hits=0 для prefill; его передача не изменилась.
Token IDs всех запросов совпали между четырьмя режимами.

Повторная генерация из RAM-сессии почти пропускает prefill. Поэтому этот
результат **не означает +11% к обычным ток/с decode**. Выигрыш относится к
новому полному prefill, который использует уже прогретые экспертные веса.

## Воспроизведение

Рабочий локальный `strata-deepseek4-ud-q3-k-xl-dspark.json` обновлён:

```text
--expert-host-copy crt
--expert-early-refill 0
--expert-prefill-cache-hits 1
```

Общие defaults движка и setup для prefill hits остаются 0. Для возврата
локального профиля достаточно сменить последний флаг на 0 и перезапустить
движок. После испытаний все тестовые процессы закрыты; HTTP-сервер не запущен.

Локальные профили `build-local/deepseek4/transfer-trial/` сохраняют одинаковые
параметры, меняя только три новых флага: `control.json`, `avx.json`,
`early.json`, `both.json`, `prefill.json`. Сырые результаты находятся в
`bench/results/transfer-trial-*.json`, журналы — рядом в `.log`.

```powershell
.venv\Scripts\python.exe tools/benchmark_deepseek4.py --config build-local/deepseek4/transfer-trial/control.json --prompt-tokens 256 --tokens 128 --repeats 3 --physical-disk PhysicalDrive6 --output bench/results/transfer-trial-control.json
.venv\Scripts\python.exe tools/benchmark_deepseek4.py --config build-local/deepseek4/transfer-trial/prefill.json --prompt-tokens 4096 --tokens 128 --repeats 1 --prefill-repeats 3 --physical-disk PhysicalDrive6 --output bench/results/transfer-trial-prefill-hits.json
.venv\Scripts\python.exe tools/benchmark_deepseek4.py --config build-local/deepseek4/transfer-trial/prefill.json --prompt-tokens 256 --tokens 128 --repeats 1 --prefill-repeats 5 --physical-disk PhysicalDrive6 --output bench/results/transfer-trial-prefill256-hits.json
```

Для A/B выбирать разные output, чтобы не перезаписывать свидетельства.
`--prefill-repeats` создаёт новые сессии, проверяет `reused=0` и совпадение
выходных token IDs; простые `--repeats` восстанавливают RAM-сессию и не подходят
для измерения полного prefill. Из пяти полных повторов первые два отводятся
на прогрев, последние три используются для сравнения; поле
`full_prefill_median_ms` в сыром JSON содержит медиану всех пяти.

## Проверки

Финальная сборка: **11/11 CTest**, **25/25 Python-тестов**
(`tools.test_deepseek4`, `serve.test_deepseek`, `serve.test_vram_settings`),
синтаксис изменённых Python-файлов. Пять некорректных комбинаций CLI отклонены
до открытия модели: неизвестный host copy, early/hits вне 0..1,
AVX2 или early без pipeline.

- AVX2: 684 побайтовых случая, смещения source/destination, короткие хвосты,
  реальные размеры IQ3_XXS/MXFP4 с padding; защитные страницы выявляют выход
  за конец буфера.
- Pipeline: CRT/AVX2 × early 0/1, перекрытие, многократное переиспользование
  кольца, отмена с непрочитанным хвостом и следующий запрос.
- GPU transfer: prefill hits в фиксированной и динамической памяти,
  без pipeline и со всеми тремя опциями; запрет новых admissions/evictions
  при prefill, побайтовое совпадение результата и padding.
- Сохранены проверки GPU-only, политики VRAM, частот, общего scratch и
  контракта speculative decoding.

Во всех графах сравнительных запусков `cpu_compute_nodes=0`.
CPU по-прежнему обслуживает чтение и копирование весов, команды и sampling.
Проверка этих изменений на Linux не проводилась.

Реальная Q3 с **всеми тремя опциями одновременно** прошла проверки
`validate_deepseek4_speculative.py --tokens 32` с DSpark и без него:
A/B/A из RAM, активное продолжение и восстановление продолжения, один токен,
отмена prefill/decode, восстановление после отмены, повтор sampling с seed 123.
Файлы: `transfer-trial-validation-dspark.json` и
`transfer-trial-validation-plain.json`, оба `passed=true`; аудит GPU — 0 CPU-узлов.

Сохраняется ранее известное ограничение DSpark:
`full_prefill_identical=false` между полным prefill продолжения и
инкрементальным продолжением. Без DSpark в этой проверке получилось `true`.
Транспортные изменения это расхождение не исправляют; совпадение ответов
между включёнными/выключенными транспортными флагами не доказывает
численную эквивалентность DSpark обычному decode.
