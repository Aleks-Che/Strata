# Почему новый путь медленнее при нуле CPU-заданий

13 октября 2026. Продолжение [сравнения этапа 5](DEEPSEEK4_CPU_STAGE5_COMPARISON.md).
Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ; target UD-Q3_K_XL,
DSpark Q8_0. Рабочие конфигурации не изменены.

Основная потеря локализована в **новом пути GPU fetch**, включая его правила
кэширования и порядок подкачки. Нулевая очередь вычислений CPU не выключает
этот путь. Это установлено переключением пути на полной модели, проверкой
трафика и отдельным тестом передачи без модели.

## Контроль на полной модели

Одна архивная сборка этапа 4:
`7f5023651d3eadb1f2dffb6e038edd4d9bf7762fe98a7f94a1c90038dbec3b1a`.
Те же лимиты памяти: target GPU-кэш 15360 МиБ, draft 1024 МиБ, RAM-кэш 2048 МиБ,
CPU 12 потоков, общий scratch, draft-max=2, совместимый SwiGLU, CUDA Graphs.
CPU-бюджет 0,01 мкс запрещает CPU-вычисления; профиль стоимости валиден,
auto-refresh выключен. В каждом процессе четыре свежих запроса: 15 входных
и 32 выходных токена. Первые два — прогрев, последние два — измерение.

Сравнение A/B/B/A:

- A (`nofetch`): `GPU_FETCH_QUEUE=0`, **CPU_GPU_QUEUE=1** и остальная CPU/RAM
  инфраструктура сохранены. Используется прежний GPU pipeline с DMA.
- B (`mapped`): полная новая инфраструктура, `GPU_FETCH_QUEUE=1`.

| Прогон | Decode, ток/с | Время двух запросов, с | CPU-seconds | CPU-задания |
|---|---:|---:|---:|---:|
| A1 | 12,847 | 7,609 | 11,781 | 0 |
| B1 | 5,066 | 15,782 | 64,156 | 0 |
| B2 | 5,352 | 14,687 | 59,703 | 0 |
| A2 | 12,575 | 7,750 | 11,781 | 0 |

Итог по общим tokens / decode-time: **12,709 против 5,205 ток/с**.
Среднее полное время пары запросов: 7,6795 против 15,2345 с.
Все входные и выходные IDs совпали, чтение H: на измеренных запросах — 0 байт.
На других дисках оставалась фоновая активность; файловый кэш ОС не очищался.

CPU-планирование в A действительно выполнялось: 1111 и 1118 публикаций CPU GPU
queue за процесс, без заданий. В B — по 3244 публикации CPU queue и GPU fetch.
Без GPU fetch планировщик отказывается от пустого CPU-снимка; с GPU fetch
продолжает готовить ветку для GPU. Поэтому A/B изолирует **полный новый путь**,
а не только замену одной инструкции копирования. Отдельный транспортный тест ниже
отделяет собственно передачу от модели и решений кэша.

В исходном GPU-only контроле этой серии получено 14,741 ток/с, в A — 12,842,
в B — 5,402. CPU-инфраструктура имеет остаточную цену и без GPU fetch,
но она существенно меньше основной потери. Это один предварительный контроль,
не самостоятельная приёмка ускорения; основной вывод подтверждает A/B/B/A выше.

## 1. Передаётся больше весов

Счётчики за **весь процесс: четыре запроса, включая prefill и прогрев**:

| Режим | H2D, ГиБ | Попадания GPU-кэша | Промахи |
|---|---:|---:|---:|
| GPU-only, исходный контроль | 133,486 | 91 386 | 24 476 |
| CPU queue + прежняя подкачка | 133,486 | 91 386 | 24 476 |
| Новый GPU fetch, исходный контроль | 227,346 | 64 401 | 50 743 |
| Новый GPU fetch, B1 / B2 | 228,889 / 228,883 | см. сырой JSON | см. сырой JSON |

Разница относится к CPU→GPU трафику, **не к физическому чтению SSD**.
Чтение файла из кэша Windows всё равно может потребовать копирования в pinned RAM
и передачи по PCIe. Суммы за процесс нельзя выдавать за трафик только позднего decode.

Особенно заметен DSpark: в исходном контроле попаданий 3876 и промахов 1284,
в новом пути — 800 и 4360. H2D DSpark вырос с 5,330 до 18,098 ГиБ.

Причины различий в правилах кэша видны в
[gpu_fetch_cache.inc](../../backends/deepseek4/gpu_fetch_cache.inc) и
[cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc):

- До появления route-ID на host защищаются все доступные cached-матрицы текущей
  ветки, а не только фактически выбранные. Текущая ветка дополнительно исключена
  из кандидатов на замещение. Это безопасно для читателей, но ограничивает замену
  уже закэшированных экспертов того же слоя, особенно в маленьком draft backend.
- Заранее предлагается ограниченное число слотов на матрицу. Четыре слота
  не означают четыре произвольных замещения: действуют размер, padding, частота,
  текущие leases и защита RAM-троек. Неиспользованные предложения возвращаются.
- `GPU_FETCH_KEEP_RAM=1` запрещает некоторым готовым RAM-тройкам попадать в GPU-кэш
  ради будущего CPU-назначения, даже если CPU-бюджет в данном опыте всегда выбирает
  GPU. Факт готовности RAM не означает, что эксперт действительно вычислен на CPU.

Однофакторные короткие пробы (тот же прогрев; CPU-заданий 0, H: 0 на измерении):

| Изменение нового пути | Decode, ток/с | H2D за весь процесс, ГиБ |
|---|---:|---:|
| Исходный контроль | 5,402 | 227,346 |
| `KEEP_RAM=0` | 6,449 | 200,874 |
| 8 предложений cache slots вместо 4 | 6,219 | 202,604 |
| Обе настройки вместе | 6,235 | 204,330 |
| Повтор исходного контроля после проб | 5,714 | 220,799 |

У восьми слотов DSpark получил 3051 попадание вместо 800, но прежний путь всё ещё
лучше. Выигрыши не складываются: варианты меняют размещение кэша и его историю.
Эти одиночные пробы подтверждают влияние политики хранения, но не выбирают
готовую производственную настройку.

## 2. Передача по новой очереди медленнее DMA

В [gpu_fetch_queue.cuh](../../backends/deepseek4/gpu_fetch_queue.cuh)
`gpu_fetch_wait` — CUDA-ядро: оно опрашивает mapped doorbell, читает pinned host
memory и пишет VRAM обычными SM-инструкциями. После каждого чанка есть grid barrier,
system fence и подтверждение CPU-service. Это не `cudaMemcpyAsync` через copy engine.
Service не вызывает CUDA API: это защищает от известного риска deadlock при
одновременных allocations и GPU-ожидании CPU. Просто заменить вызов внутри service
на `cudaMemcpyAsync` без пересмотра протокола нельзя.

Добавлен [benchmark_gpu_fetch.cu](../../backends/deepseek4/benchmark_gpu_fetch.cu).
Источник — заранее заполненные 64 МиБ pinned RAM; SSD и модель отсутствуют.
Используются настоящий `GpuFetchQueue`, публикация, consumer и CPU-service.
Каждая точка: 3 прогревочных и 12 измеренных повторов; результат передачи
сравнен побайтно. Перед каждой передачей destination заполняется `0xff` вне
измеряемого участка, чтобы прежнее содержимое не скрывало пропущенную запись.
Таблица — медианы (`micro-verified.csv`); время включает launch, синхронизацию и service.

Шесть матриц по 4 МиБ, 16 блоков:

| Способ | Время, мкс | Полезная скорость, ГБ/с |
|---|---:|---:|
| DMA: `cudaMemcpyAsync` | 1778 | 14,158 |
| Обычное CUDA-копирование mapped RAM, без очереди | 1922 | 13,096 |
| Настоящая очередь, прямой pinned-источник | 2312 | 10,886 |
| Настоящая очередь, staging по 2 МиБ с CPU memcpy | 2537 | 9,920 |

Для шести матриц по 2/8 МиБ DMA дал 13,903/14,230 ГБ/с,
очередь со staging — 9,652/8,661 ГБ/с. Предварительный запуск без заполнения
destination (`micro.csv`, верхняя медиана 12 повторов) дал для 6×4 МиБ
14,106 против 8,893 ГБ/с. В нём увеличение числа блоков 16→64/128
не устранило потерю; часть вариантов стала медленнее.
Даже запрос с нулём GPU-промахов проходит publish/service/reply/consumer:
наблюдались десятки микросекунд и выбросы до сотен микросекунд.

На этом запуске `nvidia-smi` под нагрузкой сообщил PCIe Gen3 x16 (current/max=3,
width=16). DMA около 14 ГБ/с измерена непосредственно. Это общий предел текущего
соединения для обоих вариантов, а не самостоятельное объяснение их различия.
Настройки PCIe и BIOS в этом исследовании не менялись.

## 3. Утрачена часть прежнего перекрытия чтения и вычислений

Прежний [expert_pipeline_sched.inc](../../backends/deepseek4/expert_pipeline_sched.inc)
после получения маршрута собирает slices для всех gate/up/down и вызывает
`pipeline->start(misses)`. Два reader могут готовить следующие веса до того,
как текущие GPU-операции закончатся.

Новый [gpu_fetch_sched.inc](../../backends/deepseek4/gpu_fetch_sched.inc) вызывает
публикацию отдельно перед каждой матрицей. Она идёт в том же owner stream,
после предыдущих вычислений. Только после GPU-publication service узнаёт промахи
этой матрицы и вызывает `read_at`; затем `gpu_fetch_wait` завершает её передачу,
после чего разрешается вычисление. Два staging-буфера перекрывают чтение и
передачу **чанков**, но не восстанавливают прежний предварительный запуск I/O
всего набора gate/up/down.

Это установленное различие порядка запуска по коду. Отдельная доля потерянного
перекрытия в миллисекундах пока не измерена. В исходном mapped-процессе время
native read суммарно 14,515 с, owner wait 21,679 с, подготовка CPU-снимков
0,282 с, общий select/prepare 1,222 с. Эти таймеры перекрываются, относятся
ко всему процессу и **не складываются** в длительность запроса.

## 4. Ноль CPU-экспертов не означает спящие CPU-service

Обе очереди вызывают `arm()` до решения/обслуживания ветки. Пока armed,
[cpu_gpu_queue.cuh](../../backends/deepseek4/cpu_gpu_queue.cuh) и GPU fetch service
проверяют doorbell и вызывают `std::this_thread::yield()`, даже когда compute-заданий
нет. Дополнительно выполняются чтение/копирование файлового кэша, подготовка RAM
leases и ожидание подтверждения каждого чанка.

Отсюда реальная загрузка CPU при нуле строк экспертов: в A/B/B/A 11,781 против
61,930 CPU-секунды на два запроса. Это CPU-время всего процесса; отдельную долю
busy polling без профилировщика потоков эти счётчики не выделяют. Пул из 12
вычислительных workers не следует считать выполняющим экспертов по одному лишь
проценту загрузки процесса.

## Дополнительный сбой: прежняя подкачка с реальными CPU-заданиями

Последующее исправление и проверки: [этапы О0–О1](DEEPSEEK4_TRANSFER_O0_O1.md).
Ниже сохранён исходный результат до исправления; рабочий профиль этим не менялся.

`nofetch` выше — контроль с нулём CPU-заданий, а не готовый гибридный профиль.
При снятии бюджета 0,01 мкс и включении адаптации стоимости тот же executable
завершился на первом запросе с `CPU GPU queue consumer missing from graph replay`
в `cpu_expert_lane.cuh:296`, код процесса 3221226505. Артефакты: `full-0-cpu_dma.*`.

Контроль с единственным дополнительным изменением `GGML_CUDA_DISABLE_GRAPHS=1`
прошёл все четыре запроса: 148 CPU-заданий, 168 строк, валидный профиль, обновление
поколения 0→1. Входные и выходные token IDs совпали с GPU-compatible эталоном.
Артефакты: `fullcheck-0-cpu_dma_nograph.*`, `fallback-check.json`.
Это подтверждает зависимость сбоя от CUDA Graph в данном сценарии; точная причина
пока не исправлена. По коду подозрение — переход от пустого RAM-снимка без CPU-ветки
к активному CPU-плану при повторном использовании графа без нужного consumer.
Совпадение токенов четырёх запросов не заменяет проверки всех logits и длинного контекста.

Поэтому простое выключение `GPU_FETCH_QUEUE` нельзя переносить в рабочий гибридный
профиль. До его приёмки нужна проверка смены CPU-плана при capture/replay.

## Что исправлять

Порядок реализации, контрольные варианты и критерии завершения вынесены в
[новый план оптимизации](DEEPSEEK4_TRANSFER_OPTIMIZATION_PLAN.md).

1. Восстановить раннюю подготовку всех трёх матриц и передачу через copy engine,
   сохранив порядок использования scratch и безопасное завершение service.
   Проверить CUDA Graph при переходах между пустым и непустым CPU-планом.
2. Разрешать замещение невыбранных экспертов текущего слоя после появления
   фактического GPU-маршрута. Сохранять защиту выбранных и ещё читаемых матриц;
   просто снимать существующие защиты небезопасно.
3. Защищать RAM-тройки от GPU admission только там, где это приносит пользу
   CPU-назначению; учитывать динамический отказ CPU-плана.
4. Затем убирать постоянные publish/join/scatter и polling на ветках без CPU.
   Измеренный порядок приоритетов: трафик и транспорт дают основную потерю,
   подготовка снимка не объясняет двукратное время полного запроса.

Никакой процент из микротеста не объявляется ускорением модели. Рабочий профиль
сохранён; экспериментальные флаги выше не перенесены в packs.
