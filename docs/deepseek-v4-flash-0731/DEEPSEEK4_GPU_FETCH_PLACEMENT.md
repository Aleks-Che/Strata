# Размещение RAM-троек и подготовка CPU-снимка

12 октября 2026. Продолжение этапа 2 [плана CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md)
после [прямого заполнения GPU-кэша](DEEPSEEK4_GPU_FETCH_CACHE.md).
Оба новых переключателя выключены по умолчанию; рабочий GPU-only профиль не изменён.

## Что проверяется

Обычный CPU-план допускает эксперта только при готовой RAM-тройке и отсутствии
всех трёх матриц в GPU-кэше. Даже одна GPU-матрица исключает его из CPU-кандидатов.
Это видно в `e.eligible = c.fixed || all_miss` в
[планировщике](../../backends/deepseek4/cpu_lane_hooks.inc). Диагностический fixed
отменяет это ограничение, но не является рабочим способом распределения нагрузки.

`STRATA_DS4_GPU_FETCH_KEEP_RAM=1` запрещает новым GPU admissions разбивать уже
готовую и допустимую CPU-тройку. GPU-вхождение такого эксперта по-прежнему получает
веса в scratch и вычисляется на GPU; решение о CPU-строках не меняется внутри
уже опубликованного задания. Проверка выполняется GPU-публикатором и повторяется
I/O-service. Она не возвращает прежние GPU-матрицы в RAM и не защищает тройки,
которые станут готовыми только после текущей передачи.

Это дополнительная политика для `STRATA_DS4_GPU_FETCH_CACHE_SLOTS>0`, а не новый
механизм копирования. GPU-резидентные эксперты и CPU-only вхождения обслуживаются
по прежнему пути. Предложенные, но не использованные VRAM-слоты возвращаются
с прежними весами. По умолчанию новый GPU admission по-прежнему выключен.

Независимый `STRATA_DS4_CPU_SNAPSHOT_PRUNE=1` сокращает подготовку снимка:

- сначала определяются GPU-резидентность, число недостающих байтов и частоты;
- для недопустимого CPU-кандидата RAM-поиск не выполняется;
- для допустимого кандидата поиск прекращается при первой отсутствующей матрице;
- удерживается только готовая тройка, как и в исходном варианте.

Пропускаются вызовы `HostCache::acquire(..., touch=false)`, которые не обучают
историю, не двигают LRU, не читают файл и не выделяют payload. GPU-роутер и CPU-ядра
сохранены. Для этого изменения требуется совпадение полных logits и маршрутов.
Снимок готовых кандидатов всё ещё удерживается до конца ветки; межветочное
ожидание GPU/CPU не сокращено.

## Счётчики

`STRATA_CPU_SNAPSHOT`: число вызовов `queries`, пропущенных вызовов `skipped`
и время `snapshot_us`. Сумма queries+skipped равна трём проверкам на кандидата.
Время включает GPU lookup и frequency lookup, а не только HostCache.
`select_us` — существующий счётчик выбора, с другой областью покрытия;
складывать или напрямую вычитать эти времена нельзя.

`STRATA_GPU_FETCH_PLACEMENT` считает уникальные routed IDs один раз на ветку:
`allmiss`, `partial`, `allgpu` — число GPU-резидентных матриц 0 / 1–2 / 3;
`ready` — готовые допустимые CPU-тройки; `cpu_only` — эксперты без GPU-вхождений
в этом окне. Это не число CPU-строк, поскольку эксперт может повторяться.
Счётчики охватывают только подходящие GPU-fetch ветки, не весь fallback scheduler.

`ram_bypasses` — GPU-miss матрицы с защитой RAM при наличии предложенных
VRAM-слотов. Это число срабатываний запрета, а не число гарантированно отменённых
admissions: размер или частота могли бы отклонить предложение независимо.

## Пробы политики размещения

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, SSD H: Samsung 990 PRO, Windows.
DeepSeek-V4-Flash-0731 UD-Q3_K_XL, target-only, 68 фиксированных token IDs:
префикс 36, decode 32. GPU-кэш 15 ГиБ, общий RAM-кэш 2 ГиБ, pinned pool и
fetch RAM budget по 32 МиБ. CPU12, force/cap1, graphs/direct/ordered включены,
два reader, staging 16 МиБ. В каждом запуске четыре повтора; числа ниже —
среднее последних двух, без времени префикса для decode.

| Одиночная отборочная проба | Decode по 1, мс / 32 токена | Decode по 3, мс / 32 токена |
|---|---:|---:|
| GPU fetch + RAM, cache slots=4 | 2382,82 | 1717,28 |
| То же, KEEP_RAM=1 | 2552,22 | 1695,20 |
| GPU fetch + RAM, без новых GPU admissions | 2106,89 | 1413,16 |

KEEP_RAM не дал согласованного улучшения и не отобран для рабочей настройки.
Запрет сработал для 503 GPU-miss матриц. Число готовых допустимых CPU-троек среди
routed IDs выросло 1045→1171, но CPU-задания изменились 950→947, CPU-строки
1088→1106. CPU-only эксперты: 994→1003. Частично GPU-резидентные routed IDs:
422→532. Содержимое кэша и будущие маршруты устройств изменились, поэтому эти
счётчики не описывают одни и те же ветки: их число выросло 4977→5101.

Ограничение all-miss действительно существует, но его обход такой защитой не
объясняет и не устраняет весь проигрыш нового admission. Полных RAM-троек мало;
эксперт может стать RAM-ready уже после частичного GPU admission. Политика также
не координирует три независимые матрицы в одну GPU-resident тройку. Для KEEP_RAM
это две отборочные пробы, не подтверждённая A/B/B/A и не итог новой калибровки.

## A/B/B/A для подготовки снимка

Отдельная серия, без новых GPU admissions: A — исходный снимок, B — PRUNE=1.
Каждая буква означает независимую загрузку движка; параметры и token IDs одинаковы.

| Режим | Prefill, мс | Decode по 1, мс | Decode по 3, мс | Весь workload, с | CPU-с процесса |
|---|---:|---:|---:|---:|---:|
| A | 2422,14 | 2063,04 | 1398,41 | 48,0785 | 92,3438 |
| B | 2387,99 | 2064,14 | 1396,50 | 47,2740 | 90,0938 |

Decode1 стал дольше на 0,054%, decode3 короче на 0,136%: заметного изменения
decode не обнаружено. Полный короткий workload занял на 1,67% меньше времени,
CPU time — на 2,44% меньше. Это одна промежуточная серия; разброс и изменение
других участков не позволяют целиком приписать этот выигрыш подготовке снимка.
Порог 3% и три независимые серии финального этапа здесь не выполнены.

RAM lookup вызовы сократились с 5 283 840 до 1 592 598: **−69,86%**.
Время подготовки снимков: 501 432→427 949 мкс в среднем по двум загрузкам,
**−14,65%**, около 73 мс экономии за весь workload. GPU/frequency lookup остаются;
число удерживаемых готовых троек и время их удержания не уменьшены.

Во всех четырёх A/B/B/A — 12/12 одинаковых полных logits signatures. Совпадают
также fetch-ветки (3425), CPU-задания/строки (1144/1430), RAM tickets (685),
GPU/RAM трафик и счётчики размещения. Отдельно проверены новая сборка с
отключёнными фичами и прежняя: 12/12 для режима без admissions и 12/12 для
cache slots=4 (`parity.json`).

Во всех четырёх A/B/B/A физический счётчик SSD после загрузки модели — 0 байт;
минимально доступная RAM в B — 66,36 ГиБ. Это счётчик всего workload, а не
раздельная трасса фаз. Отборочные пробы имели другие SSD-показания и не включены
в расчёт этой A/B/B/A.

## Проверки и состояние этапа

42 регрессионных CTest прошли при `CPU_SNAPSHOT_PRUNE=1` за 194,94 с.
Native fixture использует обычное all-miss правило, а не диагностический fixed:
проверены отказ для GPU-резидентного CPU-кандидата, защита готовой RAM-тройки,
сохранение GPU admissions для холодного эксперта, точные CPU/GPU-строки,
arena/managed и CUDA Graph replay. Самостоятельный GPU-тест также проверяет,
что пригодный по размеру и частоте слот не перезаписывается при KEEP_RAM.

Ещё семь проверок прошли с compact scratch, одним блоком GPU-копирования,
slabs 1 МиБ, `RAM_DROP_GPU=1` и обеими новыми фичами. Отдельный native прогон
прошёл с выключенным новым RAM admission (`GPU_FETCH_RAM_MIB=0`). Итого
42+7+1 пройденных проверок; это не число независимых модельных benchmarks.

DSpark Q8_0 проверен с обеими новыми фичами, cache slots=4, CPU12, draft max=2,
GPU-кэшем target/draft 15/1 ГиБ и общей RAM 2 ГиБ. Пройдены обычные A→B→A,
extension restore, fresh/full-prefill, один токен без draft и отмены prefill/decode
с greedy restore. Строгий seeded restore **не пройден**: два ответа по 24 токена
впервые отличаются на индексе 6 (седьмой токен), исходный assertion завершил
валидатор с кодом 1. Проверка не ослаблялась.

В этой DSpark-серии target выполнил 1374 fetch-ветки, 1851 GPU admission и
299 CPU-заданий / 484 строки; draft — 10 веток, 45 admissions и одно задание /
две строки. Финальные `oom`, `pending`, `retired_bytes` общего HostCache — 0.
Это подтверждает прохождение нового пути, но не воспроизводимость sampling.

Этап 2 остаётся открытым. Сокращение lookup не заменяет удержание только
выбранных кандидатов, перекрытие подготовки соседних веток и сокращение ожиданий.
Открыты также рост пустого GPU-кэша, совместимость нового admission с демоцией
и seeded restore. KEEP_RAM оставлен только для опытов, PRUNE — отдельным opt-in
для дальнейшей проверки; выигрыш относительно рабочего GPU-only не заявляется.

Следующий шаг: [раннее освобождение RAM-снимков](DEEPSEEK4_GPU_FETCH_RELEASE.md)
отпускает невыбранных CPU-кандидатов и источники завершённых GPU-копий. Удержание
выбранных CPU-троек и ожидание всей ветки пока сохранены.
