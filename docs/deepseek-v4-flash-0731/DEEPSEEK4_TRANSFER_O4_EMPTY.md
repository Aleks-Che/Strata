# О4: пустые CPU-ветки и обслуживание очередей

14 октября 2026. Продолжение [О3: фактическое CPU-назначение](DEEPSEEK4_TRANSFER_O3_RAM.md).

## Изменения

Три независимых opt-in, все по умолчанию выключены:

| Переменная с префиксом `STRATA_DS4_` | Действие |
|---|---|
| `CPU_EMPTY_FAST=1` | Пропустить таблицу маршрутизации, event/join/scatter и пробуждение CPU-service, когда host может доказать отсутствие CPU-работы |
| `CPU_SERVICE_LAZY=1` | При owner DMA будить CPU-service только для опубликованного задания на существующем route fence |
| `GPU_FETCH_EMPTY_FAST=1` | При owner DMA завершать пустые запросы на владельце и оставлять I/O-service спящим, если промахов нет |

Host-доказательство использует готовность и допустимость кандидатов RAM,
нулевой cap либо нижнюю границу вычислительной стоимости замороженного профиля.
Проверяются все причинные префиксы до четырёх токенов. Если ни одна положительная
измеренная стоимость unloaded compute не помещается в бюджет соответствующего
префикса, CPU-назначение невозможно. Boundary и замедление от конкурирующего
DMA неотрицательны; их игнорирование делает проверку консервативной. Force
не отклоняется по стоимости. Нет предположения «раньше не было CPU jobs —
значит, их не будет сейчас».

Пустая ветка всё ещё обнуляет стабильный GPU-пакет и состояние поколения одним
kernel. Её признак входит в существующее различение CUDA Graph: граф без
CPU-маски/join/scatter не переиспользуется как граф с реальным CPU-заданием.
RAM-снимки, leases, защита VRAM-читателей и общий scratch сохраняют прежний
срок жизни. Эта серия не удаляет стоимость построения самого RAM-снимка.

Если host не знает, какие эксперты выберет GPU, публикация маршрута сохраняется.
Владелец проверяет mapped-запрос CPU после уже имеющегося DMA-барьера. Реальное
задание получает обычный condition-variable wake; при его отсутствии сервис
остаётся припаркованным. Дополнительного D2H или синхронного чтения route IDs нет.
Цена возможного более позднего старта реального CPU-задания проверяется отдельно.
При отмене до первого DMA-барьера clear сначала завершает публикацию, затем
при необходимости будит сервис и дожидается ответа; живые leases не освобождаются.

Пустой fetch сохраняет валидацию эпохи, освобождение неиспользованных RAM-ссылок,
порядок gate/up/down и публикацию reply/consumed. Только метаданные обрабатываются
на владельце, чтение весов остаётся на I/O-service. При наличии будущего промаха
среди уже опубликованных запросов сервис просыпается на первом DMA-барьере;
предварительное чтение следующих матриц сохраняется. Отмена до этого барьера
будит сервис для завершения отменённых поколений. Mapped-путь без owner DMA
сохраняет прежнее обслуживание.

Диагностика по фазам: `cpu_empty`, `cpu_wakes`, `cpu_skips`, `fetch_empty`,
`fetch_wakes`, `fetch_skips`. Wakes считают команды arm, skips — завершённые
ветки без необходимости будить соответствующий сервис; это не системная
трасса переключения потоков. `cpu_empty` — только доказанные на host пустые
ветки, `cpu_skips` также включает отказ GPU-плана после публикации.

Код: [cpu_expert_lane.cuh](../../backends/deepseek4/cpu_expert_lane.cuh),
[cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc),
[gpu_fetch_queue.cuh](../../backends/deepseek4/gpu_fetch_queue.cuh),
[cpu_cost_model.hpp](../../backends/deepseek4/cpu_cost_model.hpp).

## Условия

Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows, CUDA 13.
DeepSeek-V4-Flash-0731 UD-Q3_K_XL + DSpark Q8_0, context 8192, draft-max 2.
GPU-кэши 15360/1024 МиБ, RAM-кэш 2048 МиБ, DMA depth 8, staging 4 МиБ,
четыре сегмента, reader mapped, early sources 1. Demand для обоих кэшей,
rank 1 / 256 только для target. Current victims 0, context overlap 0.
База N0 — прежний лучший профиль: KEEP_RAM=0, демоция 0, CPU12 с бюджетом
0,01 мкс. Калибровка новая для данной сборки, автообновление выключено.

Четыре fresh-запроса по 15 входных / 32 выходных токена в каждом коротком
процессе; первые два — прогрев. Измеряются последние два: сумма wall,
CPU-seconds и H2D decode, скорость 64 токена / суммарное decode-время.
Кэш ОС не очищается. Артефакты:
`build-local/deepseek4/transfer-o4-empty-20261014/`.

## Короткая серия

В предварительных одиночных процессах N0: база 14,095 ток/с, только
`CPU_EMPTY_FAST` 14,605, только `CPU_SERVICE_LAZY` 14,068, только
`GPU_FETCH_EMPTY_FAST` 14,063, все три 14,266. Для основного сравнения выбран
только `CPU_EMPTY_FAST=1`; два остальных флага остаются отдельными экспериментами.
Они прошли тесты протокола, но ускорение полного запроса не подтвердили.

Основная A/B/B/A, тот же бинарник и замороженный профиль:

| Процесс | Decode, ток/с | Wall двух запросов, с | CPU-seconds | H2D decode, ГиБ |
|---|---:|---:|---:|---:|
| A1: N0 | 13,448 | 7,296 | 16,125 | 25,681 |
| B1: быстрый пустой путь | 14,056 | 7,079 | 12,125 | 25,681 |
| B2: быстрый пустой путь | 14,061 | 7,078 | 12,125 | 25,681 |
| A2: N0 | 13,368 | 7,328 | 16,531 | 25,681 |

Среднее по процессам: **13,408 → 14,059 ток/с (+4,85%)**, wall
7,312 → 7,079 с (−3,19%), CPU-seconds 16,328 → 12,125 (−25,74%).
Входные/выходные token IDs и acceptance совпали во всех четырёх процессах;
каждый запрос принял 14 из 33 предложенных draft-токенов. CPU jobs/rows = 0.
Это локальный результат одной A/B/B/A, не итоговая приёмка О6.

В каждом процессе измеряемый decode: target CPU wakes 1520 → 0, draft
102 → 0. Host доказал пустоту всех этих веток. Fetch wakes остались 1520/102,
поскольку в выбранном кандидате его обслуживание не меняется. H2D и выбранная
модельная работа совпали. CUDA Graph captures/replays также прежние:
target 520/3640, draft 28/282 за два поздних decode. Счётчик изменений
CPU-сигнатуры target уменьшился с 240 до 0; это не уменьшение общего числа captures.
Физическое чтение H: в измеряемых запросах — 0;
другой диск PhysicalDrive4 имел 0,2–193 МиБ чтения на пару. Счётчики дисков
охватывают всю систему и не приписывают этот трафик движку. Кэш ОС не очищался.

Для отдельного `GPU_FETCH_EMPTY_FAST` в пилоте владелец завершил 1858/40
пустых запросов target/draft, число пробуждений I/O-service уменьшилось до
901/89. Это уменьшение обслуживания без подтверждённого выигрыша скорости.
`CPU_SERVICE_LAZY` в N0 также убрал CPU wakes, но сохранил GPU router и
join/scatter; CPU-seconds снизились, decode остался около базового.

## Контроль с реальной CPU-работой

Отдельные одиночные процессы, тот же профиль калибровки, обычный auto без
искусственного бюджета 0,01 мкс, демоция 16 МиБ, KEEP_RAM=2:

| Вариант | Decode, ток/с | Wall, с | CPU-seconds | CPU jobs / rows |
|---|---:|---:|---:|---:|
| Auto, три флага выключены | 14,248 | 7,078 | 16,641 | 55 / 75 |
| Auto + CPU_EMPTY_FAST | 14,930 | 6,734 | 12,422 | 55 / 75 |
| Auto + все три флага | 14,903 | 6,797 | 11,906 | 55 / 75 |

H2D везде 25,796 ГиБ, IDs/acceptance совпали, H: = 0. В этих запросах
реальная CPU-работа приходится на DSpark. У target быстрый путь пропустил
1520 пустых веток. Полная комбинация дополнительно снизила CPU wakes DSpark
со 102 до 55 при тех же 55 заданиях. Признаков задержки реальной CPU-работы
в этом пилоте нет, но повторы нужны для вывода о скорости auto.

GPU-only контроль той же сборки дал 15,711 ток/с, wall 6,578 с,
CPU-seconds 9,250 и H2D 31,680 ГиБ; позднее чтение H: = 0. Предварительный
GPU-only пилот с 2,15 МиБ чтения H: не использован как контроль без SSD.
Эта одиночная точка показывает необходимость дальнейшего сравнения с GPU-only;
она не заменяет чередование G/N0 и не закрывает порог О4 ≤3%.

## Корректность

Финальная сборка прошла 35 CTest с тремя включёнными флагами: CPU cost,
CPU/GPU очередь, пустая ветка → реальные задания → отказ назначения,
CUDA Graph capture/replay и отключённые графы, mixed-row RAM, demand/rank,
mapped/DMA, DMA window 8, отмена и ошибка исполнителя. Fixture полного
DMA-окна явно будит service после producer fence: тест продолжает проверять
заполнение всей глубины очереди до запуска потребителя. Отдельная серия
проверяет пробуждение по фактическому запросу, owner-only пустые callbacks,
отмену до первого барьера и повторное использование очереди.

Два дополнительных combined-context запуска с KEEP_RAM=2, demand, rank,
current victims, DMA depth 8 и тремя флагами дали по 108 точных последовательных
повторов с CUDA Graph и без него.

Fixed-history против совместимого GPU-only: равны хеши полных logits и argmax
шести префиксов и 86 шагов, включая 18 CPU jobs / 20 rows; prefill CPU rows = 0.
Проверены KEEP_RAM=2, rank target 1 / 256, демоция 16 МиБ, context overlap 1.

Lifecycle прошёл A→B→A, restore, продолжение, полный prefill, отмену
prefill/decode и повтор с одинаковым seed. Восемь greedy-сравнений совпали
с сохранённым совместимым GPU-only. Выполнены 107 CPU jobs / 146 rows,
поколения runtime-профиля 0→1. Current victims включён в этой проверке.
Это проверка сохранения поведения; прежний вопрос lossless batch/serial
DSpark не закрывается совпадением с тем же режимом GPU-only.

## Длинный контекст

Отдельная A/B/B/A, `base → host → host → base`. В каждом процессе fresh
4096, restore 4096, fresh 8152, restore 8152; по 32 выходных токена, context
8192. Во всех четырёх процессах совпали входы, ответы и acceptance: 18/26
для 4096, 18/27 для 8152. CPU jobs/rows в prefill и decode = 0.

| Процесс | Prefill fresh 4096, с | Чтение H: за запрос, ГиБ | Prefill fresh 8152, с | Чтение H: за запрос, ГиБ |
|---|---:|---:|---:|---:|
| A1 | 14,768 | 23,581 | 28,484 | 79,029 |
| B1 | 13,556 | 10,353 | 28,702 | 80,542 |
| B2 | 13,153 | 9,590 | 28,488 | 79,109 |
| A2 | 13,243 | 9,330 | 28,329 | 78,026 |

Среднее fresh 8152: prefill 28,406 → 28,595 с (+0,66%), wall
33,961 → 34,047 с (+0,25%). Объём чтения немного различается; эта серия
не изолирует чистую цену GPU-prefill от SSD. Fresh 4096 особенно зависит от
первого холодного запуска, его усреднённое ускорение не приписывается изменению.
Ускорение полного prefill не подтверждено. Явного большого ухудшения нет,
но отдельный контроль длинного prefill без физического чтения не получен.

Восстановление сессий даёт более чистое сравнение:

| Контекст | Decode A → B, с | Изменение | Wall A → B, с | CPU-seconds A → B |
|---|---:|---:|---:|---:|
| 4096 | 2,457 → 2,375 | −3,35% | 2,500 → 2,414 | 6,250 → 3,953 |
| 8152 | 2,267 → 2,191 | −3,35% | 2,328 → 2,265 | 5,445 → 3,563 |

При restore 4096 чтение H: равно нулю; при restore 8152 всего 28–48 КиБ
на запрос по системному счётчику диска. Prefill restore составляет 41–65 мс.
Нельзя переносить эти цифры на fresh/full prefill или произвольные тексты.

## Итог и следующий шаг

Подтверждён локальный выигрыш `CPU_EMPTY_FAST=1`. Кандидат сохранён в
`host-config.json` и `best-config.json` архива; два других флага выключены.
Всю связку не следует включать автоматически: дополнительного выигрыша
от неё пока нет. Для дальнейших опытов три флага остаются независимыми.

О4 ещё не закрыт по порогу ≤3% от GPU-only. Устранены лишние CPU-публикации
и пробуждения в доказанно пустых ветках; при этом остаются подготовка снимков,
поиск размещения матриц, обслуживание непустой I/O-очереди и активное ожидание
DMA. Следующий шаг — разделить их стоимость в измеряемом decode и уменьшить
ожидание непустой очереди, сохранив раннее чтение. Снижение CPU-seconds само
по себе не служит доказательством роста скорости.

Архив содержит бинарники, профиль, конфигурации и входы, короткие/длинные
JSON и логи, correctness-трассы, исходники, `o4-only.diff` относительно
О3 RAM, полный diff и SHA256 manifest. Все 119 файлов предыдущего архива
О3 RAM проверены по хешам и не изменены.
