# Одинаковые токены при полном и поэтапном prefill

10 октября 2026, продолжение [стабильного stream-K](DEEPSEEK4_STABLE_STREAM_K.md).
На фиксированном контексте из **410 токенов** без DSpark воспроизведено
расхождение полного prefill и поэтапного продолжения. Оно возникает до
выбора выходного токена. Сохранение/восстановление состояния и диагностическое
чтение в проверенных прогонах не меняют logits.

Это этап локализации численного расхождения, не оптимизация скорости.
Пакетный prefill не заменён обработкой по одному токену. Рабочие настройки
не переключаются на численный эксперимент.

## Условия и способ сравнения

Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, CUDA 13.0,
драйвер 581.80. Модель DeepSeek-V4-Flash-0731 UD-Q3_K_XL на H:,
без draft-модели. Контекст 8192, batch 4096, target cache 15360 МиБ,
stage 16 МиБ. Исследовательская сборка: MMVQ2, router MMVF,
HCA compact и `STRATA_DS4_FA_COMPACT=3`.

Token IDs взяты из прежней проверки сессий: исходный prompt 372 токена,
фиксированные 32 токена ответа и 6 токенов продолжения. Во время сравнения
выбор новых токенов не выполняется:

- Полный путь: позиции 0–408 одним пакетом, затем позиция 409 отдельно.
- Поэтапный: 0–370 одним пакетом; 371–403 по одному; 404–408 пакетом
  из пяти; затем та же позиция 409 отдельно.

Это воспроизводит способ построения активного контекста из проверки сессий.
Каждый путь начинается с очищенного контекста и тех же token IDs.
Для последнего токена используется одинаковый одиночный graph.

Для каждого пути отдельно измеряются:

1. Logits без наблюдения на естественно построенном состоянии.
2. Logits после snapshot/restore того же состояния.
3. Logits с callback чтения активаций.
4. Повтор после ещё одного восстановления без callback.

Отдельный режим захватывает раннюю позицию 371: её строку в большом пакете
и её одиночное вычисление. Для контроля влияния такой трассировки весь
prefix повторно строится с ней, а затем проверяются конечные logits.
Это не сравнение времени исполнения: callback добавляет синхронизации.

## Последний токен и сохранённые ключи

Максимальная разница полных logits — **3,58053017**, RMS **0,724725**.
Argmax полного пути — token ID **1** (EOS), поэтапного — **112496**.
Все 129280 элементов logits различаются. Восстановление, влияние callback
и повтор после восстановления дали **0** в обоих путях.

У позиции 409 одинаковы `hc_init`, `attn_norm-0`, `qr-0`, `qr_norm-0`,
Q, новый K и вход Q самого Flash Attention. Различается уже содержимое
**исторических K/V первого слоя**:

- видны те же 128 ключей с физическими индексами 282–409;
- маски и attention sinks совпадают;
- отличаются 60 ключей, 8994 FP16-элемента K и столько же V;
- максимум разницы K/V — **0,00390625**;
- выход attention различается до **0,0022130013**, выход слоя 0 — до
  **0,0015253555**.

Список отличающихся ключей включает все позиции 371–408 и 22 позиции
из ранее общего текста. Последняя позиция 409 совпадает. Следовательно,
новая сетка stream-K последнего токена не может сама устранить это
расхождение: на вход уже приходят разные исторические значения.

## Ранняя позиция и матричные операции

Для позиции 371 embedding (`hc_init`) совпадает. Первое захваченное
расхождение — `hc_mixes-0` attention-ветки: до **0,0093688965** в 24 значениях.
Вес `blk.0.hc_attn_fn.weight` имеет тип **F32**, форму **16384×24**,
операция использует `GGML_PREC_DEFAULT`. Нормализованный вход матрицы
совпадает. Это не BF16 router, исправленный на предыдущем этапе.

В этой позиции результат ветки `hc_pre` и `hc_attn_pre-0` совпадает, как и
`attn_norm-0`. При таком одинаковом входе проекция `qr-0` всё же отличается
до **0,00010628253**: вес `blk.0.attn_q_a.weight`, **Q8_0, 4096×1024**.
Следовательно, существует самостоятельное расхождение матричного
вычисления Q, не требующее отличающегося входа после HC.

Выход **K до RMSNorm** также различается при одинаковом входе: до
**0,00010615587** в 512 значениях, вес `blk.0.attn_kv.weight`,
**Q8_0, 4096×512**. После нормализации разница достигает **0,00074061751**.
Эти результаты получены захватом непосредственно в callback матрицы;
влияние наблюдения, snapshot/restore и replay на конечные logits — 0.

| Матрица слоя 0, позиция 371 | Максимальная разница входа | Максимальная разница выхода | Отличающихся значений |
|---|---:|---:|---:|
| HC attention, F32 16384×24 | 0 | 0,0093688965 | 24 |
| Q, Q8_0 4096×1024 | 0 | 0,00010628253 | 1024 |
| K, Q8_0 4096×512 | 0 | 0,00010615587 | 512 |

Обе строки Q8_0 имеют `GGML_PREC_DEFAULT`. В закреплённом CUDA dispatch
одиночные и большие пакеты выбирают разные матричные пути; фактический kernel
для этих операций ещё не трассировался. Тип веса и равенство входа сами
по себе не доказывают конкретный механизм округления внутри kernel.

Чтение матричного результата выполняется в callback **самой MUL_MAT**,
выбранной по имени веса. Чтение её предков после последующей нормализации
не подходит: allocator может уже переиспользовать временный буфер.
Диагностика сохраняет тип и форму веса, режим precision, вход и результат
операции, не копируя веса модели на CPU.

## Диагностический инструмент

Добавлен [probe_deepseek4_prefill.py](../../tools/probe_deepseek4_prefill.py).
Он принимает JSON-массив 2–1024 token IDs и отдельный профиль без DSpark:

```powershell
python tools/probe_deepseek4_prefill.py --config profile.json --tokens-json tokens.json --splits 371,372,373 --output bench/results/prefill.json
```

`--splits` — возрастающие исключающие границы пакетов до последнего токена;
оставшийся prefix дополняется автоматически. Пример выше описывает границы,
но не всю серию из этого отчёта: её полный список лежит в `splits.txt`.
`--history-row 371` захватывает ранний токен. После расширения от 11 октября
позиция может находиться и внутри многотокенного сегмента: читается только
соответствующая строка обоих пакетов. `--nodes` принимает существующие имена tensor/callback,
`@attention0`, `@attention:<имя маски>`, `@attention-sinks:<имя веса sinks>`
и `@weight:<имя веса>`. Attention selectors также поддерживают историческую
строку внутри длинного сегмента. [Проверка Q_b и attention](DEEPSEEK4_QUERY_EXPANSION.md).

Внутренние переменные: `STRATA_PREFILL_PROBE` — путь отчёта,
`STRATA_PREFILL_PROBE_SPLITS`, `STRATA_PREFILL_PROBE_HISTORY_ROW` и прежние
`STRATA_SPEC_TRACE_NODES`/`STRATA_SPEC_TRACE_NODE`. Probe запускается один раз
перед первым GEN только при явно заданной переменной. Затем контекст очищается
и обычный запрос выполняется заново. Без переменных этот путь не вызывается.

Имена файлов результата должны быть новыми, чтобы не смешивать трассы.
Есть предел числа токенов, размера readback и времени процесса. DSpark для
такого сравнения запрещён. Матрицы модели вычисляются на GPU; CPU считает
статистику уже прочитанных диагностических массивов.

## Проверки

- Финальная исследовательская сборка прошла **22/22 CTest** за 89,79 с,
  включая probe, attention, MMVQ/router, передачу экспертов и GPU-only contract.
- Python-проверки `serve.test_deepseek`, `tools.test_deepseek4` и
  `serve.test_vram_settings`: **25 тестов** за 2,270 с.
- Контроль с одинаковыми пакетами по обе стороны на 16 токенах дал нулевую
  разницу logits, snapshot/restore, observation и replay.
- Проверки сессий, отмены, одного токена и воспроизводимого sampling с
  выключенным probe завершились с `passed=true` с DSpark и без него.
  Greedy token IDs совпали между режимами для проверенных ответов,
  продолжений и восстановления. 28 проверок причинности DSpark дали 0.
- `full_prefill_identical=false` сохраняется в обоих режимах.

В каждом из диагностических прогонов — один зарегистрированный GPU-аудит,
в проверках DSpark/обычного decode — 324/1; везде `cpu_compute_nodes=0`.
Linux, другие GPU, произвольные тексты и все размеры контекста не проверены.

После возврата обычной сборки прошли **5/5 контрольных CTest** за 12,16 с:
prefill probe, выбор сетки stream-K, activation probe, GPU-only contract
и attention. Все 237 контрольных сумм attention совпали со штатным режимом,
`experiment_compiled=false`. В этой проверке также проверен новый отказ
от сравнения пустых диагностических массивов без обращения к их данным.
`STRATA_DEEPSEEK_ATTENTION_EXPERIMENT=OFF`, рабочий профиль не изменён,
движок и сервер после проверок не запущены.

## Материалы и следующий шаг

Материалы находятся в `bench/results`, префикс `ds4-prefill-20261010-`:

- `actual`, `detail` с расширениями `.json/.jsonl/.log` — конечные logits,
  видимые K/V, маски и контроль snapshot/observer/replay;
- `history` — ранняя позиция 371;
- `weight` — финальный захват входов/выходов матриц непосредственно при MUL_MAT;
- `identity` — одинаковый способ построения с обеих сторон;
- `validate-{plain,dspark}` — обычные проверки сессий с выключенным probe.
- `summary.json` — численные сравнения, CPU/GPU-аудиты и SHA-256 бинарников.
- `default-fixture.json` — контроль обычной сборки без attention-эксперимента.

Профили, фиксированные token IDs, split endpoints и команды —
`build-local/deepseek4/prefill-20261010`.

Промежуточный `projection` сохранён как диагностический материал, но его
чтение предков после нормализации не используется для вывода о raw K.
Этот результат заменён безопасным захватом `weight`.

Финальный численный прогон `weight` выполнен `experiment-final.exe`, SHA-256
`021480e46577b89b7e4dbbb9e341af2fe60a1a57de81cbb3ccecb8df7b0fc947`.
Проверки сессий и identity выполнены `experiment-projection.exe`, SHA-256
`095b7526be56ae2e3292747ef3d82f865106e3e611544b5c17a2eb6adea2d864`;
последующее изменение касалось выбора диагностического callback по весу.

Итоговая обычная сборка:
`c0865c17a069a9efc6d85ff3f37d633d1c3ff3a6b508ad0eb67a5917874734d2`.

Этот шаг выполнен 11 октября: [HC и Q/K проверены отдельно](DEEPSEEK4_PROJECTION_PARITY.md)
с трассой фактического dispatch и FP64-эталоном. Выделены TF32 в HC и
разные масштабы квантования входов Q/K. Их изменение сблизило проекции,
но не устранило расхождение конечных logits. Проверка остальных слоёв,
compressor state и всей истории остаётся необходимой; равенство одного
участка не доказывает равенство полного prefill.
