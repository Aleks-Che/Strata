# Стоимость операций и проверка двух вариантов attention

11 октября 2026. Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ,
CUDA 13.0, драйвер 581.80. Модель DeepSeek-V4-Flash-0731 UD-Q3_K_XL
на H:, DSpark Q8_0. Вычисления модели выполнялись на GPU.

**Ускорение не подтверждено.** Основная разница между рабочим режимом
и полным численным экспериментом обнаружена внутри attention. Проверены
другие размеры порций и повторное использование коэффициентов softmax
при объединении частичных результатов. Оба варианта отклонены; рабочий
профиль не изменён. В коде оставлена отключаемая диагностика затрат.

## Измерение на фиксированных токенах

Добавлены `tools/profile_deepseek4_cost.py` и `fixed_workload.hpp`.
Они выполняют четыре прохода одной последовательности из 4096 token IDs:

- полный prefill 4096;
- первые 36 токенов, затем ещё 32 фиксированных токена по одному;
- те же первые 36 и следующие 32 токена порциями по 3, с остатком 2.

Перед каждым проходом очищается KV, кэш экспертных матриц сохраняется.
Сэмплирования, DSpark и callbacks чтения активаций нет. Синхронизация
входит во время `llama_decode`; расчёт контрольных сумм logits исключён.
Первый проход исключён из приведённых медиан. Это измерение заданной
нагрузки target, а не скорости генерации ответа.

Входные токены между режимами одинаковы. Обычный режим и численный
эксперимент могут выбирать разные эксперты из-за различий арифметики.
Одинаковые входы сами по себе не гарантируют одинаковый внутренний маршрут.

Отдельная сборка `STRATA_DEEPSEEK_COST_EXPERIMENT=ON` добавляет CUDA events
вокруг операций GGML, включая слитые операции. События записываются
в назначенный операции stream; результаты считываются после подграфа
планировщика. Пул ограничен 32768 парами событий на поток, файл общий
для потоков резервирования и исполнения. Обычная сборка не содержит
этих перехватов.

Профилировщик требует `GGML_CUDA_DISABLE_GRAPHS=1`. Fusion сохраняется.
Время между событиями включает ожидания stream и промежутки между
запусками с CPU. Сумма может включать перекрывающиеся операции;
это **не чистое время CUDA-ядер и не процент GPU idle**. Передача экспертов
до начала операции также не становится её собственным временем.
Поэтому реальную скорость ниже измеряли отдельно, без событий.

Nsight Systems 2024.2.3 на этом ПК потребовал права администратора.
Вместо него использованы локальные CUDA events. Оставшийся после
неудачного запуска приостановленный тест Nsight удалён из процессов:
CPU-время 0, тест до CUDA-инициализации не дошёл.

## Где расходуется время

Оба режима: target-only, контекст 8192, batch 4096, экспертный кэш
15360 МиБ, stage 16 МиБ, конвейер, два reader-потока, один управляющий
поток модели. B — полный набор из отчёта о
[проекциях индексатора](DEEPSEEK4_INDEXER_PROJECTIONS.md).
A — обычные численные настройки. Для обоих включена одинаковая
диагностика и отключены CUDA graphs.

Медиана суммы событий за один прогретый prefill 4096, мс:

| Операции | Обычный режим A | Численный эксперимент B |
|---|---:|---:|
| Attention | 671,06 | 2368,71 |
| Routed gate | 160,17 | 148,77 |
| Routed up | 159,49 | 146,39 |
| Routed down | 161,45 | 153,17 |
| Проекция attention output-A | 74,67 | 99,83 |
| Проекция attention output-B | 45,68 | 62,29 |
| Проекция attention Q-B | 45,87 | 54,63 |
| Сумма медиан по всем группам | 1764,94 | 3603,73 |

На attention приходится около 1,70 с из 1,84 с разницы сумм событий.
Это указывает, куда направить дальнейшую оптимизацию. Оно ещё не
разделяет compact/gather, основное MMA-ядро и stream-K fixup.
Полный prefill с передачей весов занял в этих диагностических запусках
8543,19 и 10671,93 мс соответственно. Эти числа не заменяют прежнее
сравнение обычной генерации с DSpark.

Собрано 793584 и 801136 записей операций. В каждом режиме повторились
все сохранённые контрольные суммы logits. Для B проверены также запуск
без событий и прототип ниже: совпали **184 пары FNV-1a64/argmax** в каждом
сравнении. На 44 общих конечных позициях совпали контрольные суммы
обработки по одному и по три токена. Это проверка сохранённых сумм,
а не сохранение всех полных массивов logits.

## Размер порций attention

Вместо текущих 128 query проверены 16, 32, 64 и 256. Синтетические
GPU-данные: D=512, 64 головы, KV length 8192, strided Q, SWA/HCA/sparse,
257 и 4096 query. Все **36 полных сравнений массивов** побитово совпали
с вариантом 128.

Устойчивого улучшения не получено. Например, для SWA bound 128 и 4096
query исходный вариант занял 5,42/5,43 мс, порция 16 — 12,26 мс,
32 — 8,54 мс, 64 — 6,19 мс, 256 — 5,55 мс. На больших bounds разброс
контроля оказался сопоставим с разницей вариантов. Изменение удалено.

## Общие коэффициенты stream-K fixup

Прототип вычислял softmax-коэффициенты один раз на CUDA-блок и сохранял
их в shared memory для 512 элементов результата. Порядок объединения
частей оставался прежним; GPU-модель не переносилась на CPU.

Fixture: bounds 128/384/640/2048, query counts 1/3/257/4096,
порядок A/B/B/A, strided Q, masks и sinks. Все **64 сравнения полных
выходов** дали точное совпадение. На длинных пакетах ускорения не было:
при bound 640 и 4096 query медиана 130,80 → 131,28 мс. Короткие
измерения колебались в обе стороны.

В полной модели без DSpark, событий и наблюдателей:

| Фиксированная нагрузка | Исходный, мс | Прототип, мс |
|---|---:|---:|
| Prefill 4096 | 10580,26 | 10662,04 |
| 32 токена по одному | 2111,01 | 2203,17 |
| 32 токена порциями по 3 | 1328,57 | 1409,82 |

Одинаковые контрольные суммы и итоговые счётчики hits/misses/H2D/D2D
подтвердили, что в этой паре не сменились токены и пути экспертов.
Последовательная пара сама по себе не доказывает небольшую регрессию;
она также не даёт основания заявлять ускорение.

## Полный запуск с DSpark

Один executable, одинаковый численный набор с исправлением индексатора;
меняется только прототип fixup. Это **не сравнение с рабочим профилем**.
DSpark2, кэши target/draft 15360/1024 МиБ, shared scratch, stage 16,
batch 4096. Четыре свежих процесса A/B/B/A, короткий запрос 36 токенов,
ответ 32 токена, четыре повтора из RAM-сессии. После них — полный
prefill 4096 в новой сессии без восстановления KV. События отключены,
fusion и CUDA graphs работают штатно.

| Запуск | Поздние повторы 3/4, ток/с | Медиана всех четырёх, ток/с | Новый prefill, мс |
|---|---:|---:|---:|
| A1 | 14,537 | 13,598 | 10603,6 |
| B1 | 14,592 | 13,806 | 10664,5 |
| B2 | 13,569 | 13,424 | 11932,3 |
| A2 | 14,304 | 13,599 | 10718,0 |

Медианы поздних повторов: **14,420 → 14,081 ток/с (−2,36%)**.
По всем повторам: **13,598 → 13,615 (+0,12%)**.
Prefill: **10660,8 → 11298,4 мс (+5,98% времени)**.
Из-за разброса нельзя считать небольшие различия доказанной регрессией,
но устойчивого выигрыша нет ни по одному из этих критериев.

Все выходные token IDs совпали между A/B и повторами. Для коротких
повторов draft acceptance везде 18/26, для длинного ответа — 1/6.
Пиковая выборочная загрузка процесса вне загрузки модели — 5,32%
всех 32 логических CPU, системы — 16,6%. Аудит вычисления модели
не зарегистрировал операций CPU. Пик выборочной VRAM — 31616 МиБ,
включая рабочий стол.

Из 20 повторных запросов только 5 дали нулевые физические чтения H:.
Остальные — 128 КиБ–24,02 МиБ. Счётчик относится ко всему устройству,
источник чтений не установлен. Эту серию нельзя называть RAM-only.

## Что осталось в проекте

Оставлены только диагностика CUDA events и фиксированная target-нагрузка.
Неудачные варианты attention удалены из исходников. Локальная копия
прототипа и его executable сохранены для воспроизведения замеров.
Следующий шаг — разделить время attention на подготовку sparse-списков,
основное MMA-ядро и fixup, затем измерять изменение самого дорогого этапа.
Этот этап выполнен в [отдельном отчёте](DEEPSEEK4_ATTENTION_STAGES.md):
основное время приходится на MMA; пропуск пустых хвостовых блоков с
сохранением sink сократил prefill полного экспериментального набора на 16%.
Повторять подбор размера порций или общих коэффициентов без новой
гипотезы эти результаты не оправдывают.

Сборка диагностического варианта:

```powershell
cmake -S backends/deepseek4 -B build-deepseek4 -DSTRATA_DEEPSEEK_ATTENTION_EXPERIMENT=ON -DSTRATA_DEEPSEEK_PROJECTION_EXPERIMENT=ON -DSTRATA_DEEPSEEK_COST_EXPERIMENT=ON
cmake --build build-deepseek4 --target strata-deepseek4 -j 2
python tools/profile_deepseek4_cost.py --config TARGET_ONLY.json --tokens-json TOKENS.json --events --output bench/results/FRESH_NAME.json
```

Нужен отдельный target-only профиль без `--draft-model`, batch не меньше
числа входных токенов, контекст с запасом. Вход — JSON-массив 68–4096
token IDs. Для измерения без событий убрать `--events`. Команда выполняет
только ограниченную диагностику, сервер не запускает. Шесть ошибочных
вариантов входа/размеров проверены: отказ до запуска движка.

Артефакты в локальном `bench/results/`, префикс
`ds4-kernel-cost-20261011-`:

- `stock-events-v2` и `full-events-v2`: JSON, TSV, журналы;
- `cost-summary.json`: агрегаты событий;
- `chunk-fixture.json`, `fixup-fixture.json`: проверки массивов и времена;
- `fixed-control.json`, `fixed-fixup.json`: фиксированные входы и logits hashes;
- `perf-1-control`, `perf-2-fixup`, `perf-3-fixup`, `perf-4-control`;
- `performance-summary.json`: сводка A/B/B/A и физические чтения.

Первый файл `full-events` без `v2` не используется: начальный вариант
записи событий открывал файл из двух потоков. Исправление общего sink
входит в текущий исходный код; обе таблицы выше построены по `v2`.

Скрипты, конфигурации, `tokens.json`, журналы сборки и отклонённый
прототип: `build-local/deepseek4/kernel-cost-20261011/`.
SHA-256 executable, использованного для финальных A/B/B/A:
`e902e9114dbdcb2e759fc8f56489ee4f8ff119fb689c9cec81d718ce25ea5bfa`.
Проверка Linux на этом этапе не проводилась.

После проверки восстановлена обычная сборка: ATTENTION, PROJECTION и COST
эксперименты OFF. Семь контрольных CTest прошли за 69,52 с;
все 237 контрольных сумм attention совпали с исходным обычным режимом.

`70efe17aa92002803b6c42781056c882ec2d9d70170b25b38b000521bc867ec3`.

`b78e88fc60da30f6f794d9d1413f86915e3695b911fd4507fb0ab965f7025092`.
