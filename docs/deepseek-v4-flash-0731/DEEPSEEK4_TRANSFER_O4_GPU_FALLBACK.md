# О4: обычный GPU-путь при заранее исключённом CPU

14 октября 2026. Продолжение [парковки I/O-service](DEEPSEEK4_TRANSFER_O4_SERVICE.md).

## Изменение

Опция `STRATA_DS4_CPU_EMPTY_GPU_FALLBACK=1` проверяет замороженный профиль
до подготовки CPU-снимка RAM и публикации mapped-очередей. Если даже самая
дешёвая измеренная CPU-работа не помещается в бюджет ни одного причинного
префикса окна, ветка возвращается к обычному GPU-транспорту. При выключенной
опции поведение сохраняется. Значение по умолчанию — 0.

Проверка использует нижнюю оценку без неотрицательных накладных расходов
и конкуренции с DMA. Поэтому она может пропустить возможность обхода,
но не должна отвергать допустимое назначение. Отсутствие CPU jobs в прошлом
запросе не используется как доказательство. Непригодный профиль не проходит
новую проверку; `force` сохраняет назначения. Проверяются все префиксы окна
MTP, включая допустимый CPU на более позднем префиксе.

Просмотр нового профиля не меняет наблюдателя стоимости предыдущего задания.
Перед переходом завершаются все контексты CPU/fetch, освобождаются leases
и снимаются старые CPU-привязки графа. Повторный вызов старого селектора с
host IDs тоже отклоняется до выделения пула, pinned-буферов и mapped-очереди.
Для следующей ветки профиль проверяется снова, с учётом поколения текущего
запроса. Обратный переход GPU → CPU остаётся возможным.

Счётчик `cpu_gpu_fallback` в `STRATA_EXPERT_TIMING` показывает число обходов.
Нулевые `fetch_*` timings в этом режиме означают отсутствие дополнительной
очереди, а не отсутствие чтения или DMA в обычном транспорте.

## Условия измерения

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ; под нагрузкой PCIe Gen3 x16.
Target: `H:\deepseek-v4-flash-0731\UD-Q3_K_XL`, DSpark Q8_0, draft-max=2,
контекст 8192, GPU-кэши 15360/1024 МиБ, RAM-кэш 2048 МиБ.
CPU lane: 12 потоков, partitions=2, spin=0, новый измеренный профиль сборки.
Owner DMA: depth=8, staging 4×4 МиБ, mapped reader, early sources=1.
О3: demand для обоих кэшей, target rank=1/scan=256; `CPU_EMPTY_FAST=1`.
Парковка I/O-service, lazy CPU-service и empty-fetch fast path выключены.

В каждом процессе четыре одинаковых fresh-запроса по 15 входных / 32 выходных
токена. Первые два — прогрев. Скорость процесса — 64 / сумма времени двух
поздних decode; wall, CPU-seconds и трафик — суммы этих двух запросов.
Результат A/B/B/A — среднее двух скоростей процессов каждого режима.
Кэш ОС не очищался. Начальный запрос первого пилота прочитал 35,27 ГиБ с H:;
поздние измерения ниже имели нулевое физическое чтение этого устройства.
Счётчики дисков охватывают все процессы: на PhysicalDrive3 параллельно
наблюдалось около 0,5–0,7 ГиБ чтения за позднюю пару, источник не определялся.

## Нулевое CPU-назначение

N0: бюджет CPU=0,01 мкс, KEEP_RAM=0, demotion=0. A — прежняя очередь,
B — новая опция. В обоих вариантах CPU jobs/rows равны нулю.

| Запуск | Decode, ток/с | Wall, с | CPU, с | H2D, ГиБ |
|---|---:|---:|---:|---:|
| A1 | 14,373 | 6,969 | 11,734 | 25,681 |
| B1 | 13,374 | 7,437 | 10,109 | 31,680 |
| B2 | 13,341 | 7,453 | 10,172 | 31,680 |
| A2 | 13,975 | 7,219 | 12,156 | 25,681 |

Среднее: **14,174 → 13,357 ток/с, −5,76%**. Wall 7,094 → 7,445 с,
**+4,95%**; CPU-seconds 11,945 → 10,141 с, **−15,11%**.
Обход заменил 1520 target-веток и 102 DSpark-ветки; CPU-снимки и обе
дополнительные очереди в этих ветках отсутствуют.

Обычный транспорт изменил работу кэша: H2D вырос 25,681 → 31,680 ГиБ,
примерно на 23,36%. Поэтому это не абляция одной только цены очереди при
неизменном размещении матриц. Отдельный пилот GPU-only дал 15,402 ток/с
при тех же 31,680 ГиБ H2D: один рост трафика не объясняет весь остаток.
Причинное разделение оставшейся цены планировщика, RAM и транспорта в этом
опыте не выполнено.

## Смешанный режим

Отдельная A/B/B/A с бюджетом 1000 мкс, KEEP_RAM=2, demotion=16 МиБ.
В каждой поздней паре обеих конфигураций: 55 CPU jobs / 75 rows у DSpark,
ноль CPU rows в prefill. Обход заменил 156 target-веток; 1364 target-ветки
и 102 DSpark-ветки сохранили очередь. Другой допустимый префикс окна
не позволяет заранее исключить CPU у всех оставшихся target-веток.

| Запуск | Decode, ток/с | Wall, с | CPU, с | H2D, ГиБ |
|---|---:|---:|---:|---:|
| A1 | 14,436 | 7,078 | 12,859 | 25,796 |
| B1 | 14,539 | 7,094 | 12,688 | 25,881 |
| B2 | 14,728 | 6,969 | 12,766 | 25,881 |
| A2 | 14,923 | 6,875 | 12,438 | 25,796 |

Среднее: 14,680 → 14,633 ток/с, **−0,31%**; wall **+0,79%**,
CPU-seconds **+0,62%**. Ускорение не установлено. В обеих сериях и пилотах
совпали входные/выходные token IDs всех четырёх запросов и acceptance DSpark:
14 принятых из 33 предложенных за каждый поздний запрос.

## Проверка корректности

На финальной сборке прошли 39 CTest. Четыре новых запуска проверяют
CUDA Graphs on/off и context overlap on/off. В каждом — 144 побитно точных
повтора с чередованием CPU-очереди и обычного GPU-транспорта внутри одного
графа, окнами 1/3/4 и отдельными маршрутами слоёв. Дополнительно по 18 точных
повторов с поколениями 0 → 1 → 2: CPU → GPU fallback → CPU. Стоимости этого
малого теста синтетические; переходы исполняет настоящий движок.

На модели полные logits совпали с GPU-only на 6 префиксах и 86 шагах
для каждой из двух проверок: обычная hybrid-работа и бюджет 0,01 мкс с обходом.
В первой было 18 CPU jobs / 20 rows, в prefill — ноль. Во второй — ноль
CPU/fetch snapshot-подготовок, CPU jobs и выделенных mapped-байтов CPU-очереди
в обоих её контекстах.

Lifecycle с бюджетом 1000 мкс прошёл A → B → A, продолжение, восстановление,
отмену prefill/decode и повтор. Все восемь greedy-сравнений с GPU-only совпали.
Зарегистрированы 67 CPU jobs / 90 rows; максимальный накопительный счётчик
обходов одного backend — 390. Измеренный профиль остался в поколении 0.

Для обязательного обновления поколения отдельно использовалась копия профиля
с вдвое уменьшенными compute/loaded_compute costs. Этот тест тоже прошёл
восемь greedy-сравнений: 222 CPU jobs / 297 rows, поколения 0 → 1.
Копия помечена `test_fixture` и не использовалась ни в одном замере скорости.

## Решение

Опция оставлена экспериментальной и выключенной. `best-config.json` сохраняет
прежний N0 без обхода; рабочий профиль сервера не переключён. Новые длинные
замеры не проводились: кандидат не прошёл короткое сравнение. Приёмка О4
и О6 остаётся открытой.

Следующий отдельный опыт — перенести отбор и защиту матриц О3 в обычный
GPU-транспорт и повторить сравнение с контролем H2D. Затем отдельно измерить
оставшуюся подготовку CPU-планировщика при отсутствии CPU-назначений.
Снижение CPU-seconds само по себе не является ускорением генерации.
