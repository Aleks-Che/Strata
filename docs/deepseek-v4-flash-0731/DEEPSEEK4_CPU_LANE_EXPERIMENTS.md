# CPU lane: план испытаний после сравнения с Maya

12 октября 2026. Продолжение [аудита](DEEPSEEK4_CPU_LANE_V2_MAYA_AUDIT.md). Рабочий профиль остаётся GPU-only; экспериментальные режимы проверяются отдельно. Hardware: Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, SSD H: Samsung 990 PRO; DeepSeek UD-Q3_K_XL и DSpark Q8_0.

## Последовательность

| Этап | Изменение | Условие принятия |
|---|---|---|
| 1 | Выбор CPU для каждого токена, отдельные маски вычислений и передачи | Добавление/замена будущих маршрутов не меняет CPU-строку префикса; смешанные CPU/GPU-вхождения сохраняют результаты |
| 2 | Защищённые адреса готовых RAM-матриц для CPU и pipeline | Нет повторного pack; нет use-after-free, чтения незавершённого блока и выхода за бюджет; корректны отмена и вытеснение |
| 3 | Калибровка на разных весах и реальных формах | Раздельная оценка подготовки, DRAM, dot products и обмена; подтверждение новым запросом и фиксированной историей |
| 4 | Подбор cap и 8/12/16 потоков | Повторяемый выигрыш по полному запросу, без скрытой смены workload |
| 5 | Service/ring, GPU-публикация маршрутов, затем spin/sleep | Отдельное измерение убранных синхронизаций; сохранение отмены, ошибок и CUDA Graph replay |

Не считать совпадение токенов нескольких запросов доказательством равенства CPU/GPU-арифметики. Не ослаблять строгую проверку восстановления сессий ради прохождения теста. Прогретые и холодные запросы, acceptance и физическое чтение SSD учитывать отдельно.

## Этап 1: реализован и проверен

Лимит --expert-cpu-max-experts теперь относится к каждому токену. Решение просматривает только текущий токен и уже обработанный префикс. Матрица исключается из передачи только тогда, когда все её вхождения в окне назначены CPU. CUDA MMVQ использует маску отдельных строк; mixed CPU/GPU не теряет веса.

Калибровка временно приведена к одному токену: убрано деление всего времени batched CPU-вызова на длину окна. Auto учитывает уже назначенную работу CPU и уникальные GPU-передачи префикса. Это ещё не полная калибровка этапа 3: измеряется один повторяемый blob, и не моделируются все расходы планировщика.

Нативный тест прошёл: 2880 существующих сценариев и 72 новых append/replay/mixed-device сценария, IQ3_XXS/MXFP4/Q8_0, с clamp и без. CPU-строка первого токена побитно совпадает при добавлении/замене следующих токенов; GPU-строки совпадают со своим GPU-контролем. Это проверка экспертной ветки, не полных logits модели.

Условия полного бенчмарка: context 8192, batch 4096, draft-max 2, target GPU-cache 15360 МиБ, draft 1024 МиБ, stage 16 МиБ, 2 reader, private CPU RAM 256 МиБ. Запрос decode: 36 входных и 64 выходных токена, четыре cached repeat, затем свежий prefill 4096. Файловый кэш ОС не сбрасывался. Чтение PhysicalDrive6 включает весь диск.

| Режим | R4, ток/с | SSD в R4 | Все cached repeats совпали |
|---|---:|---:|---|
| GPU-only, до опытов | 17,108 | 0 | да |
| Fixed CPU 8, cap 1/token | 11,350 | 0 | да |
| Auto CPU 8, cap 1/token | 12,454 | 0 | нет |
| GPU-only, после опытов | 17,170 | 0 | да |

Исправление выбора необходимо для корректной организации MTP, но ускорения относительно GPU-only в этой серии не дало. В auto R1–R3 читали SSD: около 666/972/582 МБ; численная история менялась. Поэтому его R4 нельзя трактовать как сравнение идентичного workload с GPU. Fixed выполняет больше CPU-строк, чем прежний cap на всё окно.

Артефакты: build-local/deepseek4/cpu-causal-20261012/summary-v2.json; bench/results/ds4-cpu-causal-20261012-a1,b1,c1,a2.json; исходный executable сохранён отдельно как baseline.exe, версия этапа 1 — causal.exe. Каталоги результатов игнорируются Git.

## Этап 2: реализован и измерен

Общий HostCache получает опциональный pinned allocator и lease на готовую матрицу. CPU держит три отдельных адреса gate/up/down до завершения задания; частичное наличие отправляет работу на GPU. Опубликованность, частотное удержание и защита от prefill остаются у общего кэша. Отдельные CPU blobs в этом режиме не выделяются.

Эксперимент включается STRATA_DS4_CPU_SHARED_RAM=1 вместе с STRATA_DS4_RAM_CACHE_MIB и CPU-потоками. Объём ограничен общим RAM-бюджетом и запасом свободной памяти. GPU-передачи пока продолжают использовать существующее pinned staging; прямой H2D из общего адреса — отдельный следующий опыт. RAM/VRAM пока не exclusive tiers.


Общий кэш проверен 214 assertions, включая 1200 чтений двумя потоками, lease после уничтожения владельца, давление памяти, запрет переиспользования удерживаемого блока, padding, идентичность файла и отменённое заполнение. Ещё 30 GPU-сценариев проверили прямой CPU-доступ к общим pinned-матрицам на IQ3_XXS/MXFP4/Q8_0 при нулевом private CPU cache и смешанных CPU/GPU-вхождениях.

Общий pinned RAM-cache 2048 МиБ на target и DSpark вместе; private CPU cache 0. Остальные параметры как в этапе 1. Все режимы force используют только готовые RAM-матрицы, отсутствующие в GPU-кэше; это не диагностический TEST_FIXED.

|---|---:|---:|---:|---|
| Общий RAM, CPU 0, до опытов | 14,836 | 15,853 | 0 | да |
| Общий RAM, force 8 | 14,256 | 14,376 | 132255744 | нет |
| Общий RAM, force 12 | 14,651 | 15,182 | 0 | нет |
| Общий RAM, force 16 | 14,798 | 15,312 | 0 | нет |
| Общий RAM, auto 8 | 14,124 | 15,525 | 10866688 | нет |
| Общий RAM, CPU 0, после опытов | 14,824 | 15,819 | 0 | да |

В R4 варианты force 8/12/16 выдали одинаковые 64 token IDs друг с другом, но не с GPU-only. У 8 потоков оставалось чтение SSD. Эти цифры не доказывают самостоятельное преимущество 16 над 12 потоками. Для дальнейших сравнений нужен фиксированный workload.

Target, весь процесс force 8: 1641 CPU-задание, 2276 expert/token rows, CPU compute 0,839 с, pack 0, выбор 0,066 с. Force 12/16 выполнили те же числа заданий и строк; CPU compute 0,738/0,669 с. Отдельный CPU cache занимал 0 байт. Общий cache удерживал 2147265536 байт из бюджета 2147483648; pending=0 и OOM=0. RAM-статистика печатается обоими backend и описывает один общий cache — складывать эти строки нельзя.

Для сравнения, auto этапа 1: target pack 4,489 с и выбор 5,202 с, но другой набор CPU-заданий (4442). Устранение повторной упаковки и page residency scan подтверждено; разность сумм не является выигрышем wall time.

Сам дополнительный RAM-кэш замедляет GPU-only: около 15,82–15,85 против 17,11–17,17 ток/с в R4 без него. Он добавляет копирование при заполнении и копирование в staging; 2 ГиБ занимают часть доступной RAM. Следующий опыт должен разделить этот эффект: прямой H2D из готового pinned lease и политика, не удерживающая дубликаты горячих GPU-матриц. Exclusive RAM/VRAM tiers, демоция и service/ring пока не реализованы.

Артефакты этапа 2: build-local/deepseek4/cpu-causal-20261012/summary-shared.json, shared.exe, профили shared-*.json; bench/results/ds4-cpu-causal-20261012-d1,e1,f1,g1,h1,d2.json и .log.


## Одинаковая история без sampling и DSpark

Дополнительный target-only тест использовал ровно 68 одинаковых входных IDs: 36 токенов запроса из GPU-контроля и первые 32 токена его ответа. Каждый из четырёх проходов очищал KV, сохранял expert caches, выполнял полный prefill и два варианта decode: по одному и по три токена. Измерялось время обработки 32 известных токенов после префикса 36; это не скорость выдачи ответа с DSpark.

| Режим | По 1 токену, мс | По 3 токена, мс |
|---|---:|---:|
| GPU-only, до опытов | 1607,0 | 1073,4 |
| Общий RAM 2 ГиБ, CPU 0 | 1718,3 | 1230,3 |
| Общий RAM, force 8 | 1762,2 | 1219,2 |
| Общий RAM, force 12 | 1768,8 | 1206,8 |
| Общий RAM, force 16 | 1771,8 | 1209,6 |
| GPU-only, после опытов | 1615,4 | 1082,9 |

В таблице среднее двух последних проходов. Нет независимых повторов всей серии для доверительных интервалов; разница 12/16 потоков слишком мала для выбора победителя. CPU дал лишь небольшой выигрыш относительно GPU с тем же дополнительным RAM-кэшем на chunk=3, а chunk=1 замедлил. Обычный GPU-only быстрее обоих вариантов.

Физическое чтение SSD за все четыре прохода, включая первые холодные: 339554304 / 8432128 / 21745664 / 0 / 0 / 0 байт соответственно. Это общий счётчик диска за процесс, не отдельное измерение SSD последнего decode. При фиксированных входных IDs внутренние маршруты всё ещё могут отличаться из-за CPU/GPU-округления; тест убирает влияние sampling и acceptance, но не доказывает одинаковые внутренние активации.

Артефакты: fixed-summary.json, fixed-speed-summary.json, fixed-*.json и fixed-*.log в build-local/deepseek4/cpu-causal-20261012.


## Полная модель: корректность и ограничения

В tools/validate_deepseek4_speculative.py строгие assertions не менялись.

- GPU-only прошёл восстановление A→B→A, продолжение чата, fresh/full-prefill, single-token, отмену prefill/decode и seeded repeat. Совпали 8/8 greedy-сценариев со старым GPU-эталоном.
- Fixed CPU, 8 потоков, cap 1/token, private RAM 256 МиБ: те же проверки состояния прошли. Проверка причинности дала 24/24 max_logit_diff=0 при замене будущих draft-токенов; GPU-контроль тоже дал 24/24 нулей.
- Fixed CPU не эквивалентен GPU по всем ответам: среди восьми greedy-сценариев совпали 7/8, session_b отличается. Seeded CPU-ответ воспроизводим внутри этого режима, но отличается от GPU. Прохождение восстановления не означает одинаковую арифметику устройств.
- Shared RAM + force 8: greedy restore, full-prefill и отмена прошли, но seeded repeat после восстановления сессии выдал другой ответ. Весь validator считается проваленным. Кроме того, полные benchmark-повторы этого режима не идентичны.

Артефакты: bench/results/ds4-cpu-causal-20261012-validate-control,fixed,shared.json и .log; validation-summary.json и fixed-vs-control.json в каталоге опыта.

Динамический CPU lane остаётся экспериментальным и выключенным по умолчанию. Новое общее хранилище устраняет измеренные расходы копирования, но пока не даёт выигрыша относительно рабочего GPU-only и не обеспечивает строгую воспроизводимость ответов после смены состояния RAM/VRAM.


### Граница проверки: тот же batch и одиночный decode — разные тесты

Короткий контроль на сохранённой старой сборке также дал 3 нулевых max_logit_diff при замене будущих токенов. Значит, этот конкретный запрос не воспроизвёл ошибку старого общего cap; доказательством исправления выбора служат структурный контрпример из аудита и новые нативные append/mixed-placement регрессии.

Отдельно выполнена serial-проба: одинаковые три входных ID [128822, 7725, 8079], позиция 35, batch=3 против трёх вызовов batch=1. Observer выключен; повтор исходного batch во всех случаях даёт replay_max_abs=0.

| Режим | max_abs logits первой строки | argmax batch / serial |
|---|---:|---|
| Старая сборка, fixed CPU 8 | 2,92143 | 5 / 372 |
| Новый выбор по токенам, fixed CPU 8 | 3,04300 | 5 / 372 |
| GPU-only контроль | 1,57484 | 5 / 372 |

Полная эквивалентность serial/batch не достигнута. Расхождение есть и без CPU lane; новая CPU-ветка его не устраняет. Нельзя объявлять всю зависимость logits от длины окна исправленной на основании маски экспертов или нулевых same-shape causal-проб. Локализация оставшегося расхождения всей модели — отдельный пункт до заявлений о точной эквивалентности MTP одиночному decode.

Артефакты: baseline-causality.json/.log, baseline-serial.jsonl/.log, causal-serial.jsonl/.log и gpu-serial.jsonl/.log в каталоге опыта.

## Что пробовать дальше

1. Отдельно проверить прямой H2D из общего pinned lease, чтобы исключить RAM→staging, и политику удаления дубликатов VRAM из общего RAM-кэша. Сравнивать с GPU-only без дополнительного кэша.
2. Калибровать на вращающемся наборе реальных весов и формах 1/3 токена; учитывать стоимость самого cache/planner. Затем повторять cap/threads и подтверждать выигрыш на фиксированных IDs и свежих запросах.
3. Локализовать serial/batch расхождение и динамическую воспроизводимость CPU-назначений. Не ослаблять assertions восстановления/seeded repeat.
4. Service/ring и GPU-выбор маршрутов остаются следующими архитектурными опытами. Spin пула настраивать после устранения лишнего движения весов.

Этапы 1–2 реализованы как экспериментальные механизмы и измерены; критерий полной serial/batch эквивалентности и общий прирост производительности пока не выполнены. Рабочий профиль не изменён.

## Продолжение: прямой H2D и удаление дубликатов

Первый пункт следующей серии реализован и измерен в [отдельном отчёте](DEEPSEEK4_RAM_DIRECT_H2D.md). Он добавляет опциональные STRATA_DS4_RAM_DIRECT_H2D и STRATA_DS4_RAM_DROP_GPU. Прямой путь исключает копию готовой pinned-матрицы в staging; drop сохраняет занятые блоки в бюджете до завершения читателей. Удаление дубликатов усилило повторное заполнение RAM и замедлило фиксированную нагрузку. Рабочий GPU-only профиль сохраняется.


## Продолжение: RAM admission после GPU placement

[Отдельная серия](DEEPSEEK4_RAM_ADMISSION.md) исключает создание RAM-копии при немедленном GPU admission. Проверены GPU-only, direct, drop, новый bypass и CPU force 12 на одной фиксированной истории. CPU выполнил 803 expert/token rows без упаковки, но ускорения относительно GPU-only нет. Проблема динамической воспроизводимости CPU lane этим опытом не решена.
