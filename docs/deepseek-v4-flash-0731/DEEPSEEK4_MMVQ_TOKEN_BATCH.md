# MMVQ: короткий пакет с арифметикой одного токена

10 октября 2026 года. Продолжение пункта 4
[плана переноса GLM/Step](DEEPSEEK4_OPTIMIZATION_TRANSFER_REVIEW.md).
Windows, Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32607 МиБ, драйвер 581.80,
CUDA 13.0. Перед серией свободно 105,86 ГиБ RAM, GPU занят на 1453 МиБ.
DeepSeek V4 Flash 0731 UD-Q3_K_XL на H: Samsung 990 Pro и DSpark Q8_0.

## Что перенесено

В GLM этот механизм заменял несколько отдельных запусков matvec одним запуском.
У DeepSeek штатный MMVQ уже имеет многотокенное MoE-ядро, поэтому здесь
сравниваются две геометрии CUDA-вычисления. Веса, квантование файла, роутер,
конвейер передачи и политика GPU-кэша не меняются.

Новый путь квантует входы пакета вместе и запускает одно ядро, в котором
токены становятся независимыми samples в третьем измерении grid. Для каждой
строки сохраняются число warps, vec_dot и порядок редукции одиночного токена.
Routed ID выбирается по token/route, вход допускает broadcast или отдельную
активацию каждого выбранного эксперта.

Опция движка и `tools/setup_deepseek4.py`:

```text
--mmvq-token-batch 0   # штатный путь, default
--mmvq-token-batch 1   # только routed матрицы
--mmvq-token-batch 2   # routed и dense матрицы
```

Путь ограничен NVIDIA, форматами IQ3_XXS/MXFP4/Q8_0, 2–4 токенами,
числом выходных строк, кратным 32, и одной исходной sample-осью.
Для dense дополнительно требуется одна channel-ось. Fused gate/bias/scale,
неподдержанные кванты/формы и другие размеры batch используют штатный путь.
Сам dispatch GGML не переопределяется: если он выбирает MMQ/cuBLAS, эта
опция его не принуждает к MMVQ. Небезопасные padding views сохраняют прежний
fallback. Опция выбирается при старте процесса; изменение её внутренней
environment-переменной в живом движке с захваченными CUDA graphs не поддержано.

Патч применяется только к копии CUDA-исходника сборки DeepSeek. SHA-256
`mmvq.cu` проверяется перед заменой:
`d4c70f68ab79d463fd6fd52cac66a62e915858397ba4b2b7f658a7fbf13121f3`.
Он совпал с исходником, для которого написан патч GLM. Сам `third_party`
не редактировался. Исходники:
[CMake-патч](../../backends/deepseek4/ShortBatchPatches.cmake),
[условия и запуск](../../backends/deepseek4/mmvq_token_batch.inc),
[матрицы](../../backends/deepseek4/test_mmvq_batch.cpp).

## Матричная проверка

GPU fixture использует реальные размеры routed матриц 4096×2048 и 2048×4096,
а также малые 512×64 и 512×65; восемь разных экспертов, шесть выбранных.
Проверены dense, routed broadcast и routed per-expert, разные IDs для токенов,
обычные и увеличенные strides входов/IDs, batch 1/2/3/4/5/8. Q6_K служит
контролем неподдержанного формата. Синтетические веса заранее квантованы;
в измерении операции веса и активации уже находятся на GPU.

Прошли **560 сценариев**. Из них 162 действительно используют новый путь:
все 162 побитово совпали с независимыми одиночными токенами. Штатный batch
побитово совпал с одиночными токенами в 86 из этих 162 случаев; максимальное
абсолютное различие остальных — 1,1921×10⁻⁷ на этих синтетических входах.
Остальные сценарии проверяют точное сохранение штатного результата.
Это проверка одной операции, не доказательство идентичности всей модели.

Первый тест с искусственной формой 512×65 обнаружил нестабильный результат
штатного **одиночного routed** small-K пути, включая режим с выключенным
патчем. Такой запуск нельзя использовать как эталон. Новый путь ограничен
строками, кратными 32; на нечётной форме проверяется штатный многотокенный
fallback, без сравнения с недостоверным одиночным эталоном. Все routed
матрицы используемых GGUF имеют 2048 или 4096 выходных строк. Исправление
общего upstream small-K для произвольных нечётных форм в этот патч не входит.

CUDA graphs в fixture отключены. В каждом временном сравнении четыре
чередования control/candidate, восемь warmup и 50 операций на серию.
Время — CPU wall с GPU-синхронизацией, микросекунды на операцию, медиана.
Для трёх токенов:

| Формат, K×M | Вход | Штатный batch, мкс | Новый, мкс |
|---|---|---:|---:|
| IQ3_XXS 4096×2048 | Routed broadcast, gate/up | 59,04 | 61,35 |
| MXFP4 4096×2048 | Routed broadcast, DSpark gate/up | 59,28 | 60,43 |
| MXFP4 2048×4096 | Routed per-expert, down | 56,65 | 68,24 |
| Q8_0 4096×2048 | Dense | 30,94 | 35,36 |
| Q8_0 2048×4096 | Dense | 30,07 | 47,26 |

Новый вариант здесь медленнее уже пакетного ядра DeepSeek. Ускорение из
GLM относительно нескольких одиночных запусков на этот исходный режим
не переносится. Полные результаты:
`bench/results/ds4-mmvq-20261010-matrices.json`. Неудачная первая проверка
сохранена в `ds4-mmvq-20261010-matrices-first.json`.

## Проверка модели

Сборка SHA-256
`a886a57d916a50b0133879591a01d3b0680d8e2dcfb05049b6f0239624a7f3e8`.
15 CTest и 25 Python-тестов прошли. Реальные сравнения выполнены на
фиксированной арене 15360/1024 МиБ, context 8192, batch 4096, threads 1,
DSpark2, shared scratch, stage 16, pipeline/auto, frequency 122880/32768,
match-size и prefill hits. Slabs не активируются без динамической политики.
Файловый кэш ОС не очищается; физическое чтение H: записывается отдельно.

Для исследования полной модели добавлена отдельная диагностика
`STRATA_SPEC_CHECK_SERIAL=1`: первые три verification-пакета каждого запроса
сравниваются с одиночным исполнением тех же входных токенов из одного снимка
target. Сравниваются все словарные logits каждого ряда, максимум/RMS и argmax.
После проверки повторно восстанавливается исходный снимок и исходный пакет;
диагностика требует разницу replay не выше 1e-5. Флаг не включается при
измерении скорости. `STRATA_DS4_MMVQ_TRACE=1` подтверждает фактический выбор
нового пути по типу, размеру и batch; это тоже отдельный диагностический запуск.

### Скорость

Четыре отдельных запуска в порядке control → routed → routed+dense → control.
В каждом prefill 256 токенов, затем текстовый запрос A и запрос с кодом B,
по 128 выходных токенов. «Повтор A» — медиана трёх повторов из RAM-сессии;
«A/B» — 512 токенов / суммарное время decode в B2/A2/B3/A3.
CPU-секунды включают всю обработку этих четырёх запросов, а не только decode.

| Режим | Повтор A, ток/с | A/B, ток/с | CPU-с на A/B | Медиана VRAM на A/B, МиБ |
|---|---:|---:|---:|---:|
| Штатный, контроль до | 21,02 | 14,79 | 46,83 | 29599 |
| Новый, routed | 17,36 | 13,55 | 51,75 | 29637 |
| Новый, routed+dense | 17,07 | 13,38 | 51,33 | 29597 |
| Штатный, контроль после | 21,46 | 15,43 | 45,47 | 29596 |

В этих прогретых повторах A и фазах A/B физические чтения H: равны нулю.
Холодные начальные запросы читали SSD и в таблицу не включены.
Средняя загрузка всего CPU в A/B — 8,87–9,19%; во всех 6384 аудитах графов
четырёх запусков `cpu_compute_nodes=0`. Полезный кэш остаётся 16 ГиБ,
ошибок allocations и pipeline fallbacks нет.

**Новый путь замедлил проверенную генерацию.** Это сравнение полного процесса,
а не чистого времени одинакового вычисления: смена арифметики изменила выходы
и принятие DSpark. На A принято 78 из 98 предложенных токенов в штатном режиме
и 72 из 112 в новом. Token IDs контролей полностью совпадают; оба новых режима
также совпадают друг с другом, но расходятся с контролем с первого выходного
токена A и с 46-го токена B. Внутри каждого режима восстановление и повтор
сохраняют результат.

Суммарный H2D target за весь запуск, включая начальные запросы и prefill,
увеличился с 1186,29 до 1361,94 ГиБ; DSpark — с 64,06 до 74,99 ГиБ.
Это итог разных траекторий генерации, не ухудшение пропускной способности
копирования. Изолированный матричный замер выше отдельно показывает,
что нового выигрыша ядра на фиксированных входах тоже нет.

Исходные данные: `bench/results/ds4-mmvq-20261010-{control-a,routed,all,control-b}.json`
и соответствующие `.log`. Условия и все аргументы движка записаны в JSON.
Команда каждой серии с нужным профилем:

```powershell
.venv/Scripts/python.exe tools/benchmark_deepseek4.py `
  --config build-local/deepseek4/mmvq-20261010/mode-0.json `
  --prompt-tokens 256 --tokens 128 --repeats 3 `
  --alternate-generation-prompt build-local/deepseek4/tuning-20261010/code.txt `
  --switch-rounds 3 --physical-disk PhysicalDrive6 `
  --output bench/results/ds4-mmvq-20261010-control-a.json
```

### Численная эквивалентность всей модели

В отдельных диагностических запусках режимов 0 и 2 проверено по девять
verification-пакетов: по три при prefill-запросе, коротком запросе A и его
восстановлении. В каждом пакете три строки по 129280 logits. Трасса режима 2
подтвердила новые dense Q8_0 и routed MXFP4 при двух токенах, а также
Q8_0/IQ3_XXS/MXFP4 при трёх.

| Режим | Наибольшая абсолютная разница batch/serial | RMS по пакетам | Строк с другим argmax | Replay |
|---|---:|---:|---:|---:|
| Штатный | 3,09851 | 0,150491–0,477973 | 2 из 27 | 0 |
| Новый routed+dense | 4,00504 | 0,086074–0,549359 | 0 из 27 | 0 |

Две строки штатного режима — один случай и его повтор из RAM-сессии.
Внутри каждой проверки используются одинаковые входные токены и начальное
состояние; между режимами траектория и draft могут различаться, поэтому
строки таблицы не являются попарным измерением улучшения на одних входах.
Все сравниваемые logits batch/serial конечны. Replay исходного пакета дал
нулевую максимальную абсолютную разницу с сохранёнными logits во всех
18 проверках.

**Одного изменения MMVQ недостаточно для эквивалентности всей модели.**
Новый путь дал точный одиночный результат проверенных матричных операций,
но заметное расхождение полных logits сохранилось. Отсутствие смены argmax
на 27 строках нового режима не доказывает эквивалентность на других токенах.
Для локализации причины следующий отдельный шаг — сравнение промежуточных
активаций batch/serial и поиск первого расходящегося узла; источник в
attention, compressor, BF16/F32-операциях или иных ветках пока не установлен.

Продолжение этого исследования: [первое расхождение локализовано в Flash
Attention слоя 0](DEEPSEEK4_ATTENTION_PROBE.md). Полная эквивалентность
модели всё ещё не достигнута.

Данные: `bench/results/ds4-mmvq-20261010-probe-{0,2}.{json,log}`.
Диагностические флаги в рабочем профиле отсутствуют.

### Проверки состояния

Реальные тесты режима 2 с DSpark2 и без draft прошли: A/B/A с восстановлением
RAM-сессии, продолжение и его восстановление, повторный полный prefill,
один выходной токен, отмена prefill/decode, запрос после отмены и повтор
с фиксированным seed 123. Во всех аудитах графов этих запусков CPU-узлов нет.

Дополнительный контроль режима 0 на той же сборке также прошёл обязательные
проверки сессий и отмены. Отдельно регистрируемое сравнение продолжения после
накопленного decode и после полного prefill дало:

| Режим | `passed` | `full_prefill_identical` |
|---|---|---|
| Штатный + DSpark2 | true | false |
| Новый routed+dense + DSpark2 | true | true |
| Новый routed+dense, без DSpark | true | true |

Таким образом, в этом сценарии новый путь получил совпадающее продолжение.
Но continuation содержит ранее сгенерированный ответ A, который различается
между режимами. Это не доказательство исправления одной ошибки на общем
фиксированном входе. `passed` относится к обязательным проверкам состояния;
`full_prefill_identical` учитывается отдельно и не превращается в общий допуск
численной эквивалентности DSpark.

Token IDs DSpark и обычного decode при этом **не идентичны**: в проверенном
32-токенном ответе A первое различие на 16-м токене, в 16-токенном B — на 6-м.
Успешное восстановление сессии не доказывает равенство этих двух способов
генерации. Проверка без DSpark не измеряет ускорение MMVQ decode одного токена:
при одном токене новый путь не активируется.

Данные: `bench/results/ds4-mmvq-20261010-validate-{control,dspark,plain}.{json,log}`.

## Выбранный режим

Рабочий профиль не изменён: `--mmvq-token-batch` отсутствует, default 0.
Новый путь и численная диагностика доступны только для дальнейших экспериментов.
Список успешных оптимизаций этим кандидатом не пополнен. Поддержка Qwen и
исходники других backend не изменялись в этом этапе.
