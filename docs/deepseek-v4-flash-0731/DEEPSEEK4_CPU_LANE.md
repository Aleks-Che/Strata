# Первый матричный CPU lane: реализация и результаты

Этот отчёт описывает исходный прототип. Текущая опциональная реализация
описана в [CPU lane v2](DEEPSEEK4_CPU_LANE_V2.md); смысл лимита
экспертов изменён с матриц на целые эксперты.

12 октября 2026. Первый вариант переноса идеи CPU lane из
[project-maya](DEEPSEEK4_MAYA_TRANSFER_REVIEW.md) в отдельный DeepSeek backend.
По умолчанию выключен. Обычный профиль остаётся GPU-only.

Первый опыт на RTX 5090 не дал ускорения. На 4/8/12/16 потоках
обнаружены различия greedy-ответов между повторами из RAM-сессии.
Опция сохранена для экспериментов; рабочий профиль на неё не переключён.

Подробное [сравнение реализации с Maya](DEEPSEEK4_CPU_LANE_MAYA_AUDIT.md)
разбирает границу CPU/GPU, CUDA Graphs, выбор экспертов, пул потоков
и недостающие проверки численной точности.

## Включение

Добавить в `args` копии профиля и перезапустить движок:

```text
--expert-cpu-threads 4 --expert-cpu-max-experts 1
```

`--expert-cpu-threads` принимает 0–16, ноль отключает режим.
`--expert-cpu-max-experts` принимает 1–6 и ограничивает число уникальных
экспертов **на одну матричную операцию**, а не на весь MoE-блок.
Эти опции также принимает `tools/setup_deepseek4.py`.
Они не меняют значение обычного `--threads`, отвечающего за host-часть llama.

Нужны CUDA-сборка с `STRATA_DEEPSEEK_DIRECT_CACHE_EXPERIMENT=ON`,
`--expert-pipeline 1` и ненулевой `--expert-stage-mib`.
CLI сам включает прямой GPU-кэш и порядок экспертных передач.
Исследовательские early hits, routed MMQ и hash prefetch одновременно
с этим прототипом не поддержаны: CLI отказывает до загрузки весов.

Режим применим к IQ3_XXS, MXFP4 и Q8_0, то есть типам наших
target UD-Q3_K_XL и DSpark Q8_0. Фиксированный лимит потоков и экспертов
не является автоматической калибровкой Maya.

## Как работает

1. После настоящего router выбираются только промахи GPU-кэша. На Windows
   `QueryWorkingSetEx` проверяет резидентность всех страниц матрицы.
   Это проверка в момент планирования, не закрепление: ОС может вытеснить
   страницу позже. На других ОС проверка существующего reader не даёт
   такого фильтра; локально проверен Windows.
2. Выбранные CPU-матрицы исключаются из плана H2D. GPU продолжает получать
   остальные матрицы обычным конвейером.
3. Небольшой вход операции копируется в pinned RAM. Постоянные CPU-workers
   считают строки через `ggml-cpu` vector-dot kernels; между заданиями
   потоки спят. Работа CPU может перекрываться с передачей остальных весов
   и GPU-вычислениями. Отдельной инструментальной оценки перекрытия пока нет.
4. GPU MMVQ пропускает строки CPU-экспертов. Их готовые выходы копируются
   на исходные места в тензоре до запуска следующей операции. Порядок
   последующего взвешенного суммирования экспертов не меняется.

CPU lane ограничен короткими поддерживаемыми MMVQ-операциями до восьми
токенов; большой prefill и неподдерживаемые формы идут на GPU.
Слияние операций, несколько scheduler copies, eval callback и повторное
использование одной рабочей матрицы несколькими потребителями исключают
операцию из lane. Target и DSpark используют отдельные пулы, но вычисляются
последовательно; неактивный пул спит.

Участок графа с ожидаемым CPU-результатом исполняется напрямую, чтобы
host join происходил при каждом вызове. Полностью GPU-участки сохраняют
CUDA Graphs. Прямое выполнение не обновляет сохранённые свойства и warmup
CUDA Graph: иначе после перестроения графа можно повторно запустить старые
адреса буферов. Событие после загрузки результата защищает повторное
использование pinned-буфера. При отмене/закрытии текущая CPU-операция
завершается перед освобождением весов и scratch.

Это отличается от Maya: там CPU считает выбранного эксперта целиком
вместе со SwiGLU. Здесь граница — отдельная gate/up/down матрица. Такой
вариант проще встроить в существующий граф, но промежуточных обменов больше.
Файлы: `cpu_lane.cpp`, `cpu_lane.cuh`, `cpu_lane_hooks.inc`,
`cpu_lane_sched.inc` и `CpuLanePatches.cmake` в `backends/deepseek4`.
Закреплённые исходники llama.cpp и Qwen backend не редактируются.

## Численные различия и диагностика

Квантизация активаций и редукция CPU отличаются от GPU, особенно
IQ3_XXS: CPU использует Q8_K-активации, CUDA MMVQ — Q8_1.
Это полноценное вычисление выбранных весов, но не побитовое совпадение
двух устройств. Ответ может измениться; распределение работы зависит
от попаданий в кэш и резидентности RAM. Проверка GPU-only по битам
не заменяет отдельную оценку качества гибридного режима.

INFO сообщает `expert_compute=hybrid`, `gpu_only=0`, число потоков и лимит.
`STRATA_CPU_LANE` при закрытии показывает число матричных операций,
CPU-экспертов, пропущенные байты передачи весов, host wait и получение входов.
`skipped_weight_bytes` — логические байты исключённых весов, **не измерение
экономии SSD или суммарного PCIe-трафика**: результаты и входы передаются отдельно.
`wait_us` — хвост CPU-работы, видимый в join, не всё время CPU.

Scheduler по-прежнему отвергает обычные CPU-узлы. Его
`cpu_compute_nodes=0` означает отсутствие таких узлов, а не отсутствие
работы CPU lane. Добавлены `cpu_lane_enabled` и отдельная строка CPU audit.
Benchmark/validator требуют явного `--allow-cpu-lane` для гибридного режима.

## Проверки и измерения

Нативный fixture с четырьмя workers: **768 сценариев**, IQ3_XXS/MXFP4/Q8_0,
batch 1/3/8/9, вход с одной или шестью полосами, лимиты 1/6 экспертов,
последовательные и параллельные scheduler copies, восемь смен входов.
CPU-строки побитово совпали с отдельным CPU vector-dot reference;
остальные строки — с обычным GPU-исполнением. Проверены strided routing IDs,
следующая операция SiLU, GPU fallback для batch 9 и parallel copies,
смена адресов при перестроении графа и возврат от CPU lane к CUDA Graphs.
Счётчики: 144 CPU-операции, 22 010 880 байт исключённых весов;
максимальная разница CPU/GPU на этих синтетических данных — 0,000864312053.
Это не оценка качества полной модели.

Итоговый набор **24/24 CTest прошёл** за 53,31 с: CPU lane, GPU-only,
speculative contract, compact, ordered, direct cache, hash prefetch,
передачи и pipeline. Это не отменяет описанный ниже отказ строгой
проверки восстановленного ответа полной модели с CPU lane.

Python: 19 тестов DeepSeek/template/routes прошли; проверены синтаксис
setup/benchmark/validator и отказ setup при включении CPU lane без pipeline.

Полная модель, отдельная проверка состояния:

- CPU lane выключен: restore, продолжение, отмена prefill/decode, следующий
  запрос после отмены и повтор seeded sampling прошли. Все **8/8**
  greedy-сценариев совпали с прежним эталоном
  `ds4-remaining-20261012-validation.json` при том же лимите 16 токенов.
- CPU lane 16 потоков: строгая проверка остановилась на первом restore
  с `Target/draft session restore changed greedy output`. Поэтому весь
  state-validator для гибридного режима **не пройден**; последующие
  его проверки продолжения и seeded sampling не исполнялись.
- Отдельный диагностический запуск CPU16 подтвердил завершение отмены
  prefill без выданных токенов, отмену decode и последующую свежую генерацию
  16 токенов без падения. Он проверяет жизненный цикл запросов, но не
  заменяет точную проверку восстановленного ответа.

## Полная модель: 4, 8, 12 и 16 потоков

Windows, Ryzen 9 9950X (16 ядер / 32 логических CPU), 128 ГиБ RAM,
RTX 5090 32 ГиБ, Samsung 990 PRO на H:. CPU vector-dot kernels собраны
с `/arch:AVX512`. Target — `UD-Q3_K_XL`, DSpark — `Q8_0`, draft max 2.
Кэши target/draft 15360/1024 МиБ, pipeline 1, stage/slabs 16 МиБ,
два reader, read-mode auto; на CPU отдаётся максимум один уникальный
эксперт каждой подходящей матричной операции. Остальные настройки —
из рабочего `strata-deepseek4-ud-q3-k-xl-dspark.json`.

Шесть отдельных процессов: GPU, CPU4, CPU8, CPU12, CPU16, GPU.
В каждом prefill 4096 токенов, генерация 64 токенов, три повтора
этого запроса из RAM-сессии и ещё один полный prefill без KV reuse.
Для генерации используется отдельный prompt длиной 36 токенов.
Файловый кэш ОС не очищался. Это первичный сравнительный опыт,
а не повторённая A/B/B/A-серия для каждого числа потоков.

| CPU workers | Повтор 1, ток/с | Повтор 2, ток/с | Повтор 3, ток/с | CPU процесса в повторе 3 |
|---|---:|---:|---:|---:|
| 0, первый контроль | 14,596 | 16,161 | 16,613 | 3,50% |
| 4 | 5,505 | 10,465 | 11,958 | 4,82% |
| 8 | 5,318 | 10,509 | 12,223 | 5,10% |
| 12 | 4,787 | 8,840 | 10,109 | 5,10% |
| 16 | 5,256 | 10,006 | 9,524 | 5,17% |
| 0, последний контроль | 14,324 | 16,040 | 16,466 | 3,48% |

CPU% вычислен из CPU seconds процесса и полного времени запроса,
нормирован на все 32 логических CPU. Он не показывает краткие пики
отдельных workers. В третьих повторах всех перечисленных режимов
физических чтений H: не было. Первые два CPU-повтора ещё читали SSD:
примерно 2,6–2,9 ГБ и 0,38–0,42 ГБ соответственно. Поэтому медиану
всех трёх нельзя выдавать за установившуюся скорость без диска.

Третий ответ совпал между CPU4/8/12/16, но отличался от GPU-контроля.
У всех CPU-вариантов также различались ответы между исходной генерацией
и её повторами; benchmark сохранил результаты, затем завершился ошибкой
`Greedy cached repeat differs from original output`. Проверка не ослаблена.
Это измерение воспроизводимости, не оценка качества на наборе задач:
например, в видимом тексте «или очень близко» сменилось на «или
в непосредственной». DSpark acceptance также менялся: 37/51 или 38/51
в CPU-повторах против постоянных 38/51 у GPU.

По этим данным 12 и 16 потоков не помогают. Даже лучший из проверенных
CPU-вариантов уступает GPU. Небольшие различия между 4 и 8 потоками
не являются доказанным преимуществом восьми workers.

Во всех четырёх CPU-запусках суммарно target + draft выполнили
13 769 CPU-матричных операций; счётчик исключённых весов —
50 863 485 952 байта. Видимый хвост ожидания CPU уменьшился с 0,650 с
на четырёх потоках до 0,300 с на шестнадцати за весь процесс.
Однако скорость генерации при этом снизилась. Уменьшение одного хвоста
не означает ускорения всего пути: остаются получение входов, возврат
результатов и исполнение соответствующих участков без CUDA Graphs.
Без отдельного профилирования нельзя приписать всю разницу одному из них.

Полный повторный prefill занял 14,07–14,44 с в CPU-конфигурациях
и 14,74–14,83 с у GPU. При этом H: прочитан на 38,72–39,24 ГБ против
42,66–43,49 ГБ. Это разные условия I/O; ускорение большого GPU-prefill
CPU lane этим опытом не доказано.
