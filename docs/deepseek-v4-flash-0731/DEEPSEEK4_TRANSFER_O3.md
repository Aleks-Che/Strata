# О3: кандидаты на замещение GPU-кэша

14 октября 2026. Продолжение [плана оптимизации подкачки](DEEPSEEK4_TRANSFER_OPTIMIZATION_PLAN.md)
после [mmap reader](DEEPSEEK4_TRANSFER_O2_READER.md).

Более поздний опыт этого дня: [выбор по фактическим промахам](DEEPSEEK4_TRANSFER_O3_DEMAND.md)
дал ещё −8,04% H2D и +4,76% decode при включении только для DSpark. Ниже сохранены
исходные замеры tail limit; их результаты не заменены новой серией.

В одной A/B/B/A подтверждён небольшой локальный выигрыш экспериментальной
очереди: **10,351 → 10,670 ток/с (+3,08%)**, полное время −2,47%,
H2D −8,24%. Рабочий GPU-only всё ещё быстрее; О3 не закрыт.

## Изменения

Два независимых экспериментальных переключателя, оба по умолчанию выключены:

- `STRATA_DS4_GPU_FETCH_CURRENT_VICTIMS=1` разрешает предлагать для замещения
  матрицы текущего слоя. GPU сначала собирает полный маршрут, включая последние
  позиции пакета, CPU-only и смешанные CPU/GPU назначения. Выбранного эксперта
  нельзя вытеснить. Чужие контексты, deferred readers и direct leases сохраняют
  защиту. Выбранные записи, временно извлечённые из таблицы кэша, остаются во
  владении loan до завершения ветки; обновление LRU находит и такие записи.
- `STRATA_DS4_GPU_FETCH_TAIL_LIMIT=1` оставляет не больше одного кандидата без
  padding на каждую матрицу. Такой размер нужен только последнему эксперту.
  Остальные предложения могут использовать слоты с padding. Демоция, запись
  DMA, поколение публикации и момент возврата loan сохраняют прежний порядок.

`STRATA_DS4_GPU_FETCH_CACHE_SLOTS=8` — существующая настройка размера окна
предложений. Её сравнивали отдельно от исправлений правил. Число GPU-матриц,
бюджет VRAM и размер staging при этом не увеличиваются.

Основные файлы: [gpu_fetch_cache.inc](../../backends/deepseek4/gpu_fetch_cache.inc),
[gpu_fetch_queue.cuh](../../backends/deepseek4/gpu_fetch_queue.cuh),
[gpu_fetch_lane.cuh](../../backends/deepseek4/gpu_fetch_lane.cuh).
В снимки фаз добавлены `current_offered`, `current_admitted`, `current_protected`,
`tail_offered`, `tail_skipped`. Файлы очереди и выбора кандидатов включены в build ID
профиля стоимости, чтобы смена транспорта не принимала старую калибровку.

## Условия

Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows, CUDA 13, наблюдаемый PCIe
Gen3 x16. Target — DeepSeek-V4-Flash-0731 UD-Q3_K_XL, DSpark — Q8_0.
Контекст 8192; GPU-кэши target/draft — 15360/1024 МиБ; RAM-кэш — 2048 МиБ.
Reader `mapped`, staging 4 МиБ, DMA depth 8, четыре сегмента, раннее чтение.
`KEEP_RAM=0`, `RAM_DEMOTE=0`, context overlap выключен, draft-max 2.

В процессе четыре fresh-запроса по 15 входных и 32 выходных токена: два прогрева
и два измерения. CPU-профиль пересоздан для каждой сборки, 12 потоков, бюджет
0,01 мкс. Во всех скоростных прогонах проверяется фактический ноль CPU jobs/rows.
H2D, wall и CPU-seconds ниже относятся к сумме двух поздних запросов; decode —
выходные токены, делённые на суммарное decode-время.

Кэш ОС не очищался. Первые прогревы читали модель с H:; поздние измерения имели
нулевое физическое чтение H:. На других дисках была фоновая активность. Эти
результаты не описывают холодный SSD или дефицит RAM.

## Пробы замещения внутри слоя

Первая сборка и артефакты: `build-local/deepseek4/transfer-o3-current-20261014/`.
SHA256 EXE: `b428a0d2aa88a7f5b01d75c52534c6cb3c8d7fe8242154a90ca250061a26eede`.

Decode: 13,724 → 14,231 ток/с; полное время: 7,532 → 7,469 с. Это одна пара,
по которой нельзя утверждать устойчивое ускорение полного запроса.

## Кандидаты без padding

Вторая сборка: `build-local/deepseek4/transfer-o3-tail-20261014/`.
SHA256 EXE: `9819235823fb69b43668fbfd0cf177ad9da1ab23641e14e5b430a315ea5c03a0`.

Диагностика прежнего режима показала: в двух поздних decode DSpark **816 из
1224** предложений относились к слоту без padding. Две трети ограниченного
окна не могли принять обычного эксперта. После ограничения количество таких
предложений при четырёх слотах стало 306; H2D DSpark снизился с 9,306 до
7,857 ГиБ. Одновременно остаётся низкое число admissions: в этой паре 0 → 3.
Ограничение размеров устраняет только одну причину плохого обновления кэша.

## Повтор A/B/B/A

Контроль 4 слота → tail limit 8 → tail limit 8 → контроль 4.
Во всех четырёх процессах текущий слой исключён из кандидатов.

| Режим | Decode двух процессов, ток/с | Среднее, ток/с | Полное время, с | CPU-seconds |
|---|---|---:|---:|---:|
| Контроль | 10,366 / 10,335 | 10,351 | 8,852 | 20,383 |
| Tail limit, 8 слотов | 10,619 / 10,720 | 10,670 | 8,633 | 19,297 |

Среднее по двум процессам, в каждом — два поздних запроса. Decode **+3,08%**,
полное время **−2,47%**, CPU-seconds **−5,33%**. Это проверка сочетания двух
настроек; весь выигрыш нельзя приписывать одному tail limit. Четыре слота с
ограничением и восемь без него измерены только в пилотах выше.

| Поздний decode H2D | Контроль, ГиБ | Кандидат, ГиБ | Изменение |

Байтовые объёмы воспроизводятся в обоих процессах каждого режима. Все выходные

## Корректность и ограничения

Финальная сборка прошла 16 CTest с tail limit и ещё 8 запусков тестов с обоими
флагами. Проверялись mapped-копирование и owner DMA, CUDA Graph on/off, arena
и managed-кэш, демоция, восстановление unused loans, пересечение контекстов,
дубликаты, отмена и повторное использование очереди. Отдельный тест защищает
эксперта, впервые встречающегося в конце пакета; проверяет и padding выбранных
матриц, и фактическую запись в невыбранного кандидата. Сценарий только с текущим
слоем проверяет 54 точных GPU-повтора в трёх квантованиях, включая последний ID.

Начальные проверки первой сборки потребовали исправить сам fixture: старый
сценарий не вытеснял текущий слой, а GPU-reference в новом сценарии прогревал
RAM кандидата и непреднамеренно включал CPU. Источники эталона разделены;
проверяется ноль CPU jobs. Начальные журналы сохранены рядом с прошедшими.

Фиксированная история, tail limit + 8 слотов, текущий слой выключен:
**6 префиксов и 86 шагов**, хеш полного вектора logits и argmax совпали с
GPU-контролем. Проверены decode batch 1 и 3 в двух повторах. Реально выполнены
2459 CPU jobs / 3337 rows; CPU rows в prefill = 0. Для этой проверки включены
RAM-демоция, KEEP_RAM и context overlap; бюджет 0,01 мкс из скоростной серии
не используется.

Lifecycle с обоими флагами и 8 слотами: A→B→A, продолжение, полный prefill,
restore, отмена prefill/decode, seeded repeat; **8/8** greedy-сравнений совпали
с сохранённым совместимым GPU-контролем. Выполнены 678 CPU jobs / 1292 rows;
автоматическое пересоздание профиля прошло поколения 0 → 1 → 2.
Это проверка кандидата относительно соответствующего GPU-режима. Известная
отдельная задача lossless batch/serial DSpark ею не закрывается.

Артефакты второй сборки содержат `summary.json`, `abba-summary.json`,
`validation-summary.json`, конфигурации, новые CPU-профили, EXE, исходники,
журналы и SHA256-манифест. Профиль стоимости имеет build ID
`5520a581abc12acee85e483b9abe9154f9747770e2f72f77c9de7834a70f61c0`.

Рабочий профиль не переключён. Для продолжения локального эксперимента
используется `tail8-config.json`; обе новые опции в исходниках остаются
выключенными по умолчанию. Сравнение 4096/8152 токенов, Linux и генерация Qwen
в этой серии не повторялись. Новые изменения ограничены backend DeepSeek.

О3 остаётся открытым: требуется уменьшить оставшийся H2D относительно L0,
выбирать полезные предложения по реальным промахам и отдельно закончить
RAM-защиту по фактическому CPU-назначению. Не следует компенсировать эту
разницу числом CPU-потоков или объявлять всю экспериментальную очередь быстрее
рабочего GPU-only. Критерий О2 для 90% DMA через staging также остаётся открытым.
