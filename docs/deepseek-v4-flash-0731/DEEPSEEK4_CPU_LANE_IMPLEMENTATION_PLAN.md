вычислением остальных экспертов на GPU. Выигрыш должен подтверждаться временем
полного запроса относительно рабочего GPU-only профиля, а не только уменьшением
H2D-трафика или временем отдельного CPU-ядра.

## Как внедрять: общая архитектура, проверяемые этапы

Сначала проектируем целиком путь «готовые RAM-матрицы → GPU-выбор → очередь →
постоянный CPU-пул → объединение результатов». Затем реализуем его небольшими
этапами с проверкой корректности после каждого. Итоговую скорость этой связки
оцениваем после сборки всех необходимых частей.

Не требуем ускорения полного запроса от каждого промежуточного шага. Общий RAM-пул
или таблица резидентности могут быть необходимой основой следующего шага, не давая
самостоятельного выигрыша. Промежуточные затраты всё равно измеряем и сохраняем.
После сборки связки отключаем отдельные части и выясняем их вклад.

Независимые изменения — многотокенные SIMD-ядра, калибровка, политика ожидания
workers — сохраняем переключаемыми и проверяем отдельно. Тонкую настройку числа
потоков выполняем после изменения пути запуска. Копировать весь GLM backend Maya
не требуется: сохраняем граф DeepSeek, матричный GPU-кэш и поддержку Qwen.

## Исходное состояние и доказательства

ПК: Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, SSD H: Samsung 990 PRO, Windows.
Основной объект: DeepSeek-V4-Flash-0731 UD-Q3_K_XL; интеграционные проверки — с
DSpark Q8_0. Рабочий профиль остаётся GPU-only, CPU lane и дополнительный RAM-кэш
выключены по умолчанию. CPU lane рассматривается для decode и короткой проверки
draft-токенов; длинный prefill сохраняется на GPU.

Уже реализованы целый CPU-эксперт gate/up → SwiGLU → down, постоянный пул,
SIMD через ggml-cpu, лимит по токенам, общий HostCache с тремя защищёнными
RAM-адресами и отсутствие повторного pack в shared-режиме. Есть эксперименты
с прямым H2D, удалением RAM-дубликатов после GPU admission, отложенным заполнением,
пулом pinned allocations и фоновым сохранением. Не нужно заново реализовывать эти
части по ранним аудитам, описывающим старый прототип.

Фиксированная история: target-only, 68 одинаковых входных IDs, префикс 36 и decode
32 токенов; среднее двух последних из четырёх проходов:

| Режим | Decode по 1 токену, мс | Decode по 3 токена, мс |
|---|---:|---:|
| GPU-only, до | 1607,0 | 1073,4 |
| Общий RAM 2 ГиБ, CPU 0 | 1718,3 | 1230,3 |
| Общий RAM, CPU 12 потоков | 1768,8 | 1206,8 |
| GPU-only, после | 1615,4 | 1082,9 |

CPU уменьшил время chunk=3 примерно на 1,9% относительно одинакового RAM-кэша,
но обычный GPU-only быстрее. Независимых повторов серии для доверительных
интервалов нет; одинаковые входные IDs не гарантируют одинаковые внутренние
маршруты при различном округлении CPU/GPU.
[Методика и ограничения](DEEPSEEK4_CPU_LANE_EXPERIMENTS.md).

[Последние опыты с RAM-пулом и фоновой очередью](DEEPSEEK4_RAM_BACKGROUND.md)
проводились с CPU lane выключенным. Эта очередь заполняет RAM-кэш; она не является
GPU-очередью вычисления экспертов. В исходном shared CPU-режиме seeded repeat
после восстановления расходился. В этапе 2 явный seed выбирает GPU для всего
запроса; эквивалентность арифметики CPU/GPU этим не исправлена.
Maya на этом ПК с тем же workload не измерялась; её общий tokens/s
не является сравнением CPU lane on/off для нашего DeepSeek.

## Целевая архитектура

1. Общий реестр матриц описывает RAM/VRAM-резидентность, готовность и поколения
   адресов. Хранение gate/up/down остаётся раздельным. CPU-задание удерживает три
   адреса до завершения; незавершённые или вытесняемые матрицы не выбираются.
2. GPU-роутер использует согласованный снимок таблиц и готовый план стоимости,
   выбирает CPU-работу и публикует адреса и вход в ограниченную очередь. Основной
   host-поток не должен читать IDs и ждать GPU ради решения CPU/GPU этого пути.
3. Постоянный service thread принимает задания и запускает CPU-пул. GPU в это
   время передаёт и вычисляет остальные эксперты. CPU-ветка присоединяется в месте,
   где её down-результаты действительно нужны.
4. CPU считает несколько активаций одного эксперта с переиспользованием
   распакованных весов. Результаты возвращаются в исходные позиции top-k, чтобы
   сохранить порядок итогового суммирования.
5. Выбор допускает ноль CPU-экспертов. Он учитывает реально отменённые передачи,
   работу GPU и CPU, запуск, очередь и ожидание результата. Число потоков и
   размещение весов сами по себе не считаются доказательством ускорения.

только одно CPU-задание; счётчики заполнения нового GPU-ring появятся с этапом 2.
Существующие transfer/RAM-счётчики сохраняются в логе, SSD пока измерен за все
проходы процесса. Более длинные нагрузки и окончательная приёмка — этап 5.

## Этап 1. Общий путь хранения RAM/VRAM

- [x] Описать состояния записи: отсутствует, заполняется, готова, удерживается
  потребителем, переносится, вытесняется. Определить поколение адреса и порядок
  публикации GPU-таблицы. Таблица сама по себе не заменяет владение памятью.
- [x] Использовать имеющийся HostCache и pinned-пул как основу. CPU и H2D получают
  одни готовые матрицы; при RAM-hit нет дополнительной упаковки или копии для CPU.
- [x] Добавить общий учёт GPU-residency. Освобождать RAM-дубликат после завершения
  promotion и всех потребителей. Предусмотреть ограниченную демоцию GPU→RAM при
  вытеснении, с отдельным учётом её D2H-трафика; не демотировать всё безусловно.
- [x] Сохранять горячие RAM-матрицы при большом prefill. Проверять наличие всей
  тройки CPU-эксперта без возврата к отдельному private CPU cache.
- [x] Ограничить общий расход target/DSpark: активные блоки, свободный pinned-пул,
  временные копии и очередь. Учитывать файловый кэш ОС и запас свободной RAM.
  Большой pinned-пул не включать автоматически по принципу «занять всё свободное».
- [x] Сначала проверить малый бюджет, затем увеличивать только в пределах
  измеренного запаса памяти. Сравнивать CPU on/off при одинаковом RAM-бюджете
  и отдельно с рабочим GPU-only без дополнительного кэша.

Проверки: leases при promotion/eviction, одновременные target/DSpark, отмена,
ошибка чтения, незавершённое заполнение, смена поколения, ограничение бюджета.
Самостоятельный прирост tokens/s не является условием перехода к этапу 2.

Реализация этапа 1: поколения действуют внутри экземпляра HostCache; CUDA event
подтверждает готовность GPU-копии. Токен реестра не заменяет владение GPU allocation.
Протокол публикации будущей GPU-таблицы описан, сама таблица и её удерживаемые
снимки относятся к этапу 2. Pending демоций входит в бюджет HostCache; рабочие
буферы pipeline/CPU имеют отдельные фиксированные лимиты и учитываются проверкой
доступной системной памяти. Демоция выключена по умолчанию.

- [x] Окна 1–4, полное/частичное повторение и уникальные эксперты, 8/12/16 потоков:

  73,5/102/204 MiB. Для трёх повторений IQ3 общая распаковка дала 2,03–2,26×
  к одиночному SIMD, MXFP4 1,23–1,28×, Q8_0 1,16–1,28×.
- [x] Fast сохраняет побитный контракт reference: 150 матричных сравнений,
  24 смешанных экспертных случая на 1/8/12/16 потоках и 13 реальных строк.
  192 гибридных повтора с 144 CPU-заданиями; полные logits на 12/16 потоках
  совпали с GPU. Force и auto прошли строгие 8/8 greedy-сценариев DSpark
  при 538 и 468 вычисленных CPU-строках соответственно.

Этап 3 закрыт в этой области проверки. [Результаты и ограничения](DEEPSEEK4_CPU_MULTITOKEN.md)
разделяют ускорение CPU-эксперта и ещё не доказанное ускорение полного запроса.

Проверки: исходные CPU-ядра и точный эталон на сохранённых входах, затем полные
logits и маршруты модели. Отдельно проверить restore и DSpark; ускорение микроядра
не засчитывается как ускорение полного запроса.

## Этап 4. Калибровка, план стоимости и настройка пула

- [x] Калибровать после подготовки RAM на сменяющихся готовых экспертах, а не
  многократно на одном blob. Покрыть форматы, геометрию, число уникальных экспертов
  и число активаций каждого. Не делить фиксированную стоимость вызова на tokens.
  Область: IQ3/IQ3/MXFP4, MXFP4, проба Q8_0; 4096×2048, clamp 10,
  1–4 токена и до четырёх CPU-строк. Неизмеренные комбинации остаются на GPU.
- [x] Измерять полное CPU-вычисление и его фазы, pinned H2D, publication/input,
  join/output и scatter mapped-очереди. Считать max параллельных CPU/H2D плюс
  очередь. DRAM/распаковка и dot products пока измеряются совместно.
- [x] Добавить GPU-арифметику и измерение конкуренции за память/перекрытия веток.
  Профиль v2: 80 GPU-случаев на формат, CPU под pinned H2D, чередующаяся проба
  GPU/H2D. Формула GPU = передача + ядра − измеренное перекрытие; полное
  перекрытие автоматически не предполагается. На 8/12/16 потоках пройдены
  720 точных GPU-случаев, на полной модели — 8/8 greedy, 428 CPU-строк.
  Это калибровочная проба с независимым staging; зависимости конкретных весов
  и прерывистую нагрузку внутри полного MoE она целиком не воспроизводит.
- [x] Учесть уникальные отменяемые H2D-байты: повторное вхождение или матрица,
  нужная GPU для другого токена, не дают повторной экономии передачи.
- [x] Разрешить ноль CPU-экспертов, ограничить CPU-бюджет на токен и проверять
  прогноз по фактическим задержкам. Калибровку версионировать по сборке, формату,
  оборудованию, потокам и режиму ядер. Несовпадение профиля выключает новый auto.
- [x] При устойчивом расхождении пересчитывать CPU-профиль между запросами/сериями.
  `CPU_COST_AUTO=1`: два успешных запроса с достаточной выборкой, ограничение шага,
  публикация после завершения всех очередей. Отмена/ошибка/seeded не обучают профиль.
  GPU/H2D/queue-оценки сохраняются из offline-калибровки. Проверены реальные поколения
  0→1, 9 native-тестов и 8/8 строгих greedy-сценариев после обновления, restore/cancel/seed.
- [x] Проверять выбранные настройки чередующимися новыми запросами. Не подстраивать
  их по будущим токенам текущего speculative window и не менять посреди сравнения.
- [x] Сравнить 8/12/16 потоков, tokens/s, CPU-seconds, задержки и короткий простой.
  12 потоков — кандидат для дальнейших опытов; устойчивый выигрыш не подтверждён.
- [x] Проверить дробление заданий и spin/sleep. На 12 потоках измерены
  коэффициенты 1/2/4, ограниченное ожидание 0/50/200 мкс, паузы 0/20/80 мс.
  Полная модель: старый пул, spin=50 и parts=1; основания менять стандартные
  spin=0/parts=2 не получены. Корректность вариантов — на 1/8/12/16 потоках.
  NUMA/affinity не включались: отдельного подтверждённого выигрыша нет.
- [x] Проверить остаточную ошибку CPU-прогноза на совпадающих формах внутри
  модели. Паузы увеличивают главным образом prepare/gate-up, а не только
  задержку старта workers. Профиль v3 отдельно измеряет стоимость после 20 мс.
  На тех же 355/356 заданиях абсолютная ошибка `abs(факт/прогноз−1)` снижается
  с 30% до 9%; прогноз становится консервативным. Флаг `CPU_COST_BURST` пока
  опционален. Это измеренная оценка для прерывистого режима, не доказательство
  конкретной причины изменения частоты/кэшей и не динамическая адаптация пула.

Калибровка и принудительное назначение экспертов проверяются отдельно: улучшение
auto-плана не объясняет автоматически результаты force-режимов.

## Этап 5. Сравнение полного решения и условия принятия

Минимальные контрольные варианты:

| Вариант | Зачем нужен |
|---|---|
| Рабочий GPU-only без дополнительного RAM-кэша | Итоговая точка сравнения |
| Новый RAM/VRAM путь, CPU выключен | Цена нового хранения |
| То же хранение, старый host-запуск CPU | Вклад GPU-очереди |
| GPU-очередь, прежние CPU-ядра, фиксированный план | Проверка нового транспорта |
| GPU-очередь и многотокенные ядра, тот же план | Вклад арифметических ядер |
| Полная связка с новой калибровкой | Практический итог |

Не запускать декартово произведение всех настроек. Сначала ограниченные проверки
изменяемого компонента; длинные серии — на собранной связке и лучших вариантах.
На промежуточных этапах повторять расширенные проверки при изменении соответствующих
путей или обнаружении дефекта.

- [ ] Фиксированная история без DSpark: прежний короткий fixture и длинный контекст,
  decode по 1/3 токена, одинаковые лимиты памяти и состояние прогрева.
  Выполнены 68/4096/8152 IDs, совпали 12 prefix- и 172 decode-хэша C/B;
  CPU-prefill = 0. На длинных fixture один проход и разное чтение SSD:
  строгая повторная оценка одинаково прогретого target-only остаётся открытой.
- [x] Полный запрос с DSpark: время prefill, до первого токена и всего ответа,
  decode tokens/s, acceptance, число проверенных токенов, RAM/VRAM и чтение SSD.
  Различный сгенерированный текст не выдавать за одинаковую вычислительную нагрузку.
  Основное парное сравнение: 15 входных / 32 одинаковых выходных IDs,
  18 speculative rounds / 51 target-строка; все 12 ответов совпали.
- [x] Начать длинную проверку с 4096 токенов, затем проверить рабочий лимит 8192;
  длинный prefill выполняется на GPU. Отделить холодный запуск от прогретого режима.
  8152 входных + 32 выходных + 8 резервных; fresh и RAM restore измерены отдельно.
  Гибрид после restore проиграл и на 4096, и при верхнем лимите.
- [x] Для финальных кандидатов — не менее трёх независимых парных серий A/B/B/A,
  несколько запросов, медианы и разброс. SSD считать отдельно по фазам и учитывать
  постороннюю активность диска. Нулевое чтение SSD подтверждать счётчиком.
  Три короткие серии, два prompt, 12 процессов; H: = 0 в главной прогретой выборке.
  Фоновый I/O других устройств и различие текста первого prompt сохранены в отчёте.
- [x] Выполнить restore A→B→A, продолжение чата, fresh/full-prefill, cancel,
  seeded repeat, CUDA Graph replay, изменение будущих draft-ID и коротких окон.
  Не ослаблять существующие проверки ради прохождения; CPU/GPU-погрешность и ошибки
  управления состоянием разбирать отдельно. Seeded GPU-политика этапа 2 не заменяет
  численную приёмку гибридного auto+демоции: режим остаётся экспериментальным.
  Lifecycle 8/8 после обновления профиля, длинный restore, 24 причинные пробы C/B,
  1500 нативных CUDA Graph replay прошли. Batch/serial logits по-прежнему различны
  одинаково у GPU-compatible и гибрида; lossless batch/serial не объявлена пройденной.
- [ ] Проверить выключенную фичу и запуск старого Qwen backend. Не менять общие
  настройки CPU/GPU так, чтобы CPU lane включился в другом backend автоматически.
  GPU-only измерен. Qwen CLI --help запускается, DS4-флагов в окружении нет,
  но модель по пути H:/Q8_0 из Qwen-конфига отсутствует: генерация не проверена.

Итог измерений этапа 5 — оставить рабочий GPU-only. Повторная полная приёмка
потребуется после сокращения накладных расходов новых очередей; сейчас ускорение
CPU-ядер и адаптация профиля не перекрывают их цену. Сырые артефакты, сборки,
контроль с нулём CPU-заданий и ограничения: [отчёт](DEEPSEEK4_CPU_STAGE5_COMPARISON.md).

Рабочий критерий полезного профиля: воспроизводимое улучшение полного запроса
относительно GPU-only, превышающее шум измерений. Предварительный порог для отбора —
3%; это выбранный критерий будущего эксперимента, не измеренный или обещанный прирост.
Проверить отсутствие ухудшения длинного GPU-prefill сверх разброса и прохождение
всех обязательных проверок состояния. При выигрыше только на части нагрузок
описать область применения и оставить явный opt-in.

## Порядок работ и результаты каждого этапа

| Этап | Зависимость | Проверяемый результат |
|---|---|---|
| 0. Контроль и трасса | Нет | Baseline, разбивка ожиданий, записанные входы |
| 1. RAM/VRAM владение | 0 | Общие готовые адреса, таблицы, безопасное вытеснение |
| 2. GPU-ring и service | 1 | Полный путь CPU-эксперта без host-чтения ID для назначения |
| 3. Многотокенные ядра | 0; интеграция с 2 | Проверенная арифметика и локальные замеры |
| 4. Калибровка и пул | 2 и выбранные ядра 3 | План для фактического пути, GPU-only fallback |
| 5. Полная проверка | 1–4 | Решение о полезных профилях с замерами и ограничениями |

Для каждого этапа сохранять diff/сборку, настройки, сырые результаты, пройденные и
непройденные проверки, сравнение с контролем и следующий открытый вопрос. Менять
рабочий профиль только после этапа 5. Если полная связка не выигрывает, оставить
GPU-only и документировать измеренное ограничение; готовность инфраструктуры не
является основанием включить её по умолчанию.
