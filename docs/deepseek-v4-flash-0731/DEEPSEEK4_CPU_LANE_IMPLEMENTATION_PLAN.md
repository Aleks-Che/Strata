# План внедрения CPU lane по архитектуре Maya

Дата: 12 октября 2026. Статус: реализация начата; этап 0 внедрён и проверен
в описанной ниже области измерений. В этапе 1 реализованы поколения, общий реестр
RAM/VRAM и ограниченная демоция; измерения описаны в
[отчёте RAM/VRAM](DEEPSEEK4_RAM_TIERS.md). В этапе 2 подключены GPU-публикация
и постоянный service; [проверки и ограничения](DEEPSEEK4_CPU_GPU_QUEUE.md).
Этапы 2–5 не завершены.
Код, условия измерений и ограничения: [трасса CPU lane](DEEPSEEK4_CPU_LANE_TRACE.md).

Цель — получить полезное перекрытие CPU-вычисления экспертов с передачей и
вычислением остальных экспертов на GPU. Выигрыш должен подтверждаться временем
полного запроса относительно рабочего GPU-only профиля, а не только уменьшением
H2D-трафика или временем отдельного CPU-ядра.

## Как внедрять: общая архитектура, проверяемые этапы

Сначала проектируем целиком путь «готовые RAM-матрицы → GPU-выбор → очередь →
постоянный CPU-пул → объединение результатов». Затем реализуем его небольшими
этапами с проверкой корректности после каждого. Итоговую скорость этой связки
оцениваем после сборки всех необходимых частей.

Не требуем ускорения полного запроса от каждого промежуточного шага. Общий RAM-пул
или таблица резидентности могут быть необходимой основой следующего шага, не давая
самостоятельного выигрыша. Промежуточные затраты всё равно измеряем и сохраняем.
После сборки связки отключаем отдельные части и выясняем их вклад.

Независимые изменения — многотокенные SIMD-ядра, калибровка, политика ожидания
workers — сохраняем переключаемыми и проверяем отдельно. Тонкую настройку числа
потоков выполняем после изменения пути запуска. Копировать весь GLM backend Maya
не требуется: сохраняем граф DeepSeek, матричный GPU-кэш и поддержку Qwen.

## Исходное состояние и доказательства

ПК: Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, SSD H: Samsung 990 PRO, Windows.
Основной объект: DeepSeek-V4-Flash-0731 UD-Q3_K_XL; интеграционные проверки — с
DSpark Q8_0. Рабочий профиль остаётся GPU-only, CPU lane и дополнительный RAM-кэш
выключены по умолчанию. CPU lane рассматривается для decode и короткой проверки
draft-токенов; длинный prefill сохраняется на GPU.

Уже реализованы целый CPU-эксперт gate/up → SwiGLU → down, постоянный пул,
SIMD через ggml-cpu, лимит по токенам, общий HostCache с тремя защищёнными
RAM-адресами и отсутствие повторного pack в shared-режиме. Есть эксперименты
с прямым H2D, удалением RAM-дубликатов после GPU admission, отложенным заполнением,
пулом pinned allocations и фоновым сохранением. Не нужно заново реализовывать эти
части по ранним аудитам, описывающим старый прототип.

Фиксированная история: target-only, 68 одинаковых входных IDs, префикс 36 и decode
32 токенов; среднее двух последних из четырёх проходов:

| Режим | Decode по 1 токену, мс | Decode по 3 токена, мс |
|---|---:|---:|
| GPU-only, до | 1607,0 | 1073,4 |
| Общий RAM 2 ГиБ, CPU 0 | 1718,3 | 1230,3 |
| Общий RAM, CPU 12 потоков | 1768,8 | 1206,8 |
| GPU-only, после | 1615,4 | 1082,9 |

CPU уменьшил время chunk=3 примерно на 1,9% относительно одинакового RAM-кэша,
но обычный GPU-only быстрее. Независимых повторов серии для доверительных
интервалов нет; одинаковые входные IDs не гарантируют одинаковые внутренние
маршруты при различном округлении CPU/GPU.
[Методика и ограничения](DEEPSEEK4_CPU_LANE_EXPERIMENTS.md).

[Последние опыты с RAM-пулом и фоновой очередью](DEEPSEEK4_RAM_BACKGROUND.md)
проводились с CPU lane выключенным. Эта очередь заполняет RAM-кэш; она не является
GPU-очередью вычисления экспертов. В shared CPU-режиме остаётся провал seeded repeat
после восстановления сессии. Прохождение прежнего fixed CPU режима не закрывает
этот дефект. Maya на этом ПК с тем же workload не измерялась; её общий tokens/s
не является сравнением CPU lane on/off для нашего DeepSeek.

## Целевая архитектура

1. Общий реестр матриц описывает RAM/VRAM-резидентность, готовность и поколения
   адресов. Хранение gate/up/down остаётся раздельным. CPU-задание удерживает три
   адреса до завершения; незавершённые или вытесняемые матрицы не выбираются.
2. GPU-роутер использует согласованный снимок таблиц и готовый план стоимости,
   выбирает CPU-работу и публикует адреса и вход в ограниченную очередь. Основной
   host-поток не должен читать IDs и ждать GPU ради решения CPU/GPU этого пути.
3. Постоянный service thread принимает задания и запускает CPU-пул. GPU в это
   время передаёт и вычисляет остальные эксперты. CPU-ветка присоединяется в месте,
   где её down-результаты действительно нужны.
4. CPU считает несколько активаций одного эксперта с переиспользованием
   распакованных весов. Результаты возвращаются в исходные позиции top-k, чтобы
   сохранить порядок итогового суммирования.
5. Выбор допускает ноль CPU-экспертов. Он учитывает реально отменённые передачи,
   работу GPU и CPU, запуск, очередь и ожидание результата. Число потоков и
   размещение весов сами по себе не считаются доказательством ускорения.

## Этап 0. Зафиксировать контроль и измерить критический путь

- [x] Сохранить SHA сборки, ревизию и diff, команды, параметры, модели, входные IDs,
  состояние кэшей и сырые результаты. Использовать одну сборку с переключателями.
- [x] Ввести отключаемую трассировку: получение маршрута, CPU-выбор, ожидание
  готового RAM-адреса, публикация/приём задания, пробуждение пула, квантизация входа,
  gate/up, down, передача результата и ожидание CPU со стороны GPU.
- [x] Записывать H2D/D2D/D2H, GPU/RAM hits и misses, SSD-чтение, allocations,
  заполнение/вытеснение RAM, число CPU-экспертов и токенов на эксперт, глубину очереди.
- [x] Отделить суммарное время работы потоков от задержек полного запроса.
  Связывать CPU и CUDA events по ID задания; не вычитать несогласованные часы.
  Замерить влияние самой трассировки контрольным A/A.
- [x] Для локальных сравнений ядер сохранить маршруты, веса и входные активации:
  фиксированных token IDs недостаточно для гарантии одинаковой внутренней работы.

Результат: понятно, сколько времени можно скрыть параллельной работой и где
ожидает GPU. Профилирование не является обязательным режимом рабочего сервера.

Первое выполнение: host trace сохраняет CUDA Graphs; CUDA-интервалы измерены
отдельно без графов. Нельзя переносить их напрямую на рабочий режим. Раннее
ожидание D2H входа отдельно не изолировано. У текущего backend одновременно
только одно CPU-задание; счётчики заполнения нового GPU-ring появятся с этапом 2.
Существующие transfer/RAM-счётчики сохраняются в логе, SSD пока измерен за все
проходы процесса. Более длинные нагрузки и окончательная приёмка — этап 5.

## Этап 1. Общий путь хранения RAM/VRAM

- [x] Описать состояния записи: отсутствует, заполняется, готова, удерживается
  потребителем, переносится, вытесняется. Определить поколение адреса и порядок
  публикации GPU-таблицы. Таблица сама по себе не заменяет владение памятью.
- [x] Использовать имеющийся HostCache и pinned-пул как основу. CPU и H2D получают
  одни готовые матрицы; при RAM-hit нет дополнительной упаковки или копии для CPU.
- [x] Добавить общий учёт GPU-residency. Освобождать RAM-дубликат после завершения
  promotion и всех потребителей. Предусмотреть ограниченную демоцию GPU→RAM при
  вытеснении, с отдельным учётом её D2H-трафика; не демотировать всё безусловно.
- [x] Сохранять горячие RAM-матрицы при большом prefill. Проверять наличие всей
  тройки CPU-эксперта без возврата к отдельному private CPU cache.
- [x] Ограничить общий расход target/DSpark: активные блоки, свободный pinned-пул,
  временные копии и очередь. Учитывать файловый кэш ОС и запас свободной RAM.
  Большой pinned-пул не включать автоматически по принципу «занять всё свободное».
- [x] Сначала проверить малый бюджет, затем увеличивать только в пределах
  измеренного запаса памяти. Сравнивать CPU on/off при одинаковом RAM-бюджете
  и отдельно с рабочим GPU-only без дополнительного кэша.

Проверки: leases при promotion/eviction, одновременные target/DSpark, отмена,
ошибка чтения, незавершённое заполнение, смена поколения, ограничение бюджета.
Самостоятельный прирост tokens/s не является условием перехода к этапу 2.

Реализация этапа 1: поколения действуют внутри экземпляра HostCache; CUDA event
подтверждает готовность GPU-копии. Токен реестра не заменяет владение GPU allocation.
Протокол публикации будущей GPU-таблицы описан, сама таблица и её удерживаемые
снимки относятся к этапу 2. Pending демоций входит в бюджет HostCache; рабочие
буферы pipeline/CPU имеют отдельные фиксированные лимиты и учитываются проверкой
доступной системной памяти. Демоция выключена по умолчанию.

## Этап 2. GPU-публикация и постоянный CPU-service

- [x] Спроектировать ограниченный mapped ring: ID backend/слоя/задания, поколение,
  маска CPU, позиции top-k, адреса трёх матриц, входные активации, ответ и статус ошибки.
- [x] Сначала проверить протокол отдельно от модели: порядок видимости CPU/GPU,
  многократный оборот кольца, защита от повторного ответа и переиспользования слота.
- [x] Публиковать решение из GPU-роутера. Гарантировать время жизни весов через
  удерживаемый снимок/эпоху таблицы либо равноценный протокол до подтверждения
  потребителя. Не обращаться из GPU по устаревшим host-адресам.
- [x] Подключить service thread к существующему постоянному пулу. На этом этапе
  сохранить старые арифметические ядра, чтобы отдельно проверить новый транспорт.
- [x] Убрать получение IDs основным host-потоком на выбранном пути; проверить
  трассой, что старый scheduler не продолжает делать ту же синхронизацию скрыто.
- [x] Перенести заполнение RAM и обучение RAM/VRAM-кэшей в новый путь подкачки:
  по фактическому GPU-запросу переиспользовать свободный или вытесняемый pinned-блок,
  без CUDA allocation/free на I/O-service. Учесть резерв в общем бюджете.
- [x] Добавить admissions GPU-кэша через переиспользование allocations своего
  backend: прямое заполнение по GPU-запросу, поколение перед перезаписью, возврат
  неиспользованных записей без потери старых весов. Проверить arena/managed,
  CUDA Graph replay, точные CPU/GPU-строки и освобождение кэша.
- [ ] Завершить GPU admissions: рост пустого кэша и совместимость с демоцией
  GPU→RAM пока остаются на старом пути. Холодные слои используют старый scheduler;
  новый путь не включается в рабочем профиле и не закрывает этап 2 сам по себе.
- [x] Отпускать невыбранные CPU-кандидаты после GPU-решения и RAM-источники
  после подтверждения GPU-копии, без CUDA release на service. Смешанные
  CPU/GPU-вхождения сохраняют CPU-защиту; режим остаётся opt-in.
- [ ] Сократить удержание выбранных CPU-троек и ожидание на границе ветки.
- [x] Разрешить обработку завершённой подкачки после copy event, пока GPU ещё
  считает конец ветки. Сохранять защиту VRAM и выбранных CPU-троек до последнего
  потребителя; неполные ветки и отмену оставлять на полном fence.
- [x] После получения всех ответов разрешить не ждать засыпания CPU/I/O-service.
  Новый запрос требует `arm()`; перед уничтожением очереди worker присоединяется.
  Проверить многократные disarm/rearm и прежний путь отмены. Оба режима opt-in.
- [x] Отдельно сократить подготовку CPU-снимка: пропускать недопустимых кандидатов
  и прекращать RAM lookup для неполной тройки, без изменения CPU-решения и
  арифметики. Проверить полные logits и счётчики маршрутов.
- [x] Присоединять CPU-результаты после независимой GPU-работы, в исходном порядке
  строк. Для смешанных CPU/GPU-вхождений одного эксперта не отменять нужный GPU fetch.
- [x] Сохранить причинность: решение для префикса не зависит от будущих draft-ID.
  Определить поведение заполненной очереди заранее; переключение на GPU допустимо
  только до публикации решения, без потери или двойного выполнения эксперта.
- [ ] Проверить CUDA Graph capture/replay, уникальность задания при replay,
  cancel/restore, завершение service, ошибки и ограниченное ожидание. Начать с
  target, затем подключить DSpark с изолированными ID и общим бюджетом.

После этапов 1–2 провести первый полный замер связки. Отрицательный результат
фиксируется вместе с профилем ожиданий; он не доказывает бесполезность ещё не
реализованных многотокенных ядер и достоверной калибровки.

Исходный opt-in `STRATA_DS4_CPU_GPU_QUEUE=1`: GPU принимает CPU-решение до
host-чтения маршрутов; service считает готовые RAM-тройки. Однако старый
SSD/H2D-планировщик затем читает IDs и синхронизирует backend для подкачки
GPU-матриц. Дополнительный `STRATA_DS4_GPU_FETCH_QUEUE=1` убирает это чтение
для подходящих веток с готовой RAM-тройкой. Hash GET_ROWS пока сохраняет старый
путь. 1200 replay протокола и native whole-expert проверки не заменяют полной
проверки модели, DSpark и восстановления сессий.

Итог первого шага: queue-v3 прошёл fixed-history target-прогон и проверки
переключения callback/queue в CUDA Graph. Ускорения пока нет: 1931/1247 мс против
1822/1234 мс callback для 32 decode-токенов по 1/3. DSpark воспроизвёл расхождение
после cancel/restore; такой же результат получен с callback без очереди.
Seeded repeat в этой серии не достигнут. Режим остаётся opt-in; полный отчёт,
ограничения трассы и доказательства — в [GPU-очереди](DEEPSEEK4_CPU_GPU_QUEUE.md).

Следующий шаг: [очередь подкачки](DEEPSEEK4_GPU_FETCH_QUEUE.md) уменьшила число
host route reads на 88,37% в прогретом workload. Но без перенесённого заполнения
кэшей decode стал дольше на 26,03% / 36,69%. Пройдены native-тесты, capture/replay
и greedy cancel/restore с DSpark; seeded repeat всё ещё расходится. Этап 2
остаётся открытым, рабочий профиль не переключён.

Продолжение: [RAM из GPU-очереди](DEEPSEEK4_GPU_FETCH_RAM.md). I/O-service может
взять только уже выделенный блок подходящего размера; публикация готовых байтов
выполняется после GPU-подтверждения. Первое резервирование по популярности
отклонено из-за большого числа неиспользованных блоков. Следующий шаг —
[заполнение существующих VRAM-слотов](DEEPSEEK4_GPU_FETCH_CACHE.md): GPU выбирает
их по фактическому маршруту, без повторной передачи весов. Рост пустого GPU-кэша,
демоция, сокращение ожиданий и полная приёмка состояния ещё остаются открытыми.
На RTX 5090 + 9950X режим с четырьмя предложенными слотами прошёл 40 регрессионных
и шесть дополнительных проверок, но в одной A/B/B/A decode стал дольше на
14,16% / 20,94% для пакетов по 1/3. С одним слотом в одиночной пробе выигрыша
тоже нет. DSpark greedy restore прошёл, seeded restore расходится на десятом
токене. Перенос записи в VRAM реализован в указанной области; согласование
политики GPU admission с RAM-тройками/CPU и полная приёмка остаются открытыми.

Продолжение: [размещение и CPU-снимок](DEEPSEEK4_GPU_FETCH_PLACEMENT.md).
Защита уже готовых CPU-троек от частичного GPU admission не дала согласованного
ускорения в отборочной пробе. Удаление ненужных lookup сократило их число на
69,86%, время подготовки снимков на 14,65%; все 12/12 logits signatures и
счётчики маршрутов совпали. В одной A/B/B/A decode практически не изменился,
полный короткий workload занял на 1,67% меньше времени. Удержание готовых троек
и ожидание конца ветки пока сохранены; этап 2 не закрыт.
Пройдены 42 регрессионных и восемь дополнительных проверок. DSpark с обеими
новыми фичами проходит greedy restore/cancel, но seeded restore расходится
на седьмом токене; рабочий профиль не изменён.

Продолжение: [раннее освобождение RAM-снимков](DEEPSEEK4_GPU_FETCH_RELEASE.md).
I/O-service отпускает невыбранных CPU-кандидатов и источники завершённых GPU-копий,
сохраняя защиту смешанных CPU/GPU-вхождений и запрет CUDA free на service.
44 регрессионных проверки прошли; без нового RAM fill полные logits 12/12
совпали. При включённом fill политика размещения изменилась: 11/12 совпадений,
1144/1430 → 1143/1429 CPU jobs/rows. Прогретая B/A/A/B не показала ускорения:
decode стал дольше на 1,28% / 0,95%, полный workload на 1,06%.
Режим выключен по умолчанию. Следующий открытый пункт — время жизни выбранных
CPU-троек и ожидание всей ветки; общий критерий приёмки этапа 2 сохраняется.
Ещё десять проверок compact/slabs/drop и RAM-fill-off прошли. DSpark greedy
restore/cancel прошёл, seeded restore снова расходится с седьмого токена;
обе последовательности совпадают с результатами предыдущего шага.

Продолжение: [завершение подкачки и ожидание service](DEEPSEEK4_GPU_FETCH_RETIRE.md).
Добавлены независимые EARLY_RETIRE и ASYNC_PARK: обработка кэшей после последней
копии может пересекаться с вычислениями, ожидание перехода service в сон можно
пропустить после acquire всех ответов. Выбранные CPU-тройки и VRAM всё ещё
защищены до последнего потребителя. Восемь fixed-history прогонов дали 12/12
одинаковых logits signatures и прежние назначения CPU/GPU. Одна A/B/B/A дала
сокращение decode на 4,09% / 2,74%, полного workload — на 1,10%; разброс контроля
больше эффекта, устойчивое ускорение не установлено. ASYNC_PARK отдельно
выигрыша не показал. Оба режима выключены по умолчанию. DSpark greedy
restore/cancel прошёл, строгий seeded restore сохраняет прежнее расхождение
на седьмом токене. Общий критерий приёмки этапа 2 остаётся открытым.
Пройдены 46 основных и 12 дополнительных native-проверок, включая compact/slabs,
RAM_DROP_GPU и выключенный fetch RAM fill.

## Этап 3. Многотокенные CPU-ядра

Этот этап можно разрабатывать независимо от GPU-очереди на записанных активациях.

- [ ] Начать с IQ3_XXS: распаковывать блок весов один раз для всех использующих
  его токенов. Проверить применимость Maya-кода к раздельным gate/up, геометрии
  DeepSeek и SwiGLU clamp; при переносе сохранить лицензию и атрибуцию.
- [ ] MXFP4 и Q8_0 измерять отдельно. Неподдержанный или невыгодный формат оставлять
  на существующем пути. Поддержать смешанные форматы трёх матриц без переквантования весов.
- [ ] Сравнить окна 1/2/3 и остальные поддержанные короткие формы, полное и частичное
  повторение экспертов, 8/12/16 потоков. Вращать веса объёмом больше CPU-кэша.
- [ ] До выбора быстрого dispatch определить численный контракт: ошибка относительно
  CPU-эталона, порядок редукции, clamp и независимость результата префикса от будущего.
  Переключение single/multi по размеру окна не должно незаметно менять этот контракт.

Проверки: исходные CPU-ядра и точный эталон на сохранённых входах, затем полные
logits и маршруты модели. Отдельно проверить restore и DSpark; ускорение микроядра
не засчитывается как ускорение полного запроса.

## Этап 4. Калибровка, план стоимости и настройка пула

- [ ] Калибровать после подготовки RAM на сменяющихся готовых экспертах, а не
  многократно на одном blob. Покрыть форматы, геометрию, число уникальных экспертов
  и число активаций каждого. Не делить фиксированную стоимость вызова на tokens.
- [ ] Измерять подготовку, DRAM/распаковку, dot products, запуск, передачу результата
  и объединение. Оценивать максимальную длительность параллельных веток плюс общие
  расходы; не складывать уже перекрытые интервалы как последовательные.
- [ ] Учесть уникальные отменяемые H2D-байты: повторное вхождение или матрица,
  нужная GPU для другого токена, не дают повторной экономии передачи.
- [ ] Разрешить ноль CPU-экспертов, ограничить CPU-бюджет на токен и проверять
  прогноз по фактическим задержкам. Калибровку версионировать по сборке, формату,
  оборудованию, потокам и режиму ядер; при устойчивом расхождении пересчитывать.
- [ ] Проверять выбранные настройки чередующимися новыми запросами. Не подстраивать
  их по будущим токенам текущего speculative window и не менять посреди сравнения.
- [ ] После нового транспорта подобрать 8/12/16 потоков, дробление заданий и
  spin/sleep. Измерять tokens/s, CPU-seconds, задержки и загрузку в простое.
  NUMA/affinity не включать без топологии и отдельного выигрыша на этом ПК.

Калибровка и принудительное назначение экспертов проверяются отдельно: улучшение
auto-плана не объясняет автоматически результаты force-режимов.

## Этап 5. Сравнение полного решения и условия принятия

Минимальные контрольные варианты:

| Вариант | Зачем нужен |
|---|---|
| Рабочий GPU-only без дополнительного RAM-кэша | Итоговая точка сравнения |
| Новый RAM/VRAM путь, CPU выключен | Цена нового хранения |
| То же хранение, старый host-запуск CPU | Вклад GPU-очереди |
| GPU-очередь, прежние CPU-ядра, фиксированный план | Проверка нового транспорта |
| GPU-очередь и многотокенные ядра, тот же план | Вклад арифметических ядер |
| Полная связка с новой калибровкой | Практический итог |

Не запускать декартово произведение всех настроек. Сначала ограниченные проверки
изменяемого компонента; длинные серии — на собранной связке и лучших вариантах.
На промежуточных этапах повторять расширенные проверки при изменении соответствующих
путей или обнаружении дефекта.

- [ ] Фиксированная история без DSpark: прежний короткий fixture и длинный контекст,
  decode по 1/3 токена, одинаковые лимиты памяти и состояние прогрева.
- [ ] Полный запрос с DSpark: время prefill, до первого токена и всего ответа,
  decode tokens/s, acceptance, число проверенных токенов, RAM/VRAM и чтение SSD.
  Различный сгенерированный текст не выдавать за одинаковую вычислительную нагрузку.
- [ ] Начать длинную проверку с 4096 токенов, затем проверить рабочий лимит 8192;
  длинный prefill выполняется на GPU. Отделить холодный запуск от прогретого режима.
- [ ] Для финальных кандидатов — не менее трёх независимых парных серий A/B/B/A,
  несколько запросов, медианы и разброс. SSD считать отдельно по фазам и учитывать
  постороннюю активность диска. Нулевое чтение SSD подтверждать счётчиком.
- [ ] Выполнить restore A→B→A, продолжение чата, fresh/full-prefill, cancel,
  seeded repeat, CUDA Graph replay, изменение будущих draft-ID и коротких окон.
  Не ослаблять существующие проверки ради прохождения; CPU/GPU-погрешность и ошибки
  управления состоянием разбирать отдельно. Пока shared seeded restore не исправлен,
  режим остаётся экспериментальным независимо от скорости.
- [ ] Проверить выключенную фичу и запуск старого Qwen backend. Не менять общие
  настройки CPU/GPU так, чтобы CPU lane включился в другом backend автоматически.

Рабочий критерий полезного профиля: воспроизводимое улучшение полного запроса
относительно GPU-only, превышающее шум измерений. Предварительный порог для отбора —
3%; это выбранный критерий будущего эксперимента, не измеренный или обещанный прирост.
Проверить отсутствие ухудшения длинного GPU-prefill сверх разброса и прохождение
всех обязательных проверок состояния. При выигрыше только на части нагрузок
описать область применения и оставить явный opt-in.

## Порядок работ и результаты каждого этапа

| Этап | Зависимость | Проверяемый результат |
|---|---|---|
| 0. Контроль и трасса | Нет | Baseline, разбивка ожиданий, записанные входы |
| 1. RAM/VRAM владение | 0 | Общие готовые адреса, таблицы, безопасное вытеснение |
| 2. GPU-ring и service | 1 | Полный путь CPU-эксперта без host-чтения ID для назначения |
| 3. Многотокенные ядра | 0; интеграция с 2 | Проверенная арифметика и локальные замеры |
| 4. Калибровка и пул | 2 и выбранные ядра 3 | План для фактического пути, GPU-only fallback |
| 5. Полная проверка | 1–4 | Решение о полезных профилях с замерами и ограничениями |

Для каждого этапа сохранять diff/сборку, настройки, сырые результаты, пройденные и
непройденные проверки, сравнение с контролем и следующий открытый вопрос. Менять
рабочий профиль только после этапа 5. Если полная связка не выигрывает, оставить
GPU-only и документировать измеренное ограничение; готовность инфраструктуры не
является основанием включить её по умолчанию.
