# CPU lane v2: целые эксперты и асинхронное выполнение

12 октября 2026. Переработка по [разбору Maya](DEEPSEEK4_CPU_LANE_MAYA_AUDIT.md). CPU lane остаётся отдельной опцией, `--expert-cpu-threads 0` сохраняет GPU-only. Ниже описана новая реализация; [матричный прототип и его замеры](DEEPSEEK4_CPU_LANE.md) сохранены отдельно.

Повторный [аудит отличий от Maya](DEEPSEEK4_CPU_LANE_V2_MAYA_AUDIT.md) уточняет ограничения этой версии, включая зависимость CPU-назначения от всего speculative window.

## Реализация

- Планировщик распознаёт связанную тройку gate/up/down и SwiGLU по связям тензоров. Обход графа может начинаться с gate или up. Неподдерживаемые формы, fusion, несколько scheduler copies и eval callback сохраняют GPU-путь.
- Одно CPU-задание считает выбранного эксперта целиком: gate/up, DeepSeek SwiGLU с нужным clamp, down. Вход квантуется один раз на токен для каждого необходимого типа активаций. Общие типы gate/up используют одну квантизацию. Строки весов обрабатываются сразу для всех токенов выбранного эксперта.
- CPU выбирает холодных кандидатов по истории частот. Обычный режим рассматривает только экспертов, у которых все три матрицы отсутствуют в GPU-кэше и доступны в RAM. Готовые GPU-матрицы сохраняют свой путь.
- Вход D2H, CPU callback, выход H2D и событие готовности ставятся в отдельный CUDA stream. GPU продолжает передачу и вычисление остальных экспертов. Перед повторным использованием входного буфера стоит GPU-событие завершения D2H, без ожидания CPU-расчёта на host.
- Gate/up CPU-строки зануляются на GPU, а готовый down возвращается на исходные позиции перед штатным взвешиванием и редукцией. CPU не создаёт отдельную сумму экспертов: порядок суммирования исходного графа сохраняется.
- Down ждёт внешнее событие, которое сохраняется в CUDA Graph. Capture/replay больше не отключается для whole-expert lane. Callback не вызывает CUDA API; все CUDA-операции ставит в очередь поток движка. Это соответствует [ограничениям host function](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__EXECUTION.html) и [внешним событиям CUDA Graph](https://docs.nvidia.com/dl-cuda-graph/cuda-graph-basics/constraints.html).
- Владение scratch, событиями и весами сохраняется до окончания работы. Отмена и выход из графа завершают поставленное задание перед освобождением памяти. Ожидания GPU в spin-loop нет.
- Пул считает завершённые задания. Каждая опубликованная очередь имеет собственное время жизни, поэтому запоздавший worker не получает задания новой очереди через старый счётчик. Вызывающий CPU callback участвует в работе; пробуждение всех потоков не является условием завершения.
- Весь prefill, включая короткие хвосты и inject в DSpark, остаётся на GPU. Разрешение CPU возвращается для decode и проверки speculative batch. Переключение этой фазы не меняет структуру CUDA Graph: меняется только маска.

## Память и выбор количества экспертов

CPU-веса хранятся в ограниченном pinned RAM-кэше с LRU и удержанием используемых записей. Ключ включает исходные адреса всех трёх матриц. При промахе callback копирует веса из mmap в принадлежащий кэшу буфер. После заполнения вычисление использует закреплённую память. Начальная проверка mmap-резидентности не гарантирует, что ОС не вытеснит исходную страницу до копирования; это всё ещё надо учитывать в измерении SSD.

Калибровка измеряет целого CPU-эксперта, копирование его весов H2D, границу D2H/callback/H2D и заполнение CPU-кэша. Учитываются типы gate/up/down, размеры и длина короткого batch. План сравнивает оставшиеся передачи с CPU-работой, допускает ноль CPU-экспертов и ограничивает выбор заданным максимумом. Это приближённая модель стоимости, а не доказательство выигрыша полного запроса.

Лимит pinned CPU-кэша задаётся на backend: при target + DSpark значение 256 МиБ означает до 512 МиБ суммарно для весов. Отдельно каждый активный lane резервирует по 2 МиБ pinned input/output и по 2 МиБ GPU output. Матрицы GPU-кэша продолжают храниться отдельно; рабочий профиль автоматически не переключается на CPU.

## Параметры

```text
--expert-cpu-threads 8
--expert-cpu-max-experts 1
--expert-cpu-policy auto
--expert-cpu-ram-mib 256
```

`threads`: 0–16, по умолчанию 0. `max-experts`: 1–6, теперь это число уникальных **целых экспертов на маршрут**, а не на матрицу. `policy=auto` использует калибровку; `force` принудительно выбирает до лимита пригодных холодных экспертов для сравнительных опытов. `ram-mib`: 0–4096 на backend; ноль оставляет весь расчёт на GPU. Те же параметры доступны в `tools/setup_deepseek4.py`.

По прежнему нужны сборка direct-cache, pipeline и staging. Исследовательские early hits, routed MMQ и hash prefetch вместе с CPU lane запрещены. Старый матричный путь оставлен только для регрессионного fixture через `STRATA_DS4_CPU_MATRIX_LEGACY=1`.

`STRATA_DS4_CPU_TEST_FIXED=1` — диагностический режим фиксированного выбора экспертов для проверки состояния. Он игнорирует VRAM-резидентность, частоты и фильтр присутствия исходных страниц в RAM, поэтому может читать SSD и считать на CPU уже закэшированные GPU-веса. Его результаты скорости нельзя выдавать за обычный адаптивный режим. Рабочие профили этот флаг не включают.

## Проверки

Финальная сборка: 25/25 выбранных CTest прошли за 63,77 с, включая CPU lane, GPU-only, speculative contract, direct cache, compact buffers, hash prefetch и pipeline. Whole-expert fixture: 2880 сценариев, force/auto/нулевой RAM-бюджет, IQ3_XXS/MXFP4/Q8_0 с отдельным Q8_0 gate, input 256 и hidden 512, clamp включён/выключен, batch 1/3/8/9, лимиты 1/6, scheduler copies 1/несколько, меняющиеся маршруты и входы, десять повторов каждого графа. Между повторами CPU дважды выключается для имитации prefill. Проверяется последующая взвешенная сумма, а не только сырой down.

CPU-строки совпадают по битам с native CPU reference, остальные — с GPU-контролем. Независимый double reference использует деквантованные веса и FP64 суммы: максимальная относительная L2-ошибка в коротком матричном пути — CPU 0,016201, GPU 0,010097 на этих синтетических данных. Это не оценка качества полной модели. Для batch 9 неизменённый GPU MMQ дал до 0,212106; для него здесь проверяется побитовое совпадение с исходным GPU-путём, а не тот же порог ошибки, что у MMVQ.

Дополнительно проверены 512 очередей CPU-пула на 1/4/12/16 потоках, включая нулевое число заданий и число заданий меньше числа workers. Python-тесты DeepSeek/setup/routes: 12 прошли.

## Полная модель: результаты

Windows, Ryzen 9 9950X (16 ядер / 32 логических потока), 128 ГиБ RAM, RTX 5090 32 ГиБ, H: Samsung 990 PRO. Target UD-Q3_K_XL, DSpark Q8_0, draft max 2, context 8192, batch 4096. GPU-кэш target 15360 МиБ, draft 1024 МиБ, shared scratch, pipeline со stage 16 МиБ и двумя readers, read mode auto. CPU максимум — один целый эксперт на маршрут.

Каждый процесс: prefill 4096 токенов, отдельный короткий prompt 36 токенов с генерацией 64, четыре повтора из RAM-сессии, свежий полный prefill 4096. Файловый кэш ОС не очищался. R3/R4 — третий/четвёртый повтор генерации; чтение — весь PhysicalDrive6 за запрос, включая другие процессы. Скорость — 64 / decode_ms, без prompt/restore. Выходные token IDs и acceptance также проверяются: одинаковый prompt сам по себе не гарантирует одинаковую вычислительную нагрузку.

**Ускорение рабочего GPU-профиля не подтверждено.** CPU auto/force не дали точного совпадения greedy-повторов. Смена назначения CPU/GPU меняет арифметику, дальнейший маршрут и набор весов; эти CPU-повторы не являются сравнением без SSD. При фиксированном выборе все четыре повтора совпали, SSD не читался. В j1 также совпали 64 output IDs и acceptance с GPU a2: 38/51. Но 14,090 ток/с всё ещё примерно на 18% ниже 17,103 ток/с GPU a2. Это диагностический режим, который может считать на CPU уже находящиеся в VRAM матрицы.

Полный prefill после генераций: GPU a2 — 8,979 с, fixed j1 — 9,289 с, оба без чтения SSD за запрос. Обычные CPU h1/i1 — 13,319/14,010 с и 33,081/33,890 ГБ чтения за запрос. Эти объёмы относятся ко всему запросу, включая три выходных токена. CPU-математика prefill отключена; дополнительное чтение и состояние кэша всё равно влияют на его время.

Суммы target за весь процесс, не время одной генерации:

| g1, сокращённый выбор auto | 4801 | 1,825 | 4,169 | 3,263 | 19 / 4788 |
| h1, force 256 МиБ | 5310 | 2,028 | 4,246 | 3,258 | 2 / 5308 |
| i1, force 2048 МиБ | 5310 | 2,086 | 3,934 | 3,292 | 570 / 4740 |
| j1, fixed 2048 МиБ | 6063 | 2,173 | 5,515 | 0,353 | 695 / 5368 |

Сокращение residency-проверок уменьшило суммарный выбор даже при большем числе CPU-заданий. Больший RAM-кэш повысил число попаданий, но не ускорил запрос: содержимое мало переиспользуется при выборе холодных экспертов, а закреплённые копии конкурируют за RAM с файловым кэшем. Последнее — объяснение, согласующееся с ростом чтения, а не отдельное измерение механизма вытеснения ОС.

Калибровка пока недооценивает влияние выбора, истории GPU/RAM-кэшей и изменившихся маршрутов на полный запрос. Её положительный прогноз нельзя использовать как основание для включения CPU в рабочем профиле. Следующий предмет работы — стабильное назначение вычислений и совместная политика CPU/GPU/RAM, а не увеличение числа потоков. Spin/affinity ещё не настраивались; качество модели на наборе задач не оценивалось.

Рабочий GPU-профиль не переключался на CPU.

## Состояние сессий

Полный валидатор DSpark с 16 токенами прошёл для GPU-only и fixed CPU: A → B → A, продолжение активной сессии и восстановление продолжения, fresh prefill, один токен, отмена prefill, отмена decode, следующий запрос после отмены, sampling с seed 123 и его повтор. Для обоих `full_prefill_identical=true` на данном коротком сценарии.

GPU-only совпал с прежним GPU-эталоном во всех восьми greedy-сценариях. Отдельное сравнение сохранённых JSON показало совпадение входных и выходных IDs fixed CPU с новым GPU-контролем также в 8/8 сценариях. Это не утверждение о побитовой эквивалентности logits или качестве на произвольных запросах.

**Адаптивный auto эту проверку не прошёл:** после A → B → A изменились output IDs. Assert оставлен строгим; последующие сценарии этого запуска не выполнялись. Успех fixed-опыта поддерживает объяснение через меняющееся CPU/GPU-назначение, но не доказывает отсутствие всех возможных дефектов состояния в auto. Обычный auto/force пока нельзя считать режимом с точной воспроизводимостью сессий.

Артефакты: `bench/results/ds4-cpu-whole-20261012-validate-{control,fixed,auto}.json/.log`; сводка `build-local/deepseek4/cpu-whole-20261012/validation-summary.json`, сравнение IDs — `fixed-vs-control.json` рядом. Пороги и проверки вывода не ослаблялись.
