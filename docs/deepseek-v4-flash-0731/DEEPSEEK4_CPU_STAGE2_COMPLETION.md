# Этап 2 CPU lane: независимые контексты и завершение GPU-очередей

13 октября 2026. Реализация инфраструктуры этапа 2 завершена: два независимых
контекста, холодный GPU-кэш, демоция и согласованное время жизни RAM/VRAM.
Это не принятие всей CPU lane в рабочий профиль: ускорения нет, строгая численная
повторяемость auto+демоции не пройдена. Рабочий GPU-only профиль не переключён.
CPU lane, очередь подкачки, два контекста и демоция остаются опциональными.

ПК: Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, Windows, H: Samsung 990 PRO.
Target — DeepSeek-V4-Flash-0731 UD-Q3_K_XL, 43 слоя; draft — DSpark Q8_0,
3 слоя. Сборка MSVC 2022 / CUDA 13, параллелизм сборки — 2.

## Что изменено

Вместо переиспользования одного host-контекста на каждой границе ветки есть
кольцо из двух. У каждого свои таблица маршрутизации, задания, CPU/I/O service,
закреплённые адреса, ответы и события завершения. Один постоянный пул из N CPU
workers разделяется между контекстами backend. Следующая ветка готовится, пока
предыдущая работает; ждать приходится при обороте кольца, повторном использовании
тех же весов либо выходе из пути GPU fetch. Это ограниченное перекрытие подготовки,
а не параллельное вычисление зависимых слоёв модели.

CUDA Graph сохраняет стабильные адреса packet/output и читает текущую привязку
очереди, установленную в том же stream. Публикация следующей привязки происходит
после прежнего GPU-потребителя. Закрытие графа, отмена и переход на старый путь
дренируют оба контекста в порядке их запуска. Target и DSpark имеют отдельные
очереди и совместно используют ограниченный HostCache.

Новый путь работает с пустым RAM/GPU-кэшем. Owner резервирует VRAM-слоты внутри
существующих arena/managed бюджетов; GPU выбирает их по фактическим запросам.
Неиспользованный слот возвращается. Если между двумя снимками один ключ получил
вторую копию, сохраняется каноническая запись, а второй allocation становится
пустым бюджетированным слотом. Освобождать его под ещё работающим GPU нельзя.

При демоции owner ставит D2H перед возможной перезаписью GPU-адреса. Лимиты числа
и объёма демоций сохраняются. RAM публикуется при завершении своего контекста;
произвольный опрос CUDA event больше не публикует данные младшей ветки. Upload,
для которого уже пройден copy fence, сразу получает состояние ready, без нового
event в хвосте чужой работы.

Для RAM-заполнения owner заранее резервирует ограниченный набор свободных блоков
и допустимых жертв. Раннее окончание CPU-задания не добавляет новые жертвы посреди
I/O-запроса. Логические ссылки эпохи сохраняют снимок до FIFO-завершения контекста,
даже если service уже отпустил отдельные read leases. Это удержание ссылок,
без копирования весов. CUDA-backed освобождения вынесены из mutex HostCache;
I/O service не выделяет и не освобождает pinned/CUDA payload.

Ожидание GPU fetch ограничено: 2 с без прогресса, не более 16 с на операцию.
Прогресс подтверждается завершённой передачей chunk. Native Windows read в этом
пути имеет срок 1,5 с с отменой и дренированием OVERLAPPED. Старые пользователи
общего `expert_file.hpp` сохраняют прежний режим без этого срока.

## Численный контракт

Адаптивное размещение меняет набор экспертов, вычисленных CPU, по мере прогрева
кэшей. Нынешние квантованные CPU/GPU-ядра не побитно эквивалентны. Совпадение весов
не означает совпадения logits и sampled token IDs.

Запрос с явным seed теперь выполняет экспертов на GPU на всём протяжении запроса,
включая DSpark, переходы фаз и восстановление. В журнале есть
`STRATA_CPU_REQUEST lane=GPU reason=explicit_seed`. После запроса политика CPU
восстанавливается. Это обеспечивает один арифметический путь для проверенного
seeded restore; это не исправление арифметики CPU. Запросы без seed продолжают
использовать CPU lane. Длинный prefill сохраняет GPU-путь.

`auto + демоция` пока не является принятым численно воспроизводимым профилем.
Его провал после отмены воспроизведён и на сохранённой исходной сборке
`7610929f06f173f4f6b5aa15b14df1bc805779e65710a810afd588e3c9af056a`.
Поэтому закрытие транспортного этапа не означает исправления этого прежнего
ограничения. Сопоставление квантования активаций и арифметики CPU/GPU включено
первым пунктом этапа 3, до выбора новых быстрых ядер.

## Проверки и отвергнутые промежуточные варианты

Сборка `336a124680bf4716e81727930b4f6758a21867df7cdf748eab21b814e819e320`:

- 82/82 CTest за 427,70 с. Три последовательные MoE-ветки проверяют оборот
  кольца; IQ3_XXS, MXFP4 и Q8_0, окна 1/3/8, CUDA Graphs on/off, arena/managed,
  compact, cache/drop, возврат неиспользованных loans и коллизии admissions.
- CPU-пул проверен на 1/4/12/16 потоках. Протоколы проверяют многократный replay,
  уникальность задания, ошибки, отмену, rearm и завершение service.
- Управляемо замедленные передачи: шесть chunks с паузой 30 мс проходят при
  idle deadline 120 мс; остановившийся на 180 мс reader получает timeout.
  Это воспроизводимый тест протокола, не замер физически холодного SSD.
- Полный validator DSpark прошёл на 12 и 16 потоках без демоции: A→B→A,
  продолжение, fresh prefill, отмена prefill/decode, восстановление после отмены,
  24/24 seeded repeat и совпадение восьми greedy-сценариев с прежним контролем.
- Совмещение CPU lane и демоции в промежуточных сборках не прошло строгую проверку
  token IDs после восстановления либо сравнение с GPU-контролем. Эти прогоны
  сохранены как неуспешные; проверки validator не ослаблены.
- Диагностический capture сравнивал выбранные CPU-матрицы с исходными байтами GGUF:
  несовпадений не найдено. Этот режим добавляет I/O и не годится для замера скорости.

Первые модельные прогоны выявили две коллизии возврата loans: новая запись
сталкивалась с возвращённой старой, и наоборот. Оба случая исправлены и вынесены
в отдельные `deepseek4_cpu_expert_ring_cache_g0/g1` проверки. Ранний тест давления
RAM выявил отложенное освобождение после refresh; исправлено. Логи ошибок
сохранены вместе с принятыми результатами.

Сборка с публикацией по эпохам (`publication.exe`):
`4a8c4472d685f9c521232a3ce95676557085f543f7ebca7bb221b4c2d2152765`.
После изменения публикации по эпохам девять целевых native-проверок прошли за
55,33 с, включая отдельный запрет ранней публикации готовой демоции до её эпохи.
Затем общая серия прошла **82/82** за 430,56 с (`native-publication-final.log`).

| Проверка DSpark на сборке с публикацией по эпохам | Результат |
|---|---|
| Force, 12 потоков, без демоции | Полный validator пройден; 8/8 greedy-сценариев, seeded 24/24 |
| Force, 16 потоков, без демоции | Полный validator пройден; 8/8 greedy-сценариев, seeded 24/24 |
| Force, 16 потоков, демоция 16 МиБ | Собственные restore/cancel/seed прошли; 7/8 greedy-сценариев с GPU-контролем; общий validator **не пройден** из-за session_b |
| Auto, 16 потоков, демоция 16 МиБ | A→B→A прошёл, after_cancel изменился; validator **не пройден**, seeded не достигнут |
| GPU-проверка одной сессии вокруг hybrid auto+демоции и отмены | 24/24 одинаковых токенов; гибридные ответы при этом различаются |

Последняя строка — отдельная диагностика сохранённого состояния, не замена
проваленного гибридного validator. Два запроса с seed=123 и temperature=0
действительно включили GPU-политику (проверены два сообщения в логе).
Между ними работали hybrid B и отменённая hybrid-генерация; RAM restore
переиспользовал 371 из 372 prompt-токенов. Это свидетельство против ошибки
состояния в данном сценарии, а не доказательство побитной эквивалентности всех
CPU/GPU-вычислений. Первичная попытка с seed=0 отвергнута: Python-протокол
не передал этот seed, GPU-политика не включилась; её файлы `state-probe.*` сохранены.

В force-прогоне с демоцией фактически выполнены 1482 поворота кольца target и
62 draft; draft выполнил 48 CPU jobs. Опубликованы 297 демоций общим объёмом
1 044 795 392 байта, pending в конце равен нулю. Это проверка работающих веток,
а не только включённых флагов. Audit предыдущей сборки проверил 1188 CPU-матриц,
4 519 755 776 байт, без несовпадений с GGUF.

Физически холодный кэш ОС не сбрасывался. В force+демоции этой сборки H:
прочитал 140 615 680 байт всеми процессами, в auto — 32 624 640 байт. Не следует
называть эти короткие модельные проверки полностью холодным запуском. Управляемый
slow/stalled I/O проверен отдельно на уровне очереди; длительная нагрузка и 4096/8192
контекст остаются приёмкой полного решения на этапе 5.

## Включение для эксперимента

Итоговый executable (`experiment.exe` и `build-deepseek4/bin/strata-deepseek4.exe`):
`c084e442b9075fbf5e958afccab7f35c4f9acf79a1560893eed9b2ff2e0c8f52`.
Последнее изменение только в `main.cpp`: GPU-политика явного seed применяется,
когда CPU lane действительно включён. При CPU threads=0 сохраняется прежнее
управление фазами RAM-кэша. Ядра и транспорт совпадают с проверенными выше.

На этой итоговой сборке повторно пройден полный DSpark validator на 12 и 16
потоках без демоции (`dspark-release-12`, `dspark-release-threads16`): оба exit=0,
8/8 greedy-сценариев и 24/24 seeded repeat. Два GPU-only запроса с seed=123 также
совпали 24/24 между собой и с исходным GPU-only binary. В этих двух итоговых
DSpark-прогонах счётчик чтения H: всеми процессами дал 0 байт; это прогретые проверки.

Использованы `--expert-cpu-threads 12` (или 16),
`--expert-cpu-max-experts 1`, `--expert-cpu-policy force`,
`--expert-cpu-ram-mib 0`, pipeline и direct cache. Полные JSON каждого запуска
сохранены в артефактах. Ключевые переменные нового пути:

```text
STRATA_DS4_CPU_SHARED_RAM=1
STRATA_DS4_RAM_CACHE_MIB=2048
STRATA_DS4_RAM_RESIDENCY=1
STRATA_DS4_CPU_GPU_QUEUE=1
STRATA_DS4_GPU_FETCH_QUEUE=1
STRATA_DS4_CPU_CONTEXT_OVERLAP=1
STRATA_DS4_GPU_FETCH_CACHE_SLOTS=4
STRATA_DS4_GPU_FETCH_RAM_MIB=32
STRATA_DS4_RAM_POOL_MIB=32
```

В измеренных профилях также включены KEEP_RAM, RELEASE_RAM, RELEASE_WEIGHTS,
SNAPSHOT_PRUNE, EARLY_RETIRE и QUEUE_ASYNC_PARK; SNAPSHOT_OVERLAP и CONSUMER_HANDOFF
выключены. Новый двухконтекстный путь заменяет прежний частичный handoff при
CONTEXT_OVERLAP=1. `STRATA_DS4_RAM_DEMOTE_MIB=16` добавляет экспериментальную
демоцию с указанным выше численным ограничением.

## Скорость

Один последовательный контроль на указанной сборке, target-only, 68 фиксированных
IDs, префикс 36 и decode 32, четыре прохода с сохранением expert cache:

| Параметр | Один контекст | Два контекста |
|---|---:|---:|
| Полный workload без загрузки модели, с | 61,844 | 68,219 |
| Decode по 1 токену, среднее последних двух проходов, мс | 3138,86 | 4199,55 |
| Decode по 3 токена, среднее последних двух проходов, мс | 2262,31 | 3177,11 |
| CPU time процесса, с | 151,41 | 236,84 |
| Чтение H: всеми процессами, байт | 1 158 189 056 | 52 588 544 |

Условия: CPU 12, force cap=1, RAM 2 ГиБ, pinned/fetch reserve 32 МиБ,
GPU cache 15 ГиБ, cache slots=4, KEEP_RAM=1, release weights=1. Второй запуск
получил более прогретый файловый кэш; размещение и logits различаются.
Эта пара не доказывает отдельную стоимость кольца и не является оценкой
устойчивого ускорения. Выигрыша не получено, включать связку по умолчанию оснований
нет. Многотокенные ядра, калибровка и полное сравнение остаются этапами 3–5.
