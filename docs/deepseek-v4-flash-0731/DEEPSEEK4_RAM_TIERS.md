# Поколения и общий учёт RAM/VRAM

12 октября 2026. Продолжение этапа 1 из
[плана CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md).
Это основа безопасной очереди CPU-заданий. GPU-роутер и постоянный service thread
из этапа 2 ещё не реализованы. Производственный профиль остаётся GPU-only.

## Что изменено

`HostCache` присваивает новое поколение каждому заполнению внутри своего экземпляра. Оно относится к
публикации матрицы, а не к адресу allocation: повторное использование того же
pinned-буфера для другого источника получает другое поколение. CPU и прямой H2D
продолжают удерживать существующие leases без повторной упаковки весов.

Незавершённые заполнения теперь зарегистрированы по ключу «живой Source, смещение,
размер». Второй producer может доставить данные своему потребителю, но не получает
вторую резервацию того же ключа. Отмена, ошибка чтения и promotion запрещают позднюю
публикацию старого заполнения; его память остаётся учтённой до завершения владельца.

| Состояние | Значение |
|---|---|
| Absent | Доступной записи нет |
| Filling | Producer заполняет RAM; acquire не выдаёт адрес |
| Ready | Полная матрица опубликована |
| Held | RAM-матрицу удерживает потребитель |
| Transferring | Незавершённый H2D или D2H; готовность ещё не опубликована |
| Retired | Новые RAM-читатели запрещены, старые leases продолжают владеть данными |

Target и DSpark используют один HostCache и его реестр GPU-публикаций. Каждая
GPU-запись получает отдельный токен поколения. После H2D записывается CUDA event;
только успешная проверка event публикует Ready и разрешает удаление RAM-дубликата.
Удаление GPU-записи отзывает её токен перед переиспользованием адреса. Если другая
GPU-копия той же матрицы ещё жива, запрет нового RAM-дубликата сохраняется.

Токен GPU-резидентности сам не владеет CUDA allocation. За его время жизни
по-прежнему отвечают GPU-кэш, direct-reader leases и зависимости CUDA streams.
Будущая GPU-таблица должна удерживать свой снимок до подтверждения потребителя;
копирование в неё сырых адресов без такого удержания недопустимо.

## Ограниченная демоция GPU → RAM

При вытеснении можно сохранить матрицу в RAM. Она должна пройти обычную частотную
политику HostCache, уместиться в его бюджете и не иметь готовой RAM-копии либо другой
GPU-копии с политикой удаления дубликатов. Prefill не запускает демоцию и не обучает
частоты decode.

Ограничение — два незавершённых D2H на общий HostCache и заданный лимит их байтов.
Назначение D2H выделяется непосредственно из RAM-пула; отдельной промежуточной
копии нет. Pending учитывается вместе с активными, удерживаемыми, retired-блоками
и свободным pinned-пулом. Существующие рабочие буферы pipeline/CPU сохраняют свои
отдельные фиксированные лимиты; системная проверка запаса памяти учитывает весь
процесс и доступную RAM, включая влияние файлового кэша ОС.

D2H ставится в stream владельца после старых чтений и до fence переиспользования.
При передаче allocation от target к draft зависимость второго stream включает и
эту D2H-копию. После завершения event данные можно опубликовать в RAM. Новая
promotion той же матрицы отменяет старую публикацию демоции. При разрушении очереди
буфер удерживается до завершения DMA, затем ещё не опубликованное заполнение
отменяется. Обычный drain может опубликовать готовые неизменяемые веса: отмена
пользовательского запроса не требует удаления таких матриц из кэша.

## Переключатели

Все новые режимы выключены по умолчанию; профиль сервера не менялся.

| Переменная | Назначение |
|---|---|
| `STRATA_DS4_RAM_RESIDENCY=1` | Включить GPU-поколения и события готовности при наличии RAM-кэша |
| `STRATA_DS4_RAM_DROP_GPU=1` | Удалять RAM-дубликаты; теперь автоматически включает реестр |
| `STRATA_DS4_RAM_ON_BYPASS=1` | Существующее отложенное RAM-admission; тоже включает реестр |
| `STRATA_DS4_RAM_DEMOTE_MIB=64` | Разрешить до 64 МиБ незавершённых демоций; включает реестр и pinned storage |
| `STRATA_DS4_RAM_CACHE_MIB` | Общий бюджет HostCache, включая pending демоций |
| `STRATA_DS4_RAM_POOL_MIB` | Лимит свободных allocations внутри этого бюджета |

`STRATA_RAM_TIERS` отдельно записывает GPU-residency, ожидающие публикации,
отклонённые дубликаты, устаревшие заполнения и демоции. `d2h_bytes` — реально
поставленные в очередь байты данного backend; `demotion_bytes` — опубликованные
байты общего RAM-кэша. Они могут различаться при отмене/повторной promotion.

## Модель: корректность и стоимость

Target-only, те же 68 входных IDs: префикс 36 и decode 32 токенов, отдельные режимы
по одному и по три токена. CUDA Graphs включены. Target GPU-cache 15360 МиБ,
pipeline 16 МиБ, два reader, frequency policy. Ниже — среднее последних двух
из четырёх проходов процесса, единица измерения — миллисекунды decode.

Сначала проверен только реестр: RAM 2 ГиБ, CPU 12 потоков/force, прежние политика
хранения и арифметика; демоция и удаление дубликатов выключены. Серия A/B/B/A,
где A — сохранённая сборка этапа 0, B — новая с реестром.

| Вариант | По 1 токену | По 3 токена |
|---|---:|---:|
| A, прежний CPU12 | 1767,14 | 1210,83 |
| B, CPU12 с поколениями GPU | 1761,94 | 1208,66 |

Разница около −0,3% / −0,2%; убедительного изменения скорости эта короткая серия
не показывает. Хэши всех 12 наборов полных logits новой сборки совпали с CPU-контролем
в обоих повторах B. SSD: 0 байт за каждый процесс. К завершению запросов очередь
GPU-публикаций пуста; в каждом B опубликовано 12866 GPU-поколений.

Затем включены direct H2D, RAM-on-bypass, удаление GPU-дубликатов, pinned pool
64 МиБ и демоция до 64 МиБ. Это другой профиль хранения, поэтому его отличие
от таблицы выше нельзя приписать только демоции. Для каждого RAM-бюджета
проверены CPU0 и CPU12/force. Рабочий GPU-only без RAM проверен до и после серии
реестра; в таблице среднее этих двух контролей.

| Профиль | По 1 токену | По 3 токена | D2H демоций за весь процесс, ГиБ |
|---|---:|---:|---:|
| Рабочий GPU-only, без RAM | 1635,47 | 1086,13 | 0 |
| RAM 2 ГиБ, CPU0 | 1863,07 | 1238,42 | 2,61 |
| RAM 2 ГиБ, CPU12 | 1851,52 | 1405,80 | 2,02 |
| RAM 4 ГиБ, CPU0 | 2069,15 | 1370,57 | 3,92 |
| RAM 4 ГиБ, CPU12 | 2049,13 | 1445,93 | 4,48 |

Оба CPU0-профиля дали 12/12 совпадений хэшей полных logits с GPU-контролем. CPU12 меняет
размещение вычислений и округление; совпадение его logits с GPU-only не заявляется.
В CPU12 `pack_us=0`, отдельный private CPU weight cache занимает 0 байт: используются
готовые матрицы общего HostCache.

Отдельный контроль отключает только демоцию при RAM 2 ГиБ и CPU0, сохраняя остальные
настройки. Два процесса дали в среднем 1850,78 / 1242,20 мс против
1863,07 / 1238,42 мс с демоцией. Разница +0,66% / −0,30% слишком мала для вывода
о выигрыше по этой серии. Хэши полных logits совпали в обоих контролях. Демоция остаётся
выключенной по умолчанию; большее число готовых RAM-матриц само по себе не ускорило
полный запрос. Каждый полный tier-профиль измерен одним процессом, независимых
серий и доверительных интервалов для него нет.

Во всех четырёх tier-профилях `pending=0`, `demotion_pending=0`, `oom=0` в конце;
учтённая RAM укладывается в 2/4 ГиБ. Минимум доступной системной памяти во время
серий — 59,78 ГиБ. GPU0-процессы не читали SSD. CPU12 с RAM 2/4 ГиБ прочитал
соответственно 121327616 / 83140608 байт за **все** проходы процесса; эти числа
не локализуют чтение в прогретом decode.

Артефакты: `registry-valid/`, `tiers-{2048,4096}-cpu{0,12}/`, `no-demotion/`;
в каждом есть конфигурация, SHA executable, точные IDs, сырые logits-хэши и логи.
Первая прерванная попытка `registry/` имела неверный счётчик физического диска и
исключена; все приведённые SSD-числа относятся к `PhysicalDrive6` (H:).

## DSpark и состояние сессий

`validate_deepseek4_speculative.py --tokens 8` прошёл с DSpark Q8_0, CPU0,
RAM 2 ГиБ, demotion/pool по 64 МиБ и остальными настройками tier-профиля.
Проверены переключение сессий и восстановление ответа, продолжение активной
сессии и её восстановление, полный повторный prefill, одиночный токен без draft,
отмена prefill/генерации и последующее восстановление, seeded sampling и повтор.
`passed=true`, `full_prefill_identical=true`; результат и лог —
`dspark-validation.json` / `dspark-validation.log`.

Известное расхождение shared CPU lane при seeded repeat после restore этим этапом
не объявляется исправленным. Критерий приёмки всей связки остаётся в этапе 5 плана.
