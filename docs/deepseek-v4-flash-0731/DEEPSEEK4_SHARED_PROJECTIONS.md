# Проекции shared expert: gate/up, SwiGLU и down

11 октября 2026. Windows, RTX 5090 32 ГиБ, Ryzen 9950X, RAM 128 ГиБ,
CUDA 13, драйвер 581.80. DeepSeek-V4-Flash-0731 UD-Q3_K_XL, четыре GGUF
на H: (Samsung 990 PRO 4 ТБ, PhysicalDrive6).

Продолжение [проверки длинного router](DEEPSEEK4_ROUTER_LONG_PREFILL.md).
На одинаковом входе FFN выделены независимые расхождения gate/up и down
shared expert. Экспериментальный фиксированный MMQ выравнивает эту ветку
на проверенной позиции модели. Routed MoE всё ещё различается; полного
равенства logits нет. Рабочий профиль этим экспериментом не заменяется.

## Реализация

`STRATA_DS4_SHARED_MMQ` действует только при
`STRATA_DEEPSEEK_PROJECTION_EXPERIMENT=ON`, по умолчанию выключен:

- `1`: фиксированный MMQ для shared gate/up;
- `2`: тот же путь для gate/up/down.

Использован существующий частный helper фиксированного Q8_0 MMQ:
постоянный размер плитки и разбиение K, штатные GPU-квантизация и device math.
В этом этапе J=64, splits=4. Отдельного device-ядра не добавлялось.

Границы: NVIDIA Ampere и новее, Q8_0-веса, F32-вход/выход, обычный precision,
плотные двумерные тензоры, 1–4096 токенов, вес без `view_src`, точные суффиксы:

| Матрица | K × M |
|---|---:|
| `.ffn_gate_shexp.weight` | 4096 × 2048 |
| `.ffn_up_shexp.weight` | 4096 × 2048 |
| `.ffn_down_shexp.weight` | 2048 × 4096 |

В штатном пути на 371/409 токенах работают MMQ, на 1/5 — MMVQ. Помимо
разного порядка редукции у этих путей различается точность scale при
квантизации активаций. Фиксированный путь сохраняет одну арифметику.

Одного изменения MUL_MAT недостаточно: на одном токене CUDA backend может
объединять gate/up/GLU в MMVQ. Один и тот же предикат в
`shared_projection.hpp` теперь используется для выбора матричного ядра
и отказа от fusion для подходящих проекций. Предикат подключён также к
выбору MMVQ fusion-путей со scale/bias; исследуемая цепь модели без них.
Остальные формы и имена сохраняют штатную
обработку. Код подключается к создаваемой CMake копии; закреплённый
`third_party/llama.cpp` не меняется, его SHA-256 проверяется.

## Изолированные GPU-проверки

Новый `test_shared_projection.cpp`: **51 матричный сценарий, 14 цепочек,
34 проверки границ**. Для трёх матриц взяты размеры пакета
1/2/3/4/5/8/9/16/17/32/64/128/371/409/512/1024/4096.
Проверены выбранные столбцы против одиночного CUDA-вычисления и независимого
FP64-эталона, полный общий префикс 371/409, нулевой токен среди ненулевых,
неподходящие имена, суффиксы, K/M, тип, precision, strides, weight view и
пакет 4097. Mode 1 для down сохраняет штатный результат.

Эталон матриц использует декодированные сохранённые веса и исходный F32-вход.
Дополнительно считаются эталоны с int8-активациями и half/float scale.
CPU выполняет только проверку; все исследуемые операции запускаются на CUDA.
Максимальная ошибка фиксированного результата относительно исходного FP64
на этих данных — **0,0432067704**. Относительно эталона с float scale —
0,0009512010; здесь возможны разные решения на границе округления int8.
Все выбранные столбцы нового режима побитово равны serial.

| Весь общий префикс 371/409 | Различающихся элементов, штатный | Max Δ, штатный | Новый путь |
|---|---:|---:|---:|
| Gate | 591415 | 3,8146973e−6 | 0 |
| Up | 591176 | 3,8146973e−6 | 0 |
| Down | 1065304 | 2,3841858e−6 | 0 |

Цепь gate/up → SwiGLU clamp → down проверена на 1/2/5/9/371/409/4096
токенах с limit=10 из метаданных модели и limit=0,3 для активного clipping.
Gate и up имеют разные синтетические веса. Сравниваются целый граф,
четыре отдельные GPU-операции, выбранные serial-столбцы и весь префикс.
В новом режиме эти результаты совпали побитово. Независимый FP64-расчёт
SwiGLU на наблюдаемых входах дал max Δ **6,1648880e−6**.
Отдельная проверка заполняет промежуточные gate/up значениями NaN:
штатный объединённый граф на одном токене их не записывает, а новый путь
записывает конечные значения. Это подтверждает, что тест действительно
попадает в fusion и проверяет его обход. Проверка прошла при обоих limit.

Первая версия теста использовала постоянный допуск 0,25 для down после
SwiGLU; это не учитывало увеличившийся диапазон активаций. Вместо этого
добавлена граница ошибки для каждой выходной строки: сумма модулей весов,
умноженных на погрешность int8-квантизации каждого блока входа, с запасом
для half-scale штатного пути и накопления F32. Максимальная фактическая
ошибка составляет **5,76% этой границы**. Относительно FP64 с int8-входом
и float scale max Δ — **9,5217396e−6**. Исходный неуспешный прогон сохранён
как `fixture-j64-s4.json`, повтор — `fixture-final-j64-s4.json`, оба с общим
префиксом имён этого этапа.

## Локализация на модели

Использованы прежние 410 token IDs: полный префикс 409 против префикса 371,
одиночных токенов 371–403 и пакета 404–408. Последний токен 409 отдельно
в обоих путях. Остальные параметры: MMQ=5/J64/4, FA=4, HCA=1, HC=3,
router sample=3, прежний короткий router=1, MMVQ=2, TF32 off.

На row 371 вход FFN, router, top-k и веса маршрутов уже побитово совпадают.

| Узел первого слоя, max Δ | Shared=0 | Только gate/up | Gate/up/down |
|---|---:|---:|---:|
| Gate | 0,000284672 | 0 | 0 |
| Up | 0,000338018 | 0 | 0 |
| SwiGLU / вход down | 0,000382423 | 0 | 0 |
| Down | 0,001514137 | 0,000228584 | 0 |
| Routed MoE | 0,044727374 | 0,044727374 | 0,044727374 |
| Сумма FFN | 0,044744875 | 0,044739679 | 0,044727374 |
| Выход слоя | 0,022314658 | 0,022312066 | 0,022305930 |

Режим gate/up подтверждает собственное расхождение down: его вход уже
одинаков, а выход ещё различается. Полный режим выравнивает shared expert;
вся разница суммы FFN на этой позиции теперь равна разнице routed MoE.
На row 282 (два больших пакета) все наблюдаемые узлы первого слоя, включая
FFN и выход слоя, теперь побитово равны. На последнем токене 409 наблюдаемые
узлы первого слоя также совпали. Во всех пяти probes observer,
snapshot/restore и replay дали max Δ = 0.

| Режим | Max Δ конечных logits | RMS Δ | Argmax full / segmented |
|---|---:|---:|---|
| Shared=0 | 2,676424503 | 0,470839858 | 539 / 1 |
| Только gate/up | 3,205773830 | 0,638154317 | 1 / 1 |
| Gate/up/down | 3,050496578 | 0,613766569 | 1 / 1 |

Совпадение argmax не означает совпадения всех logits или улучшения качества
ответов. Локальная коррекция shared expert не уменьшила общую разницу logits
на этой истории. В probes контролируются observer, snapshot/restore и replay;
их времена не используются для оценки скорости.

## Проверки модели

В экспериментальной сборке прошли **32/32 CTest** за 116,87 с. Проверки
сессий без DSpark и с ним прошли: A/B/A, восстановление и продолжение,
отмена, следующий запрос, одиночный токен и повторяемый sampling.
Во всех восьми сравниваемых greedy-сценариях token IDs DSpark совпали
с обычным запуском того же численного режима. **29 проверок причинности
DSpark** дали max Δ logits = 0.

При этом `full_prefill_identical=false` в обоих запусках: ответы полного
prefill и продолжения различаются уже с первого выходного токена.
Успех проверок сессий не означает устранения этого известного расхождения.

## Скорость модели и ресурсы

Последовательная серия A/B/B/A, один архивный `final.exe`. A — shared=0,
B — shared=2; остальные численные эксперименты и настройки одинаковы.
DSpark и трассировка выключены. В каждом процессе: prefill 4096,
отдельный decode 32 токенов, четыре закэшированных повтора и ещё один
полный prefill 4096. Кэш экспертов 15360 МиБ, staging 16 МиБ,
pipeline=1, readers=2, policy=frequency, CRT, early refill=0,
prefill cache hits=1, slabs 16 МиБ, один поток управления.

| Запуск | Медиана последних двух повторов, ток/с | Все четыре повтора, ток/с | Полный прогретый prefill, мс |
|---|---:|---:|---:|
| A1 | 20,275 | 19,339 | 9578,62 |
| B1 | 19,769 | 19,094 | 9621,54 |
| B2 | 19,841 | 19,194 | 9658,70 |
| A2 | 20,427 | 19,713 | 9580,93 |
| Медианы A → B | **20,351 → 19,805** | **19,526 → 19,144** | **9579,775 → 9640,120** |

Поздние повторы медленнее на **2,68%**, все четыре — на **1,96%**;
время prefill выросло на **0,63%**. Внутри каждого режима повторные ответы
совпадают. Между A и B decode различается с 26-го токена; output IDs после
prefill совпадают. Поэтому сравнение decode включает разные маршруты
экспертов, а не только стоимость новых ядер. Ускорение не подтверждено.

Во всех 16 закэшированных decode и четырёх полных прогретых prefill
физическое чтение H: равно **0 байт / 0 операций**. В первых запросах
чтения есть; ноль не распространяется на холодный запуск или другие тексты.
Медиана CPU процесса по запускам — 4,52–4,94% всего 32-поточного CPU,
максимум 6,28%; пик общего CPU в этих выборках — 11,6%.
Пик занятой VRAM по NVML — 28663 МиБ. Сбор метрик раз в две секунды
может пропускать короткие пики. Во всех **376** записях аудита probes,
валидации и замеров `cpu_compute_nodes=0`: CPU обслуживает данные
и запуск работы, граф модели выполняется на GPU.

## Следующий участок

На row 371 одинаковы вход FFN, router, выбранные ID, веса маршрутов и
shared-ветка. Дальше нужно отдельно наблюдать входы и выходы routed
gate/up/down `MUL_MAT_ID`, включая ID и strides, затем сравнить реальную
раскладку с изолированным GPU-тестом. Текущий селектор `@weight:` принимает
обычный `MUL_MAT`; его нельзя считать проверкой внутренних матриц MoE.
Перед изменением routed-ядер необходимо снова проверить нулевое влияние
observer, snapshot/restore и replay. Полное равенство logits и ускорение
DSpark этим этапом не достигнуты.

Продолжение: [routed MUL_MAT_ID и короткий MMQ](DEEPSEEK4_ROUTED_MMQ.md).
Новый этап отдельно контролирует влияние наблюдения на fusion.
