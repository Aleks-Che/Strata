# О3: частота и цена вытеснения в кэше target

14 октября 2026. Продолжение [demand admission для DSpark](DEEPSEEK4_TRANSFER_O3_DEMAND.md).

Следующая серия: [RAM-защита по фактическому CPU-назначению](DEEPSEEK4_TRANSFER_O3_RAM.md).

В одной A/B/B/A ранжирование target со штрафом 1 и окном 256 дало
**10,80 → 13,01 ток/с (+20,44%)**, wall **−12,03%**, общий H2D **−31,22%**
относительно лучшего предыдущего варианта очереди. Короткий N0-сценарий теперь
проходит критерий общего H2D относительно L0. Рабочий GPU-only всё ещё быстрее;
это не переключение рабочего профиля и не закрытие всех пунктов О3.

## Политика

Прежний demand-путь брал первую подходящую запись LRU. Теперь opt-in
`STRATA_DS4_GPU_FETCH_DEMAND_RANK=1` сначала ранжирует реальные промахи по
убывающей частоте. Среди безопасных слотов точного размера выбирается запись
с наименьшей оценкой цены вытеснения, при равенстве сохраняется порядок LRU.
Меняется только приоритет допуска: порядок запроса, scratch-индексы и порядок
вычислений и суммирования на GPU сохраняются.

Оценка цены — `(частота жертвы + margin) × bytes`, для пустого слота — 0.
Допуск разрешён, если она не выше `частота входящей матрицы × bytes`.
Частота входящей матрицы включает текущий доступ, как и прежняя политика.
`margin=1` добавляет цену одной полной повторной загрузки и не позволяет
постоянно менять равноценные по истории матрицы только за счёт текущего промаха.
Это относительная оценка в байтах с весом частоты, **не измеренная задержка,
вероятность следующего обращения или прогноз времени SSD**.

Частоты взяты из существующей истории с затуханием. Проверяются прежние условия:
точный размер с padding, `KEEP_RAM`, полный выбранный маршрут, direct leases,
защита других контекстов и отложенных читателей. При отказе остаётся scratch;
при отсутствии подходящего кандидата можно выделить свободный слот в пределах
старого бюджета. Демоция и публикация адресов сохраняют прежний протокол DMA.

Настройки с префиксом `STRATA_DS4_`:

| Настройка | Значение по умолчанию | Назначение |
|---|---:|---|
| `GPU_FETCH_DEMAND_RANK` | 0 | Включить ранжирование; требует demand, DMA и frequency policy |
| `GPU_FETCH_DEMAND_RANK_MIN_CACHE_MIB` | 0 | Нижняя граница бюджета для ранжирования |
| `GPU_FETCH_DEMAND_RANK_MARGIN` | 1 | Штраф 0–16 за вытеснение непустого слота |
| `GPU_FETCH_DEMAND_RANK_SCAN` | 64 | Просмотреть 8–1024 позиции LRU на промах |
| `GPU_FETCH_REFAULT_AUDIT` | 0 | Считать повторные промахи после замен GPU-fetch |

В сравниваемом варианте demand включён для обоих кэшей, его верхняя граница
бюджета снята (`GPU_FETCH_DEMAND_MAX_CACHE_MIB=0`), но rank применяется только
при бюджете ≥1025 МиБ. Так target 15360 МиБ получает новую политику, DSpark
1024 МиБ сохраняет проверенный простой demand. Current victims выключен.

Код: [gpu_fetch_cache.inc](../../backends/deepseek4/gpu_fetch_cache.inc),
[gpu_fetch_lane.cuh](../../backends/deepseek4/gpu_fetch_lane.cuh),
[cuda_expert_transfer.inc](../../backends/deepseek4/cuda_expert_transfer.inc).

## Диагностика повторных загрузок

Audit хранит только ключи последних 8192 фактических замен непустых GPU-fetch
слотов. Первое последующее GPU-fetch miss по такому ключу прибавляет bytes
в `fetch_refault_bytes` и удаляет ключ из истории. Номера поколений защищают
повторно добавленный ключ от удаления старой записью FIFO. Дополнительных
матриц или GPU-аллокаций нет. По умолчанию диагностика выключена.

Это ограниченная история замен данной очереди, не полный учёт всех вытеснений
движка. Вытеснение могло произойти в предыдущем запросе, а повторный промах —
в текущем. Поэтому нельзя трактовать отношение refault bytes к replaced bytes
одной фазы как долю именно её замен. `rank_cost` также является суммой оценок,
а не фактически переданными байтами. `rank_rejected` считает промахи без допуска,
при просмотре которых встретился более дорогой слот; проверка цены предшествует
проверке защиты читателей, поэтому этот счётчик не отделяет цену от всех других
причин отказа. Трафик берётся из `h2d_bytes`.

Audit включён у обоих вариантов. Одни EXE, профиль CPU, входы и бюджеты.

private до 36,33 ГиБ, доступная RAM 52,72–53,06 ГиБ, VRAM 31076–31120 МиБ,

8,703 → 7,594 с (−12,74%). H2D снова 37,340 → 25,681 ГиБ, IDs и acceptance
совпали. Следовательно, выигрыш сохраняется без диагностической истории.
Из одной такой пары нельзя точно выделить собственную стоимость audit.

## Проверки корректности

Прошли **23 запуска CTest, 21 разный тест**: исходная очередь и demand,
новое ранжирование, графы on/off, early sources on/off, DMA window,
arena/managed, IQ3_XXS/MXFP4/Q8_0, защита выбранного эксперта при замене,
освобождение кэша и переключение контекстов. Для frequency-сценария тест
замещения сделан тесным (1 МиБ) с повторным спросом на отсутствующего эксперта;
это заставляет выполнить реальную замену. Отдельная проверка с запасом памяти
требует сохранить более частые старые матрицы. Прежние проверки демоции
неранжированного demand сохранены.

Fixed-history на модели: одинаковые **6 префиксов и 86 шагов**, совпали hash
полного вектора logits и argmax с совместимым GPU-only. Rank 1 / 256 включён
для target, `KEEP_RAM=1`, демоция 16 МиБ, context overlap 1. Реально выполнены
**33 CPU jobs / 34 rows**, prefill CPU rows = 0. Более редкая CPU-работа в этом
прогоне не является отдельным доказательством ускорения CPU lane.

Lifecycle с тем же rank и current victims 1 прошёл A→B→A, restore/extension,
сравнение с полным prefill, отмену prefill/decode и seeded repeat.
**182 CPU jobs / 266 rows**, runtime profile generation **0→1**. Все восемь
greedy-сравнений имеют одинаковые input/output IDs с сохранённым совместимым
GPU-only контролем. В логе подтверждены вызовы rank и фактическая демоция.
Прежний отдельный вопрос lossless batch/serial DSpark этим опытом не закрыт.

Во всех 15 скоростных процессах совпали IDs и acceptance; в поздних prefill и
decode не было CPU-заданий, физические чтения H: равны нулю. Сохранены EXE,
профиль, конфигурации, запросы, JSON, trace, логи, исходники, `target-only.diff`
относительно прошлого опыта и SHA256 manifest. Неудачные первые запуски
тестовых сценариев тоже оставлены в каталоге артефактов. Предыдущие архивы
не перезаписывались.

## Старый транспорт и GPU-only

Одиночные контроли на той же сборке и manifest, после двух прогревов:

| Режим | Decode, ток/с | Wall, с | CPU-seconds | H2D decode, ГиБ |
|---|---:|---:|---:|---:|
| L0: старый транспорт, CPU-инфраструктура, jobs=0 | 12,285 | 7,922 | 12,469 | 31,680345 |
| G: совместимый GPU-only | 14,198 | 7,203 | 9,594 | 31,680345 |

В rank-связке общий H2D уже **на 18,94% ниже L0**. Результат показан отдельно: у L0 target
29,646420 ГиБ, draft 2,033925 ГиБ; у rank — 22,970564 и 2,710516 ГиБ.
У DSpark по-прежнему есть 0,677 ГиБ лишнего H2D, компенсированные снижением
target. Поэтому прохождение общего порога не означает оптимальность каждого
кэша или всех сценариев.

GPU-only остаётся быстрее при большем H2D: остаток задержки нельзя объяснять
только количеством переданных байтов. Следующие направления — эффективность
staging/DMA (О2), цена пустых CPU-веток и обслуживания очередей (О4), а также
защита RAM по фактическому CPU-назначению (незакрытая часть О3). Длинные
4096/8152-токенные тесты, Linux и Qwen в этой серии не выполнялись.
