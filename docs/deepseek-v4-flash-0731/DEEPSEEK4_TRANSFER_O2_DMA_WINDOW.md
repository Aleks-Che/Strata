# О2: несколько DMA-передач в полёте

13 октября 2026. Продолжение [первого DMA-прототипа](DEEPSEEK4_TRANSFER_O2.md)
и [плана оптимизации подкачки](DEEPSEEK4_TRANSFER_OPTIMIZATION_PLAN.md).

Окно DMA реализовано и проверено на DeepSeek-V4-Flash-0731 UD-Q3_K_XL +
DSpark Q8_0. При одинаковых решениях кэша повтор A/B/B/A дал **8,15 → 9,01
ток/с, +10,55%** относительно последовательного owner DMA с ранним чтением.
Полное время двух измеряемых запросов уменьшилось на 7,06%, CPU-seconds —
на 9,02%. Это локальное улучшение экспериментального транспорта; рабочий
GPU-only в отдельном контрольном процессе той же сборки дал 14,07 ток/с.

В микротесте прямой источник в pinned RAM достиг 97,8% пропускной способности
DMA-контроля. Путь через staging достиг 84,8%; критерий О2 «не ниже 90%»
для него пока не выполнен. Производственные настройки не изменены.

## Что изменилось

В [gpu_fetch_queue.cuh](../../backends/deepseek4/gpu_fetch_queue.cuh)
добавлено кольцо до восьми опубликованных дескрипторов копирования.
Владелец CUDA stream ставит несколько `cudaMemcpyAsync` подряд и проверяет
завершения через отдельные events. Больше не требуется синхронно завершать
каждый чанк перед постановкой следующего.

Это несколько незавершённых передач в одном CUDA stream, а не восемь
физических DMA-движков. Перед матрицей остаётся fence маршрута и предыдущих
читателей общего scratch. I/O-service по-прежнему не вызывает CUDA API.

Источники удерживаются до фактического завершения DMA. Для каждого staging-
сегмента сохраняются слот очереди и номер использующей его передачи;
перезапись разрешена только после подтверждения этой передачи. Подтверждения
идут по порядку. Исключение service после публикации нескольких чанков не
завершает запрос до их обработки; timeout не освобождает источник живого DMA.

Полезная staging-память осталась **4 МиБ на очередь**: два allocations по
2 МиБ. В новом режиме их можно делить на четыре сегмента по 1 МиБ либо восемь
по 512 КиБ. Добавились небольшие структуры дескрипторов и CUDA events.
Увеличение числа сегментов не увеличивает резерв pinned payload.

Экспериментальные настройки:

| Переменная | Значение для проверенного кандидата | По умолчанию |
|---|---:|---:|
| `STRATA_DS4_GPU_FETCH_DMA` | 1 | 0 |
| `STRATA_DS4_GPU_FETCH_EARLY_SOURCES` | 1 | 0 |
| `STRATA_DS4_GPU_FETCH_DMA_DEPTH` | 8 | 1 |
| `STRATA_DS4_GPU_FETCH_DMA_STAGE_SLOTS` | 4 | 2 |

Глубина ограничена диапазоном 1–8; число staging-сегментов нормализуется до
2/4/8. При depth=1 используется прежний последовательный DMA, при DMA=0 —
прежний SM-путь. Эти настройки применяются внутри включённой GPU fetch queue.
Счётчики `copies`, `peak_inflight`, `stage_reuse_waits`, `stage_slots` добавлены
в строку `STRATA_GPU_FETCH_TRANSPORT`.

## Микротест транспорта

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, Windows, CUDA 13.0.
Под нагрузкой PCIe Gen3 x16. Тест: 1/6 матриц по 2/4/8 МиБ, три прогрева,
12 измерений, проверка payload. Ниже медиана для **6×4 МиБ**, ГБ/с в десятичных
единицах; в стоимость очереди входят её управление и staging-копирование.

| Режим | ГБ/с |
|---|---:|
| Прямой DMA-контроль | 14,108 |
| SM-очередь, готовый pinned RAM | 11,788 |
| Последовательный owner DMA, pinned RAM | 12,619 |
| DMA depth=2, pinned RAM | 12,988 |
| DMA depth=4, pinned RAM | 13,618 |
| DMA depth=8, pinned RAM | **13,801** |
| Последовательный owner DMA, staging 2×2 МиБ | 11,090 |
| DMA depth=8, staging 2×2 МиБ | 10,987 |
| DMA depth=4, staging 4×1 МиБ | 11,819 |
| DMA depth=8, staging 4×1 МиБ | **11,966** |
| DMA depth=8, staging 8×512 КиБ | 11,661 |

Само увеличение глубины при двух staging-буферах не помогло. Четыре сегмента
дали лучший измеренный staging-результат; восемь добавили слишком много мелких
копий и в этой серии были медленнее. У прямого RAM-источника нет промежуточного
заполнения staging и ожидания его повторного использования.

Отдельно проверены write-combined staging allocations в изолированной копии
микротеста: depth=8/slots=4 дал 11,735 ГБ/с против 11,966 у обычных allocations.
Ускорения нет, изменение отклонено. Такие allocations также не удовлетворили
нынешнему требованию одинаковых host/device UVA-адресов для SM-пути; проба
после этого была ограничена owner DMA. Основной код этого изменения не содержит.

## Модель: одинаковые маршруты и решения кэша

Одна сборка и свежий замороженный CPU-профиль, 12 потоков. Контекст 8192;
GPU-кэши target/DSpark 15360/1024 МиБ, общий pinned RAM cache 2048 МиБ,
`draft-max=2`. Каждый процесс: четыре свежих запроса по 15 входных и 32 выходных
токена; первые два прогревают кэши. Ниже последние два запроса каждого процесса.

Для изоляции транспорта во всех этих конфигурациях выключены
`GPU_FETCH_KEEP_RAM`, `RAM_DEMOTE_MIB` и `CPU_CONTEXT_OVERLAP`. Это контроль,
а не новая принятая политика RAM. CPU budget=0,01 мкс; фактические jobs/rows=0.
Раннее чтение включено и в последовательном DMA, и в кандидате.

Предварительный выбор:

| Режим | Decode, ток/с | Полные два запроса, с |
|---|---:|---:|
| depth=1, slots=2 | 8,216 | 10,515 |
| depth=8, slots=2 | 8,246 | 10,484 |
| depth=8, slots=4 | 9,050 | 9,750 |
| depth=4, slots=4 | 9,147 | 9,641 |

Одиночный результат depth=4 не доказывает превосходства над depth=8.
Для повторной проверки выбран depth=8/slots=4 с лучшим прямым RAM-путём.
Порядок повтора: последовательный → окно → окно → последовательный.

| Режим | Decode двух процессов, ток/с | Среднее decode | Среднее полное время двух запросов, с | Средние CPU-seconds |
|---|---|---:|---:|---:|
| Последовательный DMA | 7,935 / 8,360 | 8,148 | 10,6095 | 25,5625 |
| DMA depth=8, slots=4 | 9,045 / 8,969 | **9,007** | **9,8600** | **23,2578** |

Совпали IDs всех четырёх ответов, а также счётчики **всех четырёх запросов
по фазам**: hits/misses/admissions, H2D/D2D/D2H, file/mmap bytes, RAM GPU bytes,
CPU jobs/rows. Последние два decode передают 44,255 ГиБ H2D:
target 34,949 и DSpark 9,306. Физическое чтение диска модели H: в измеряемых
запросах нулевое. При этом был фоновый I/O другого диска PhysicalDrive3;
система не объявляется полностью свободной от фоновой нагрузки.

На обоих backend журнал фиксирует `peak_inflight=8` вместо 1. Суммарный
owner DMA wait за весь процесс из четырёх запросов снизился в среднем
с 15,574 до 13,335 с. Это время ожидания, включающее подготовку источников;
оно не является отдельной величиной, которую можно прибавлять ко времени
запроса, и относится к другой фазе учёта, чем таблица позднего decode.

## Модель с прежней RAM-защитой и реальными CPU-заданиями

Дополнительные одиночные пары той же сборки, раннее чтение включено:

| Режим | Decode, ток/с | Полные два запроса, с | Decode H2D, ГиБ | CPU jobs / rows в decode |
|---|---:|---:|---:|---:|
| RAM-защита, CPU jobs=0, последовательный DMA | 6,766 | 12,266 | 59,977 | 0 / 0 |
| RAM-защита, CPU jobs=0, окно DMA | 7,392 | 11,453 | 59,977 | 0 / 0 |
| Реальная CPU-ветка, последовательный DMA | 6,851 | 12,047 | 53,831 | 606 / 1153 |
| Реальная CPU-ветка, окно DMA | 7,488 | 11,344 | 53,831 | 606 / 1153 |
| G: GPU-only с совместимой арифметикой | 14,071 | 7,234 | 31,680 | 0 / 0 |

Все выходные IDs совпали. В каждой из двух пар совпали все перечисленные
счётчики по всем запросам и фазам. Полезная CPU-работа в последних двух decode
реального гибрида одинакова: target 538 jobs / 1029 rows, DSpark 68 / 124.
Это дополнительная проверка, а не приёмка настройки CPU по этапу О5.

Несмотря на локальный прирост, сохраняется лишний H2D. Вариант с RAM-защитой
и нулём CPU-заданий передаёт 59,977 ГиБ против 31,680 у G в тех же поздних
decode. У DSpark при RAM-защите здесь ноль новых GPU admissions, тогда как
у G — 114. Исправление правил замещения и RAM-защиты остаётся задачей О3;
окно DMA этих правил не меняет.

## Проверки и ограничения

Пройдены 13 CTest: SM и последовательный DMA как контроли, окна 2/4/8,
CPU-ветка с ранними/поздними источниками и CUDA Graph on/off, два контекста.
В тест очереди добавлены принудительно заполненное кольцо, проверка payload,
исключение после публикации всего окна и 40 чередований ошибки/восстановления.
Также проходят существующие проверки staging wrap, отмены, частичной ранней
публикации, leases, кэша и 400 повторов CUDA Graph.

На фиксированной истории из 68 токенов совпали FNV-64 полных массивов logits
и argmax с GPU-контролем: шесть префиксов и 86 шагов одиночного/трёхтокенного
decode, два повтора. В гибриде действительно выполнены 2815 CPU-заданий /
3834 строки; CPU-строк в prefill — ноль. Эта проверка точности не используется
как сравнение скорости: в GPU-контроле было физическое чтение H:, в гибриде
история уже была прогрета.

Проверка сессий A→B→A, продолжения, отмены и повторов пройдена. Все восемь
сопоставимых greedy-сценариев совпали по входным и выходным IDs с сохранённым
GPU-контролем. Выполнены 624 CPU-задания / 1162 строки. Автоматическое обновление
CPU-профиля было включено и действительно прошло через поколения 0 → 1 → 2.
Подробности сохранены в `validation-summary.json` серии. Это сравнение с тем
же режимом G; известная отдельная задача полной batch/serial-эквивалентности
из О6 этим не закрывается.

Длинные контексты 4096/8192 и генерация Qwen в этой серии не повторялись.
Это не полная приёмка О6 и не основание включать CPU lane или новый транспорт
в рабочем профиле. Изменения ограничены backend DeepSeek.

Следующий открытый вопрос О2 — оставшаяся цена подготовки и оборота staging
при прежнем лимите памяти. Новое увеличение окна без изменения этого пути
измеренного выигрыша не обещает. О3 должен отдельно уменьшить объём H2D;
ускорение копирования не заменяет исправления кэша.
