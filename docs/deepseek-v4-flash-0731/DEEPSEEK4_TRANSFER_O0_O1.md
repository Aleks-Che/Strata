# О0–О1: измерения по фазам и исправление CUDA Graph

13 октября 2026. Выполнены первые два этапа
[плана оптимизации подкачки](DEEPSEEK4_TRANSFER_OPTIMIZATION_PLAN.md).
Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, Windows;
target UD-Q3_K_XL, DSpark Q8_0. Рабочие packs не изменены.

Исправлен пропуск CPU consumer при повторном использовании CUDA Graph.
Прежняя DMA-подкачка теперь проходит модельный сценарий с реальными
CPU-заданиями и включёнными графами. Ускорение относительно рабочего
GPU-only этим исправлением не подтверждено.

## Причина ошибки и изменение кода

GGML проверяет формы, адреса и свойства тензоров, а для совпавшего UID графа
может сразу вернуть «изменений нет». Наличие CPU mask/scatter/join зависит
дополнительно от готовности RAM-снимка и выбранного пути. Поэтому один набор
тензоров мог воспроизводить граф без нужного consumer либо со старыми CPU-узлами.

В [cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc) добавлено
отдельное состояние захватываемой CPU-ветки: позиции её матричных узлов,
адреса packet/output, событие готовности и binding очереди для down.
Состояние хранится на backend для каждого ключа split graph. Его изменение
включает обычный механизм прогрева и повторного захвата GGML. Проверяются оба
направления: GPU → CPU и CPU → GPU, даже при неизменном UID.
Динамические значения масок не входят в состояние: их по-прежнему обновляет
очередь перед каждым replay; захват не повторяется только из-за новых route-ID.

Проверка незавершённого consumer сохранена. CPU-арифметика, порядок суммирования,
таблица выбора экспертов и протокол подкачки не переписаны.

## Исправлена и настройка тестов

В используемом upstream `GGML_CUDA_DISABLE_GRAPHS` проверяется на **наличие**.
Значение `0` тоже отключает CUDA Graph. Поэтому прежние CTest-варианты с этим
значением не подтверждали работу графов, несмотря на имена `g0`.
Это ограничение относится к таким CTest-запускам; отдельные модельные прогоны
без переменной и тест с явными CUDA Graph API этим не опровергаются.

[CMakeLists.txt](../../backends/deepseek4/CMakeLists.txt) теперь удаляет переменную
для вариантов с графами, включая значение, унаследованное от shell.
Контроль с отключёнными графами сохраняет значение `1`.

Новый тест в [test_cpu_expert.cpp](../../backends/deepseek4/test_cpu_expert.cpp)
прогревает GPU-граф, включает реальные CPU-задания и возвращается к GPU при тех
же адресах тензоров. На исходном коде, с действительно включёнными графами,
он завершался `GPU replay retained a CPU mask or join`.
После исправления он проверяет не только выходы, но и ненулевые счётчики
настоящих capture/replay.

## Проверки О1

- Нативный тест: IQ3_XXS, MXFP4 и Q8_0, окна 1/3/4 токена, четыре смены режима
  на комбинацию. 216 гибридных выполнений, 576 CPU-строк; CPU-строки сверены
  с независимым вызовом CPU-ядра, GPU-строки — с GPU-контролем.
  При включённых графах суммарно 243 capture и 1485 replay.
  Контроль без графов имеет нулевые capture/replay.
- Восемь CTest прошли: новые переходы с графами/без, прежняя подкачка и GPU fetch
  с графами/без, два варианта передачи контекста с включёнными графами.
  После окончательного уточнения счётчика admissions повторены оба новых теста.
- Модельный сценарий, ранее падавший: четыре свежих запроса по 15 входных и
  32 выходных токена. 152 CPU-задания, 174 строки; все входные и выходные IDs
  совпали с GPU-compatible контролем. Реальные CPU-задания были у target;
  DSpark использовал GPU, включая общий scratch. Профиль стоимости принят.
- Target-only: одинаковые 68 входных IDs, префикс 36, decode по 1/3 токена,
  два повтора. Совпали FNV-1a хэши всех байтов logits и argmax для шести префиксов
  и 86 шагов decode. 112 CPU-заданий, 118 строк; CPU-заданий в prefill — 0.
  Это сравнение одинакового режима между CPU/GPU, не новая lossless batch/serial
  приёмка DSpark.
- Сессии: A→B→A, продолжение и его восстановление, fresh/full prefill,
  один токен, отмена prefill/decode, повтор после отмены, seeded repeat.
  Восемь greedy-сценариев совпали с сохранённым GPU-compatible эталоном.
  Вся серия: 280 CPU-заданий, 426 строк; использованы поколения профиля 0 и 1.
  Seeded-запросы по действующей политике используют GPU и не проверяют CPU-арифметику.

## Счётчики О0

Опциональный `STRATA_DS4_EXPERT_SNAPSHOTS=1` пишет cumulative-снимки на границах
`begin`, `prefill_end`, `end`; при исключении — `error`. Выключен по умолчанию.
Снимки берутся на существующих границах фаз, без дополнительной CUDA-синхронизации.
Они разделяют backend по идентификатору и включают:

- H2D/D2D/D2H, hits/misses и фактические GPU admissions;
- чтение через native file и mmap, CPU RAM hits и объём GPU-копий из pinned RAM;
- CPU branches/jobs/rows, GPU fetch branches;
- изменения CPU-структуры графа, capture/replay.

[benchmark_deepseek4_stage5.py](../../tools/benchmark_deepseek4_stage5.py)
вычисляет дельты prefill/decode/total, хранит исходные снимки и различает target
и draft по бюджету кэша только при однозначном соответствии. Идентификатор backend
сохраняется; при неоднозначности роль — `unknown`. Новый backend начинается с нуля,
незавершённому запросу не приписываются выдуманные decode-счётчики.

Инструмент также записывает TTFT, время запроса, CPU-seconds, RAM/VRAM,
физическое чтение всех дисков и параметры PCIe. Опрос CPU/RAM/VRAM — раз в две
секунды. `prefill_observed`/`decode_observed` в Python относятся к получению progress
и токенов; это приблизительные границы для OS-телеметрии. Нативные счётчики имеют
границы фаз самого движка. Файловое чтение не равно физическому чтению SSD.

Три теста [разбивки по фазам](../../tools/test_deepseek4_phase_counters.py) прошли:
история существующего backend и появление нового, незавершённый запрос, защита
от сброса cumulative-счётчиков внутри запроса.

Цена снимков в одной A/B/B/A серии GPU-compatible, последние два запроса каждого
процесса: полное время **+1,02%**, decode **+0,50%** с включёнными снимками.
Это предварительный контроль накладных расходов, не оценка ускорения модели.
Все ответы совпали; чтение диска H: на измерении — 0.

## Контрольные скорости и трафик

Одна окончательная сборка, одинаковые запросы и лимиты: target GPU-кэш 15360 МиБ,
draft 1024 МиБ, общий scratch, контекст 8192, draft-max=2. В L0/Q0 дополнительно
RAM 2048 МиБ, CPU 12 потоков, валидная замороженная калибровка и бюджет 0,01 мкс.
Два прогрева, затем два измеренных запроса. CPU jobs/rows в L0/Q0 действительно 0.

| Режим | Decode, ток/с | Время двух запросов, с | CPU-seconds | H2D двух decode, ГиБ |
|---|---:|---:|---:|---:|
| G: GPU-compatible | 14,680 | 7,000 | 9,578 | 31,680 |
| L0: прежняя подкачка, CPU-заданий 0 | 12,695 | 7,719 | 12,234 | 31,680 |
| Q0: новая очередь, CPU-заданий 0 | 5,406 | 14,562 | 59,531 | 67,947 |

Здесь H2D относится **только к decode измеренных запросов**, не к прогреву или
prefill. У target разница 29,646 → 59,023 ГиБ, у DSpark 2,034 → 8,924 ГиБ.
Ответы совпали, физическое чтение H: — 0. На других дисках была фоновая активность.
Это повтор локализации регрессии, отдельные короткие контроли; критерий принятия
нового рабочего профиля с тремя A/B/B/A и длинным контекстом ещё не выполнялся.

В предварительной сборке с тем же исправлением графов гибрид с прежней подкачкой
дал **12,428 ток/с**, 7,828 с на два запроса; GPU-only — 14,251, L0 — 12,510,
Q0 — 5,177 ток/с. Для этой пары исправление лишь сделало гибрид работоспособным:
выигрыша CPU lane относительно L0 или G нет. Эти числа не объединяются с таблицей
окончательной сборки. Между сборками уточнён счётчик GPU admissions: в ранних
`check-*` поле `admissions` содержало только direct admissions и для выводов
о полном кэше не используется.
