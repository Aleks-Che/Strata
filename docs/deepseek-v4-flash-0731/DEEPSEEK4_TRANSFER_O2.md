# О2: DMA из потока владельца и раннее чтение матриц

13 октября 2026. Эксперимент по
[плану оптимизации подкачки](DEEPSEEK4_TRANSFER_OPTIMIZATION_PLAN.md).
Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows.
Target UD-Q3_K_XL, DSpark Q8_0. Рабочие packs не изменены.

## Переключатели

Оба по умолчанию выключены; работают внутри `STRATA_DS4_GPU_FETCH_QUEUE=1`.

| Переменная | Действие |
|---|---|
| `STRATA_DS4_GPU_FETCH_DMA=1` | Веса переносит `cudaMemcpyAsync` из потока владельца. I/O-service не вызывает CUDA API |
| `STRATA_DS4_GPU_FETCH_EARLY_SOURCES=1` | Все три запроса публикуются на первой матрице. Следующий источник читается заранее; запись в VRAM остаётся на исходной границе матрицы |

Флаги независимы: можно сравнить SM-копирование с DMA, затем раннее чтение
с поздним. Выбор CPU-экспертов, арифметика и правила GPU admission не изменены.
Ранний режим учитывает фактический порядок gate/up: разные графы посещают
эти узлы в разном порядке.

## Владение и зависимости

1. GPU завершает маршрутизацию и публикует CPU/GPU mask.
2. Публикатор строит три запроса из того же снимка кэша. Он записывает адреса
   в дескриптор; это ещё не разрешение перезаписывать scratch или общую
   таблицу адресов MMVQ.
3. I/O-service обслуживает запросы строго в порядке потребителей. Источник —
   удерживаемая pinned RAM lease либо один из двух staging-буферов по 2 МиБ.
   Чтение следующего чанка может идти одновременно с передачей предыдущего.
4. На исходной границе матрицы поток владельца ставит bind таблицы адресов
   после предыдущих GPU-читателей. В DMA-режиме событие CUDA завершает этот
   участок, после чего владелец читает опубликованный дескриптор.
5. Владелец ставит `cudaMemcpyAsync`; событие завершения разрешает подтверждение
   чанка. Только после этого service может переиспользовать его источник.
   Service ни на одном из этих шагов не вызывает CUDA API.
6. GPU вычисляет матрицу. Следующий запрос уже позволяет service читать данные,
   но его первый чанк ждёт следующей границы матрицы. Общий scratch в это время
   принадлежит текущему вычислению.
7. Полное завершение подкачки позволяет вернуть RAM leases; защита VRAM-адресов
   сохраняется до завершения GPU-потребителей. Контексты и очереди target/DSpark
   отдельные, существующие fences общего scratch сохранены.

DMA не захватывается внутрь CUDA Graph: копирование стоит между захваченными
вычислительными графами. Попытка вызвать owner DMA во время capture явно
отклоняется. Это не отключает CUDA Graph у матричных операций.

При отмене неполной ветки сначала завершаются GPU-публикаторы, затем останавливаются
ранние запросы без потребителя. Подтверждения и буферы переиспользуются только
после ответа service. Неиспользованные GPU loans не публикуются как заполненные.
Объём staging не вырос: два буфера по 2 МиБ на очередь, как у прежнего SM-пути.

Первый вариант ранней публикации выявил взаимное ожидание: service мог начать
будущую матрицу прежде нужной владельцу. Исправление — явная последовательность
источников, публикуемая до GPU-запросов, включая графы с up перед gate.

## Проверки

Все 10 выбранных CTest прошли: обычная очередь и owner DMA; CPU-эксперты с
DMA, с ранним чтением/без, с графами/без; совмещённый тест смены контекстов
и контроль прежнего пути. Нативный тест очереди включает 400 replay, изменение
маршрутов, CPU masks, cache loans, payload, границы staging, ошибки чтения,
отмену, новое выделение CUDA-памяти и повторное использование.

Добавленная проверка удерживает GPU-потребителя, дожидается чтения следующего
источника и проверяет, что текущая матрица ещё не перезаписана. Проверены
отмена между матрицами и следующий проход после отмены. На Windows тест
явно отправляет накопленные WDDM-команды перед ожиданием host atomics.

Модельные проверки после замеров также прошли:

- Target-only, одна фиксированная история из 68 IDs, префикс 36, окна 1/3,
  два повтора: 6 префиксов и 86 шагов. Полные FNV-хеши массива logits и argmax
  совпали с G. В CPU-трассе 2801 непустое задание, 3818 строк; это не проверка
  случайно оставшегося GPU-only. Сравнивались одинаковые окна; утверждения
  об эквивалентности разных размеров batch здесь нет.
- Полная связка с DSpark: 3 прогревочных запроса, создание/восстановление сессий,
  продолжение, свежий prefill, отмена prefill/decode и следующий запрос,
  seeded repeat. Валидатор вернул `passed=true`; все 8 greedy-сценариев совпали
  с сохранённым GPU-compatible контролем. В трассе 634 CPU-задания / 1174 строки.
  Автообновление стоимости включено, но в этой серии поколение осталось 0:
  новую смену поколения данный прогон не проверяет.

Длинный контекст 4096/8192 в этом этапе повторно не измерялся; это остаётся
частью полной приёмки О6. Изменения ограничены отдельным DeepSeek backend;
модельный регрессионный прогон Qwen здесь не проводился.

## Первый модельный контроль

Одна сборка, один свежий профиль стоимости, 12 CPU-потоков. Четыре свежих
запроса по 15 входных и 32 выходных токена: первые два прогревочные, ниже
сумма последних двух. Контекст 8192; кэши target/DSpark 15360/1024 МиБ;
MTP `draft-max=2`; pinned RAM cache 2048 МиБ. Лимиты и остальные настройки
сохранены в соответствующих `*-config.json`.

| Режим | Decode, ток/с | Полные два запроса, с | CPU-seconds | Decode H2D, ГиБ | CPU jobs / rows в decode |
|---|---:|---:|---:|---:|---:|
| Q0, SM-очередь | 5,666 | 14,015 | 57,219 | 66,557 | 0 / 0 |
| DMA, поздние источники | 6,737 | 12,218 | 47,078 | 59,977 | 0 / 0 |
| DMA, ранние источники | 6,843 | 12,062 | 46,109 | 59,977 | 0 / 0 |
| SM, ранние источники | 5,795 | 13,781 | 55,625 | 66,557 | 0 / 0 |
| L0, прежняя подкачка | 12,688 | 7,719 | 12,063 | 31,680 | 0 / 0 |
| G, совместимый GPU-only | 14,658 | 6,953 | 9,297 | 31,680 | 0 / 0 |
| DMA + ранние источники + реальные CPU-задания | 7,004 | 11,843 | 53,000 | 54,145 | 572 / 1096 |

Все выходные IDs совпали. Физическое чтение H: на последних двух запросах
нулевое; это не утверждение об отсутствии I/O на других дисках или при запуске.
В N+ были реальные задания и у target (504 / 972), и у DSpark (68 / 124).
Всего за четыре запроса — 1168 заданий и 2310 строк.

**Это не чистое сравнение транспорта:** при переходе от SM к DMA изменились
также попадания и admissions. При нулевых CPU-заданиях прежняя RAM-защита
продолжает влиять на GPU-кэш; стоимость и момент завершения операций меняют
последующие снимки. Поэтому прирост 5,666 → 6,737 нельзя целиком приписать DMA.
Между поздним и ранним DMA все собранные счётчики prefill/decode совпали;
единичный прирост decode 1,57% пока недостаточен для принятия раннего режима.

Счётчик ранних native reads на всех четырёх запросах вырос с 21 чанка / 42 МиБ
до 7855 чанков / примерно 15,21 ГиБ. Он означает чтение до старта потребителя
своей матрицы, а не измеренное время перекрытия с GPU. Таймеры fence, I/O и
полного ожидания не следует суммировать как независимые части запроса.

## Ограничение первого DMA-протокола

В микротесте 6×4 МиБ окончательной сборки: прямой DMA — 14,147 ГБ/с,
SM-очередь из pinned RAM — 11,432, owner DMA — 12,520; со staging —
10,824 и 11,166 соответственно. Это 88,5% и 78,9% прямого DMA-контроля.
Критерий плана **не ниже 90%** пока не пройден. Каждый чанк требует отдельного
завершения CUDA event и host acknowledgement; двухбуферный протокол сохраняет
эту цену. Измерялись 1/6 матриц по 2/4/8 МиБ, 3 прогрева и 12 повторов,
с проверкой payload после серии.

Рабочий профиль остаётся GPU-only. О2 пока не закрыт по критерию транспорта;
обе новые настройки остаются экспериментальными и выключенными по умолчанию.

## Сравнение при одинаковых решениях кэша

Для изоляции транспорта во всех трёх вариантах выключены `GPU_FETCH_KEEP_RAM`,
`RAM_DEMOTE_MIB` и `CPU_CONTEXT_OVERLAP`. Это контрольный режим, не принятая
новая политика для реальной CPU-ветки. Остальные параметры прежние; CPU budget
0,01 мкс, фактические CPU jobs/rows — ноль. Порядок процессов: SM → DMA →
DMA early → DMA early → DMA → SM. Каждый процесс снова выполняет два прогрева
и два измеряемых запроса.

| Режим | Decode, ток/с: два процесса | Среднее decode | Среднее полное время двух запросов, с | Средние CPU-seconds |
|---|---|---:|---:|---:|
| SM | 7,763 / 7,522 | 7,642 | 11,062 | 26,836 |
| DMA | 7,982 / 7,996 | 7,989 | 10,727 | 25,914 |
| DMA + early | 8,371 / 8,320 | 8,345 | 10,328 | 24,906 |

Совпали выходные IDs и **все четыре запроса по фазам**: hits, misses, admissions,
H2D/D2D/D2H, file/mmap bytes, RAM GPU bytes, CPU jobs/rows. Различий в объёме
передаваемой работы в этой серии не было. На последних двух decode H2D всегда
44,255 ГиБ: target 34,949 и DSpark 9,306. Физическое чтение H: — ноль.

В этих условиях DMA даёт +4,53% к среднему decode, ранние источники дополнительно
+4,46%; вместе +9,20%. Полные запросы сокращаются на 6,64%, CPU-seconds — на
7,19%. У SM разброс двух процессов около 3,2%, поэтому проценты не являются
прогнозом для других запросов или производственного профиля. В частности,
результат не переносится на оставленную включённой RAM-защиту из первой таблицы.

Раннее чтение сохранено как проверенный локальный кандидат. Полной приёмки О6
и выигрыша относительно G/W эта серия не подтверждает. Превышение трафика
DSpark относительно прежней подкачки остаётся отдельной задачей О3.
