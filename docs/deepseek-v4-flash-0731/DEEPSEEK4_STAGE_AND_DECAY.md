# Размер staging, частотная история и стоимость allocations

После этой серии slabs интегрированы в динамический кэш; результаты модели,
учёт VRAM и проверки описаны в [следующем отчёте](DEEPSEEK4_DYNAMIC_SLABS.md).

Продолжение [плана переноса GLM/Step](DEEPSEEK4_OPTIMIZATION_TRANSFER_REVIEW.md),
10 октября 2026 года. Windows, Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090
32607 МиБ, драйвер 581.80, CUDA 13.0. До первого запуска свободно 105,95 ГиБ
RAM, GPU занят примерно на 1,35 ГиБ. Другие приложения не закрывались.

Модель UD-Q3_K_XL на H: Samsung 990 Pro, DSpark Q8_0 на другом диске.
Контекст 8192, batch 4096, один host thread, GPU-only, resident layers 0,
кэши target/draft 15360/1024 МиБ, DSpark2, shared scratch, frequency,
match-size 1, pipeline 1, readers 2, read mode auto. Prefill cache hits включены,
AVX2 и early refill выключены. Файловый кэш ОС не очищался.

## Stage 8 против 16 МиБ

Одна неизменная сборка, SHA-256
`ba1a8f3ea9d3d317518045d65f0faefb78427e8b58ca8f1f6b8d3574db8f4bd6`.
Последовательность: текст stage16 → текст stage8 → код stage8 → код stage16.
Prefill 256 токенов, первый decode 128 токенов, затем три повтора из RAM-сессии.
Первые холодные запросы не входят в таблицу.

| Запрос | Stage, МиБ | Три повтора, ток/с | Медиана, ток/с | CPU-с / запрос, медиана | CPU всей системы, среднее % |
|---|---:|---|---:|---:|---:|
| Русский текст L1/L2/L3 | 16 | 19,86 / 20,11 / 20,41 | 20,11 | 8,70 | 16,09 |
| Тот же текст | 8 | 17,60 / 19,68 / 19,72 | 19,68 | 9,38 | 18,83 |
| Код | 8 | 12,72 / 15,13 / 16,02 | 15,13 | 11,28 | 10,84 |
| Тот же код | 16 | 13,52 / 16,80 / 17,02 | 16,80 | 10,33 | 9,05 |

Выходные token IDs, H2D/D2D и счётчики кэша совпали в каждой паре.
Все 12 прогретых повторов прочитали **0 байт** с физического H:;
`pipeline_fallbacks=0`, `cpu_compute_nodes=0`.
Код в этой серии продолжает ускоряться по мере обучения GPU-кэша;
три повтора не доказывают достижение стационарной скорости.

Stage 8 уменьшает суммы размеров выделяемых pinned-буферов target/draft
192 → 96 МиБ и device rings 128 → 64 МиБ. Это размеры allocations по коду,
не разница общей занятости RAM/VRAM. Ускорение не получено, поэтому рабочий
stage сохранён **16 МиБ**. Дополнительные испытания stage 8 без DSpark и на
длинном prefill не проводились: этот вариант не выбран для включения.

## Раздельная настройка затухания частот

Добавлены параметры движка и `tools/setup_deepseek4.py`:

```text
--expert-frequency-decay 0
--draft-expert-frequency-decay 0
```

Единицы — зарегистрированные обращения к матрицам. Это не число токенов и
не миллисекунды. Допустимо 0..1000000000; 0 сохраняет прежнюю формулу
`max(4096, cache_bytes >> 17)`: 122880 у target, 8192 у DSpark в этом профиле.
При каждом пересечении периода частотный счётчик лениво делится на два.
Prefill больше восьми токенов не обучает историю.

Настройки выбираются на потоке исполнения перед первым графом каждого backend.
Каждый backend сохраняет собственную историю и период; переключение target/draft
и изменение лимита VRAM не сбрасывают счётчики. Периоды относятся к политике
`frequency`; при `lru` не используются. Параметры видны в `INFO`, фактически
созданный период — в `STRATA_EXPERT_FREQUENCY decay=...`.

Для сравнения используется одна новая сборка, SHA-256
`240f4d75a33fe8bfb6ca89f8ffb530da8184398305896a53f89fd56c7c9cf9c6`.
В benchmark добавлены `--alternate-generation-prompt` и `--switch-rounds`:
после обычных повторов A выполняются B/A, B/A, B/A. У запросов разные
RAM-сессии, но общий GPU-кэш экспертных весов. Скрипт проверяет совпадение
token IDs A с исходным A, B с первым B. Это позволяет увидеть стоимость
смены нагрузки вместо оценки только одного многократно повторяемого ответа.

Порядок: auto → target×4 → draft×4 → target÷4 → повтор auto → повтор draft×4. Нагрузка A —
тот же русский текст, B — тот же запрос с кодом. Первый B прогревает новый
набор матриц и не входит в итог смешанной нагрузки. Для неё взяты вторые
и третьи B/A-пары: суммарно 512 токенов, ток/с = 512 / сумма decode seconds.
CPU-с также суммируются по этим четырём запросам. Это ограниченная серия,
не универсальный подбор для всех текстов.

| Периоды target / draft | Медиана повторов A, ток/с | B/A, ток/с | B/A, CPU-с | CPU всей системы в B/A, % |
|---|---:|---:|---:|---:|
| Auto: 122880 / 8192 | 20,74 | 14,16 | 49,42 | 10,23 |
| 491520 / 8192 | 20,82 | 14,07 | 49,31 | 9,20 |
| 122880 / 32768 | 20,71 | 14,58 | 47,33 | 9,58 |
| 30720 / 8192 | 19,19 | 13,94 | 50,06 | 9,80 |
| Auto, повторный контроль | 20,62 | 14,36 | 48,36 | 9,23 |
| 122880 / 32768, подтверждение | 20,70 | 14,53 | 48,09 | 10,09 |

Суммы H2D/D2D относятся ко **всему запуску**, включая начальный prefill,
четыре A до переключений и все три B/A-пары:

| Вариант | Target H2D, ГиБ | Target D2D, ГиБ | Draft H2D, ГиБ |
|---|---:|---:|---:|
| Auto | 1186,29 | 2806,44 | 63,53 |
| Target×4 | 1203,00 | 2795,28 | 63,53 |
| Draft×4 | 1186,29 | 2806,44 | 64,06 |
| Target÷4 | 1236,42 | 2913,97 | 63,53 |

Удлинение истории target удерживает старый запрос, но мешает новому;
сокращение ускоряет первую адаптацию к B, но увеличивает общие передачи
и ухудшает возврат к A. У draft×4 небольшой выигрыш времени сопровождается
ростом H2D; поэтому он проверен повторно после возврата к auto.
Выходные token IDs совпали во всех запросах шести серий, вычислительные
узлы CPU отсутствовали. Все зачётные B/A-пары прочитали 0 байт H:.

Повторный auto воспроизвёл прежние H2D/D2D и счётчики кэша до байта,
token IDs также совпали. Скорость смешанной нагрузки изменилась на +1,44%
без изменения настроек; это часть наблюдаемого разброса.

Подтверждение draft×4 дало 14,53 ток/с против 14,36 у повторного auto,
первые запуски — 14,58 против 14,16. Это **+1,22% и +2,99%** в двух парах;
по отношению средних скоростей — около +2,1%. Все четыре B/A-запроса каждого
повтора читали 0 байт H:. Однотипный A остаётся около 20,7 ток/с, заметного
ускорения этого сценария нет. Это небольшой наблюдаемый эффект на данных
запросах, не оценка ускорения произвольного текста, длинного контекста или
режима без DSpark. Общий default остаётся auto.

В локальном Q3 + DSpark выбран `--draft-expert-frequency-decay 32768`.
Target сохраняет auto (122880), stage — 16 МиБ. Для возврата к прежней истории
draft нужно выставить 0 и перезапустить движок. Режимы AVX2/early выключены,
prefill cache hits включены, объёмы GPU-кэшей не меняются.

## Измерение накладных расходов динамической VRAM

Отдельный процесс с CUDA 13, без модели. 128 матриц по 3211776 байт
(IQ3_XXS gate/up + padding) и 128 по 4456960 байт (MXFP4 down + padding),
всего **981598208 байт**, 936,125 МиБ. Каждая allocation заполнена через
`cudaMemset`, выполнен synchronize; до/после прочитаны CUDA и NVML счётчики.
Сравнивались отдельные allocations и укладка одноразмерных матриц в блоки
до 16 МиБ, включая неполный последний блок. Порядок A/B/B/A.

| Размещение | Allocations | Прирост занятой VRAM, оба повтора | Полезные данные |
|---|---:|---:|---:|
| Каждая матрица отдельно | 256 | 1280 МиБ | 936,125 МиБ |
| Блоки до 16 МиБ | 69 | 1008 МиБ | 936,125 МиБ |

Разница **272 МиБ**, или 21,25% фактической памяти этой выборки.
CUDA и NVML дельты совпали. После освобождения каждый раз восстанавливалась
исходная занятость. Дополнительный объём NVML до проб включает CUDA context.

Это подтверждает смысл slabs для **динамического** режима DeepSeek, где сейчас
используются отдельные CUDA allocations. Это не интеграция slab allocator,
не измерение ток/с и не обещание такой же экономии на полном наборе матриц.
Частично пустые slabs, удаление под давлением и смесь размеров изменят результат.
Фиксированный рабочий GPU-кэш уже выделен одной ареной и этой потери не имеет.

Перед интеграцией необходимо сохранить межконтекстный reuse: текущий
`strata_managed_copy` может забрать allocation у другого backend на том же GPU.
При отдельных pool на target/draft нельзя затем освобождать чужой слот через
неправильный allocator. Нужен общий pool устройства либо явный владелец каждого
слота. Также требуется раздельный учёт полезных bytes и зарезервированных blocks,
освобождение при VRAM pressure и запрет `cudaFree` для указателей внутрь slab.
Уплотнение допустимо только после завершения всех потребителей. Эти изменения
ещё не внесены; allocation probe проверяет только физическую стоимость размещения.

## Проверки и воспроизведение

Сборка с настройками частот прошла 11/11 CTest и 25/25 Python-тестов.
Новые проверки покрывают прежние автоматические периоды, независимость двух
backend и сохранение периода уже созданной истории после переключения.
Четыре некорректных значения CLI отклонены до открытия модели.

Реальные проверки `validate_deepseek4_speculative.py --tokens 32` пройдены с
DSpark и без него. В проверочных профилях target использует 491520, draft —
32768, чтобы проверить независимость параметров одновременно. Проверены
A/B/A из RAM, активное продолжение и его восстановление, один токен, отмена
prefill/decode, восстановление после отмены и повтор с seed 123.
Оба JSON `ds4-tuning-20261010-validation-{dspark,plain}.json` имеют `passed=true`.
В журналах только `cpu_compute_nodes=0`.

Известное расхождение DSpark между полным prefill продолжения и инкрементальным
продолжением сохраняется (`full_prefill_identical=false`); без DSpark в этом
fixture — true. Изменение хранения матриц не исправляет это численное различие.
Качество модели и Linux в этом этапе не оценивались.

Рабочий профиль обновлён после проверок. Резервная копия до изменения —
`build-local/deepseek4/tuning-20261010/production-before-decay.json`.
Все тестовые процессы закрыты; сервер в ходе работы не запускался.

Локальные профили, исходная сборка, allocation probe и журнал сборки находятся
в `build-local/deepseek4/tuning-20261010/`. Сырые JSON и `.log`:
`bench/results/ds4-tuning-20261010-*`. H: измеряется через `PhysicalDrive6`;
это счётчик всего устройства, он включает сторонние процессы и не включает
DSpark на другом диске. CPU-с — user + system процесса за весь запрос;
ток/с — только по `decode_ms`.

```powershell
.venv\Scripts\python.exe tools/benchmark_deepseek4.py --config build-local/deepseek4/tuning-20261010/stage16.json --prompt-tokens 256 --tokens 128 --repeats 3 --physical-disk PhysicalDrive6 --output bench/results/ds4-tuning-20261010-stage16-text.json
.venv\Scripts\python.exe tools/benchmark_deepseek4.py --config build-local/deepseek4/tuning-20261010/decay-auto.json --prompt-tokens 256 --tokens 128 --repeats 3 --alternate-generation-prompt build-local/deepseek4/tuning-20261010/code.txt --switch-rounds 3 --physical-disk PhysicalDrive6 --output bench/results/ds4-tuning-20261010-decay-auto.json
```

Сохраняйте новый output при повторе, чтобы не заменять исходные результаты.
AVX2/early в этом этапе не включались; арифметика MMVQ и схема DSpark не менялись.
