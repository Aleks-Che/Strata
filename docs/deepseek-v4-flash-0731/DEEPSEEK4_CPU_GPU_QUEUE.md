# GPU-очередь и постоянный CPU-service

12 октября 2026. Экспериментальный путь этапа 2
[плана CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md).
Рабочий профиль GPU-only не изменён. Это ещё не завершённый этап 2:
старый scheduler продолжает читать экспертные IDs для подкачки весов.

Продолжение от того же дня: [GPU-запросы подкачки](DEEPSEEK4_GPU_FETCH_QUEUE.md)
добавляют отдельный экспериментальный путь без этого чтения для подходящих веток.
Измерения ниже относятся к исходному CPU-ring без новой очереди подкачки.

## Что изменено

- Перед чтением маршрутов основным host-потоком строится снимок готовых RAM-троек
  up/gate/down. Он удерживает leases и их поколения. Не выбранные кандидаты
  не обучают частотную политику RAM-кэша и не считаются RAM hits.
- GPU читает свой routing tensor, выбирает CPU-строки последовательно по токенам
  и публикует их вместе с активацией в mapped ring. Будущие IDs не участвуют
  в выборе предшествующего токена. Формула auto остаётся прежней; её калибровка
  на одном готовом эксперте не заменяет запланированный этап 4.
- Постоянный service thread проверяет backend, слой, эпоху и три пары
  адрес/поколение, затем запускает прежний `CpuExpertWork` и постоянный CPU-пул.
  В этом потоке нет CUDA-вызовов, чтения SSD, изменения HostCache или уничтожения
  leases. Пока нет задания, поток спит; при активной очереди опрашивает её с yield.
- GPU присоединяет ответ у down-результата. Существующий scatter возвращает строки
  в исходные позиции top-k; взвешенная редукция графа не меняется. Если эксперт
  нужен также GPU-строке другого токена, его матрицы всё равно подкачиваются.
- Производитель назначает новый номер на GPU, включая CUDA Graph replay.
  Освобождение слота требует ответа CPU и подтверждения потребителя GPU.
  Полная очередь означает GPU-only до публикации CPU-назначения. После публикации
  нет повторного исполнения на другом устройстве при ошибке.
- Захваченный down-граф всегда содержит event wait и queue join. Для callback
  queue join пустой; для GPU-очереди event готов сразу. Выбор транспорта не меняет
  узлы уже захваченного графа. Пропущенное GPU-подтверждение — явная ошибка.

Перед итоговой проверкой обнаружен и исправлен дефект этого переключения:
первый вариант обхода пустых RAM-снимков мог оставить в CUDA Graph старый join.
Вариант `queue-v2` отклонён; его скорость и проверки модели не являются результатом.

Кольцо имеет два слота, по 2 МиБ входа и выхода на слот плюс метаданные:
8 397 952 байта pinned RAM на активный backend. Дополнительно сохраняются прежние
рабочие буферы CPU lane и небольшая GPU-таблица. Target и DSpark имеют отдельные
очереди и номера; веса используют общий ограниченный HostCache.
Текущий scheduler удерживает одно активное CPU-задание на backend; глубина два
сама по себе не означает межслойный конвейер.

Протокол использует выровненные 32-битные atomic load/store системной области
видимости и release/acquire; mapped-host read-modify-write не используется.
Основание: [модель памяти CUDA C++](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#atomicity).
Тайм-аут GPU join — 500 мс, с ошибкой и NaN вместо старого ответа. CPU drain
ограничен 10 секундами. При отмене без down-потребителя слот подтверждается
host-потоком только после завершения GPU-потока и CPU-задания.

## Включение и границы

Дополнение к существующему тестовому CPU/RAM-профилю:

```text
STRATA_DS4_CPU_GPU_QUEUE=1
STRATA_DS4_CPU_SHARED_RAM=1
STRATA_DS4_RAM_CACHE_MIB=2048
```

Также нужны CPU threads > 0, pipeline, direct cache и ordered experts. Проверены
IQ3_XXS, MXFP4, Q8_0; сохраняются прежние ограничения unfused ветки, до 8 токенов
и 8 top-k. Длинный prefill остаётся на GPU. Неподходящие ветки сохраняют прежний
dispatch. Hash-routed GET_ROWS с ранней подкачкой пока остаётся на прежнем пути.
Qwen backend и production-конфигурация не менялись.

Host trace поддержан. `STRATA_DS4_CPU_TRACE_GPU=1` для очереди явно отклоняется:
прежние CUDA-интервалы callback не описывают этот транспорт. Итоговая строка
`STRATA_CPU_GPU_QUEUE` содержит branches/jobs/rows, выделенные mapped bytes и
`legacy_route_wait=1`. Статистика `cpu_queue_jobs/rows` позволяет проверить, что
тест действительно использовал очередь, а не старый callback.

## Открытая часть этапа 2

CPU-решение уже не зависит от host-копии IDs. Однако SSD/H2D-планировщик всё ещё
получает эти IDs и ждёт CUDA backend. После этого он читает опубликованную маску
только для отмены ненужных GPU fetch. Поэтому синхронизацию нельзя считать
устранённой, а весь этап — завершённым. Для следующего шага нужен отдельный
протокол GPU-запросов подкачки и владения destination-буферами. Простая замена
`tensor_get_async` на опрос mapped памяти не устраняет эту зависимость.

Пустой снимок не запускает service; после него допускается прежний callback-путь,
если RAM-тройка успела стать доступной к чтению маршрутов. Поэтому счётчики
всего CPU lane и queue jobs различаются. Это также нужно убрать при полном
переносе планирования на GPU, сохранив явный GPU-only fallback до публикации.

Не закрыты также полная проверка DSpark/session restore и прежний дефект
seeded repeat shared CPU lane. Ускорение требует сравнения полного workload;
само наличие очереди не является результатом по скорости.

## Проверки и измерения

ПК: Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, Windows, CUDA 13.0.
Артефакты: `build-local/deepseek4/cpu-queue2-20261012/`.

На первом шаге прошли 30 CTest-проверок: протокол очереди, whole-expert с графами
и без них, HostCache/residency, GPU-only audit, pipeline/direct/compact и speculative
unit tests. Протокол проверяет 1200 replay, видимость разных входов/ответов,
переполнение, поколения, причинность, ошибки, отмену и тайм-аут. Whole-expert
тест дополнительно требует 10 queue jobs / 30 rows в shared RAM для каждого
из трёх форматов, чтобы старый путь не мог незаметно выдать успех теста.
После исправления переключения повторены пять затронутых CTest-проверок.
Whole-expert теперь сначала выполняет 24 коротких prefill без CPU, затем
10 queue-вычислений и шесть переключений prefill/decode на том же графе.
В shared-части каждого формата подтверждены 16 jobs / 48 rows.

## Замеры модели и проверка DSpark

Итоговая сборка `queue-v3.exe` и `build-deepseek4/bin/strata-deepseek4.exe`:
SHA-256 `9b8dc2fc9c257d60570b2b6994fd673becd6e52aff97c6bc0d2764eacafbbc2d`.
В `final-manifest.json` сохранены SHA baseline, промежуточных сборок и 116
исходников; `source-final/`, CMakeCache, команды и полные логи лежат рядом.

Target-only, UD-Q3_K_XL, 68 фиксированных IDs, префикс 36 и decode 32 токенов.
CPU 12 потоков, force, cap=1 на токен, общий RAM-кэш 2048 МиБ, GPU-кэш 15360 МиБ,
pipeline 16 МиБ / 2 readers, CUDA Graphs. Сравнение одной сборки с флагом очереди
0/1; среднее двух последних из четырёх проходов:

| Режим | Decode по 1 токену, мс | Decode по 3 токена, мс | Prefill 68, мс |
|---|---:|---:|---:|
| Callback, очередь выключена | 1822,43 | 1234,20 | 2420,14 |
| GPU-очередь | 1931,07 | 1246,95 | 2431,89 |
| GPU-очередь с host trace | 1947,24 | 1242,40 | 2451,41 |

Ускорения нет: в этой паре +5,96% / +1,03% времени decode. Это предварительная
пара, не три независимые серии с доверительным интервалом. GPU-prefill численно
не изменён; его отличие времени около 0,5% нельзя приписывать очереди по одной
паре. Физическое чтение `PhysicalDrive6` во время каждого fixed-history прогона
равно 0; запуск/загрузка модели в этот счётчик не входят. Минимум свободной RAM
в серии вместе с DSpark — 59,51 ГиБ. OOM и незавершённых RAM fills на выходе нет.

Queue-прогон выполнил 885 jobs / 1018 rows. Trace on/off дали одинаковые полные
сигнатуры logits во всех 12 проходах. С callback совпали 8/12, включая все
prefill; четыре прогретых decode отличаются. Shared RAM и адаптивная доступность
CPU/GPU допускают разное размещение экспертов; совпадение CPU/GPU арифметики
этим тестом не доказано. Native-тесты проверяют каждый результат против выбранного
CPU-эталона и GPU-эталона отдельно.

Трасса `queue-v3/01-on.tsv` содержит 9296 записей подготовки/веток. Для r2/r3
decode1 получение маршрутов занимает суммарно 151/154 мс, отдельный route wait —
1,27/1,26 мс. D2H API с pageable host-буфером сам может ожидать предшествующую
GPU-работу: малый `route_wait` не означает устранения барьера. Суммы retirement
и других интервалов нельзя складывать как независимые задержки. Подготовка
пустого снимка пока не имеет полного отдельного таймера; число записей trace
не равно числу MoE-слоёв. Следующая работа — GPU-запросы подкачки и обновление
таблицы по изменениям вместо полного host-обхода кандидатов на каждом слое.

DSpark Q8_0: очередь использована и target (77 jobs / 103 rows), и draft
(1 job / 2 rows). Прошли A→B→A, продолжение и его восстановление, fresh prefill,
одиночный токен, отмена prefill и decode. Однако точная проверка ответа
**после cancel/restore не прошла**: изменились два из восьми IDs. Validator
остановился на этом assert, поэтому seeded repeat в этой серии не выполнялся.

Повтор той же проверки с `STRATA_DS4_CPU_GPU_QUEUE=0` на этой же сборке дал
тот же провал; во всех десяти выполненных сценариях token IDs совпали между
callback и queue. Это воспроизведение общей проблемы CPU lane, не доказательство
её причины. Проверка не ослаблялась. Нельзя считать режим готовым для рабочих
сессий или ставить весь этап 2 завершённым.

Сырые результаты: `queue-v3/`, `callback-v3/`, `queue-trace-summary.json`,
`dspark-v3-result.json`, `dspark-callback-v3-result.json`, `final-memory.json`.
Историческая серия `comparison/` относится к первому варианту; `queue-v2/`
отклонён из-за дефекта переключения графов. Production остаётся GPU-only.
