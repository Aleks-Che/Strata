# Освобождение CPU-весов по фазам

12 октября 2026. Продолжение этапа 2 [плана CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md).
`STRATA_DS4_CPU_RELEASE_WEIGHTS=1` — опциональный режим, выключенный по умолчанию.

## Что изменилось

В GPU-очереди CPU-service теперь может отпустить выбранные RAM-матрицы по окончании
последнего CPU-чтения. После первого барьера постоянного пула освобождаются gate/up,
после второго — down. Повторные вхождения одного эксперта в окне учитываются
однократно для каждой фазы. Арифметика, clamp, группировка строк и порядок
объединения результата не меняются.

Освобождение использует неблокирующий `HostCache::release_cached`: под mutex проверяются
публикация и владение блоком. Уменьшение счётчика ссылок не может уничтожить
последнее владение pinned-памятью на CPU-service. Если кэш больше не владеет
публикацией, lease остаётся до обычного завершения ветки; такой случай учитывается
в `deferred`. Payload allocation/free на service по-прежнему запрещены.
При занятом mutex CPU-service также сразу оставляет lease до завершения ветки.
Он не должен ждать владельца кэша, который может удерживать mutex при CUDA
allocation/free и ждать GPU join этого самого CPU-задания. Отдельный тест
моделирует такое встречное ожидание; lease сохраняется, callback не блокируется.

I/O-service обрабатывает только **невыбранные** CPU-leases; новый callback — только
выбранные. Если тот же эксперт нужен GPU для другого токена, отдельный fetch lease
удерживает его до окончания копии. Чтобы освобождённая CPU-матрица стала доступна
для повторного использования уже внутри ветки, полезно сочетать режим с
`STRATA_DS4_GPU_FETCH_RELEASE_RAM=1`: иначе ненужный GPU-снимок может продолжать
удерживать тот же блок. Это не увеличивает RAM-бюджет и не обещает снижение RSS.

Учёт CPU RAM-hit при последующем `queue_adopt` опирается на состоявшееся чтение
валидированного RAM-снимка. Он не пытается заново захватить блок, который к этому
моменту мог быть использован для другой матрицы.

Результат, входные активации, описание задания и общий контекст ветки остаются
живы до подтверждения GPU-потребителя. Общее ожидание перед переиспользованием
контекста этим изменением не снято. Старый callback-путь и GPU-prefill не используют
новое освобождение.

## Диагностика и проверки

`STRATA_CPU_WEIGHT_RELEASE` сообщает число заданий, отпущенных gate/up и down,
сумму байтов leases, deferred, удержание для capture и время освобождения.
Сумма байтов учитывает повторное использование одной памяти в разных заданиях;
это не объём уникальной освобождённой RAM. Счётчики выбранных весов атомарны,
поскольку статистика может читаться во время работы CPU-service.

Запись CPU fixture выполняется после GPU join и читает сами веса. При активной
трассе с настроенным capture новый режим удерживает их до записи, включая задания
после исчерпания capture quota. Обычная трасса без capture может освобождать веса.
Время освобождения учитывается отдельно; интервалы арифметических фаз в трассе
его не включают, а полное `compute_us` включает.

Новый тест немедленно перезаписывает gate/up в callback первой фазы и down во
второй. Результат сравнивается с обычным вычислением. Покрыты смешанные форматы
IQ3_XXS/Q8_0, MXFP4/Q8_0 и Q8_0, окна 1/3/8, повторные и разные эксперты,
1/4/12/16 потоков — 72 случая. Native-тесты с graphs=0/1 дополнительно проверяют
точные CPU/GPU-строки и счётчики освобождения; capture fixture воспроизводится
на 12 и 16 потоках с побитным сравнением выходов.

Первый полный CTest-прогон дал 49/50: повторный capture пытался записать уже
существующий fixture. Защита движка от перезаписи сохранена; тест исправлен —
каждый запуск использует новый подкаталог. Исправленный тест дважды прошёл с
EARLY_RETIRE и ASYNC_PARK. Четыре первых smoke-проверки и повторная проверка
этого исправления не считаются новыми независимыми тестами.
После добавления try-lock окончательная сборка прошла все 50 CTests за 218,34 с,
включая новый тест встречного ожидания, capture, повторное использование очередей,
ошибки, отмену, compact/direct/ordered, HostCache и speculative/GPU-only контракты.
Ещё 11 проверок прошли с compact scratch, slabs 1 МиБ, одним GPU-copy block,
RAM_DROP_GPU, KEEP_RAM и обоими режимами завершения очередей. Отдельно прошёл
native fixture с выключенным fetch RAM fill. Итого 50+11+1=62 проверки конфигураций.

## Условия модельных проверок

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, H: Samsung 990 PRO, Windows.
DeepSeek-V4-Flash-0731 UD-Q3_K_XL; target-only, фиксированные 68 входных IDs.
Полный prefill — 68 токенов, decode — 32 после префикса 36, по одному либо
пакетами до трёх. GPU-кэш 15 ГиБ, общая RAM 2 ГиБ, pinned pool и fetch budget
по 32 МиБ. CPU12, force/cap1, graphs/direct/ordered, PRUNE, EARLY_RETIRE
и GPU_FETCH_RELEASE_RAM включены; ASYNC_PARK, KEEP_RAM и GPU admissions выключены.
Между A/B меняется только CPU_RELEASE_WEIGHTS. Без GPU_FETCH_RELEASE_RAM
ненужные fetch leases могли бы скрыть эффект освобождения CPU-весов.

Каждая загрузка делает четыре прохода по трём режимам. Время фаз — среднее
последних двух; время всего workload и CPU-с процесса — все проходы после
загрузки модели. Физические счётчики SSD относятся к тому же периоду и могут
включать посторонний I/O. `file_bytes` движка включает чтение из файлового кэша ОС.

Начальные `off-a`, `phase-a`, `no-fill-off`, `no-fill-phase` использовали сборку
до добавления try-lock. Их результаты сохранены отдельно по SHA, но не входят
в итоговое сравнение скорости. Оно использует одну финальную сборку:
`15c49be921f49577d1c58895930277d7996cc3f34e677217a72753324944a9b0`.

## Скорость и размещение

Порядок отдельных загрузок финальной A/B/B/A: `off-b`, `phase-b`, `phase-c`,
`off-c`. Физическое чтение SSD за workload: 0 / 8192 / 0 / 0 байт.
Минимум свободной системной RAM — 64,30 ГиБ.

| Режим | Prefill 68, мс | Decode по 1, мс / 32 | Decode по 3, мс / 32 | Весь workload, с | CPU-с процесса |
|---|---:|---:|---:|---:|---:|
| A: CPU-веса до конца ветки | 2434,04 | 2052,27 | 1408,34 | 47,430 | 89,617 |
| B: освобождение по фазам | 2400,19 | 2030,34 | 1386,21 | 47,313 | 90,141 |

В одной этой серии время decode уменьшилось на 1,07% / 1,57%, полного workload —
на 0,25%; CPU time вырос на 0,58%. Отдельные A заняли 47,297 и 47,563 с, B —
47,515 и 47,110 с. Полный выигрыш меньше разброса и выбранного порога отбора 3%.
Устойчивое ускорение не подтверждено; сравнения полного решения с рабочим
GPU-only и длинным контекстом здесь нет. Рабочий профиль не переключён.

В каждом B выполнено 1139 CPU-заданий, раньше отпущены 2658 gate/up и 1310/1314
down leases. 25/21 попыток оставлены до конца ветки через безопасный fallback.
Учитываемое время освобождения — 1,902/1,905 мс за весь workload; сумма байтов
leases — 14 587 199 488 / 14 605 027 328, с повторным использованием блоков.

RAM fills выросли с 688 до 698, CPU jobs/rows изменились с 1143/1429 до 1139/1430.
Внутри повторов A и B полные logits signatures совпадают 12/12; между A и B —
9/12. Новый момент доступности RAM меняет последующее содержимое кэша и CPU/GPU
назначение. Результат с включённым fill не является побитным эквивалентом прежней
политики размещения, хотя отдельные арифметические ядра не изменены.

В отдельной паре `GPU_FETCH_RAM_MIB=0` совпали 12/12 полных logits signatures,
4642 fetch-ветки, 336 CPU jobs / 346 строк и объёмы RAM/file/H2D. Новое освобождение
реально выполнялось: 676 gate/up и 338 down leases, deferred=0. Обе пробы прочитали
0 физических байт с SSD. Это контроль транспорта без новых admissions RAM;
он не показывает ускорения полного workload (48,734 → 48,984 с) и не входит
в A/B/B/A выше. Выключенный режим финальной сборки также совпал 12/12 с сохранённой
предыдущей сборкой при той же политике освобождения GPU-снимков.

## DSpark и оставшиеся ограничения

DSpark Q8_0: target/draft GPU cache 15/1 ГиБ, общий RAM budget 2 ГиБ,
shared scratch, CPU12, max draft=2, GPU slots=4. KEEP_RAM, PRUNE, RELEASE_RAM,
EARLY_RETIRE, ASYNC_PARK и CPU_RELEASE_WEIGHTS включены. Пройдены A→B→A,
extension restore, fresh/full-prefill, один токен без draft, cancel prefill/decode
и greedy restore после отмены.

Строгий seeded restore **не пройден**: последовательности по 24 токена расходятся
на индексе 6. Обе совпадают с соответствующими последовательностями предыдущей
сборки. Исходный assertion и код валидатора 1 сохранены. Это не устанавливает
причину расхождения и не закрывает приёмку состояния.

На target выполнены 1374 fetch-ветки и 299 CPU jobs / 484 строки: раньше отпущены
676 gate/up и 335 down, deferred=18. На draft — 10 fetch-веток и одно CPU-задание /
две строки: отпущены 2 gate/up и 1 down, deferred=0. Финальные RAM `oom`, `pending`
и `retired_bytes` — 0. Этот прогон подтверждает совместимость путей, но не является
парным замером ускорения DSpark.

Этап 2 остаётся открытым: общий контекст ветки пока требует ожидания последнего
потребителя, рост пустого GPU-кэша и новый admission с демоцией не перенесены,
строгий seeded restore не пройден. Освобождение выбранных CPU-весов выполнено
с безопасным fallback; ожидание перед переиспользованием контекста — следующий
отдельный пункт. Режим остаётся выключенным по умолчанию.

## Артефакты

`build-local/deepseek4/cpu-phase-release-20261012/`: исходники до/после, сборки,
команды, конфигурации, логи, фиксированные входные IDs и результаты. Рабочий
GPU-only профиль и Qwen backend не меняются.
`summary.json` содержит сырые показатели и A/B/B/A, `parity.json` — результаты
сравнения logits и DSpark. `final-manifest.json` фиксирует сборки, исходники,
документы и файлы моделей. `turn-source.diff` отделяет этот шаг от ранее staged
изменений; индекс Git не менялся.

Воспроизведение: `build.bat`, `checks.py full`, `studies.py off-b phase-b phase-c
off-c`, `dspark.py`, `remaining.py`, `summarize.py`, `parity.py`.
`studies.py` не перезаписывает существующие результаты; для повторов нужны новые
имена, содержащие `phase` для включённой фичи и `no-fill` для выключенного RAM fill.
Настройки каждого запуска сохранены в его config. Проверять именно
`dspark-final-exit.json`: driver сохраняет ошибку валидатора, но сам возвращает 0.
