# О4: подготовка ветки и обслуживание RAM

14 октября 2026. Продолжение [проверки бюджета и пустой очистки](DEEPSEEK4_TRANSFER_O4_CPU_PROOF.md).

Расходы подготовки уменьшены, но итоговая скорость оказалась нестабильной.
Три основные серии N0 дали **15,311 → 16,383 ток/с (+7,00%)** и wall −4,08%.
Три дополнительные серии финального бинарника дали **15,588 → 15,796 ток/с
(+1,33%)**, при этом wall **+0,99%**; одна серия замедлилась на 5,90%.
H2D сохранён побайтно, CPU jobs/rows = 0. Устойчивый выигрыш полного запроса
не подтверждён; все три новых переключателя остаются выключенными.

## Изменения

Три независимые опции, по умолчанию выключены:

- `STRATA_DS4_CPU_PREP_FAST=1`: общие условия численной совместимости читаются
  один раз при попытке подготовить целую ветку, затем используются для трёх
  матриц. Отдельный отбор старого matrix CPU lane пропускается, когда этот lane
  выключен. Настройки не сохраняются навсегда: следующая попытка читает их заново.
  Проверки формы, типа, связей графа и допустимого размера окна остаются.
- `STRATA_DS4_ORDINARY_PREP_SPARSE=1`: обычный GPU-путь О3 готовит попадания,
  удержания и оценки частоты только для уже выбранных экспертов. Маршрут к этому
  моменту известен полностью. Выбор жертв по стоимости и частоте, порядок LRU
  при равенстве, защита других контекстов и правила current-branch victims
  сохранены. GPU-очередь, где маршрут ещё неизвестен, использует полный снимок.
- `STRATA_DS4_RAM_HISTORY_HASH=1`: история частот RAM использует хеш-таблицу и
  одно обращение для обновления записи. Ключ по-прежнему содержит идентичность
  файла, смещение и размер; слабая ссылка защищает от переиспользования адреса
  другого файла. Затухание, насыщение счётчика, лимит истории, порядок выбора
  RAM-жертв и политика prefill не изменены. Метаданные резидентности, которым
  нужен поиск диапазона, остаются в упорядоченных контейнерах.

Изменения ограничены отдельным backend DeepSeek. Арифметика экспертов, порядок
суммирования, передаваемые веса и алгоритм DSpark не менялись. Ограничение RAM
и проверки физической/commit-памяти сохранены. Настройки Qwen не менялись;
генерация Qwen в этой серии не проверялась.

## Измерения подготовки

`STRATA_DS4_PREP_PROFILE=1` добавляет интервалы host wall time без CUDA events
и дополнительных GPU-синхронизаций. `STRATA_EXPERT_TIMING` содержит подготовку
плана, обычного О3, CPU hook, завершение контекста, refresh/collect/promotion RAM
и запуск pipeline. Планировщик отдельно измеряет `cpu_lookahead` и `slice_plan`.

`STRATA_RAM_TIMING` выводит единственный общий снимок HostCache на границе фазы:
проверки памяти, метаданные чтения, получение mutex с reap, чтение источника, публикацию
и GPU-резидентность. Строку нельзя складывать для target и DSpark. Интервалы
вложены или перекрываются между потоками; их сумма не равна времени запроса.
`publish_ns` включает выделение/переиспользование, освобождение вытесненных
блоков и копирование payload, а не только `memcpy`.

Первые два профиля старой сборки выявили разницу N0/GPU-only в подготовке:
379/231 мс на два поздних decode по 32 токена. Уточнённый профиль исходного
алгоритма: CPU hook 174 мс, обычный О3 153 мс, RAM read metadata 50 мс,
проверки памяти 10 мс, публикация RAM 184 мс. Поэтому периодичность проверок
свободной памяти в этом опыте не снижалась.

Отдельная пара на сборке основных замеров (`experiment.exe`), два поздних
decode / 64 токена:

| Обычный О3 | 167,88 | 64,67 |

Это вложенные интервалы, не слагаемые. Число RAM-проб одинаково: 8613;

размещении; стоимость чтения и публикации payload почти не изменилась.

## Условия

Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows, PCIe Gen3 x16.
DeepSeek-V4-Flash-0731 UD-Q3_K_XL с H:, DSpark Q8_0, context 8192,
GPU-кэш target/draft 15360/1024 МиБ, draft-max=2. В обеих сторонах включены
обычный отбор О3 и GPU fallback при заранее исключённом CPU-назначении.

N0: 12 CPU-потоков, partitions=2, spin=0, RAM-cache 2048 МиБ,
CPU budget 0,01 мкс. Нулевое назначение проверяется по jobs/rows. Профиль
стоимости пересоздан для каждой сборки, автоматическое обновление выключено.
Предыдущие `CPU_BUDGET_PROOF_CACHE` и `CPU_EMPTY_CLEANUP_FAST` в замерах
производительности выключены с обеих сторон: измеряются только новые изменения.

Короткий процесс: четыре fresh-запроса по 15 входных / 32 выходных токена.
Первые два — прогрев. Скорость процесса: 64 / сумма секунд decode последних
двух запросов; сравнение серий — среднее этих скоростей. Wall и CPU-seconds
также относятся к двум последним запросам. Профилировщики выключены в замерах
скорости; отдельные диагностические процессы проверяют механизм изменения.

Кэш ОС не сбрасывался. Счётчики физического чтения относятся ко всему диску,
включая другие процессы. Новое приложение не означает холодный файловый кэш.
Сборка, калибровка, GPU-тесты и модельные процессы выполнялись последовательно.

## GPU-only и реальные CPU-задания

Отдельная A/B/B/A GPU-only, без CPU lane и дополнительного RAM-кэша:
**17,346 → 17,945 ток/с (+3,45%)**, wall **6,1560 → 6,0235 с (−2,15%)**,
CPU-seconds **−2,56%**. H2D прежний, позднее чтение H: = 0. Здесь улучшения
подготовки действуют на обычный GPU-путь; RAM hash при выключенном RAM-кэше
не участвует. Это одна серия, отдельно от трёх повторов N0.

Смешанный режим: CPU budget 1000 мкс, KEEP_RAM=2, demote=16 МиБ, те же
12 потоков и новая аппаратная калибровка. В A/B/B/A каждый поздний отрезок
выполнил 50 jobs / 68 rows; H2D одинаков: 26290752000 байт. IDs и acceptance
сохранены. Среднее **15,503 → 15,385 ток/с (−0,76%)**, wall **+2,73%**,
CPU-seconds **+5,64%**. Два B дали 14,853 и 15,917 ток/с: разброс заметен.
Ускорение со включёнными CPU-назначениями не подтверждено; результат N0
нельзя переносить на N+.

## Длинный контекст

A/B/B/A, по четыре запроса в процессе: fresh и restore 4096, затем fresh и
restore 8152 входных токена; в каждом случае 32 выходных, лимит 8192.

| Сценарий | Wall A, с | Wall B, с | Изменение wall | H: A / B, ГиБ |
|---|---:|---:|---:|---:|
| 4096 fresh | 29,789 | 25,750 | −13,56% | 28,633 / 8,618 |
| 4096 restore | 2,5625 | 2,5000 | −2,44% | 0 / 0 |
| 8152 fresh | 30,008 | 29,414 | −1,98% | 47,988 / 42,459 |
| 8152 restore | 2,0160 | 1,9295 | −4,29% | около 0 / 0 |

В одном restore 8152 у A счётчик всего диска показал 12 КиБ. Время decode
restore уменьшилось на 2,24% / 4,55%. Есть разброс между процессами: restore
4096 у B занял 2,313 и 2,687 с, у A — 2,422 и 2,703 с.

двух B — 9,099 / 8,138 ГиБ. Поэтому разница средних fresh не доказывает
ускорение полного prefill. Для fresh 8152 чтение тоже различается.

Все 16 запросов сохранили входные/выходные IDs и acceptance. H2D одинаков
побайтно для каждого сценария и фазы, CPU jobs/rows = 0 как в prefill,
так и в decode. GPU-only на длинном контексте этой серией не проверялся.

## Корректность

Основная сборка прошла 46 CTest: RAM-кэш, четыре комбинации CUDA Graph /
current victims для обычного О3, CPU fallback, пустые ветки, переходы графа,
перекрытие контекстов, GPU-очередь, DMA, demand/rank и assigned RAM.
Тест обычного О3 теперь проверяет полный и сокращённый снимки относительно
очереди: одинаковые GPU-результаты, H2D и admissions, отмена и частичная ветка.
Полный тест RAM выполняется с новой историей частот, включая давление памяти,
удерживаемые leases, отмену, затухание и ограничение метаданных.

На фиксированной истории совпали полные hashes logits и argmax всех 6 префиксов
и 86 шагов в hybrid, fallback и forced относительно GPU. В forced реально
выполнено 86 CPU jobs / 96 rows; CPU-работы в prefill нет.

Lifecycle прошёл A→B→A, продолжение, restore, fresh/full prefill, single token,
отмену и seeded repeat. Все 8 greedy-сценариев совпали с GPU-контролем;
выполнено 25 CPU jobs / 33 rows. Отдельный тест обновления профиля на восьми
запросах выполнил 208 jobs / 285 rows и поколения 0/1/2/3 при прежних IDs
и acceptance. Для последнего намеренно использован профиль с уменьшенными
вдвое compute costs: это проверка жизненного цикла, не измерение ускорения.

Эти проверки не закрывают отдельный вопрос batch/serial lossless DSpark,
описанный в общем плане. Сравнение ведётся с той же арифметикой GPU-контроля.

После основных измерений запись счётчика `prep_cpu_hook_ns` перенесена под
тот же mutex, который защищает остальные transfer counters. Это поправка
диагностики: правила назначения, загрузки и вычисления не менялись. Финальный
`final.exe` повторно прошёл 8 CTest с включённым профилировщиком, в том числе
численные проверки на 12/16 потоках и guards старого matrix lane. С учётом
основной серии проверены 48 различных CTest; отдельно повторён HostCache
с выключенной хеш-историей. Для финальной сборки создан новый профиль стоимости.

Финальный бинарник повторно сохранил точные logits 6 префиксов / 86 шагов
при 86 CPU jobs / 96 rows с включёнными таймерами. HostCache: 360 проверок
и 1200 конкурентных чтений. В отдельной паре финальный профиль подтвердил:
обычный О3 **159,47 → 69,09 мс**, CPU hook **183,73 → 73,86 мс**,
RAM read metadata **57,92 → 37,57 мс** на те же 64 токена. Чтение источника
при этом изменилось с 1147,25 до 1231,06 мс, публикация — со 165,07 до
180,12 мс; счётчики размещения и байты остались прежними.

## Решение и следующий шаг

Служебная подготовка ускорена; прирост N0 воспроизведён в части серий, но
финальная проверка не подтвердила устойчивое улучшение полного запроса.
GPU-only ускорился в отдельной основной серии; с реальными CPU-заданиями
прирост не подтверждён. Рабочая конфигурация
сервера не переключена, новые опции выключены по умолчанию, сервер не запущен.

Общий О4 остаётся открыт: N0 по-прежнему медленнее нового GPU-only, длинная
приёмка GPU-only ещё не выполнена. Следующая измеряемая задача — объяснить
разброс RAM-чтения и передач, отделить выделение/освобождение pinned RAM
от копирования при публикации и установить
стоимость оставшихся повторных CPU hooks в смешанном пути. Число memory probes
в этой серии не уменьшалось: их вклад мал и контроль давления памяти сохранён.
