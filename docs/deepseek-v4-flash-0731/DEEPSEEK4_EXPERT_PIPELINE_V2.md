# Очередь чтения и обновление GPU-кэша DeepSeek

3 октября 2026. Продолжение [первого конвейера](DEEPSEEK4_EXPERT_PIPELINE.md).
Изменения находятся в отдельном backend DeepSeek и применяются к target
и DSpark. Код движка Qwen не менялся.

Последующая оптимизация размещения матриц и её замеры:
[частотный допуск в GPU-кэш](DEEPSEEK4_FREQUENCY_CACHE.md).

## Что изменено

Четыре слота pinned RAM → H2D → VRAM теперь обслуживает ограниченная очередь
из 1–4 постоянных читателей. В Windows каждый читатель может отправить
отдельный `ReadFile` с `OVERLAPPED`, собственным событием и точным смещением
в исходном GGUF. Завершения чтений могут приходить в любом порядке; потребитель
получает матрицы в порядке плана. Отмена вызывает `CancelIoEx` и дожидается
завершения операции до повторного использования pinned-буфера. Дескриптор
файла живёт до завершения использующих его заданий.

При обычной замене матриц одинакового размера динамический GPU-кэш повторно
использует выделенную VRAM. На одном CUDA stream порядок операций достаточен;
между stream разных контекстов используются CUDA events. CPU больше не ждёт
`cudaStreamSynchronize` на каждой такой замене. Для поиска подходящего размера
просматриваются до 64 доступных записей у хвоста LRU. Нужные текущему плану
попадания остаются защищены от вытеснения.

Исправлен случай на границе резерва VRAM: запас 64 МиБ запрещал рост кэша
раньше достижения его логического лимита. Раньше новые матрицы тогда обходили
кэш, а старые записи переставали обновляться. Теперь подходящая по размеру
старая запись заменяется без нового выделения памяти. Ограничения числа
матриц, общего объёма и бюджета каждого backend сохраняются.

Полностью потреблённый план больше не требует отдельного CPU-ожидания всего
H2D stream. Безопасность повторного заполнения слотов обеспечивают события
`used`. При отмене загруженного хвоста ожидание его H2D остаётся.

## Режимы чтения

```text
--expert-pipeline 1 --expert-stage-mib 16 --expert-readers 2 --expert-read-mode auto
```

| Режим | Prefill, больше 8 токенов в графе | Decode и малые графы |
|---|---|---|
| `mmap` | Копирование отображённых страниц, до N читателей | Один постоянный читатель mmap |
| `auto` | Резидентные страницы через mmap, остальные через Windows overlapped reads, до N читателей | Один постоянный читатель mmap |
| `file` | Windows overlapped reads, до N читателей | Тот же путь, до N читателей |

Общий default — `mmap`, два читателя; сам конвейер по умолчанию выключен.
В локальных Q3-профилях с DSpark и без него выбран `auto`, два читателя,
конвейер включён. Их launcher применит настройки при следующем запуске.
На Linux `auto` остаётся на mmap, принудительный `file` отклоняется.
Реализация и производительность Linux в этом этапе не проверялись.

`auto` намеренно использует mmap для decode: чтение через файловый API может
попасть в RAM-кэш ОС, не сделав страницы отображения резидентными в working
set процесса. Первоначальная попытка выбирать API только по резидентности
оставляла даже прогретый decode на `ReadFile`: на этом ПК получалось 10,51
ток/с вместо примерно 18. Эта стратегия в итоговый вариант не вошла.

Количество слотов и их память не выросли. При staging 16 МиБ каждый backend
использует 64 МиБ pinned RAM и 64 МиБ VRAM для кольца, плюс прежние 32 МиБ
pinned RAM для резервного пути. Target + DSpark: 192 МиБ pinned RAM и 128 МиБ
VRAM колец; кэши матриц и остальные выделения модели считаются отдельно.

## Прогрев и SSD

Прогретые матрицы действительно можно читать из RAM без обращения к SSD.
Здесь используется файловый кэш ОС и mmap; это не закреплённый в RAM кэш всей
модели. Windows может вытеснять страницы при нехватке памяти. Другой текст
может выбрать матрицы, которых ещё не было в рабочем наборе.

И `ReadFile`, и mmap могут обслуживаться из RAM. Счётчик `file_bytes` в строке
`STRATA_EXPERT_IO` показывает байты через файловый API, а не физические чтения
SSD. `mmap_bytes` также не доказывает отсутствие дисковых промахов.
`read_peak` — максимум одновременно занятых читателей, включая ожидание
переиспользования слота; это не измерение глубины очереди устройства.

Для проверки добавлен параметр `--physical-disk PhysicalDrive6` в
`tools/benchmark_deepseek4.py`. Он записывает разность счётчиков чтения
физического устройства до и после каждого запроса. Счётчики включают все
процессы на этом диске. На данном ПК `PhysicalDrive6` соответствует H:,
Samsung SSD 990 PRO 4TB с основной моделью. DSpark находится на другом диске,
его физические чтения этим измерением не охвачены.

Итоговый запуск с фиксированным GPU-кэшем:

| Запрос | Физически прочитано с H:, байт | Операций чтения | Decode, ток/с |
|---|---:|---:|---:|
| Prefill 4096 и короткий ответ | 37 175 115 776 | 27 811 | — |
| Первая генерация, 128 токенов | 6 157 119 488 | 69 557 | 4,68 |
| Прогретый повтор 1 | **0** | **0** | 17,95 |
| Прогретый повтор 2 | **0** | **0** | 18,08 |
| Прогретый повтор 3 | **0** | **0** | 17,99 |

Это подтверждает отсутствие физических чтений SSD с основной моделью в трёх
измеренных повторах. Это не гарантия для другого текста или давления на RAM.

## Сравнение скорости

Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, CUDA 13.0,
драйвер 581.80. Target `DeepSeek-V4-Flash-0731 UD-Q3_K_XL`, DSpark Q8_0,
два draft-токена, контекст 8192, batch 4096, CPU threads 1, staging 16 МиБ.
Настроенные GPU-бюджеты target/draft — 15/1 ГиБ.

Русский запрос про L1/L2/L3: 36 входных и 128 выходных токенов, temperature 0,
три повтора с восстановлением prompt из RAM. Перед ним выполнялся отдельный
prefill: в фиксированном сравнении 256 токенов до изменения и 4096 после;
в обоих динамических запусках — 4096. Это замер генерации на коротком запросе,
не скорости decode на контексте 4096. Файловый кэш ОС не очищался.

| Политика GPU-кэша | Предыдущий конвейер, медиана ток/с | Текущий конвейер, медиана ток/с | Изменение |
|---|---:|---:|---:|
| Фиксированная арена | 17,84 | 17,99 | +0,9%, существенный прирост не установлен |
| Динамическая, настроенные бюджеты, резерв 1024 МиБ | 9,40 | 15,92 | +69,4% в этом сравнении |

Текущий динамический запуск: 15,62 / 15,92 / 15,95 ток/с. Все выходные token IDs
в соответствующих генерациях совпали между версиями. DSpark принял 78 из 98
предложенных токенов за 50 раундов в каждом повторе. В завершённых benchmark
запусках не было fallback или неиспользованных фрагментов конвейера.

Сравнение динамической политики включает все изменения вместе: способ чтения
prefill, обновление LRU и устранение ожиданий при повторном использовании VRAM.
Оно не выделяет вклад каждого изменения. Резидентность RAM между запусками
различалась: минимальная доступная RAM в прогретых фазах составляла около
1–1,6 ГиБ до изменения и 40 ГиБ после. Физические чтения старого запуска
не измерялись, поэтому весь выигрыш нельзя приписать только CUDA events.

Одиночный prefill 4096 занял 52,43 с в старом динамическом варианте и 9,24 с
в новом. В итоговом фиксированном запуске — 15,35 с. Из-за неконтролируемого
файлового кэша эти числа не доказывают устойчивый коэффициент ускорения prefill.

В новом динамическом запуске target повторно использовал выделения 125 570 раз;
из них 4 622 замены потребовали событий между stream. Физических освобождений
с ожиданием осталось 185. У DSpark — 6 608 переиспользований и 30 освобождений.
Окончательный общий GPU-кэш — 12 474 410 496 байт, 3 385 матриц; ошибок
выделения памяти не было.

В выборках прогретой генерации текущей фиксированной версии CPU-процесс
занимал в среднем 3,95–4,41% суммарной мощности 32 логических CPU. Это
обслуживание памяти, очередей и sampling. В проверенных вычислительных графах
`cpu_compute_nodes=0`; матричные операции модели выполнялись на GPU.

Локальные исходные данные в `bench/results/`:

- `deepseek4-pipeline-v2-before.json` — предыдущий фиксированный конвейер;
- `deepseek4-pipeline-v2-final-static.json` — текущий, с физическими чтениями H:;
- `deepseek4-pipeline-v2-managed-before.json` и
  `deepseek4-pipeline-v2-managed-after.json` — динамическое сравнение;
- журналы с теми же именами и расширением `.log`.

## Границы реализации

Проверки итоговой сборки: 6 CTest, 25 Python-тестов (`tools.test_deepseek4`,
`serve.test_deepseek`, `serve.test_vram_settings`), синтаксис JS и Python.
GPU-тест блокирует compute stream, проверяет готовность четырёх H2D-слотов
и побайтовое совпадение данных. Отдельно проверяются переиспользование VRAM
на одном и разных stream без ожидания CPU, кольцо с несколькими читателями,
чтение по дескриптору при запрещённом доступе к mmap, отмена и повторный запуск.
Тест динамического кэша покрывает замену при недостаточном запасе для роста.

Реальная Q3 + DSpark с `auto` и динамической политикой прошла A/B/A,
восстановление продолжения, один выходной токен, отмену prefill, отмену decode,
восстановление после отмены и повторяемый sampling с seed 123. Результат —
`bench/results/deepseek4-pipeline-v2-validation.json`, `passed=true`.
При STOP через 50 мс prefill завершился отменой без выходных токенов, но возврат
занял около 4,8 с: немедленного прерывания текущего CUDA-графа нет.
Известное различие полного повторного prefill и инкрементального продолжения
сохраняется (`full_prefill_identical=false`); точное восстановление сохранённого
состояния прошло. Это ограничение описано в [DEEPSEEK4_DSPARK.md](DEEPSEEK4_DSPARK.md).

SHA-256 проверенного `build-deepseek4/bin/strata-deepseek4.exe`:
`d0609f88c8c8e13e5fe250c35e211a027a4d975e4211314bb2091b7cc3e163ed`.

Реальное сокращение кэша при давлении на VRAM всё ещё требует безопасного
освобождения памяти с ожиданием CUDA. Замена матрицей другого размера также
может вызвать освобождение и новое выделение. Предсказания экспертов следующего
слоя нет: очередь планируется после получения router IDs текущего слоя.
Разбиение касается транспорта матриц; ядра matmul не выполняют матрицу
по мере прибытия её фрагментов. Между кольцом/кэшем и рабочим тензором остаётся
D2D-копирование. Это не устранение всех возможных пауз движка.

Семантика API: [Microsoft ReadFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile),
[ReOpenFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-reopenfile),
[CUDA events](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__EVENT.html).
