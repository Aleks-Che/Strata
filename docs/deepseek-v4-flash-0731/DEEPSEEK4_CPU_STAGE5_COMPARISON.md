# Этап 5: полная CPU/GPU-связка против рабочего GPU-only

Измерения 13 октября 2026 на Windows, Ryzen 9 9950X (16 ядер / 32 потока),
128 ГиБ RAM, RTX 5090 32 ГиБ. Target DeepSeek V4 Flash 0731 UD-Q3_K_XL на H:,
DSpark Q8_0. Этот отчёт проверяет итог этапов 1–4 относительно рабочего профиля.

Полная связка проигрывает в прогретом decode. Контроль с
активными GPU-очередями и **нулём CPU-заданий** тоже медленнее рабочего GPU-only.
Следовательно, ускорение CPU-ядра или уточнение его калибровки само по себе
не устраняет основную потерю. Рабочий профиль остаётся GPU-only.

## Условия

- Один GPU-процесс за раз; без параллельной сборки и калибровки.
- Контекст 8192, batch 4096, target GPU-кэш 15360 МиБ, draft 1024 МиБ,
  общий scratch, DSpark draft-max=2. Общий CPU `--threads=1`.
- A: рабочий `strata-deepseek4-ud-q3-k-xl-dspark.json`, CPU lane выключен.
  Включены пакетное копирование кэша, прямое чтение и ordered experts.
- B: полная связка этапа 4, CPU 12 потоков, не более одного CPU-эксперта,
  auto-план, быстрые совместимые ядра, общий RAM-кэш 2048 МиБ, GPU fetch queue,
  CPU GPU queue, context overlap, release/prune, демоция 16 МиБ,
  fetch RAM 32 МиБ / 4 cache slots, spin=0 / partitions=2.
  `CPU_COST_BURST=0`, `CPU_COST_AUTO=1`; запись TSV и снимков профиля выключена
  в измерениях полного запроса. Журнал подтверждает обновление профиля.
- C: A + `STRATA_DS4_SWIGLU_COMPAT=1`. Отделяет арифметику от новой подкачки.
- Z: B + `STRATA_DS4_CPU_BUDGET_US=0.01`, обновление профиля выключено.
  Профиль валиден, очереди работают, бюджет оставляет все вычисления на GPU.

Отдельная попытка B с нулём CPU-потоков **не является** контролем новых очередей:
планировщик выключает этот путь, `GPU_FETCH_QUEUE branches=0`. Её сырые результаты
сохранены как `pilot-1-storage`, но выводы о цене новых очередей на них не основаны.

Файловый кэш Windows не очищался. Новый процесс означает холодные собственные
кэши движка, но не гарантирует холодный SSD. Физические чтения измерены через
счётчики устройств `psutil.disk_io_counters(perdisk=True)`; H: соответствует
`PhysicalDrive6`, C: — `PhysicalDrive4` (проверено через storage device number).
Это весь трафик устройства, включая другие процессы. Логические чтения процесса
сохраняются отдельно и не называются чтениями SSD. Фазы prefill/decode привязаны
к сообщениям progress; их границы приблизительны, общий счётчик запроса точнее.

На другом устройстве, PhysicalDrive3, наблюдалось фоновое чтение и во время
контрольного простоя: 128–226 МиБ за две секунды после коротких серий.
На C: также были небольшие чтения. «Ноль чтений» в таблицах означает именно
**диск H: с target-моделью**, а не отсутствие любого I/O на компьютере.
Чужие процессы не останавливались; это ограничение абсолютных замеров.

## Полный запрос: три короткие серии A/B/B/A

12 отдельных процессов, по четыре в каждой серии. В каждом процессе шесть
прогревочных свежих запросов по 16 выходных токенов, затем четыре свежих
по 32 токена. Два prompt (372 и 15 токенов) чередуются. KV reuse отключён
разными session ID; файловый кэш ОС сохраняется между процессами.

На prompt 372 токена режимы A и B расходятся с 16-го выходного токена.
Отдельный C-прогон повторил все 10 ответов B, включая это расхождение:
источник — изменение режима SwiGLU. Суммарное время всех четырёх запросов
сохранено, но не используется как сравнение одинаковой вычислительной работы.

## Полный запрос: длинный контекст

Разведочная серия: A → B → неактивный storage-контроль → C → Z.
В каждом процессе сначала шесть коротких запросов, затем fresh и restore
для 4096 и 8152 входных токенов, по 32 выходных токена.
8152 + 32 + 8 резервных токенов занимают рабочий лимит 8192;
это не запрос с 8192 входными токенами. Восстановление действительно использовало
RAM-сессию: reused=4095 / 8151. Все prefill выполнялись на GPU.

| Вход / режим | Полный запрос A / B, с | Prefill A / B, с | TTFT A / B, с | Физическое чтение H: A / B, ГиБ |
|---|---:|---:|---:|---:|
| 4096 fresh | 26,391 / 22,718 | 14,093 / 14,194 | 14,500 / 14,797 | 36,725 / 28,309 |
| 4096 restore | 2,796 / 6,625 | 0,047 / 0,045 | 0,234 / 0,563 | 0 / 0 |
| 8152 fresh | 34,157 / 30,375 | 31,045 / 21,953 | 31,282 / 22,579 | 99,161 / 15,409 |
| 8152 restore | 2,375 / 6,313 | 0,071 / 0,074 | 0,250 / 0,563 | 0 / 0 |

Меньшее время B на fresh-запросах сопровождается другим объёмом чтения SSD.
Это измеренное время конкретного запуска, а не доказательство ускорения
GPU-prefill. Порядок запусков и состояние файлового кэша не позволяют приписать
разницу одной оптимизации хранения. Полные значения сохранены, включая первый
проход; они не смешиваются с прогретым decode.

| Восстановленный контекст | A, ток/с | C, ток/с | B, ток/с | Z, ток/с |
|---|---:|---:|---:|---:|
| 4096 | 11,654 | 11,493 | 4,866 | 4,950 |
| 8152 | 13,876 | 12,953 | 5,132 | 6,498 |

В строке 4096 все четыре ответа совпали по token IDs. В строке 8152 B, C и Z
совпали между собой, но отличаются от A. Поэтому для одинакового текста на 8152
сравниваются **C и B**, а A остаётся практической рабочей точкой сравнения.
У A/C/B чтение H: при restore равно нулю; у Z на 8152 прочитано 0,588 ГиБ.
Нулевые чтения в последней ячейке Z не предполагаются.

Acceptance на 4096: 18/26 у всех вариантов; на 8152: 18/26 у A,
18/27 у C/B/Z. Эти счётчики не заменяют сравнение token IDs.

## Одинаковая история без DSpark

Расширен [fixed_workload.hpp](../../backends/deepseek4/fixed_workload.hpp):
`STRATA_FIXED_PREFIX_TOKENS`, `STRATA_FIXED_REPEATS`, prefill несколькими batch
до размера контекста, явное выключение CPU lane на всём префиксе.
Прежние значения по умолчанию — prefix=36, четыре повтора.

Семь отдельных процессов: A/C/B на 68 входных IDs, C/B на 4096 и 8152.
Входы фиксированы; sampling и DSpark отсутствуют. Каждая фаза очищает KV,
но сохраняет экспертные кэши: полный prefill, prefix + 32 фиксированных токена
по одному, затем тот же prefix + 32 токена пакетами по три (последний — два).
Для короткого fixture два повтора, для длинных один. CPU-профиль заморожен на
весь диагностический запрос, измерения не обучают auto-refresh.

**C и B совпали:** 12 prefix-векторов и 172 проверенных decode-вектора.
Сопоставлены FNV-1a всех байтов полного массива logits и argmax; NaN/Inf нет.
Это сравнение одинаковых окон между C и B, а не утверждение равенства
арифметики окна 1 арифметике окна 3. A имеет другие decode-хэши из-за SwiGLU.

| Prefix / шаг decode | Время 32 фиксированных токенов C, с | B, с |
|---|---:|---:|
| 36 / 1, повтор 2 | 1,460 | 6,022 |
| 36 / 3, повтор 2 | 0,954 | 4,484 |
| 4064 / 1, первый проход | 8,846 | 10,477 |
| 4064 / 3 | 2,408 | 5,457 |
| 8120 / 1, первый проход | 13,561 | 11,284 |
| 8120 / 3 | 2,386 | 6,451 |

В одном длинном проходе по одному токену B оказался быстрее C. Он не повторён
как отдельная парная серия; состояние кэшей не выровнено, физическое чтение
измерено за весь fixture, а не за каждую внутреннюю фазу. Этот локальный результат
не объявляется ни ошибкой, ни доказанным выигрышем прогретого CPU lane.
Полное время fixture 8152 с загрузкой: C 83,813 с, B 88,203 с.
Основной вывод о прогретой генерации основан на полном DSpark-сравнении выше.

TSV подтвердил действительные CPU-вычисления: 2540/938/896 заданий и
3482/1327/1278 строк для короткого/4096/8152 fixture. **CPU-заданий в prefill — 0**;
все CPU-строки относятся к decode. Профиль загружен с совпадающим fingerprint.
Сырые результаты `fixed-*.json/.tsv/.log`, сводки `fixed-summary.json` и
`fixed-parity.json` сохраняют также первые проходы и время каждого prefill.

## Состояние и численные ограничения

Отдельная диагностическая серия C/B: fresh 4096 → fresh 8152 → restore 4096 →
restore 8152, по 8 выходных токенов. В обоих режимах восстановленные ответы
повторились, cache_source=ram, reused=4095/8151; все ответы C и B совпали.
Измерения этой серии не включены в таблицы скорости из-за дополнительных
снимков состояния и повторных вычислений.

В каждом режиме:

- 12 подмен будущих draft-ID: max logit diff текущего токена = 0.
- Четыре replay из одного pre-decode snapshot: max abs = 0.
- Четыре сравнения batch/serial, 12 target-строк: argmax совпал, но logits
  не совпали, max abs = 2,231445. Все сохранённые расхождения **одинаковы у C
  и B**. Это ограничение пакетной арифметики данного GPU-профиля; приёмку
  lossless batch/serial эти результаты не закрывают. CPU/GPU-сравнение одного
  и того же окна в fixed fixture выше прошло.

Настройки CUDA Graphs не отключались; CPU lane использовал external events.
Отдельного счётчика CUDA Graph replay эти измерения не добавляют: точный replay
выше означает повтор `llama_decode` после восстановления состояния.
Артефакты: `long-state*`, `long-state-gpu*`, `long-state-summary.json`.

Дополнительно:

- Строгий lifecycle после трёх прогревочных запросов прошёл: 8/8 greedy-сценариев
  совпали с сохранённым GPU-compatible контролем этапа 3. Проверены A→B→A,
  продолжение и его восстановление, fresh/full-prefill, один выходной токен,
  отмена prefill/decode, повтор после отмены и seeded repeat.
  В запросах использовалось обновлённое поколение 1; отменённые и seeded-запросы
  не обновили профиль. Seeded по прежней политике вычисляет экспертов на GPU;
  это не отдельная проверка точности CPU-арифметики. Артефакты `lifecycle*`.
- Нативный `deepseek4_cpu_gpu_queue` прошёл: 168 689 проверок, 1500 настоящих
  CUDA Graph replay, включая 300 async rearm, 80 deferred consumers и 80 gated
  handoffs; full/error/cancel/timeout. Журнал `queue-graph-ctest.log`.
- Qwen executable запускается с `--help`, exit 0; окружение Qwen не содержит
  `STRATA_DS4_*`. **Генерация Qwen не проверена:** файл модели из действующей
  конфигурации `H:/Q8_0/Qwen3.8-Flash-Next-Q8_0-00001-of-00006.gguf` отсутствует.
  Рабочий Qwen-конфиг и backend не изменены. Артефакты `qwen-smoke.json`,
  `qwen-help.log`; запуск справки не выдаётся за запуск модели.

Решение по этапу 5: **не включать полную связку по умолчанию**. Критерий улучшения
полного запроса относительно рабочего GPU-only не пройден. Для будущего кандидата
остаются повтор длинных target-only измерений с учётом I/O, полная lossless
batch/serial приёмка и проверка генерации Qwen при наличии его файлов.
Повторять весь набор настроек старых CPU-ядер и host-запуска ради включения
данного кандидата нет основания: даже контроль Z без CPU-арифметики проигрывает.

## Что отделяют контрольные варианты

В полном пилотном процессе Z журнал подтвердил 4860 проходов GPU fetch queue
и ровно 0 CPU-заданий / 0 CPU-строк. При этом короткий прогретый decode остался
около 4–5 ток/с. Одна совместимая арифметика C сохраняет около 10–12 ток/с.
Таким образом, большая потеря присутствует уже в новой инфраструктуре
планирования и подкачки без вычисления экспертов на CPU.

Это не локализация до отдельной функции. В Z всё ещё работают CPU-service,
подготовка RAM-кандидатов, план на GPU, публикация запросов подкачки и ожидания.
Бюджет CPU, равный нулю, не возвращает старый быстрый GPU-путь. Offline-калибровка
сравнивает ветки внутри нового пути и не учитывает всю разницу с рабочим путём.

Следующая оптимизация должна сначала уменьшить стоимость **Z относительно C**:
измерить подготовку кандидатов, план на GPU, публикацию/fetch, ожидания и join;
сохранить быстрый GPU-путь там, где CPU не назначен. Только после этого имеет
смысл повторять настройку числа CPU-экспертов и адаптации профиля.

## Воспроизводимость

Последующая [локализация замедления при нуле CPU-заданий](DEEPSEEK4_ZERO_CPU_QUEUE_AUDIT.md)
отделила новый GPU fetch от остальной инфраструктуры: на одинаковом коротком
прогретом запросе 12,71 против 5,20 ток/с в A/B/B/A. Отчёт содержит счётчики H2D,
микротест транспорта и ограничение обходного пути с реальными CPU-заданиями.
Это отдельный набор запросов и истории кэша; абсолютные скорости не сравниваются
с таблицами этапа 5 как ускорение новой сборки.

Сырые конфигурации, входные и выходные IDs, журналы, периодические CPU/RAM/VRAM
наблюдения и счётчики I/O: `build-local/deepseek4/stage5-20261013/`.
Интервал CPU/RAM/VRAM наблюдений — 2 секунды; пики короче интервала могут
не попасть в выборку. CPU-seconds измеряются на границах запроса, отдельно
от нормированного процента использования всех 32 логических процессоров.

Инструмент: [benchmark_deepseek4_stage5.py](../../tools/benchmark_deepseek4_stage5.py).
Каждому запуску нужен новый путь результата:

```powershell
.venv/Scripts/python.exe tools/benchmark_deepseek4_stage5.py `
  --config build-local/deepseek4/stage5-20261013/gpu-config.json `
  --requests build-local/deepseek4/stage5-20261013/compare-requests.json `
  --output build-local/deepseek4/stage5-20261013/recheck-gpu.json
```

Для гибридной конфигурации требуется `--allow-cpu-lane`. Инструмент проверяет
режим движка и отсутствие KV reuse у fresh-запросов. Он не изменяет рабочий pack
или конфигурацию сервера и не очищает файловый кэш ОС.

`7f5023651d3eadb1f2dffb6e038edd4d9bf7762fe98a7f94a1c90038dbec3b1a`.

`d90b4cf42f1c06a9dccb19820e7a392a273cf147b96ed6ee97a89c52b93da950`.
