# О3: защита RAM по фактическому назначению CPU

14 октября 2026. Продолжение [ранжирования target](DEEPSEEK4_TRANSFER_O3_TARGET.md).

В одной A/B/B/A новое правило дало **13,31 → 13,97 ток/с (+4,98%)**,
wall **−3,27%**, H2D **−4,59%** относительно прежнего `KEEP_RAM=1`
с реальными CPU-заданиями. Преимущество перед `KEEP_RAM=0` не установлено;
GPU-only быстрее. Рабочий профиль не изменён.

## Изменение

`STRATA_DS4_GPU_FETCH_KEEP_RAM=2` ограничивает запрет GPU admission экспертами,
действительно назначенными CPU в текущей ветке. Прежнее значение 1 запрещает
admission всех готовых и подходящих RAM-троек, в том числе после отказа
CPU-плана. Значение 0 и значение по умолчанию остаются без запрета.

Используется уже опубликованный полный маршрут и `cpu_selected`: он учитывает
каждое CPU-вхождение эксперта, включая смешанные CPU/GPU строки. Только маски
`cpu_only` недостаточно. При отказе по бюджету готовая тройка не мешает GPU-кэшу;
частота, стоимость вытеснения и все прежние проверки читателей действуют дальше.

Правило одинаково в GPU publisher, owner demand admission и проверке I/O-service.
До публикации маршрута предварительный резерв учитывает возможные GPU-промахи.
Дополнительных ожиданий, копирований, матриц или кэша истории нет. Защита действует
одну ветку, ограничена её 64 маршрутными позициями и прежними бюджетами RAM/VRAM.
Это не защита полезных троек на несколько следующих запросов: такой прогноз
не добавлялся. Существующие leases удерживают CPU-данные до окончания чтения.

В снимках добавлены `ram_bypasses`, `ram_unblocked`, `ram_promoted`: соответственно
GPU-промахи с действующим запретом, готовые кандидаты без фактического CPU-назначения
в режиме 2 и выполненные admissions из второй группы. Счётчики считают матрицы,
не целые тройки. Отказ ранжирования может оставить `unblocked` без `promoted`.
`ram_bypasses` теперь учитывает demand-отказы и при нуле предложенных слотов;
прежде он требовал непустое окно предложений и мог их недосчитывать.

Код: [gpu_fetch_queue.cuh](../../backends/deepseek4/gpu_fetch_queue.cuh),
[gpu_fetch_cache.inc](../../backends/deepseek4/gpu_fetch_cache.inc),
[cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc).

## Условия проверки

Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows, CUDA 13.
DeepSeek-V4-Flash-0731 UD-Q3_K_XL + DSpark Q8_0, context 8192, draft-max 2.
GPU-кэши 15360/1024 МиБ, RAM-кэш 2048 МиБ, DMA depth 8, staging 4 МиБ,
четыре сегмента, reader mapped. Demand для обоих кэшей, rank 1 / 256 только
для target. Current victims 0, context overlap 0, подробная трасса выключена.

Для сравнения правил KEEP_RAM демоция 16 МиБ включена во всех трёх режимах,
чтобы были готовы RAM-тройки. Это отдельная серия относительно прошлого
лучшего N0 с демоцией 0. CPU-профиль пересоздан для сборки, 12 потоков,
автообновление выключено. Нулевой режим использует бюджет 0,01 мкс;
реальное назначение проверяется счётчиками. В варианте auto лимит снят.

Четыре fresh-запроса по 15 входных / 32 выходных токена в каждом процессе.
Первые два — прогрев, измеряются последние два. H2D, wall и CPU-seconds —
их суммы; decode — 64 токена / суммарное decode-время. Кэш ОС не очищался.

Артефакты: `build-local/deepseek4/transfer-o3-ram-20261014/`.
EXE SHA256: `42006fa17ed2b927f583536b09e40ec3c765997bec6d93368bcbecf447556e25`.
CPU cost build ID: `c771b18891c6dcd19f70e843b9b5fab25134b1f612ae2f1a66e277a85efe679e`.

Новая политика меняет накопленное состояние кэша уже при прогреве; эффект
не объясняется только тремя admissions последних двух decode. Часть матриц
становится GPU-резидентной и больше не проходит правило CPU all-miss eligibility.
Уменьшились и H2D, и CPU-работа. Это результат размещения и дальнейшего
распределения работы, не ускорение CPU-арифметики при одинаковом наборе заданий.
Поздних D2H в этой серии нет, хотя демоция разрешена в конфигурации.

Во всех 13 скоростных процессах совпали входы, output IDs и acceptance
(14/33 в каждом запросе). Prefill CPU rows = 0. Короткие prefill не доказывают
отсутствия регрессии на длинном контексте.

## Корректность и границы

Прошли 29 CTest: прежние queue/demand/rank и KEEP_RAM=1, новые проверки режима 2
на mapped/DMA-пути, CUDA Graph on/off, arena/managed, IQ3_XXS/MXFP4/Q8_0,
реальное CPU-назначение, освобождение и восстановление кэша, отмена.
Тест публикации включает эксперта со смешанными CPU/GPU строками и готового
кандидата без назначения CPU, которому действительно достаётся GPU-слот.

Ещё два запуска combined-context fixture с KEEP_RAM=2, demand, frequency rank,
current victims и DMA window дали по 108 точных последовательных повторов.
Они выполнены отдельно от перечисленных 29 CTest.

Fixed-history относительно совместимого GPU-only: совпали хеши полного вектора
logits и argmax всех шести префиксов и 86 шагов. Выполнены 18 CPU jobs / 20 rows;
prefill CPU rows = 0. Включены KEEP_RAM=2, rank target 1 / 256, демоция 16 МиБ
и context overlap 1.

Lifecycle прошёл A→B→A, восстановление и продолжение сессии, сравнение с полным
prefill, отмену prefill/decode и повтор с одинаковым seed. Все восемь greedy
сравнений совпали с сохранённым совместимым GPU-only контролем. Выполнены
107 CPU jobs / 146 rows, поколения runtime-профиля 0→1. Для этой проверки
дополнительно включён current victims.

Сохранены EXE, профиль, конфигурации, запросы, JSON, трассы, логи, исходники,
`ram-only.diff` относительно предыдущего target-опыта и SHA256 manifest.
Предыдущие архивы не перезаписываются. Длинные контексты 4096/8152, Linux
и генерация Qwen в этой серии не проверялись. Прежний отдельный вопрос
lossless batch/serial DSpark не закрыт.

Пункт О3 о фактической RAM-защите выполнен в пределах ветки. Вместе с прошлой
серией target пройдены локальные критерии О3 для короткого N0; это не общая
приёмка гибридного режима. Перед изменением рабочего профиля остаются О4–О6
и длинный контекст; критерий staging 90% из О2 также остаётся открытым.
