# BF16 router: одинаковая арифметика короткого batch и serial

10 октября 2026. Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090
32607 МиБ, CUDA 13. Продолжение [изолированного attention](DEEPSEEK4_ATTENTION_FIXTURE.md).

**Причина расхождения первого MoE — дополнительное округление активаций
router в пакетном BF16-ядре.** Выбранные IDs и результаты экспертных матриц
совпадали; различались веса смешивания. Добавлен отключаемый переход на
MMVF для router batch 2–4. С прежними экспериментами attention и MMVQ
выходы первых трёх слоёв теперь совпадают во всех 25 проверенных строках.
Эквивалентность всей модели ещё не достигнута.

## Как локализована причина

Q3 target, DSpark Q8_0, draft-max=2, контекст 8192, кэши 15360/1024 МиБ.
Уплотнение raw attention включено, `--mmvq-token-batch 2`. Prefill 256 токенов,
отдельный запрос 36 токенов, 4 выходных токена и повтор.

Начальная серия — 21 строка из 7 проверочных пакетов:

| Узел слоя 0 | Максимальная разница batch/serial |
|---|---:|
| Вход FFN | 0 |
| Router logits | 0,00438857 |
| IDs выбранных экспертов | 0 |
| Нормализованные и масштабированные веса маршрутов | 0,000395209 |
| Выход экспертной down-проекции до смешивания | 0 |
| Взвешенный результат MoE | 0,000952244 |

В первых трёх слоях текстовые токены выбирают экспертов по таблице hash
routing. Одинаковые IDs здесь не означают одинаковые веса их смешивания.
Эффект трассировки на batch и на serial в этой серии — 0, replay — 0.

У router матрица BF16 4096×256, активации F32. В закреплённом CUDA backend
одиночный токен использует MMVF с F32-активациями и накоплением. На RTX 5090
batch 2–4 переходит на MMF; его Tensor Core путь округляет активации в BF16.
Накопление F32 не отменяет это округление входов.

## Изменение

[RouterPatches.cmake](../../backends/deepseek4/RouterPatches.cmake) проверяет
SHA-256 исходного CUDA dispatch и добавляет
[router_mmvf.inc](../../backends/deepseek4/router_mmvf.inc) в частную копию
DeepSeek backend. Изменение не затрагивает закреплённую зависимость и Qwen.
Правки `.inc` включены в зависимости конфигурации CMake.

`STRATA_DS4_ROUTER_MMVF=1` разрешает один пакетный запуск MMVF при условиях:

- NVIDIA, BF16-матрица 4096×256, один канал и одна последовательность;
- имя веса заканчивается на `.ffn_gate_inp.weight`;
- F32-вход/выход, точность накопления F32, batch 2–4;
- поддерживаемые MMVF strides/выравнивание и непрерывный выход.

В остальных случаях сохраняется штатный dispatch. Один токен не меняется.
Нет отдельных запусков по каждому токену, нового формата весов или CPU-графа.
При отсутствии переменной новый путь выключен. Переменная задаётся до старта
процесса; в работающем движке режим не переключается.

## Проверка операции

[test_router_batch.cpp](../../backends/deepseek4/test_router_batch.cpp)
сравнивает CUDA batch, независимые одиночные CUDA-запуски и скалярный FP64
по фактическим BF16-весам. Второй эталон дополнительно округляет вход в BF16,
чтобы проверить источник ошибки. CPU считает только маленький тестовый
эталон; инференс модели остаётся на GPU.

**216 сценариев прошли.** Проверены BF16/F16/F32, batch 1/2/3/4/5/16,
обычные и увеличенные strides, другое имя веса, другое значение precision,
контрольная форма 512×64. В шести применимых случаях новый результат
побайтово совпал с serial; в остальных 210 — со штатным результатом.

Максимальная ошибка по FP64 на применимых случаях:

- штатный batch с исходными F32-активациями: **0,012844757**;
- тот же штатный выход, но эталон с BF16-активациями: **0,0000037323**;
- новый MMVF с исходными F32-активациями: **0,0000010156**.

Такое сравнение подтверждает дополнительное округление входа как причину
основной ошибки в этой операции. Это не измерение качества всей модели.

Время операции, непрерывный вход, медиана четырёх чередований:

| Токенов | Штатный batch, мкс | Новый MMVF, мкс |
|---|---:|---:|
| 2 | 30,278 | 27,638 |
| 3 | 30,133 | 27,916 |
| 4 | 31,291 | 29,085 |

Веса и активации уже на GPU, 8 warmup, 100 запусков, CUDA graphs выключены.
Это CPU wall time с GPU-синхронизацией после серии, включая dispatch.
Уменьшение времени этой маленькой операции на 7–9% не переносится напрямую
на скорость генерации.

## Проверка модели и следующая граница

После включения router MMVF, вместе с прежними MMVQ2 и compact attention1:

- router logits, IDs, веса маршрутов, limited SwiGLU, down и выход слоя 0
  совпали на **25/25 строках**;
- выходы слоёв 0, 1 и 2 совпали на всех 25 строках;
- следующая разница — HCA-attention слоя 3: max **0,000922203**;
- выходная проекция этого attention: max **0,00444837**;
- итоговые logits пока расходятся до **3,42724**.

У последних двух достоверных проверок эффект трассировки на batch/serial
и replay — 0. Q и текущий KV перед HCA совпадают. **Фактические видимые
ключи объединённого raw/compressed cache и HCA-маска ещё не сопоставлены**:
нельзя пока приписывать всю разницу только ядру Flash Attention.

Расширенная трассировка внутренних узлов слоя 3 меняла итоговые logits
до 3,33796 у batch и до 2,26845 у serial, поэтому её численные результаты
не использованы как доказательство. Граница HCA подтверждена повторно
минимальным набором точек без такого эффекта.

Внутренние сравнения batch/serial выполняются из одного состояния.
Траектории генерации разных режимов могут отличаться; максимум ошибки до
и после изменения не является попарной оценкой качества режимов.

## Скорость всей модели

Четыре запуска **A/B/B/A** на итоговом обычном бинарнике; A — router MMVF
выключен, B — включён. Compact attention и экспериментальный MMVQ выключены
в обоих вариантах. Профиль Q3 + DSpark2 прежний, 64 выходных токена,
два повтора русского запроса и два цикла английский/русский. Трассировки нет.

| Серия | Два прогретых повтора, ток/с | Смена запросов после первого английского, ток/с | CPU-с на прогретый ответ |
|---|---:|---:|---:|
| A1 | 20,579 | 15,853 | 4,141 |
| B1 | 20,483 | 16,229 | 4,336 |
| B2 | 20,644 | 16,231 | 4,344 |
| A2 | 20,876 | 15,807 | 4,195 |

Скорость агрегирована как сумма выходных токенов / сумма decode-времени.
Столбец смены запросов объединяет `switch_1_original`, `switch_2_alternate`,
`switch_2_original`. Первое чтение нового английского запроса вынесено из
этого сравнения: оно включает подгрузку холодных весов с H:.
В измеренных прогретых повторах и трёх указанных переключениях физические
чтения H: равны 0 во всех четырёх сериях.

**Устойчивого выигрыша на повторе нет.** При переключениях наблюдается около
2,5%, но token IDs между A и B различаются. Принятие DSpark тоже изменилось:
у русского запроса 38/51 → 37/52, у английского 34/59 → 35/57.
Внутри каждого режима IDs воспроизвелись между двумя запусками. Поэтому
результат смены запросов нельзя считать чистым ускорением той же работы.
Новый router оставлен выключенным в рабочем профиле; польза этого этапа —
устранение доказанного округления и продвижение проверки batch/serial.

В четырёх сериях скорости 599/603/603/599 аудитов, везде
`cpu_compute_nodes=0`. В достоверных численных сериях route/fixed/layer1/
layers/hca также нет вычислительных CPU-узлов: 29/35/35/35/35 аудитов.

## Регрессионные проверки

На итоговой сборке прошли **18/18 CTest** (61,41 с) и **25 Python-тестов**
`serve.test_deepseek`, `tools.test_deepseek4`, `serve.test_vram_settings`
(2,251 с).

С `STRATA_DS4_ROUTER_MMVF=1` отдельно проверен настоящий Q3 target с DSpark2
и без draft-модели. Оба запуска `validate_deepseek4_speculative.py` завершились
с `passed=true`: восстановление сессии после другого запроса, продолжение
активной сессии и его восстановление, один выходной токен, отмена prefill и
decode, повтор после отмены и воспроизводимость sampling с фиксированным seed.

Восстановленные сессии воспроизвели свои token IDs. Но продолжение активной
сессии и обработка того же полного prompt с нуля при DSpark всё ещё дают
разные IDs (`full_prefill_identical=false`); без DSpark в этом сценарии они
совпали. Успех проверок состояния не означает устранения расхождений всех
вариантов batch. В логах DSpark — 351 GPU-аудит, без DSpark — один; везде
`cpu_compute_nodes=0`.

## Воспроизведение

После сборки backend:

```powershell
cmake --build build-deepseek4 --target strata-deepseek4 deepseek4_router_batch_test -j 2
ctest --test-dir build-deepseek4 -R deepseek4_router_batch --output-on-failure
```

Для проверки модели добавить в `env` отдельного экспериментального JSON-профиля
`"STRATA_DS4_ROUTER_MMVF": "1"`. Проверки первых трёх слоёв дополнительно
требуют сборки с compact attention, соответствующего флага, MMVQ2 и serial
activation probe из предыдущих отчётов. Эти диагностические режимы не
используются в измерении скорости.

Материалы в `bench/results`:

- `ds4-moe-20261010-router-fixture.{json,log}` — 216 сценариев и времена;
- `ds4-moe-20261010-route.{json,jsonl,log}` — локализация BF16 router;
- `ds4-moe-20261010-fixed.{json,jsonl,log}` — слой 0 после исправления;
- `ds4-moe-20261010-layer1.{json,jsonl,log}` — следующий слой;
- `ds4-moe-20261010-layers.{json,jsonl,log}` — границы всех 43 слоёв;
- `ds4-moe-20261010-hca.{json,jsonl,log}` — минимальная проверка слоя 3;
- `ds4-moe-20261010-layer3.{json,jsonl,log}` — трассировка с ненулевым
  влиянием наблюдения, не используется для доказательства.
- `ds4-moe-20261010-perf-{a1,b1,b2,a2}.{json,log}` — сравнение скорости,
  token IDs, CPU time и физические чтения H:.
- `ds4-moe-20261010-validate-{dspark,plain}.{json,log}` — восстановление
  сессий, отмена и воспроизводимость с включённым router MMVF.

Профили и команды сохранены в `build-local/deepseek4/moe-20261010`.
SHA-256 итогового обычного бинарника:
`29dba8891cdab736f534643d4caaaacabffac734f1c2087e59fc02469d44d3b9`.
Численная диагностика с compact attention выполнена на бинарнике
`40628cad0b8a6d5d3825d6b0073f2abeea81515ef14d77ee166f41f41ca44747`,
сохранённом как `experiment.exe`. Итоговый CMake-кэш оставлен с
`STRATA_DEEPSEEK_ATTENTION_EXPERIMENT=OFF`.
Следующий численный шаг — сопоставить видимые raw/compressed K/V и маску HCA
при одном состоянии и разном размере batch. Затем проверять сохранение
порядка операций HCA, полные logits и DSpark на длинном контексте.

Этот этап продолжен в [отчёте HCA](DEEPSEEK4_HCA_COMPACT.md): видимые входы
совпали, уплотнение устранило расхождение полных logits на коротком контексте.
На 4096 токенах отдельно проверен порядок операций CSA.
