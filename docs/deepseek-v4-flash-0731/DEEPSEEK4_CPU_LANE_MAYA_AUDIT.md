# CPU lane: что потерялось при переносе из Maya

Реализация по этому разбору: [CPU lane v2](DEEPSEEK4_CPU_LANE_V2.md).
Ниже сохранён аудит первого матричного прототипа.

12 октября 2026. Сравнение локальных исходников `project-maya` и DeepSeek backend, с проверкой логов `ds4-cpu-lane-20261012`. Новых запусков модели для этого разбора не было; Maya на этом ПК не измерялась. Условия и результаты прежних запусков — в [отчёте CPU lane](DEEPSEEK4_CPU_LANE.md).

Главная ошибка нашего переноса — слишком мелкая граница CPU-вычислений. В Maya CPU считает целого эксперта, а результат требуется в конце GPU-ветки MoE. Наш прототип считает отдельные матрицы с промежуточными обменами и ожиданиями. Мы перенесли CPU kernels, но не весь механизм, который может сделать их выгодными. Отрицательные замеры проверяют этот прототип, а не CPU lane вообще.

## Что показывают замеры

Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, H: Samsung 990 PRO. Target UD-Q3_K_XL, DSpark Q8_0, draft max 2. Последний из трёх повторов генерации 64 токенов из RAM-сессии; физическое чтение H: во всех случаях — 0.

| Режим | Скорость, ток/с |
|---|---:|
| GPU, первый контроль | 16,613 |
| CPU 4 | 11,958 |
| CPU 8 | 12,223 |
| CPU 12 | 10,109 |
| CPU 16 | 9,524 |
| GPU, последний контроль | 16,466 |

Сумма `STRATA_EXPERT_TOTAL.h2d_bytes` по target и draft **за весь процесс**: GPU — 393 411 709 952 байта, каждый CPU-вариант — 353 025 030 144 байта. Разница — 40,387 ГБ, около 10,3%. Это передачи экспертных весов, не весь PCIe-трафик. В сумму входят два больших prefill и несколько генераций; CPU/GPU ответы и acceptance DSpark различались. Поэтому разницу нельзя считать изолированной экономией decode или делить на время последнего повтора.

Все четыре CPU-варианта выполнили по 13 769 CPU-матричных операций. Логически исключённые веса — 50 863 485 952 байта; это не разница фактических передач между процессами. При переходе с 4 на 16 workers хвост ожидания `wait_us` уменьшился с 0,650 до 0,300 с за весь процесс, `input_us` — с 1,875 до 1,722 с. Генерация замедлилась. Эти счётчики не включают всю работу выбора, проверки RAM, квантизации, возврата результатов и запуска графа. Они не позволяют установить вклад каждого источника задержки.

У CPU4/8/12/16 совпали суммарные объёмы передачи весов, число CPU-операций и текст третьего ответа. Источники: `bench/results/ds4-cpu-lane-20261012-{a1,b2,c1,d1,e1,a2}.log` и `.json`. Методика и SHA256 бинарника приведены в отчёте CPU lane.

## 1. Граница вычислений проходит внутри эксперта

**Maya:** `Glm5Model::lane_experts()` квантует вход один раз, считает gate/up, SwiGLU и down, возвращает взвешенный вклад CPU-экспертов. Промежуточные тензоры остаются на CPU. См. [glm_fast_path.cu](../../../project-maya/src/core/glm_fast_path.cu), `lane_experts`, около строк 1562–1688.

**У нас:** [cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc), `strata_cuda_expert_cpu_begin()`, копирует вход текущей матрицы на CPU и синхронизирует stream. [StrataCpuLane](../../backends/deepseek4/cpu_lane.cuh) квантует входы, считает строки и возвращает их на GPU. SwiGLU остаётся в GPU-графе. CPU выбирается независимо для отдельных матриц: контракта «этот эксперт целиком на CPU» нет.

**Что менять:** единое задание `gate/up → SwiGLU → down`. Матричный GPU-кэш можно сохранить: единицы хранения и вычисления не обязаны совпадать. Решение должно учитывать состояние всех трёх матриц, чтобы не отдавать CPU уже выгодную GPU-часть. Нужно сохранить именно DeepSeek SwiGLU/clamp, веса router и порядок объединения результатов; копирование GLM-функции этого само по себе не обеспечивает.

## 2. Промежуточные host-ожидания и потеря CUDA Graphs

**Maya:** GPU публикует маршрут и вход в mapped pinned ring. Отдельный service thread считает CPU-экспертов, пока GPU получает и считает остальных. `moe_cpu_wait()` стоит после GPU down. В поддерживаемом пути `fast_layers()` CUDA Graph включает CPU-план в ключ `LayerGraphs::Key{F->cpu_plan, Rc, Ro}`. Это не означает, что любой слой любой модели Maya исполняется в CUDA Graph. См. [glm_fast_path.cu](../../../project-maya/src/core/glm_fast_path.cu), service около 3439, `fast_moe` около 4389, `fast_layers` около 4539; [glm_fast.cu](../../../project-maya/src/kernels/cuda/glm_fast.cu), `MoeRequest` и `moe_cpu_wait_kernel`.

**У нас:** `cudaStreamSynchronize(s.stream)` требуется перед CPU-работой каждой выбранной матрицы. После запуска GPU matmul деструктор `StrataCpuResultScope` выполняет host join перед дальнейшей подачей операций. Перекрытие с передачами остальных весов и текущей GPU-операцией есть, но окно короче целой ветки экспертов. Guard `!strata_expert_cpu_active(cuda_ctx)` отключает capture/replay для соответствующего scheduler split. См. [expert_direct.cuh](../../backends/deepseek4/expert_direct.cuh), [CpuLanePatches.cmake](../../backends/deepseek4/CpuLanePatches.cmake), [CMakeLists.txt](../../backends/deepseek4/CMakeLists.txt).

**Что менять:** ранняя публикация целого CPU-задания, отдельный обработчик, позднее объединение и совместимость с CUDA Graphs. Протокол должен защищать владение RAM, номера запросов, отмену и ошибки. GPU spin-wait нельзя переносить без корректного поведения при timeout и остановке workers. Исправленная ранее ошибка устаревших адресов CUDA Graph не объясняет медленную серию: её запускали после исправления.

## 3. Фиксированный промах вместо расчёта выгодного объёма

**Maya:** `fast_cpu_lane_setup()` измеряет CPU-эксперта и PCIe. Для числа RAM-промахов `f` выбирает `k`, минимизирующее `max(p_ms * (f-k), 0.04 + c_ms * k)`. При равенстве оставляет PCIe; если выгодного распределения нет, выключает lane. Калибровка вращает экспертов, чтобы не измерять только чтение из L3. Это приближённая модель стоимости, не гарантия оптимального расписания. См. [glm_fast_path.cu](../../../project-maya/src/core/glm_fast_path.cu), строки 2371–2404.

**У нас:** `strata_cuda_expert_cpu_select()` берёт первый подходящий VRAM-промах до фиксированного `max_experts`. В тесте это один эксперт на матрицу при любом числе потоков. Размер экономии H2D, остальные промахи и доступное окно перекрытия не оцениваются.

**Что менять:** калибровка на размерах и типах target/DSpark, план с допустимым `k=0`, оценка полного пути с обменами и объединением. Периодически свободный CPU не означает, что работа на нём выгодна. RTX 5090 может дать другой оптимум, чем GPU в отчётах Maya; коэффициент `0.04` также требует местного измерения.

## 4. CPU-назначение может мешать прогреву GPU-кэша

**Maya:** среди RAM-экспертов выбирает менее частых по route counters, оставляя более частым PCIe-путь с продвижением в VRAM. См. [glm_fast.cu](../../../project-maya/src/kernels/cuda/glm_fast.cu), выбор `host_set` около строки 3059.

**У нас:** частота не участвует в выборе. В [cuda_expert_transfer.inc](../../backends/deepseek4/cuda_expert_transfer.inc) ветки `cpu_lane.selected(...)` около строк 457 и 619 учитывают частоту и делают `continue`, минуя загрузку и допуск в GPU-кэш. Частая матрица может снова остаться первым промахом и снова уйти на CPU. Структура выбора подтверждена кодом; число таких повторов в замерах не измерялось, поэтому считать это доказанной главной причиной замедления нельзя.

**Что менять:** выбирать холодную часть среди пригодных целых экспертов, оставляя горячим путь в VRAM. Считать повторные CPU-назначения и время до попадания в кэш. Безусловная загрузка всех CPU-весов на GPU уничтожила бы исходную экономию трафика.

## 5. Пул требует подтверждения от каждого worker

**Maya:** [Workers](../../../project-maya/src/core/glm_fast_state.hpp) считает завершённые задания; вызывающий service thread тоже работает. Между близкими заданиями использует spin и последующий сон. Для CPU lane задаётся 20 мс spin. Разбиение строк зависит от числа потоков.

**У нас:** [CpuLanePool](../../backends/deepseek4/cpu_lane.cpp) вызывает `notify_all` для каждого пакета. `left = workers.size()` требует пробуждения и подтверждения от всех workers, даже если задания уже разобраны другими. Задания разбиты по 64 строки; входы до их отправки квантует вызывающий поток движка.

**Что менять:** ждать завершения заданий, укрупнить работу, вынести CPU-подготовку в service thread. Spin/sleep подбирать на Windows с учётом readers и target/DSpark. Копирование 20 мс spin вслепую может отнять CPU у чтения весов и подачи GPU-работы. Замедление 12/16 потоков согласуется с накладными расходами, но текущие логи не доказывают, какая часть пула доминирует.

## 6. Короткие batch и владение RAM

`win_cpu_merged()` Maya объединяет короткое окно по экспертам: одна строка весов используется для нескольких токенов подряд, помогая CPU-кэшу. В используемом `native_gu_rows_split` dot product всё равно вызывается для каждого токена; обещать одну деквантизацию на всё окно нельзя. У нас задания токенов независимы. После целого CPU-эксперта стоит проверить группировку для короткой проверки DSpark. См. [glm_fast_path.cu](../../../project-maya/src/core/glm_fast_path.cu), `win_cpu_merged`, и [native_expert.cpp](../../../project-maya/src/kernels/cpu/native_expert.cpp).

RAM tier Maya владеет закреплёнными mapped blobs и сохраняет их до завершения задания. Наша [resident()](../../backends/common/expert_file.hpp) проверяет mmap-страницы через `QueryWorkingSetEx`, но не закрепляет: ОС может вытеснить их до чтения CPU. Сама проверка также имеет стоимость. Нужен ограниченный объём принадлежащей кэшу памяти с гарантированным сроком жизни. При этом третий повтор не читал SSD — объяснять его замедление дисковыми промахами неверно. Большой prefill по требованию пользователя остаётся на GPU.

## Численная корректность: чего пока не доказали

Maya также использует `ggml-cpu` traits, `from_float` и `vec_dot`. Наши kernels уже собраны с AVX512: дело не просто в отсутствии SIMD. CPU/GPU различаются квантизацией активаций и редукциями. Maya содержит `STRATA_GLM_CPU_LANE_CHECK` — сравнение CPU и GPU с независимым эталоном из деквантованных весов и суммами в double. Это проверка численной ошибки, не обещание побитового совпадения устройств. См. [glm_fast_path.cu](../../../project-maya/src/core/glm_fast_path.cu), строки 2498–2560.

Наш fixture проверяет маску, размещение и строки против CPU vector-dot reference. Он не заменяет независимую оценку реального целого эксперта и качества модели. Ошибка `session restore changed greedy output` подтверждает отсутствие точной воспроизводимости, но сама по себе **не доказывает повреждение KV-сессии**. При изменении кэша меняется назначение CPU/GPU и арифметика. Эту правдоподобную причину ещё нужно отделить от дефекта состояния контролируемым опытом с фиксированным распределением работы.

Нужны сравнение реальных экспертов CPU/GPU/double, проверка logits и близких top-token оценок, затем restore с фиксированным распределением и оценка качества. Ослабить assert и объявить проверку пройденной нельзя. Whole-expert lane не устранит численные различия автоматически. Maya добавляет отдельную CPU-сумму к GPU-сумме в конце, меняя общий порядок редукции. Наш текущий возврат отдельных строк сохраняет исходный порядок; это свойство стоит сохранить при переработке.

## Порядок следующей реализации

1. Измерить выбор/residency, подготовку, пробуждение, CPU compute, обмены и ожидание по отдельным запросам; добавить GPU events и временную шкалу подачи операций. Отдельно оценить потерю CUDA Graphs. Подготовить независимую численную проверку реальных экспертов.
2. Реализовать опциональное задание целого эксперта с DeepSeek-математикой и исходным порядком редукции. Проверить отмену, restore и владение буферами.
3. Убрать host join между матрицами: отдельный service, позднее объединение, совместимость с CUDA Graphs. Калибровать стоимость полного пути.
4. Выбирать выгодное число холодных CPU-экспертов, включая ноль. Затем настраивать workers и объединение коротких batch DSpark.
5. Повторить GPU/CPU сравнение при одинаковом прогреве, отдельно короткий decode и длинный GPU-prefill. Учитывать изменения ответов, acceptance, RAM/SSD и полное время запроса.

CPU lane остаётся выключенным в рабочем профиле. Прирост после такой переработки пока не измерен и не гарантирован. Автоматически выбрать GPU-only на этом ПК — допустимый результат калибровки.
