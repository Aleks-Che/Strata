# О2: чтение весов в staging

13 октября 2026. Продолжение [проверки размера staging](DEEPSEEK4_TRANSFER_O2_STAGING.md)
и [плана оптимизации подкачки](DEEPSEEK4_TRANSFER_OPTIMIZATION_PLAN.md).

**На коротком прогретом запросе подтверждены +12,81% decode внутри
экспериментальной очереди:** 9,363 → 10,562 ток/с. Это локальный выигрыш
от подготовки источника; весь экспериментальный путь пока проигрывает
GPU-only, а критерий 90% DMA-контроля не выполнен.

## Что меняется

В [GpuFetchReader](../../backends/deepseek4/gpu_fetch_reader.hpp) добавлен
переключатель `STRATA_DS4_GPU_FETCH_READER`. Он относится только к подготовке
источников GPU fetch queue; арифметика экспертов, GPU-маршрут, политика допуска
в кэш и порядок DMA не меняются.

| Значение | Подготовка источника |
|---|---|
| `native`, значение по умолчанию | Прежний `ReadFile`; объект Request с Windows event на один вызов матрицы |
| `reuse` | Тот же `ReadFile`, но Request/event живёт вместе с service и используется повторно |
| `resident` | Проверка `QueryWorkingSetEx`; если все страницы доступны в working set процесса — memcpy из отображения, иначе native read |
| `mapped` | memcpy из существующего отображения модели без предварительной проверки страниц |

Неизвестное значение сохраняет `native`. Новые режимы экспериментальные;
рабочий профиль не переключён. Общий reader других backend не изменён.

Для mmap проверяются границы Source и соответствие адреса файловому смещению.
Источник остаётся отображённым на время ветки: `finish_plan()` завершает service
до уничтожения контекста и модели. Сам `Source` владеет файловым дескриптором,
но не отображением; его нельзя считать защитой времени жизни mmap.

Проверка resident не фиксирует страницы в RAM. Даже после неё Windows может
вытеснить страницу. В отличие от native read, page fault внутри memcpy нельзя
отменить или ограничить таймером 1500 мс; отмена проверяется между чанками.
Поэтому эти mmap-режимы не являются готовой заменой native read при недостатке RAM.
Новый pinned-кэш не создаётся, бюджет staging остаётся 4 МиБ на очередь.

В `STRATA_GPU_FETCH_READER` записываются режим, native/mmap bytes и число
проверок/промахов resident. В `STRATA_GPU_FETCH_QUEUE` общий объём источника
переименован из `file_bytes` в `source_bytes`. Снимки фаз учитывают native и mmap
отдельно, складывая вклад очереди и прежнего pipeline. Файловое чтение — вызов
API, а не доказательство обращения к SSD; физические чтения H: измеряются отдельно.

## Микротест

В отдельной пробе используется реальный GpuFetchReader и настоящая очередь.
Файл 64 МиБ отображён и заранее прочитан; передача сравнивается с прямой DMA
из pinned RAM. Проверяется весь payload, первые три повтора прогревочные,
следующие 12 измеряемые. Полная серия: 1/6 матриц по 2/4/8 МиБ, три процесса.
Это тест тёплого отображения, а не скорости SSD.

Ниже медианы **6×4 МиБ**, десятичные ГБ/с:

| Режим | Процесс 1 | Процесс 2 | Процесс 3 |
|---|---:|---:|---:|
| DMA-контроль | 14,154 | 14,165 | 14,209 |
| native | 11,493 | 11,314 | 11,605 |
| reuse | 10,664 | 11,527 | 11,428 |
| resident | 11,890 | 11,846 | 12,059 |
| mapped | 11,903 | 12,072 | 12,131 |

Mapped достигает 84,10–85,38% DMA-контроля. Критерий 90% не пройден.
Повторное использование Request само по себе устойчивого ускорения не дало.
Исходные пробы сохранены отдельно от итоговых `final-probe-*.csv`; начальная
ошибка открытия временного файла исправлена разрешением совместного чтения.

## Условия модельного сравнения

Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows, CUDA 13;
наблюдаемый PCIe Gen3 x16. Target — DeepSeek-V4-Flash-0731 UD-Q3_K_XL,
DSpark — Q8_0. Контекст 8192, GPU-кэши target/draft 15360/1024 МиБ,
RAM-кэш 2048 МиБ, `draft-max=2`. Staging 4 МиБ, четыре сегмента, DMA depth 8,
ранние источники включены. `KEEP_RAM=0`, `RAM_DEMOTE=0`, context overlap выключен.

В каждом процессе четыре свежих одинаковых запроса: 15 входных и 32 выходных
токена. Первые два — прогрев, последние два — измерение. Кэш ОС не очищается.
Профиль CPU заморожен, 12 потоков, бюджет 0,01 мкс; отсутствие CPU-работы
проверяется фактическими jobs/rows. Для сравнения работы native/mmap bytes
складываются; остальные счётчики фаз сравниваются отдельно для target и draft.

Артефакты: `build-local/deepseek4/transfer-o2-reader-20261013/`.

## Результаты на модели

Сначала выполнены четыре отдельные пробы:

| Режим | Decode, ток/с | Полное время двух поздних запросов, с | CPU-seconds |
|---|---:|---:|---:|
| native | 9,329 | 9,312 | 21,922 |
| reuse | 9,324 | 9,375 | 22,188 |
| resident | 8,538 | 10,000 | 24,250 |
| mapped | 10,541 | 8,594 | 20,062 |

У resident все **134481** проверки за четыре запроса закончились native read;
mmap bytes = 0. Данные могли находиться в системном файловом кэше, но проверяемые
страницы отображения не были valid в working set процесса. Проверки добавили
работу и не заменили чтение. Этот вариант отклонён для выбранного профиля.
Reuse также не дал выигрыша, поэтому отдельно повторялся только mapped.

Повтор A/B/B/A: native → mapped → mapped → native.

| Режим | Decode в двух процессах, ток/с | Среднее, ток/с | Полное время, с | CPU-seconds |
|---|---|---:|---:|---:|
| native | 9,367 / 9,359 | 9,363 | 9,273 | 22,000 |
| mapped | 10,556 / 10,568 | 10,562 | 8,578 | 19,664 |

Среднее берётся по двум процессам, в каждом измеряются два поздних запроса.
Итог: **+12,81% decode, −7,49% полного времени, −10,62% CPU-seconds**.
Все четыре ответа в каждом из восьми процессов пилота/повтора имеют одинаковые
output IDs. После сложения file+mmap совпадают все записанные счётчики фаз
всех четырёх запросов, включая hits/misses/admissions, передачи и CUDA Graph.
CPU jobs/rows = 0. Decode H2D двух поздних запросов — **44,255 ГиБ**,
target 34,949 и draft 9,306 ГиБ.

Чтения H: в измеряемых поздних запросах — 0. Первый прогрев native пилота
прочитал 33,745 ГиБ с H: и исключён из сравнения скорости. На других дисках
шли фоновые чтения; чужие процессы не останавливались. Эти измерения
не являются проверкой полностью холодного диска или режима с дефицитом RAM.

В отдельном GPU-only контроле G с совместимой арифметикой той же сборки:
**15,746 ток/с, 6,563 с, 8,875 CPU-seconds**; H2D **31,680 ГиБ**, те же
output IDs, чтения H: = 0. Это один контрольный процесс. Полный новый путь
не принят как ускорение рабочего GPU-only: лишний H2D и цена CPU-инфраструктуры
остаются следующими отдельными задачами.

## Память и таймеры

В A/B/B/A выборочный максимум RSS был 17,52 ГиБ у native и 39,73 ГиБ у mapped.
Минимум доступной RAM — 74,89–74,98 против 54,50–54,70 ГиБ. Private bytes
в обоих режимах около 36,33 ГиБ, общий максимум занятой VRAM 31446–31455 МиБ.
Переход к mmap увеличивает working set файловыми страницами; отсутствие
нового pinned allocation не означает отсутствия влияния на доступную RAM.
Измерения раз в две секунды не гарантируют захвата кратковременных пиков.

Таймеры за **весь процесс из четырёх запросов**, отдельно от позднего decode:

| Счётчик | native, среднее двух процессов | mapped, среднее двух процессов |
|---|---:|---:|
| read callback, с | 11,668 | 7,639 |
| owner DMA wait, с | 13,371 | 14,002 |
| staging reuse waits | 4440,5 | 57860 |
| DMA copies | 138001 | 138001 |

Быстрее заполняемый staging чаще упирается в ожидание освобождения сегмента.
Рост этого счётчика сам по себе не означает замедления модели. Таймеры
перекрываются; складывать их как независимые части времени запроса нельзя.

## Проверки и воспроизводимость

Собраны движок, тест очереди, тест CPU-экспертов, новый тест reader и calibrator.
24 выбранных CTest имеют успешный итог. В исходном прогоне 20 прошли, четыре
новых mmap-варианта остановились на старом требовании роста именно native
file bytes. Проверка исправлена на file+mmap с отдельным требованием реально
использовать выбранный reader; сравнение результатов GPU/CPU сохранено.
После этого восемь затронутых/контрольных тестов прошли повторно. Оба журнала
сохранены, включая исходный отказ; ошибки не исключены из отчёта молча.

Новый тест проверяет границы, ненулевое файловое смещение, короткий хвост,
отмену до чтения, несовпадающий mmap-адрес, fallback без view, заведомо
нерезидентные страницы и native read после закрытия исходного fd/снятия view.
Проверки очереди покрывают wrap, leases, cancellation, replay и общий scratch.

На модели выполнена фиксированная история из 68 IDs, prefix 36, два повтора:
совпали FNV-64 полных массивов logits и argmax у **6 префиксов и 86 шагов**
с GPU-контролем этой же сборки. Гибрид действительно выполнил **2785 CPU jobs,
3797 строк**, prefill CPU rows = 0; mmap bytes в fetch queue ненулевые.

Lifecycle/DSpark проверка прошла: **8/8** сценариев с теми же входными и
выходными IDs, RAM restore, продолжение, отмена, повтор seeded-запроса.
Выполнено **588 CPU jobs / 1102 строки**, автоматическое обновление профиля
реально перешло с поколения 0 на 1 между запросами. Это проверка корректности,
не измерение выигрыша CPU lane.
