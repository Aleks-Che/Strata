# Завершение подкачки и ожидание служебных потоков

12 октября 2026. Продолжение этапа 2 [плана CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md).
Два независимых переключателя, оба выключены по умолчанию.

## Обработка кэшей после копирования

`STRATA_DS4_GPU_FETCH_EARLY_RETIRE=1` записывает CUDA event после последнего
из трёх GPU fetch waits, перед вычислением последней матрицы. При завершении
полностью отправленной ветки владелец ждёт этот event и ответы I/O-service,
затем обрабатывает RAM fills, частоты, LRU и возвращает GPU cache loans.
Эта работа может пересекаться с оставшимися вычислениями GPU/CPU.

Перед освобождением выбранных CPU-троек, VRAM protection и переиспользованием
буферов владелец всё ещё ждёт последнего потребителя ветки. Это не отменяет
зависимость следующего слоя от результата текущего и не создаёт второй контекст
для подготовки соседнего слоя. GPU admissions не перезаписывают текущие weights
при обработке кэшей; готовность публикации отмечается существующим CUDA event.

Для неполной ветки, отмены без финального потребителя и `keep_whole` сохраняется
прежний stream fence. Новый `arm()` сбрасывает признак event: нельзя принять
завершение предыдущей ветки за готовность новых копий.

`STRATA_GPU_FETCH_RETIRE` сообщает `early`, `fallback`, `tail_pending` и
`candidate_overlap_us`. Последний счётчик — время обработки RAM/статистики
на ветках, где после copy fence оставалась GPU-работа. Это верхняя граница
работы, доступной для перекрытия, а не измеренная экономия: GPU может закончить
в любой момент. Время финализации GPU loans в этот счётчик не входит.

## Постановка служебных потоков на ожидание

`STRATA_DS4_QUEUE_ASYNC_PARK=1` после подтверждения всех ответов запрещает
CPU/I/O-service дальнейший опрос, но не ждёт его перехода в condition-variable
sleep. Следующий запрос публикуется только после `arm()`. Если он приходит до
засыпания, worker продолжает работу; если после — получает обычное пробуждение.
Постоянного опроса между запросами этот режим не требует.

Callback заканчивает все обращения к данным backend до release-записи `reply`.
Владелец получает ответы через acquire и только затем меняет контекст. Очереди
проверяют номера request/reply/consumed; новое назначение не может перезаписать
ещё используемый слот. Cancel без down-consumer сохраняет ожидание парковки;
деструктор всегда останавливает и присоединяет service перед удалением памяти.

`STRATA_CPU_QUEUE_PARK` и `STRATA_GPU_FETCH_PARK` считают асинхронные disarm,
обычные ожидания и их host-время. Арифметика CPU и выбор экспертов не изменены.

## Проверки протокола

Пройдены 46 CTests (198,90 с): очереди, CPU lane, HostCache/residency,
compact/direct/ordered, pipeline и контракты speculative/GPU-only. Два новых
теста проверяют раннюю обработку подкачки с graphs=0/1 и реальное срабатывание
счётчика для всех 12 веток fixture.

CPU-очередь проверена на 1500 graph replay, включая 300 disarm/rearm с изменением
входа. Очередь подкачки — на 400 replay с 399 disarm/rearm. Проверяются полные
ответы, номера последовательностей, mixed CPU/GPU-вхождения, ошибки и отмена.
Отдельный GPU-тест удерживает вычислительный хвост после copy event: обработка
подкачки должна вернуться до его завершения. Удержание ограничено 500 мс;
повторный `arm()` без нового event и выключенный режим используют полный fence.

Ещё 11 проверок прошли с compact scratch, slabs 1 МиБ, одним GPU-copy block,
RAM_DROP_GPU и сочетанием KEEP_RAM/PRUNE/RELEASE_RAM с новыми флагами. Отдельный
native прогон с выключенным fetch RAM fill также прошёл. Итого 46+11+1=58
проверок конфигураций; четыре ранние smoke-проверки к этому числу не прибавлены.

## Условия замеров

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, H: Samsung 990 PRO, Windows.
DeepSeek-V4-Flash-0731 UD-Q3_K_XL, target-only, 68 фиксированных входных IDs.
Полный prefill обрабатывает все 68; decode использует префикс 36 и следующие
32 токена по одному либо пакетами до трёх. GPU-кэш 15 ГиБ, общий RAM-кэш 2 ГиБ,
pinned pool и fetch RAM budget по 32 МиБ. CPU12, force/cap1,
graphs/direct/ordered и snapshot prune включены; GPU admissions, KEEP_RAM
и RELEASE_RAM выключены, чтобы изолировать новые переключатели.

В каждой загрузке четыре прохода по трём режимам; время отдельных фаз — среднее
последних двух. Полное время и CPU-с процесса охватывают все проходы после
загрузки модели. Чтение SSD — разница физических счётчиков H: за этот же период;
оно может включать посторонний I/O. `file_bytes` в логе движка учитывает также
чтение из файлового кэша ОС и не является мерой физического SSD-трафика.

В начальном `off-probe` прочитано 12 930 686 976 физических байт; этот запуск
не используется для сравнения полного времени. Отдельные прогретые пробы
`early-probe`, `async-probe`, `early-async-probe` прочитали 0 байт. Их одиночные
измерения нужны для отбора кандидата, а не для заявления об ускорении.

## Результат на фиксированной истории

Для A/B/B/A выбран EARLY_RETIRE отдельно, ASYNC_PARK выключен.
Порядок новых загрузок движка: `off-b`, `early-b`, `early-c`, `off-c`.
Первые три workload прочитали 0 физических байт, последний — 12 288 байт.
Весь последний прогон поэтому нельзя называть тестом с нулевым SSD-трафиком.
Минимум свободной системной RAM в серии — 64,63 ГиБ.

| Режим | Prefill 68, мс | Decode по 1, мс / 32 | Decode по 3, мс / 32 | Весь workload, с | CPU-с процесса |
|---|---:|---:|---:|---:|---:|
| A: обработка после всей ветки | 2515,32 | 2208,57 | 1481,50 | 49,540 | 96,555 |
| B: обработка после copy event | 2501,52 | 2118,25 | 1440,87 | 48,993 | 93,391 |

В этой одной серии время decode уменьшилось на 4,09% / 2,74%, всего workload —
на 1,10%, CPU time — на 3,28%. Контрольные загрузки A сами различались:
decode по одному — 2119,50 и 2297,64 мс, по три — 1453,29 и 1509,71 мс.
Прирост меньше разброса контроля, полное время не достигло принятого для отбора
порога 3%. Это предварительный замер, а не подтверждённое устойчивое ускорение.
Флаги оставлены выключенными; полноценного сравнения с рабочим GPU-only здесь нет.

Во всех восьми запусках совпали 12/12 полных logits signatures, включая каждый
измеряемый decode-результат. Выключенный новый режим также совпадает с сохранённым
`off-b` предыдущей сборки. Счётчики одинаковы: 3425 fetch-веток, 1144 CPU jobs /
1430 строк, 685 завершённых RAM fills; RAM/file/H2D-байты не изменились.
Это сравнение транспорта при фиксированном назначении, без новых CPU-ядер.

В каждом B copy event позволил начать обработку до конца GPU-работы во всех
3425 ветках, fallback=0. Но `candidate_overlap_us` составил всего 28 635 и
29 479 мкс за workload около 49 с. Такой объём учтённой работы сам по себе
не объясняет всё наблюдаемое изменение времени.

ASYNC_PARK в одиночных пробах убрал по 3425 ожиданий парковки CPU и I/O-service,
но согласованного выигрыша не показал. Исходные ожидания в контрольных A
занимали суммарно всего 2,938 и 3,690 мс. Флаг сокращает конкретное ожидание,
но эти данные не подтверждают полезное ускорение всего запроса.

Сборка для всех восьми прогонов и DSpark:

## DSpark и оставшаяся работа

DSpark Q8_0: CPU12, target/draft GPU cache 15/1 ГиБ, общая RAM 2 ГиБ,
shared scratch, max draft=2, GPU cache slots=4. KEEP_RAM, PRUNE, RELEASE_RAM
и оба новых переключателя включены. Пройдены A→B→A, extension restore,
fresh/full-prefill, один токен без draft, отмена prefill/decode и greedy restore
после отмены.

Строгий seeded restore **не пройден**: последовательности по 24 токена
расходятся на индексе 6. Обе совпадают с соответствующими последовательностями
предыдущей сборки. Исходный валидатор завершился с кодом 1, assertion не менялся.
Это подтверждает сохранение прежнего симптома, но не устанавливает его причину
и не заменяет полной приёмки состояния.

Новый путь использовался в 1374 ветках target (299 CPU jobs / 484 строки)
и 10 ветках draft (одно CPU-задание / две строки). Во всех copy event обработан
до конца GPU-работы; fallback=0. Обе очереди использовали async disarm.
Финальные RAM `oom`, `pending`, `retired_bytes` и GPU/demotion pending — 0.

Выбранные CPU-тройки по-прежнему удерживаются до конца ветки. Следующие открытые
пункты этапа 2: их время жизни и переиспользование контекста без общего ожидания,
рост пустого GPU-кэша, новый admission вместе с демоцией, строгий seeded restore.
Рабочий GPU-only профиль и Qwen backend не менялись; этап 2 не закрыт.

## Артефакты

`build-local/deepseek4/gpu-fetch-retire-20261012/`: исходники до/после, сборки,
конфигурации, логи тестов, фиксированные входные IDs и сырые результаты.
`summary.json` содержит все прогоны, счётчики и A/B/B/A; `parity.json` — проверку
logits и сравнение DSpark с предыдущей сборкой. `final-manifest.json` фиксирует
хеши исходников, документов, исполняемых файлов и размеры файлов моделей.

Скрипты воспроизведения: `build.bat`, `checks.py full`, `studies.py <имена режимов>`,
`dspark.py`, `remaining.py`, `summarize.py`, `parity.py`. Имена с `early` включают
EARLY_RETIRE, с `async` — ASYNC_PARK; остальные флаги заданы в сохранённом config.
`studies.py` отказывается перезаписывать существующие результаты. DSpark driver
сохраняет настоящий код валидатора в `dspark-final-exit.json`; код самого driver
не является признаком прохождения строгой проверки.
