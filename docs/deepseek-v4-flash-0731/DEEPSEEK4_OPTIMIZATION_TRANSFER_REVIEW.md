# Что перенести в DeepSeek из оптимизаций GLM и Step

Проверено 6 октября 2026 года по двум сводкам и текущему коду backend:

- [Удачные оптимизации GLM-5.3-Flash](../GLM53/GLM53_FLASH_SUCCESSFUL_OPTIMIZATIONS.md).
- [Удачные оптимизации Step-3.7-Flash](../Step-3.7-Flash/STEP37_FLASH_SUCCESSFUL_OPTIMIZATIONS.md).

**Первыми стоит проверить AVX2-копирование, раннее заполнение host-слотов и
использование уже закэшированных матриц при prefill.** Блочное размещение
GLM полезно рассматривать отдельно для динамического кэша. Большая часть
остальных идей уже реализована в DeepSeek либо устраняет накладные расходы,
которых в его текущем пути нет.

Ниже сохранён анализ до реализации. Последующее внедрение трёх первых
кандидатов и замеры DeepSeek описаны в
[отчёте об экспериментах](DEEPSEEK4_TRANSFER_TRIALS.md).
Проценты ниже относятся только к исходным экспериментам GLM/Step,
не являются прогнозом для DeepSeek.

Продолжение от 10 октября: [stage 8/16, раздельные периоды частот и
измерение стоимости allocations](DEEPSEEK4_STAGE_AND_DECAY.md).
Пункты 1–2 реализованы и проверены ранее. В пункте 3 выполнен подбор
staging/частот, затем [slabs перенесены в динамический кэш и проверены
на модели](DEEPSEEK4_DYNAMIC_SLABS.md). В пункте 4 перенесён и проверен
[короткий пакет MMVQ с арифметикой одного токена](DEEPSEEK4_MMVQ_TOKEN_BATCH.md):
560 матричных сценариев, четыре запуска модели, диагностика logits и сессии.
Перенос не дал ускорения: повтор 21,02–21,46 → 17,07–17,36 ток/с;
новый путь выключен. Проверка этого кандидата завершена, но численная
эквивалентность **всей модели** batch/serial не достигнута.
Последующая [трассировка активаций](DEEPSEEK4_ATTENTION_PROBE.md) локализовала
первое расхождение в Flash Attention слоя 0 при одинаковых видимых входах.
Две модификации attention не дали равенства всей модели и исключены из
рабочего движка. Затем выполнен [изолированный GPU-тест с FP64-эталоном](DEEPSEEK4_ATTENTION_FIXTURE.md):
182 сочетания batch/padding/маски. Уплотнение ключей устранило расхождение
первого attention на 21 строке реальной модели. С MMVQ следующий найденный
участок — routed FFN слоя 0; shared expert и вход FFN совпадают. Новый
attention доступен только в экспериментальной сборке, default OFF,
ускорение всей модели не подтверждено.
Следующая [проверка BF16 router](DEEPSEEK4_ROUTER_MMVF.md) выявила дополнительное
округление F32-активаций в пакетном MMF. Опциональный MMVF для batch 2–4
прошёл 216 сценариев; в сочетании с предыдущими численными экспериментами
совпадают первые три слоя. Полная эквивалентность остаётся открытой:
следующая найденная граница — HCA-attention слоя 3.
В [проверке HCA](DEEPSEEK4_HCA_COMPACT.md) видимые входы оказались одинаковыми.
Консервативный bound для уплотнения дал совпадение полных logits на коротких
запросах. На 4096 токенах отдельные query устранили расхождение CSA слоя 2;
следующий шаг — одинаковое разбиение stream-K в одном пакетном запуске.
Таблица ниже сохраняет состояние исходного анализа до этих изменений.

## Сопоставление

| Оптимизация источника | Состояние в DeepSeek | Вывод |
|---|---|---|
| Step: AVX2 temporal stores для mmap → pinned RAM | Общий конвейер поддерживает callback копирования, но DeepSeek его не передаёт и использует `std::memcpy` | Первый кандидат для отдельного A/B |
| Step/GLM: раннее заполнение host slot после H2D | Параметр общего конвейера есть; DeepSeek оставляет `refill_early=false` | Проверить отдельно и вместе с AVX2 |
| Step: prefill не добавляет новые записи, но использует cache hits | DeepSeek при `tokens > 8` обходит и размещение, и поиск готовой матрицы | Перенести идею чтения готовых записей; особенно для повторного длинного prefill |
| GLM: несколько матриц в одном CUDA allocation, slabs | Фиксированный режим уже использует одну арену; динамический выделяет отдельные матрицы | Кандидат для динамического режима, не обещание роста фиксированного кэша |
| GLM: уплотнение частично заполненных slabs | Slab allocator пока отсутствует; фиксированная арена умеет сливать соседние свободные блоки | После slabs и только при измеренных потерях памяти |
| GLM: общий запуск MMVQ для 2–4 токенов с арифметикой одиночного matvec | Нет GLM-патча, но штатный DeepSeek CUDA уже имеет multi-token MoE kernel | Отдельное исследование численной воспроизводимости и скорости DSpark |
| GLM: одна пара событий на весь весовой тензор; Step: одно ожидание на тензор | DeepSeek уже отправляет D2D в stream модели без host fence после каждого эксперта | Не переносить буквально; сначала измерить оставшиеся барьеры |
| Step: reuse CUDA allocation | Есть для динамического кэша, включая порядок между streams; арена переиспользует свои блоки | Уже используется |
| GLM: длительная история частот | У target 15 ГиБ период 122880 обращений, у draft 1 ГиБ — 8192 | Основная идея уже есть; значение 131072 из GLM не даёт основания обещать новый выигрыш |
| Step: общий embedding с MTP | DSpark использует embedding и output target без второй копии | Уже используется |
| GLM: общий compute scratch | Есть `--draft-shared-scratch 1`, в рабочем профиле экономит 1168 МиБ | Уже перенесено |
| GLM: cache-only MTP prefill/catch-up | В DSpark feature injection уже строит только проекции и запись в KV, без MoE/LM head | Повторно внедрять не требуется |
| GLM/Step: уменьшение chunk/ring | У DeepSeek staging 16 МиБ; типичные матрицы 3,0625 и 4,25 МиБ плюс padding | Подбор 8 МиБ возможен как отдельный эксперимент, 4 МиБ дробит MXFP4 |
| GLM: убрать создание `std::string` в проверке каждого logit | Аналогичного цикла `require(bool, std::string)` в DeepSeek нет | Нет найденной точки прямого переноса |
| GLM: mmap только экспертов, остальное через staging | DeepSeek уже отключает полный prefetch; более узкая загрузка — отдельное изменение loader | Низкий приоритет: в GLM подтверждалась RAM, не скорость |

## 1. AVX2-копирование: наиболее прямой перенос

Step использует обычные, cacheable записи AVX2 в повторно используемый pinned
буфер. В его финальной серии с MTP2 результат — 13,803 → 14,777 ток/с (+7,06%),
CPU time на ответ уменьшилось на 10,95%. Без MTP ускорение decode не подтвердилось.
Это [результаты STEP-17](../Step-3.7-Flash/STEP37_FLASH_HOST_COPY.md),
полученные на том же Ryzen 9 9950X и RTX 5090.

Точки переноса:

- [Step host_copy.cpp](../../backends/step35/host_copy.cpp) — функция с выравниванием,
  обработкой prefix/tail и обычными AVX2 stores.
- [Step host_copy.hpp](../../backends/step35/host_copy.hpp) — проверка CPU/OS и
  необязательные счётчики. ISA-специализация собирается отдельным translation unit.
- [Общий expert_pipeline.hpp](../../backends/common/expert_pipeline.hpp) —
  `HostCopy` callback уже вызывается вместо memcpy для mmap-пути.
- [DeepSeek cuda_expert_transfer.inc](../../backends/deepseek4/cuda_expert_transfer.inc) —
  конструктор `StrataExpertTransfer` пока передаёт только первые пять аргументов
  `StrataExpertPipeline`; callback остаётся пустым.

Подключение не требует менять router, квантование или CUDA-математику модели.
В режиме `auto` прогретый decode использует mmap, поэтому проходит через эту
точку копирования. Нативное файловое чтение сразу в pinned buffer callback
обходит: на этой ветке AVX2 не ускоряет чтение.

Нужно перенести функцию с проверкой CPUID/OSXSAVE/XCR0 и запасным CRT-путём,
не включая AVX2 для всех исходников backend. Вынесение общей функции для
нескольких backend должно сохранить прежние defaults других моделей.
Это оптимизация уже существующего CPU-копирования; вычисление слоёв остаётся
на GPU. Для первого теста достаточно подключить callback конвейера, сохранив
прежний резервный путь без pipeline.

Не подменять этот вариант non-temporal stores из
[common/host_staging_copy.hpp](../../backends/common/host_staging_copy.hpp):
это другая стратегия, не давшая того же результата. Write-combined memory
также не является эквивалентом cacheable AVX2-копирования.

## 2. Раннее заполнение host slot

По умолчанию producer ждёт `slot.used` перед повторной записью pinned RAM:
host buffer ждёт окончания использования device slot. При `refill_early=true`
он сначала ждёт только `slot.ready` — окончания предыдущего H2D — и копирует
новые данные в host buffer. Перед следующей H2D в тот же device slot всё равно
ожидается `slot.used`. Память кольца не увеличивается.

Этот механизм уже реализован в [общем конвейере](../../backends/common/expert_pipeline.hpp).
DeepSeek его не включает. В Step поверх batching он дал ещё +2,10% с MTP2,
но без MTP дополнительный выигрыш не установлен. В GLM уменьшилось ожидание
слотов, а устойчивого выигрыша всей генерации не получилось.
[Step batching/early refill](../Step-3.7-Flash/STEP37_FLASH_BATCH_COPY.md),
[GLM host pipeline](../GLM53/GLM53_FLASH_HOST_PIPELINE.md).

Для DeepSeek нужны четыре режима одной сборки: CRT, CRT + early, AVX2,
AVX2 + early. Общий primitive можно использовать без изменения правил
владения слотами. Нельзя убирать ожидание `used` перед перезаписью device slot.
Проверять нужно target и DSpark, отмену заполненного кольца и следующий запрос.

## 3. Prefill: читать готовый GPU-кэш, не заполняя его новыми матрицами

У Step `prefill admission off` сохраняет cache hits и не делает новые cache
fills. В DeepSeek ситуация строже:

- `StrataExpertTransfer::copy` проверяет `tokens > 8` до `entries.find`.
- `strata_managed_copy` также отправляет большой batch через bypass до поиска hit.
- `plan` исключает из загрузки только записи с `slice.cacheable=true`.
  Scheduler выставляет этот признак только при `ids_tensor->ne[1] <= 8`.

Следовательно, готовые матрицы перечитываются через RAM/H2D даже тогда, когда
есть в GPU-кэше. Это видно в
[коде передачи](../../backends/deepseek4/cuda_expert_transfer.inc) и
[построении плана](../../backends/deepseek4/expert_pipeline_sched.inc).

Полезный вариант: при большом prefill брать существующие записи через D2D,
промахи передавать напрямую, новые записи не добавлять. Отдельно решить,
обновлять ли историю; для первого изолированного сравнения разумно сохранить
нынешний запрет обучения частот большим prefill. Все готовые записи текущего
плана должны быть защищены от вытеснения и исключены из списка чтений.

Нужно разделить поиск hit, разрешение admission и выбор режима чтения.
Просто присвоить всем slices `cacheable=true` нельзя: общий конвейер использует
тот же флаг для выбора decode reader и файлового пути `auto`.

Выигрыш возможен только при наличии полезных весов в GPU-кэше. Первый запрос
с пустым кэшем этим не ускорится. В Step −29,8% времени prefill сравнивало
разрешённое и запрещённое заполнение кэша; DeepSeek уже запрещает заполнение,
поэтому этот процент к нему неприменим. Здесь проверяется дополнительное
использование hits. [Метод Step](../Step-3.7-Flash/STEP37_FLASH_SUCCESSFUL_OPTIMIZATIONS.md).

## 4. Slabs GLM: для динамического режима

У GLM группировка матриц в блоки до 16 МиБ увеличила полезный кэш
12,902 → 17,307 ГиБ и дала 9,865 → 11,764 ток/с в одной серии без MTP.
В DeepSeek фиксированный кэш уже выделяется одной ареной `cudaMalloc(capacity)`;
потерь от отдельного CUDA allocation каждой матрицы в этом режиме нет.
Обещать ему дополнительные 4,4 ГиБ по аналогии с GLM нельзя.

После включения динамического управления VRAM DeepSeek освобождает арену
и использует индивидуальные allocations. Именно здесь уместен подход
[expert_slab.hpp](../../backends/glm5next/expert_slab.hpp): несколько слотов одного
размера, уменьшенный последний блок и освобождение пустых блоков.
В текущем динамическом пути reuse одинаковых allocations уже есть;
польза slabs должна измеряться поверх него.

Перенос требует учитывать физически зарезервированные блоки отдельно от
полезных bytes матриц, сохранять бюджеты target/draft и глобальный резерв,
корректно освобождать память при внешнем давлении. У DeepSeek смешаны размеры
IQ3_XXS/MXFP4 и padding; нужен учёт классов размера. Нельзя оставить
индивидуальный `cudaFree` для указателя внутрь slab.

Уплотнение из GLM следует добавлять только при подтверждённой фрагментации,
между запросами и после завершения всех CUDA-потребителей. Оно может вернуть
VRAM, но самостоятельный прирост ток/с у GLM не доказан.
[Отчёт об уплотнении](../GLM53/GLM53_FLASH_COMPACTION.md).

## 5. MMVQ для DSpark: другой исходный режим

GLM сначала ввёл tokenwise-исполнение короткого batch для сохранения арифметики
одиночного decode. Затем специальный MMVQ объединил эти 2–4 прохода в один
запуск, сохранив порядок редукции одного токена. В GPU fixture IQ3_XXS
4096×1536 два токена ускорились 75,0 → 58,7 мкс, четыре — 128,2 → 77,7 мкс.
Это времена операции, не скорость всей модели.
[Замеры](../GLM53/GLM53_FLASH_MMVQ_TOKEN_BATCH.md),
[патч](../../backends/glm5next/ShortBatchPatches.cmake),
[условия включения](../../backends/glm5next/mmvq_token_batch.hpp).

У DeepSeek уже есть штатная ветка `has_ids && ncols_dst > 1` с вызовом
`mul_mat_vec_q_moe_launch` в
[CUDA MMVQ закреплённой зависимости](../../third_party/llama.cpp/ggml/src/ggml-cuda/mmvq.cu).
Нет GLM-цикла принудительного исполнения по одному токену. Поэтому это будет
сравнение двух алгоритмов, а не автоматическое устранение нескольких запусков.
При `draft-max=2` target обычно проверяет anchor и два draft-токена, так что
интересующий размер batch действительно встречается.

Отдельная ценность GLM-подхода — проверка причины расхождения обычного decode
и DSpark. Но даже совпадение matvec не доказывает совпадения attention,
compressor state и всей модели. Это направление исследования, не готовое
исправление. Нужны тесты IQ3_XXS, MXFP4, dense Q8_0, routed IDs, strides,
padding и полные logits/rollback. GLM и DeepSeek используют разные закреплённые
версии llama.cpp; CMake-патч с чужими SHA/anchors напрямую не применим.

## Что уже есть или не стоит копировать буквально

**Групповые ожидания.** В GLM сокращается дополнительная пара событий между
stream копирования и stream модели. В Step batching устраняет
`cudaStreamSynchronize` после каждого эксперта/cache fill. У DeepSeek D2D
и вычисление идут в stream модели; в обычном цикле `copy` нет такого
поштучного ожидания CPU. События `ready/used` общего кольца защищают его слоты
и не эквивалентны лишним событиям GLM. Их нельзя заменить одним событием на
целый тензор без нового протокола владения.

В scheduler остаются барьеры, включая получение router IDs и защиту scratch.
Ранее удаление одного барьера в DeepSeek дало 19,76 → 17,36 ток/с при различиях
фоновой нагрузки и VRAM; полезный эффект не доказан, патч удалён.
Это не запрет исследования, но нет основания переносить +19–22% Step как
ожидаемый результат. [Эксперимент DeepSeek](DEEPSEEK4_CACHE_SIZE.md).

**История частот.** DeepSeek использует период `max(4096, capacity >> 17)`:
122880 у target с кэшем 15360 МиБ, 8192 у draft с 1024 МиБ. Main уже близок
к GLM 131072. Можно сделать периоды отдельно настраиваемыми, но нужен подбор
на чередовании запросов, чтобы длительная история не мешала смене нагрузки.
[Реализация](../../backends/deepseek4/cuda_expert_transfer.inc),
[общая история](../../backends/common/expert_frequency.hpp).

**Cache-only DSpark.** В `graph_dsv4` ветка `if (ubatch.embd)` выполняет
проекцию признаков, нормализацию, RoPE и запись K каждого слоя, после чего
возвращается до MoE и LM head. `DSpark::inject` уже использует эту ветку.
Повторный перенос GLM MTP cache-only не добавит такую экономию заново.
[Граф DSpark](../../third_party/llama.cpp/src/models/dflash.cpp),
[инъекция](../../backends/deepseek4/speculative.hpp).

**Embedding, scratch, reuse.** Совместное использование embedding/output,
compute scratch и повторное использование блоков динамического кэша уже
описаны в [сводке DeepSeek](DEEPSEEK4_SUCCESSFUL_OPTIMIZATIONS.md).
Нативные MTP-головы Step/GLM не совместимы с архитектурой DSpark.

**Размер кольца.** При переходе stage 16 → 8 МиБ суммарные pinned-буферы
target/draft, включая резервный путь, уменьшатся по конструкции
192 → 96 МиБ, device rings — 128 → 64 МиБ. Это расчёт размеров, не замер
ускорения. В 8 МиБ помещается типичная матрица DeepSeek вместе с padding;
4 МиБ уже разделит матрицу MXFP4 4,25 МиБ. Эксперимент проводить отдельно
от AVX2/early, поскольку он меняет геометрию передачи.

**Прочие варианты.** Для устранения временных `std::string` из GLM не найден
аналогичный цикл проверок словаря в DeepSeek. Полная private RAM-загрузка,
дополнительный warmup весов, второй decode reader и write-combined staging
не имеют достаточного подтверждения, чтобы включать их по аналогии.

## Порядок внедрения и проверки

1. Добавить отключаемые AVX2 и early refill в DeepSeek, используя существующие
   возможности общего конвейера. Сначала сравнить четыре сочетания при текущих
   stage 16 МиБ, reader1 в decode, кэшах 15/1 ГиБ и DSpark2.
2. Отдельно добавить чтение GPU-cache hits при большом prefill с запретом
   новых admissions и сохранением прежней политики частот.
3. Подбирать stage 8/16 и периоды частот отдельными сериями. Slabs проверять
   в динамическом режиме после измерения полезных bytes против занятой VRAM.
4. MMVQ и численную эквивалентность рассматривать отдельным этапом после
   транспорта; не смешивать изменение арифметики с тестом копирования байтов.

Для каждого изменения нужны одинаковые запросы, отдельные режимы без DSpark
и с ним, повторения с обращением порядка A/B, два типа текста и смена запросов.
Prefill 4096 и короткий decode измерять раздельно. Повтор после восстановления
RAM-сессии почти не выполняет prefill, поэтому для теста cache hits нужно
сбросить KV/сессию, сохранив кэш экспертов.

Собирать H2D/D2D и hits/misses, CPU-с/ответ, время host copy и ожиданий,
занятость RAM/VRAM и физические чтения устройства модели. Сейчас интерфейс
[StrataExpertCounters](../../backends/deepseek4/expert_transfer.h) агрегирует
`stage_us`/`wait_us`; для диагностики полезно вывести отдельно ожидания producer
и consumer, уже имеющиеся в общем конвейере. Время этих перекрывающихся этапов
нельзя складывать в процент GPU idle. Подробное профилирование выключать
в итоговых замерах скорости.

Транспорт проверять побайтово, включая padding, хвосты и повторное использование
кольца; затем сравнивать token IDs и logits полного инференса. Сохранить
`cpu_compute_nodes=0`, отдельные бюджеты target/draft, отмену prefill/decode,
повтор после отмены, A/B/A сессии и проверки VRAM pressure. Предыдущие
8 CTest/25 Python-тестов и сохранённые проверки DSpark — исходная регрессия,
не замена новым тестам. Рабочий default выбирать только после DeepSeek-замеров.
