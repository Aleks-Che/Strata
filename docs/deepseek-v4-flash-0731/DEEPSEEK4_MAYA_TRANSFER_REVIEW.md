# Что можно перенести из project-maya

Дата: 12 октября 2026. Проверены локальные исходники соседнего
`project-maya`, присланный анализ и отчёты нашего DeepSeek backend.
Maya в этом сравнении не запускалась. Её результаты на V100/3090/4090D
не являются прогнозом для DeepSeek на RTX 5090.

По уточнению пользователя CPU lane теперь допустим как **отдельная опция**.
Обычный профиль сохраняет вычисления модели на GPU.

## Новые направления

| Идея Maya | Что есть у DeepSeek | Что имеет смысл проверить |
|---|---|---|
| Prefill временно занимает хвост GPU-пула экспертов | Общий compute buffer target/DSpark уже экономит 1168 МиБ, но резерв 2452,06 МиБ остаётся и при decode | Раздельное резервирование prefill/decode и возврат свободной памяти кэшу на границе фаз |
| GPU сам читает таблицы VRAM/RAM и запускает fetch из mapped pinned RAM | MMVQ читает VRAM-кэш напрямую, однако router IDs и план передач обслуживает CPU | Сначала маленькая GPU-таблица адресов и pinned-арена для ограниченного числа горячих матриц |
| Сохраняемая статистика экспертов, загрузка горячих весов при старте | Частотный допуск и затухание есть; история не переживает процесс | Сохранить небольшую таблицу частот и измерить первый/второй запрос после перезапуска |
| CPU lane параллельно с GPU | До этого этапа CPU-математика намеренно запрещалась | Ограниченный пул потоков для части промахов VRAM, большой prefill на GPU |
| Router следующего слоя применяется к текущей активации | Наш shadow-тест использовал прошлые ID, а не текущую активацию | Сначала измерить прогноз top-1/top-2 без загрузки весов; это другой предсказатель |
| Prefill считает resident-экспертов, пока поступают остальные; результаты держит окном | Есть конвейер передачи, использование cache hits и отрицательный опыт early hits для короткого MMVQ | Отдельный потоковый MMQ-путь большого prefill, с ограниченным окном результатов |

## 1. Временная память prefill и кэш в одной арене

В Maya `prefill_carve()` вычисляет необходимый объём под реальный chunk,
`prefill_lend()` передаёт этот участок prefill, а `lend_tail()` сначала
завершает фоновые передачи и обновляет таблицы адресов. Горячие эксперты
перемещаются на место более холодных или паркуются в RAM. После prefill
слоты возвращаются пулу. Короткий prompt забирает только нужную часть.
См. [реализацию](../../../project-maya/src/core/glm_prefill.cu),
функции `prefill_carve`, `prefill_lend`, `lend_tail`, `prefill_return`.

Это отличается от нашего [компактного размещения](DEEPSEEK4_COMPACT_RAM_PREDICTOR.md):
там уменьшается размер отдельных тензоров, но большой зарезервированный
граф остаётся. Заимствование затрагивает жизненный цикл самого allocator.
**2452,06 МиБ — весь текущий общий compute buffer, а не обещанная экономия**:
decode также требует рабочую память. Сначала нужно измерить его минимальный
резерв с DSpark2, затем только разницу отдавать экспертам.

Проверка должна включать чередование коротких запросов и prefill 4096,
отмену, restore и рост графа. Важна общая длительность цикла: выигрыш decode
можно потерять на перемещении экспертов перед каждым prompt.

## 2. План на GPU и настоящая pinned RAM

В Maya `MoeDev` хранит таблицы GPU-адресов и mapped RAM-адресов.
`moe_route` выбирает источник на GPU, `moe_fetch_kernel` переносит данные
из закреплённой RAM в слот VRAM. Работа с SSD всё равно требует host service.
Это не GPUDirect Storage и не прямое вычисление всей матрицы с SSD.
См. [таблицы](../../../project-maya/include/strata/kernels/glm_fast.hpp),
[ядра](../../../project-maya/src/kernels/cuda/glm_fast.cu),
[размещение и service](../../../project-maya/src/core/glm_fast_path.cu).

Наш экспериментальный RAM-кэш хранит pageable-копии и передаёт их через
pinned staging. Его отрицательный результат не проверяет вариант Maya,
который убирает промежуточное CPU-копирование и часть синхронизаций.
Однако постоянно закреплять большую часть 128 ГиБ опасно для доступной
памяти ОС; такой кэш надо начинать с малого фиксированного бюджета и
учитывать commit, файловый кэш и сессии вместе.

У Maya GPU-fetch использует SM, а у нас H2D идёт через copy engine.
Нужно сравнить оба пути на PCIe 5.0 x16 RTX 5090. Заявлять пользу от
устранения CPU-копии без измерения этой конкуренции нельзя.

Полный перенос потребует нового протокола владения матрицами и адресами.
Наш глобальный матричный кэш и разделённые gate/up/down отличаются от
слотов целых экспертов с разделением по слоям Maya. Переносить весь
`glm_fast_path.cu` в llama-граф DeepSeek напрямую нельзя.

## 3. История частот между запусками

Maya `save_usage()` сохраняет counts через временный файл и rename;
`fast_warm()` использует пользовательские counts вместе с prior.
См. [исходник](../../../project-maya/src/core/glm_fast_path.cu).

Для нас переносима сама идея. Ключ файла должен включать модель,
квантование и идентичность shards; ключ записи — слой, эксперт и матрица,
а не адрес mmap текущего процесса. Target и DSpark требуют разных историй.
Нужны затухание старых частот и ограниченная загрузка, иначе старт начнёт
заранее читать с SSD веса, не нужные новому запросу.

Ожидаемая область эффекта — старт и смена процесса. Ускорение уже
прогретого одинакового запроса этим механизмом не доказано.

## 4. CPU lane

Maya считает gate/up, SwiGLU и down выбранных RAM-экспертов в CPU-пуле,
после чего возвращает их вклад. Калибровка сравнивает стоимость CPU с PCIe.
См. `lane_experts` и `fast_cpu_lane_setup` в
[glm_fast_path.cu](../../../project-maya/src/core/glm_fast_path.cu),
[native CPU kernels](../../../project-maya/src/kernels/cpu/native_expert.cpp).

Наш первый вариант использует границу отдельного `MUL_MAT_ID`: часть
матриц на CPU, остальные на GPU, итоговое суммирование остаётся в графе.
Это ограниченный прототип, **не полный перенос CPU lane Maya**. Он требует
больше промежуточных обменов, чем вычисление эксперта целиком. У CPU другая
квантизация активаций/редукция; совпадение с GPU по битам не предполагается.
Результаты реализации и измерений вынесены в [отчёт CPU lane](DEEPSEEK4_CPU_LANE.md).
Первый локальный опыт с 4/8/12/16 потоками не дал ускорения и выявил
изменение greedy-ответа после restore; опция остаётся экспериментальной
и выключенной по умолчанию.

## 5. Другой предсказатель

`STRATA_GLM_PREFETCH_N` применяет router будущего слоя к текущему FFN-input.
В [настройках Maya](../../../project-maya/docs/SETTINGS.md) есть ограничение
ранга, числа экспертов, момента запуска и числа CUDA-блоков копирования.
Там же сохранены как положительные, так и отрицательные результаты.

Наш лучший прошлый shadow-результат 62,62% полезных ID относится к
повторению прошлого маршрута. Он ничего не измеряет про такой lookahead.
Для DeepSeek сначала надо проверить применимость входа следующего router
с учётом HC и его нормализации. В отчёте прогноза считать только матрицы,
отсутствующие в VRAM, отдельно цену дополнительного router, байты ошибок
и время до использования. Подкачку включать только после этой проверки.

## Что уже есть или не подходит напрямую

- Частотный GPU-кэш, частичная загрузка DSpark, конвейер, прямое чтение
  VRAM-матриц и состояния сессий уже реализованы. Повторять их под другими
  именами не даёт новой оптимизации.
- Пример `~11` запусков вместо `~60` — описание специального пути GLM,
  не замер наших накладных расходов. У DeepSeek другой attention и HC;
  KDA-графы сюда не переносятся. CUDA Graphs в обычном CUDA backend уже есть.
- DFlash2 из Maya обучен под GLM и использует его скрытые состояния.
  Его веса не являются заменой DSpark для DeepSeek. Confidence-фильтр
  и длины draft мы уже проверяли в [отдельном этапе](DEEPSEEK4_DSPARK_TUNING.md).
- Меньше бит у постоянно резидентных весов может освободить VRAM,
  но меняет модель и требует оценки качества. Результаты Maya-S24
  не подтверждают безопасность такой же переквантизации нашего GGUF.
- `--parallel` улучшает совокупную скорость нескольких запросов;
  это не обещание ускорить один ответ. На 32 ГиБ дополнительные состояния
  также конкурируют с экспертным кэшем.
- Пропуск экспертов меняет вычисляемую модель и не входит в этот перенос.

После CPU lane наиболее предметный следующий опыт — измерить рабочую
память короткого decode и проверить возврат её избыточного резерва кэшу.
GPU-таблица с pinned RAM перспективна по устройству, но требует более
крупного изменения движка и отдельной проверки на нашем ПК.
