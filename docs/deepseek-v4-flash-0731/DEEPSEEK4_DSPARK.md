# DSpark для DeepSeek V4 Flash 0731

Дата: 3 октября 2026. Backend использует закреплённый llama.cpp
`3cf03257f219afbe7334045ff7c6a06ac68c627d`. Путь Qwen и его MTP остаются отдельными.

Дополнительные замеры длины черновика, фильтр confidence и направления
оптимизации: [DEEPSEEK4_DSPARK_TUNING.md](DEEPSEEK4_DSPARK_TUNING.md).

Конвейер чтения матриц, отдельный H2D stream, ограничения памяти и замеры:
[DEEPSEEK4_EXPERT_PIPELINE.md](DEEPSEEK4_EXPERT_PIPELINE.md).

## Какие веса нужны

В локальных `UD-Q3_K_XL` и `UD-Q8_K_XL` отсутствуют MTP-тензоры.
Для 0731 нужен отдельный DSpark, а не MTP pack Qwen и не MTP старого DeepSeek.
Архитектура его GGUF — `dflash`, три блока DeepSeek с MoE, Markov head,
максимальная длина черновика — пять токенов. По умолчанию предлагаются три.

Проверенный заголовок `dspark-DeepSeek-V4-Flash-0731-Q8_0.gguf`:

| Данные | Размер |
|---|---:|
| Файл | 10 896 057 440 байт |
| 81 тензор | 10 890 804 124 байта |
| Routed experts MXFP4 | 10 267 656 192 байта / 9,5625 ГиБ |
| Остальные веса | 623 147 932 байта / 0,580 ГиБ |

FP8-проекции исходного checkpoint переведены в Q8_0; эксперты уже представлены
MXFP4. Поэтому опубликованный BF16 вариант лишь немного больше (11,31 GB).
Состав и происхождение описаны в [README автора GGUF](https://huggingface.co/unsloth/DeepSeek-V4-Flash-0731-GGUF/blob/fbbb5b93fb787c21338159b0af3318bb3f4d9768/dspark/README.md).

Загрузчик фиксирует revision `fbbb5b93fb787c21338159b0af3318bb3f4d9768` и проверяет
SHA-256 `2c7ac54b0b64a99df1f139a9f1371a00198265e1d6a614b77597d20a655a4249`.
До проверки файл имеет расширение `.part`; готовый GGUF появляется только после
проверки размера и контрольной суммы. Скачать:

```powershell
.venv\Scripts\python.exe tools/fetch_deepseek4_dspark.py
```

## Частичная загрузка и GPU

По умолчанию плотные слои DSpark размещены в VRAM, эксперты читаются через mmap
и пересылаются выбранными матрицами. Embedding и output head берутся у основной
модели без второй копии. Применяются те же pinned-буферы и LRU, что у target.

У контекстов отдельные арены: `--expert-cache-mib` — основная модель,
`--draft-expert-cache-mib` — DSpark (по умолчанию 1024 МиБ). Бюджеты складываются;
плотные веса, KV, снимки compressor и рабочие буферы требуют дополнительной VRAM.
Перед READY проверяется остаток памяти с резервом 512 МиБ.

На RTX 5090 при контексте 8192 и кэше draft 1024 МиБ: плотные веса — 594,28 МиБ,
рабочие CUDA-буферы — 1168 МиБ, KV — 48 МиБ. Вместе с кэшем это **2834,28 МиБ /
2,77 ГиБ**. Снимки отката target при `draft-max=3` добавляют примерно 34,92 МиБ
к его compressor states. Это размеры выделений из журнала, без памяти драйвера
и других приложений; пиковая память всей карты приводится в замерах ниже.

Кэш работает на уровне отдельных матриц gate/up/down по 4,25 МиБ, а не целых
экспертов или слоёв. Матрицы используют исходные байты MXFP4. Размер бюджета
1024 МиБ вмещает около 240 матриц с padding. Более мелкое дробление само по себе
не уменьшит нужный объём весов: все части матрицы участвуют в вычислении.

`--draft-gpu-expert-layers 0` оставляет все три слоя экспертов в mmap;
значения 1–3 держат последние слои постоянно в VRAM. Один такой слой занимает
3,1875 ГиБ. При значении 3 кэш холодных экспертов draft не выделяется.

GPU-only audit действует на основной граф, инъекцию скрытых признаков, черновой
граф и проверку токенов. CPU упаковывает данные, копирует память и выполняет
sampling; математика слоёв модели на CPU запрещена. Число CPU threads остаётся 1.

## Проверка и кэш сессий

DSpark получает признаки выходов слоёв 40, 41, 42 target. В GGUF они обозначены
входами следующих слоёв: `[41, 42, 43]`. CPU лишь копирует эти массивы, их
объединение и проекция выполняются графом draft на GPU.

Target одним batch проверяет anchor и предложенные токены. Его sampler выбирает
каждый выходной токен; совпавший префикс принимается, после первого несовпадения
остальной черновик отбрасывается. Это работает и при temperature > 0: состояние
sampler продвигается только для фактически выбранных выходных токенов.

Параметр `n_rs_seq` сохраняет ограниченные снимки compressor на GPU. Ошибка отката
прерывает запрос; неподтверждённые токены не отправляются клиенту. После проверки
в draft KV добавляются только признаки подтверждённого префикса. Noise KV
удаляется до проверки. EOS и лимит ответа обрабатываются внутри принятого блока.

Снимок сессии включает target и draft. Сохраняется префикс перед последним токеном
prompt, как и без speculation. Размер обоих состояний учитывается в RAM budget;
отмена очищает оба активных контекста. Счётчики `drafts_offered` и
`drafts_accepted` передаются через DONE в статистику сервера. INFO и About
показывают `speculative=dspark`, при этом `mtp=0` остаётся честным описанием режима.

При проверке обнаружена и исправлена прежняя проблема whole-context restore:
llama.cpp ставил позицию записи KV в начало буфера. Для SWA это меняло порядок
ключей уже при первом продолжении. Локальная сборка теперь продолжает запись
после восстановленных строк. На prompt из 372 токенов первые logits до/после
восстановления стали совпадать точно; прежнее расхождение воспроизводилось и
без DSpark. Исправление применяется только к копии исходника DeepSeek backend.

## Включение

Backend собирается прежней командой из [DEEPSEEK4.md](DEEPSEEK4.md).
Без `--draft-model` поведение остаётся обычным autoregressive decode.
Пример отдельного профиля с потоковой загрузкой обоих наборов экспертов:

```powershell
.venv\Scripts\python.exe tools/setup_deepseek4.py --model-dir H:/deepseek-v4-flash-0731/UD-Q3_K_XL --cuda-dir build-local/cuda-13.0 --profile-tag ud-q3-k-xl-dspark --batch-size 4096 --expert-cache-mib 15360 --expert-stage-mib 16 --draft-model models/deepseek4-dspark/dspark-DeepSeek-V4-Flash-0731-Q8_0.gguf --draft-max 2 --draft-expert-cache-mib 1024
```

Для этого ПК подготовлены `strata-deepseek4-ud-q3-k-xl-dspark.json` и
`run-deepseek4-ud-q3-k-xl-dspark.bat`. Выбран черновик из двух токенов по замерам
ниже. Исходный `run-deepseek4-ud-q3-k-xl.bat` запускает профиль без DSpark.

`tools/setup_deepseek4.py --check-only` проверяет метаданные и полноту копирования
обоих файлов. Он не скачивает и не запускает модели.

## Проверки

- `deepseek4_speculative_contract`: полное/частичное/нулевое принятие, EOS,
  ограничение длины, отсутствие sampling отклонённого хвоста.
- `deepseek4_expert_transfer`: точность байтов, LRU, eviction, staging и раздельные
  бюджеты двух CUDA-контекстов с независимым временем жизни.
- `deepseek4_gpu_only_contract`: отказ до исполнения CPU-узла.
- `python -m unittest tools.test_deepseek4 serve.test_deepseek`: приём моделей,
  неполные sidecar-файлы, несовместимые признаки и формат DeepSeek/Qwen.
- `tools/validate_deepseek4_speculative.py --config ...`: реальные сессии A/B/A,
  продолжение активного контекста, отмена, один токен и seeded sampling.
  `--baseline` проверяет профиль без DSpark. `--check-causality` дополнительно
  меняет будущие токены при сохранении anchor и размера batch; эта диагностика
  требует нескольких GPU-проходов и не используется при замере скорости.
- `tools/benchmark_deepseek4.py --config ...`: prompt/decode/repeat, скорость,
  принятые черновики, CPU/RAM/VRAM; движок закрывается после замера.

Реальный тест состояния на Q3 прошёл: A/B/A по 64 токена, точное восстановление
продолженного контекста, отмена и следующий запрос, лимит в один токен, повтор
temperature 0,6 / seed 123 / repeat penalty 1,05. В 28 проверках причинности
максимальная разница logits anchor при изменении будущих токенов равна **0**.
Результат: `bench/results/deepseek4-dspark-validation-final.json`.

**Ограничение:** восстановление одной и той же сессии воспроизводимо, но полное
prefill того же текста после инкрементальной генерации давало другой ответ.
Обычная генерация и DSpark также не дали одинаковые 128 token IDs. Поэтому
нельзя обещать побитовое совпадение или считать качество автоматически
проверенным. Сходное расхождение для квантованных target зарегистрировано в
[llama.cpp #25618](https://github.com/ggml-org/llama.cpp/issues/25618); точная
причина локального различия не установлена. DSpark подготовлен отдельным
экспериментальным профилем, прежний профиль Q3 сохранён.

## Замеры скорости

Windows, Ryzen 9 9950X (32 логических CPU), 128 ГиБ RAM, RTX 5090 32 ГиБ,
Samsung 990 Pro. Target `UD-Q3_K_XL`, DSpark Q8_0, context 8192, batch 4096,
CPU threads 1, два pinned-буфера по 16 МиБ на контекст. Prompt генерации —
36 токенов, ответ — 128, temperature 0. Перед ним — отдельный prefill 256 токенов.
«Повтор» восстанавливает prompt из RAM. Файловый кэш ОС не очищался.

| Режим | Кэш target / draft, ГиБ | Первый decode, ток/с | Повтор, ток/с | Принято / предложено | Пик VRAM карты, МиБ |
|---|---:|---:|---:|---:|---:|
| Без DSpark | 15 / 0 | 3,02 | 12,11 | — | 28275 |
| DSpark, 3 токена | 12 / 1 | 3,80 | 11,55 | 80 / 141 | 28362 |
| DSpark, 3 токена | 15 / 1 | 5,14 | 12,25 | 80 / 141 | 30915 |
| **DSpark, 2 токена** | **15 / 1** | **7,36** | **14,85** | **78 / 98** | **31140** |

Два токена дали около **+23%** к прогретому повтору исходного режима; три токена
с тем же кэшем — лишь около +1%. Это один prompt и один прогретый повтор на
конфигурацию, не универсальная оценка ускорения. Первый decode сильно зависит
от резидентности страниц: рост 3,02 → 7,36 нельзя приписывать только DSpark.
При разных размерах batch получались разные ответы, поэтому это также не
сравнение одинаковой последовательности выходных токенов.

Пиковая загрузка процесса в этих замерах — 3,15–3,22% всех 32 логических CPU.
Аудит каждого графа подтвердил `cpu_compute_nodes=0` для target, draft и инъекции
признаков. Статистика и сырые token IDs сохранены в `bench/results/`:
`deepseek4-dspark-regression-baseline.json`, `deepseek4-dspark-streamed-3.json`,
`deepseek4-dspark-cache15-3.json`, `deepseek4-dspark-cache15-2.json`.

Контроль выбранного профиля после prefill **4096 токенов**:

- prompt: **44,69 с** (включая снимок сессии 51 мс);
- следующий decode 128 токенов: **3,48 токена/с**;
- повтор с восстановлением prompt: **14,85 токена/с**, те же 128 token IDs;
- пик памяти всей карты: **31193 МиБ**, CPU процесса: **3,17%**;
- минимальная свободная RAM: **2,17 ГиБ**.

Это подтверждает GPU-only работу на длинном prompt, но не устраняет задержки
подгрузки при нехватке RAM. Первый decode после большого prefill остаётся
существенно медленнее прогретого повтора. Результат:
`bench/results/deepseek4-dspark-cache15-2-4k.json`.
В INFO добавлены отдельные объёмы весов, KV и рабочих буферов draft; About
показывает резерв VRAM DSpark при запуске с учётом выбранного кэша.

Итоговые проверки сборки: 3/3 CTest, 16/16 Python tests и синтаксис `app.js`.
Проверка реальных сессий завершилась успешно; сравнение с полным prefill
остаётся указанным выше ограничением. После замеров тестовые процессы закрыты.

Проверка режима без DSpark после изменения: 128 токенов совпали с прежним
`deepseek4-transfer-cache.json`; cached repeat — 12,11 токена/с при кэше 15 ГиБ,
пиковая загрузка процесса — 3,17% 32 логических CPU. Файловый кэш ОС не очищался.
Первый decode после холодного prompt был 3,02 токена/с, поэтому прогретую скорость
нельзя считать гарантией для любого запроса.
