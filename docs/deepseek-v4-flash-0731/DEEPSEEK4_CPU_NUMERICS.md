# Этап 3: численная совместимость CPU/GPU

13 октября 2026. Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ,
Windows, CUDA 13.0, MSVC 2022. Модель: DeepSeek-V4-Flash-0731
UD-Q3_K_XL, DSpark Q8_0. Это проверка арифметики, не замер ускорения.

Найдена основная причина расхождения: CPU и GPU используют разные квантованные
активации для IQ3_XXS. Реализован отдельный CPU-эталон арифметики GPU. На сохранённых
экспертах и проверенном окне полной модели он дал точное совпадение. Однако
специальная проверка границ округления обнаружила различие SwiGLU.
Продолжение: [общий SwiGLU, Q8_1 и короткая редукция](DEEPSEEK4_SWIGLU_COMPATIBILITY.md).
Ниже сохранён исходный аудит до этих исправлений; этап 3 и приёмка адаптивного
CPU lane остаются открытыми.

## Где появляется разница

| Операция | Прежний CPU lane | GPU MMVQ |
|---|---|---|
| Активации для IQ3_XXS | Q8_K, блок 256, масштаб F32 | Q8_1, блок 32, масштаб F16 |
| Активации для MXFP4/Q8_0 | Q8_0, блок 32 | Q8_1, блок 32 |
| Округление Q8 на половинной границе | CPU SIMD может округлять к чётному | CUDA `roundf`, от нуля |
| Суммирование матрицы | CPU SIMD-редукция ggml | Частичные целочисленные dot, FMA, четыре warp, XOR-редукция |
| SwiGLU | CPU `std::exp(float)` | CUDA `expf` |

Совпадающие исходные веса не означают совпадающих результатов. Для IQ3_XXS первая
разница возникает при квантовании входа, до умножения матрицы. Небольшая разница
SwiGLU может затем пересечь границу повторного квантования перед down.

Сравнение выполнено с фактическим CUDA-квантизатором и графом pinned llama.cpp.
Дополнительно посчитан независимый double dot по распакованным весам и исходному
либо Q8_1-входу. Более близкое значение к float64 само по себе не является
совместимостью с выбранным GPU-путём.

## Реализованный эталон

[cpu_mmvq_reference.cpp](../../backends/deepseek4/cpu_mmvq_reference.cpp)
читает исходные IQ3_XXS, MXFP4 и Q8_0 без переквантования весов:

- повторяет Q8_1: блоки 32, масштаб и сумма F16, округление как у CUDA;
- повторяет частичные целочисленные dot, IQ3 scale/sign decoding, FMA и порядок
  редукции generic NVIDIA MMVQ;
- выполняет полный эксперт через существующий постоянный пул и сохраняет
  барьеры освобождения gate/up и down;
- включается только через `STRATA_DS4_CPU_MMVQ_REFERENCE=1`.

Это скалярный диагностический путь, не готовое быстрое многотокенное ядро.
Он относится к целому CPU-эксперту, не к старому `CPU_MATRIX_LEGACY`.
GPU-выбор ограничен окнами 1–4 и generic NVIDIA dispatch от Ampere, кроме DGX
Spark. На остальных GPU/длинных окнах сохраняется GPU-путь. Рабочий профиль и
калибровку по результатам этого опыта не меняли.

Реализация основана на `ggml-cuda/quantize.cu`, `vecdotq.cuh`, `mmvq.cu`;
MIT-атрибуция сохранена в файле. `third_party/llama.cpp` не редактировался.

## Сохранённые эксперты

Использованы восемь бинарных снимков из этапа 2: 13 пар «выбранный эксперт,
активация токена». Веса и входы взяты из реального исполнения, не пересозданы
из float. Двенадцать пар имеют gate/up IQ3_XXS и down MXFP4; одна — все три
матрицы MXFP4. Геометрия target: 4096 → 2048 → 4096.

| Проверка | Результат |
|---|---|
| Прежний CPU replay на 12 и 16 потоках | Совпадает с сохранённым CPU-выходом во всех 8 файлах |
| Q8_1 CPU-эталона против реального CUDA quantizer | Совпадают все байты на проверенных входах, включая down |
| Gate, up и down при одинаковом входе | Все 39 матричных результатов эталона совпадают с GPU побитно |
| Полный gate/up → SwiGLU → down | Эталон совпадает с GPU во всех 13 парах |
| Эталон через пул 12/16 потоков | Совпадает с однопоточным эталоном во всех 13 парах |
| Прежний CPU против GPU, 12 IQ3-экспертов | Относительная L2-ошибка полного выхода 1,00–1,54%; max abs до 0,01415034 |
| Прежний CPU против GPU, MXFP4-эксперт | Max abs полного выхода 1,43051e-6 |

Относительная L2 здесь — норма разницы векторов, делённая на норму GPU-выхода.
Это не процент ошибочных токенов и не оценка качества модели.

Дополнительно: четыре синтетические цепочки, включая смешанные
Q8_0/IQ3_XXS/MXFP4 и Q8_0 с геометрией 4096 → 2048 → 4096; zero/tie/outlier
входы квантизатора, clamp, окна 1/2/3/4/8. Для окон 1–4 префикс GPU совпал
побитно. У Q8_0 на окне 8 получена max abs 5,96046e-8: другое разбиение GPU
редукции. Поэтому поддержка окна 8 в эталоне не заявлена.

## Полные logits и смена размещения

Добавлена диагностика [cpu_numerics_probe.hpp](../../backends/deepseek4/cpu_numerics_probe.hpp).
`STRATA_DS4_CPU_NUMERICS_REPORT=<jsonl>` сохраняет сравнения. По умолчанию берётся
третий раунд DSpark; `STRATA_DS4_CPU_NUMERICS_ROUND=1..64` выбирает другой.

Один снимок состояния target, одно и то же окно token IDs, пять проходов:
исходный hybrid, GPU A, GPU B, hybrid A, hybrid B. Каждый повтор восстанавливает
снимок до decode. Отдельная пара GPU A/B проверяет воспроизводимость контроля.
Сохраняются max abs/RMS, argmax каждого токена и границы времени для сопоставления
с CPU trace. Диагностика меняет прогрев кэшей; её времена не являются benchmark.

Условия: контекст 372 токена, окно `[17900, 7421, 88240]`, **387 840 logits** на
проход; CPU policy `force`, один эксперт на токен, демоция 16 МиБ, target GPU-кэш
15 ГиБ, DSpark 1 ГиБ, RAM-кэш 2 ГиБ, два контекста этапа 2.

| Арифметика | Потоки | Исходный hybrid против GPU | Реальные CPU-строки в исходном проходе |
|---|---:|---|---:|
| Прежняя | 16 | Max abs **2,362428665**, не совпадает | 3 |
| MMVQ-эталон | 16 | Побитное совпадение всех logits | 3 |
| MMVQ-эталон | 12 | Побитное совпадение всех logits | 3 |

GPU A/B совпали во всех трёх опытах. После GPU-прогрева в hybrid A/B CPU-строк
было ноль: матрицы уже оказались на GPU. Это проверка перехода CPU → GPU,
а не доказательство повторного исполнения на CPU при неизменном размещении.
Последнее отдельно проверено на фиксированных бинарных снимках.
Одинаковый snapshot используется внутри каждого опыта; между отдельными
запусками legacy/reference бинарный snapshot не переносился.

Первый пробный запуск на раунде 1 также совпал, но не захватил нужное CPU-вычисление.
Он сохранён как неинформативный контроль и не используется для вывода о совместимости.

## Проверки жизненного цикла

Стандартный `tools/validate_deepseek4_speculative.py` не изменялся и не ослаблялся.
Диагностика logits в этих прогонах выключена.

- Эталон, force + демоция, 16 потоков: A→B→A, продолжение, fresh/full-prefill,
  cancel prefill/decode, after_cancel прошли; 8/8 сравнений greedy с GPU-контролем.
  Трасса содержит 316 CPU-заданий / 595 экспертных строк.
- Эталон, такой же профиль, 12 потоков: тот же validator прошёл, 8/8 greedy;
  299 CPU-заданий / 534 строки. Это отдельный запуск с меняющимся прогревом,
  не сравнение скорости 12 против 16 потоков.
- Seeded repeat: 24/24 одинаковых token IDs. Как и в этапе 2, явный seed запускает
  GPU-политику; это проверка GPU, а не доказательство численной совместимости CPU.
- Прежняя арифметика, тот же force-профиль и 16 потоков, в этой серии также прошла
  validator. Прохождение короткого greedy-теста не означает равенства logits;
  расхождение 2,36 выше измерено отдельно. Старые провалы этапа 2 не переписаны.
- Пять native CTest: numerical audit, CPU expert, CPU matrix lane, два контекста
  combined/cache с CUDA Graph режимами — прошли. Первый запуск CTest из PowerShell
  не нашёл CUDA DLL (`0xc0000135`); повтор с явным PATH через Python прошёл 5/5.

## Оставшееся препятствие: SwiGLU

На 13 обычных снимках raw hidden различается до 4,76837e-7, но это не изменило
Q8_1 перед down. Поэтому весь выход экспертов совпал.

Отдельный тест поставил hidden на половинные границы Q8_1. На 4096 значениях:

- CPU/GPU SwiGLU: 1637 различающихся float, max abs 1,43051e-6;
- после квантования: **718 различных Q8-значений**;
- CPU-квантизатор на самом GPU-hidden по-прежнему совпадает с CUDA побайтно.

Оставшееся расхождение локализовано в вычислении активации, а не в Q8_1 packing.
Эти специально подобранные данные не оценивают частоту проблемы на пользовательских
запросах, но опровергают обещание всеобщего побитного равенства текущего эталона.

## Контракт следующих ядер

1. Packing Q8_1 и dot/reduction оптимизированного CPU-ядра должны совпадать с
   эталоном побитно. Процентный допуск не заменяет эту проверку.
2. Число CPU-потоков, повтор эксперта и будущие токены в коротком окне не должны
   менять результат уже заданной строки. Начальная область — окна 1/2/3/4.
3. До приёмки адаптивного размещения нужен общий воспроизводимый путь SwiGLU
   и проверка его квантованных hidden, включая половинные границы. Просто
   увеличить epsilon или ослабить validator нельзя.
4. Затем повторить полные logits и lifecycle с существенной фактической CPU-работой,
   в том числе auto + демоция. Пока проверены force-профиль и ограниченный корпус.
5. Только после этого выбирать SIMD/multi-token реализацию, калибровать стоимость
   и измерять ускорение полного запроса. Численный эталон сам по себе ускорением
   не считается.

## Воспроизведение и артефакты

CTest: `deepseek4_cpu_numerics`. Отдельный запуск:

```powershell
.\build-deepseek4\deepseek4_cpu_numerics_test.exe <cpu-job-*.bin> ...
```

нативного приложения). Без аргументов выполняется синтетическая часть. Требуются
CUDA DLL в PATH. Возврат 77 — нет подходящего GPU; `status=passed` означает прохождение
проверок эталона, а не всеобщую совместимость цепочки. Для последней в JSON явно
указано `universal_chain_compatibility_proven=false`.
