# О4: отбор О3 в обычном GPU-пути

14 октября 2026. Продолжение [обхода пустой CPU-ветки](DEEPSEEK4_TRANSFER_O4_GPU_FALLBACK.md)
и [плана оптимизации](DEEPSEEK4_TRANSFER_OPTIMIZATION_PLAN.md).

## Изменение

Предыдущий обход очереди исключал CPU-service и GPU-fetch, но возвращал старый
поочерёдный допуск матриц. В его короткой A/B/B/A H2D вырос с 25,681 до
31,680 ГиБ, а decode замедлился на 5,76%.

Новая опция `STRATA_DS4_ORDINARY_DEMAND_CACHE=1` переносит отбор О3 в обычный
планировщик. По умолчанию она выключена. Очередь и обычный путь вызывают одну
функцию выбора слотов; её правила не продублированы.

Планировщик передаёт три матрицы целой ветки up/gate/down и уже прочитанный
маршрут. Дополнительной синхронизации для чтения IDs нет. Для короткого пакета
до восьми токенов владелец строит полный снимок GPU-попаданий, собирает реальные
промахи и выбирает слоты сразу для трёх матриц. Приоритет учитывает частоту,
стоимость вытеснения и точный размер с padding. Порядок суммирования на GPU
сохраняется. Обучение частот и LRU отложено до завершения ветки и повторяет
порядок О3: up/gate/down, затем порядок первого появления эксперта в маршруте.

Новые admissions читаются напрямую из GPU-кэша, как в очереди О3. Непринятые
промахи используют обычный временный буфер. Защита живых читателей и бюджет
VRAM сохраняются. При отмене неиспользованные слоты возвращаются с прежним
содержимым; публикуются только матрицы, для которых действительно отправлено
копирование. Отсутствующий элемент staging завершает производителя, сохраняя
владение слотами до конца ветки.

Новая ветка не создаёт GPU-fetch queue, CPU snapshot или CPU-service.
Обычный конвейер чтения и передачи продолжает работать. Ветки с назначением
CPU сохраняют прежний транспорт. Полный prefill с пакетом больше восьми
токенов также сохраняет прежний путь. Изменения находятся только в DeepSeek
backend; общий ABI `StrataExpertSlice` не менялся.

## Включение

Для обхода заведомо пустой CPU-ветки нужны обе опции:

```text
STRATA_DS4_CPU_EMPTY_GPU_FALLBACK=1
STRATA_DS4_ORDINARY_DEMAND_CACHE=1
```

Отбор использует настройки О3: `GPU_FETCH_CACHE_SLOTS=8`,
`GPU_FETCH_DEMAND_CACHE=1`, rank, scan, margin, границы бюджета и разрешение
замены матриц текущей ветки. В этой серии rank включён только для target:
`GPU_FETCH_DEMAND_RANK_MIN_CACHE_MIB=1025`, scan 256, margin 1,
current victims 0. Все перечисленные имена имеют префикс `STRATA_DS4_`.
Одного нового флага без slots/demand недостаточно. Путь доступен и при
полностью выключенном CPU lane, если переданы настройки отбора.

`ordinary_cache_branches` в `STRATA_EXPERT_TIMING` показывает фактическое
число веток нового пути. `cpu_gpu_fallback` отдельно считает доказанный
отказ от CPU-очереди; эти счётчики не обязаны совпадать. Обычный отбор
охватывает также первые hash-слои, которые очередь О3 не обслуживала.

## Проверки

- 43 CTest прошли. После усиления проверки отмены четыре новых теста
  повторены: всего 47 выполнений, без изменения бинарного файла движка.
- Новый тест проверяет 18 сочетаний IQ3_XXS/MXFP4/Q8_0, 1/3/8 токенов,
  фиксированной арены и управляемого кэша. На каждом — 24 маршрута с
  повторами, хвостовым экспертом и давлением на кэш. Результаты побитно
  совпали с чистым GPU; H2D, попадания, промахи и admissions совпали с О3.
- Эти проверки повторены с CUDA Graphs и без них, с разрешёнными и
  запрещёнными жертвами текущей ветки. Отмена и частичная загрузка
  проверяют реальный возврат слотов, синхронный fallback staging и точный
  результат после восстановления.
- На модели target-only совпали полные logits шести префиксов и 86 шагов:
  автоматический режим, заведомый обход CPU и отдельный режим `force`.
  В автоматическом тесте CPU jobs = 0, поэтому он сам по себе не проверяет
  CPU-арифметику. В проверке `force` выполнены 86 заданий / 96 строк, CPU
  в prefill = 0; её время не используется как показатель ускорения.
- Lifecycle с измеренным профилем прошёл все восемь сравнений greedy с
  GPU-эталоном, restore/continue/cancel/seeded; выполнены 25 CPU jobs / 33 rows.
  Ветка обычного отбора и обход CPU обе реально использовались.
- На измеренном профиле поколение осталось 0. Отдельный lifecycle с намеренно
  заниженной вдвое оценкой CPU-вычислений также прошёл, но собрал только
  21 job / 29 rows: недостаточно наблюдений для обновления по отдельным
  ячейкам. Поэтому добавлена проверка восьми fresh-запросов по 32 токена с
  тем же тестовым профилем: 208 jobs / 285 rows, используются поколения 0–3,
  на последней границе опубликовано поколение 4. Все input/output IDs и
  acceptance совпали с GPU-контролем. Этот искусственный профиль служит
  проверке переходов и не используется в таблицах производительности.

## Условия модельных замеров

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ; фактический PCIe Gen3 x16.
Target — `H:\deepseek-v4-flash-0731\UD-Q3_K_XL`, DSpark — Q8_0, draft max 2.
Контекст 8192, GPU-кэш target/DSpark 15360/1024 МиБ, RAM-кэш 2048 МиБ.
Для N0 — CPU 12 потоков, partitions 2, spin 0, budget 0,01 мкс,
KEEP_RAM 0, demotion 0. Профиль стоимости пересоздан после сборки.

Прежний О3 использует DMA depth 8, staging 4×4 МиБ, mapped reader,
early sources 1 и `CPU_EMPTY_FAST=1`. Остальные опции пустых очередей и
парковки выключены. Новый вариант добавляет обычный обход и отбор О3.

В каждом коротком процессе четыре fresh-запроса по 15 входных и 32 выходных
токена. Первые два — прогрев; скорость считается как 64 токена / суммарный
decode последних двух. Wall, CPU-seconds и H2D также относятся к последним
двум запросам. Процент между режимами считается по среднему скоростей
процессов. Файловый кэш Windows не очищался; новый процесс не означает
холодный SSD. Физические счётчики дисков относятся ко всем процессам.

Артефакты серии: `build-local/deepseek4/transfer-o4-ordinary-cache-20261014/`.
Конфигурации, исполняемый файл, свежий профиль, исходники, логи, JSON замеров
и проверки SHA-256 сохраняются вместе. Предыдущие архивы не изменяются.

## Короткий N0: три A/B/B/A

База — предыдущий лучший О3 с `CPU_EMPTY_FAST=1`. Кандидат — обычный
GPU-путь с общим отбором О3. В каждой серии по два процесса каждого режима.

| Серия | База, ток/с | Кандидат, ток/с | Decode | Wall базы → кандидата, с |
|---|---:|---:|---:|---:|
| 1 | 14,774 | 15,873 | +7,44% | 6,813 → 6,508 |
| 2 | 14,828 | 15,869 | +7,02% | 6,821 → 6,492 |
| 3 | 13,605 | 14,296 | +5,08% | 7,437 → 7,187 |
| Среднее | **14,403** | **15,346** | **+6,55%** | **7,0235 → 6,7292 (−4,19%)** |

CPU-seconds: **11,818 → 9,089 (−23,09%)**. Третья серия медленнее для обоих
режимов; она включена в итог. Причина общего снижения скорости не установлена.
Температура GPU в измеряемых пробах 39–42 °C, доступная RAM примерно 56–57 ГиБ.

H2D двух поздних decode одинаков во всех повторах каждого режима:

| Путь | Target, ГиБ | DSpark, ГиБ | Всего, ГиБ |
|---|---:|---:|---:|
| Обычный путь без переноса О3, отдельный пилот | 29,646 | 2,034 | 31,680 |
| Очередь О3, база A/B/B/A | 22,971 | 2,711 | 25,681 |
| Обычный путь с О3 | **21,737** | **2,711** | **24,448** |

Таким образом, общий H2D снизился на **4,80% относительно очереди О3** и
на **22,83% относительно обычного пути без переноса**. У DSpark новый путь
повторяет О3; его трафик выше старого обычного допуска. Общий результат
определяется уменьшением загрузок target.

В двух поздних decode кандидат обрабатывает обычным отбором 1634 ветки target
и 102 DSpark. Из них 1520/102 — доказанный обход CPU-очереди, ещё 114 target —
hash-слои. Это объясняет более широкую область действия по сравнению с
очередью; отдельная абляция hash-слоёв в этой серии не проводилась.
Подготовка слотов занимает примерно 82–90 мс против 38–40 мс у очереди,
но исключены CPU snapshot/selection и её обслуживание. Интервалы разных
счётчиков могут перекрываться и не суммируются как компоненты времени запроса.

Все четыре запроса каждого процесса совпали по input/output IDs и acceptance;
в поздних запросах принято 14 из 33 draft-токенов на запрос. CPU jobs/rows = 0,
физическое чтение модельного H: = 0. На другом диске наблюдается фоновое чтение;
его системный счётчик не приписывается движку.

## Длинный контекст

Порядок процессов: очередь О3 / новый N0 / новый N0 / очередь О3.
В каждом последовательно идут 4096 fresh/restore и 8152 fresh/restore,
по 32 выходных токена. Все входы, ответы и acceptance совпали. CPU jobs/rows
в prefill и decode равны нулю.

| Запрос | Prefill базы → кандидата, с | Decode базы → кандидата, с | Wall базы → кандидата, с |
|---|---:|---:|---:|
| 4096 fresh | 18,605 → 18,655 (+0,27%) | 17,746 → 20,185 (+13,74%) | 36,344 → 38,836 (+6,86%) |
| 4096 restore | 0,041 → 0,041 | 2,360 → 2,348 (−0,49%) | 2,407 → 2,390 (−0,69%) |
| 8152 fresh | 33,586 → 33,719 (+0,40%) | 5,472 → 5,749 (+5,06%) | 39,063 → 39,461 (+1,02%) |
| 8152 restore | 0,064 → 0,065 | **2,171 → 1,914 (−11,84%)** | **2,235 → 1,985 (−11,17%)** |

Fresh 4096 читает в среднем 62,08 → 63,96 ГиБ с H: за весь запрос,
fresh 8152 — 122,16 → 122,19 ГиБ. Fresh 4096 имеет заметный разброс:
wall базы 34,187–38,500 с, кандидата 37,312–40,360 с. Это не контроль с
одинаковым состоянием файлового кэша. Причину ухудшения нельзя целиком
приписать движку или SSD по этим счётчикам; ускорения холодного запроса
серия не подтверждает. Полный prefill без физических чтений здесь не получен.

H2D тоже не улучшается на каждой истории:

| Запрос | H2D prefill базы → кандидата, ГиБ | H2D decode базы → кандидата, ГиБ |
|---|---:|---:|
| 4096 fresh | 83,921 → 83,921 | 33,589 → 34,110 |
| 4096 restore | 0 → 0 | 17,080 → 16,005 |
| 8152 fresh | 138,142 → 138,304 | 17,111 → 16,897 |
| 8152 restore | 0 → 0 | 13,891 → 13,820 |

Оба restore идут без чтения H:. У 4096 изменение времени мало;
на 8152 подтверждён выигрыш прогретого decode. Новый флаг остаётся
опциональным: он устраняет короткую регрессию H2D прежнего обхода,
но не гарантирует меньший трафик и ускорение любого холодного запроса.

## GPU-only и оставшаяся цена гибрида

Сначала отдельная G/N0/N0/G дала прежнему GPU-only 15,709 ток/с и 6,586 с,
новому N0 — 15,938 ток/с и 6,4605 с: +1,46% decode, −1,91% wall.
Короткий порог относительно прежнего G выполнен.

Затем тот же отбор включён при полностью выключенном CPU lane. В этом
профиле также нет экспертного RAM-кэша гибрида; это отдельная GPU-only
конфигурация, а не изоляция одной проверки CPU-планировщика. При прежних
GPU-бюджетах, модели, численных настройках и DSpark новая A/B/B/A дала:

| Показатель | GPU-only без О3 | GPU-only с О3 | Изменение |
|---|---:|---:|---:|
| Decode, ток/с | **15,787** | **17,669** | **+11,92%** |
| Wall двух запросов, с | 6,5235 | 6,0310 | −7,55% |
| CPU-seconds | 8,758 | 8,195 | −6,42% |
| H2D decode, ГиБ | 31,680 | 24,448 | −22,83% |

В каждом процессе первый и второй запросы исключены как прогрев.
Во всех четырёх процессах позднее чтение H: = 0, CPU jobs/rows = 0,
input/output IDs и acceptance совпали. Отбор реально обработал 1634 ветки
target и 102 DSpark. Это одна GPU-only A/B/B/A; длинная серия выше относится
к гибридному N0, отдельная длинная приёмка GPU-only с О3 ещё не проведена.

Первый диагностический `pilot-4-gpu-ordinary` включал новый флаг, но не
задавал cache slots. Его счётчик ordinary = 0; он не считается испытанием
нового GPU-only пути. Правильный профиль называется `gpu-o3-config.json`.

В архиве `best-config.json` сохраняет GPU-only с О3 для дальнейших испытаний,
`best-n0-config.json` — вариант с отключением заведомо пустых CPU-веток.
Рабочий профиль сервера и глобальные значения по умолчанию не переключены.

Перенос отбора выполнен, но весь О4 не закрыт. При одинаковом H2D новый
GPU-only быстрее гибридного N0; оставшаяся разница уже не объясняется лишними
байтами передачи. Следующий шаг — измерить цену ранней проверки CPU-бюджета,
повторных завершений ветки и обслуживания RAM при нулевом назначении.
Для холодных запросов отдельно сравнить план чтения и передачу после полного
prefill. Автоматический выбор транспорта по прогреву пока не реализован.
