# Router на длинном prefill и граница shared expert

11 октября 2026. Windows, RTX 5090 32 ГиБ, Ryzen 9950X, RAM 128 ГиБ,
CUDA 13, драйвер 581.80. Модель — DeepSeek-V4-Flash-0731 UD-Q3_K_XL,
четыре GGUF-файла на H: (Samsung 990 PRO 4 ТБ, PhysicalDrive6).

Этот этап продолжает [проверку проекций HC](DEEPSEEK4_HC_PROJECTIONS.md).
Цель — одинаковая арифметика полного и поэтапного prefill для дальнейших
проверок DSpark. Исправлено локальное расхождение BF16-router при одинаковом
входе. Полные logits пока различаются; следующий участок — shared и routed
expert. Изменение остаётся исследовательским, рабочий профиль не меняется.

## Изменение

Новый `STRATA_DS4_ROUTER_SAMPLE_MMVF=1/2/3` доступен только при
`STRATA_DEEPSEEK_PROJECTION_EXPERIMENT=ON`; по умолчанию выключен.
Он использует тот же адаптер оси samples, что и HC: группы по 1/4/8 токенов,
один запуск CUDA на полные группы и ещё один на остаток. Весовая матрица
передаётся всем samples через штатный broadcast MMVF. Меняются только метаданные
тензора, без упаковки данных, новых GPU-буферов и host-цикла по токенам.

Границы применения: NVIDIA, BF16-веса `[4096,256,1,1]`, точный суффикс
`.ffn_gate_inp.weight`, F32-вход/выход, `GGML_PREC_F32`, плотные тензоры,
1–4096 токенов. Другие формы, типы, strides, precision и имена сохраняют
штатный путь. Прежний `STRATA_DS4_ROUTER_MMVF=1` для 2–4 токенов не менялся.
Контроль SHA-256 исходника MMVF защищает зависимость адаптера от его strides
и broadcast. Изменений в `third_party/llama.cpp` нет.

Фактическая трасса контрольного router: `cuBLAS` при 371/409 токенах,
`MMVF` при одном, `MMF` при пяти. Новый путь использует MMVF с постоянной
редукцией при всех этих размерах и сохраняет исходные F32-активации.
Трассировка расширена на router и gate/up/down shared expert.

## Изолированная проверка

Новый `test_router_projection.cpp` проверяет реальную форму BF16-router
на синтетических данных: **19 размеров пакета и 12 проверок границ** для
каждого из трёх режимов. Размеры: 1/2/3/4/5/6/7/8/9/15/16/17/32/128/
371/409/512/1024/4096. Независимый FP64-эталон использует сохранённые
BF16-веса и исходный F32-вход; CPU вычисляет только эталон теста.

Проверены выбранные столбцы против одиночного GPU-вычисления и FP64,
весь общий префикс 371/409, нулевой токен среди ненулевых, хвосты групп,
неподходящее имя/суффикс, strides входа и весов, K/M, F32/F16-веса,
неподходящий precision и пакет 4097. Во всех трёх режимах выбранные столбцы
побитово равны serial. Максимальная ошибка относительно FP64 —
**1,1249438785e−6**.

На всём префиксе 371/409 штатный путь различался в 86829 элементах,
max Δ = 4,2915344238e−6; новый путь дал **0 отличающихся элементов**.

Ниже медианы трёх измерений одной проекции, мкс. CUDA graphs выключены;
веса и входы уже в VRAM. Это не скорость модели.

| Токенов | Штатный путь, серия режима 3 | Группа 1 | Группа 4 | Группа 8 |
|---:|---:|---:|---:|---:|
| 1 | 31,31 | 30,16 | 29,14 | 29,86 |
| 4 | 36,71 | 31,52 | 31,76 | 32,96 |
| 371 | 65,26 | 271,95 | 155,79 | 145,99 |
| 409 | 70,55 | 288,87 | 165,80 | 153,77 |
| 4096 | 206,08 | 2556,23 | 1222,67 | 996,45 |

Группа 8 быстрее группы 1 в 2,57 раза при 4096 токенах, но примерно
в 4,84 раза медленнее штатной проекции. Эти группы дают одинаковые
проверенные значения. Численная воспроизводимость здесь имеет стоимость.

Первый прогон обычной сборки выявил ошибку нового fixture: штатный MMF
на 5–16 токенах сравнивался только с исходным F32-входом. Его ожидаемое
округление до BF16 даёт max Δ до 0,01499049 относительно такого эталона.
Добавлен отдельный FP64-эталон с BF16-входом для fallback. При выключенном
эксперименте по-прежнему обязательно побитовое совпадение с обычным CUDA-путём;
строгий допуск MMVF относительно исходного F32-входа не расширялся.
Исходный неуспешный результат сохранён как `default-router-initial.json`
с общим префиксом имён этого этапа.
С BF16-эталоном max Δ этих пакетов составляет 4,841713235e−6.
После исправления все три экспериментальных режима проверены повторно:
их результаты FP64 и serial полностью совпали с первоначальными.

## Проверка модели и локализация FFN

Использованы прежние 410 token IDs: полный префикс 409 против
префикса 371, одиночных токенов 371–403 и пакета 404–408; последний токен
409 всегда отдельно. Во всех вариантах MMQ=5/J64/4, FA=4, HCA=1, HC=3,
прежний короткий router=1, MMVQ=2, TF32 off. Менялся только новый router.

На обеих исторических позициях вход FFN точно одинаков. После изменения
побитово совпадают выход router, top-k IDs и веса маршрутов.

| Узел первого слоя | Row 282: до / после, max Δ | Row 371: до / после, max Δ |
|---|---:|---:|
| BF16 router | 7,7486e−7 / 0 | 8,3447e−7 / 0 |
| Веса маршрутов | 1,1921e−7 / 0 | 1,7881e−7 / 0 |
| Routed MoE | 5,9605e−8 / 0 | 0,044727396 / 0,044727374 |
| Shared gate | 4,7684e−7 / столько же | 0,000284672 / столько же |
| Shared up | 9,5367e−7 / столько же | 0,000338018 / столько же |
| Shared down | 2,3842e−7 / столько же | 0,001514137 / столько же |
| Выход слоя | 5,9605e−8 / столько же | 0,022314670 / 0,022314658 |

На row 282 сравниваются два больших пакета. На row 371 — большой пакет
и одиночный токен: здесь routed MoE различается уже при одинаковых входе,
IDs и весах маршрутов. Следовательно, router не был единственной причиной.
На последнем токене 409 все наблюдаемые узлы первого слоя совпадают.

Shared gate/up имеют Q8_0-веса `[4096,2048,1,1]`, down — Q8_0
`[2048,4096,1,1]`; precision у всех обычный. Трасса показывает MMQ
на 371/409 токенах, MMVQ на 1/5. У gate/up входы совпадают, а выходы уже
различаются. Вход down на row 371 различается на 0,0003824234, поэтому
ошибку down нельзя целиком приписать его собственному умножению.

| Режим | Max Δ конечных logits | RMS Δ | Argmax full / segmented |
|---|---:|---:|---|
| Новый router выключен | 5,439953566 | 1,153730412 | 539 / 112496 |
| Новый router, группа 8 | 2,676424503 | 0,470839858 | 539 / 1 |

Разница logits уменьшилась на этой истории, но **совпадение всей модели
не достигнуто**. Это не измерение качества ответов на корпусе.
Observer, snapshot/restore и replay дали max Δ = 0 во всех probes.
Наблюдение синхронизирует GPU; времена probes не используются как benchmark.

## Сессии и DSpark

Экспериментальная сборка прошла **31/31 CTest за 110,28 с**, включая
все три режима router, прежние режимы HC/attention, передачи экспертов
и GPU-only контракт. Плотные проекции также отдельно проверены с обычной
настройкой TF32. Проверки модели без DSpark и с ним прошли за
**60,04 / 81,03 с**.

Greedy token IDs совпали между режимами без DSpark и с ним во всех восьми
сценариях: две сессии, восстановление, продолжение активной и восстановленной
сессии, полный prefill продолжения, один токен, генерация после отмены.
Проверены отмена prefill/decode и повтор с фиксированным seed.
**30 проверок причинности DSpark дали max Δ logits = 0**.

`full_prefill_identical=false` в обоих режимах: продолжение после полного
prefill отличается от поэтапного начиная с пятого выходного токена.
Восстановление собственной сессии остаётся точным. Этот флаг в существующем
валидаторе выводится отдельно и не является assert: успешный выход скрипта
не означает равенства всех вариантов prefill. Linux, другие GPU и качество
ответов на корпусе этим этапом не проверялись.

## Скорость модели

Один архивный `final.exe`, A/B/B/A, без DSpark: новый router выключен
против группы 8. Все остальные численные параметры равны. Контекст 8192,
batch 4096, expert-кэш 15360 МиБ, staging 16 МиБ, pipeline=1, slab=16,
readers=2, frequency, MMVQ=2. Это сравнение с предыдущим исследовательским
профилем, не с рабочим. Трассировка выключена. Повторный prefill использует
новую сессию и сохранённый кэш весов; файловый кэш ОС не очищался.

Первая серия: два повтора decode по 32 токена, один повторный полный
prefill 4096. В таблице decode — медиана двух повторов.

| Порядок | Новый router | Decode, ток/с | Повторный prefill 4096, мс |
|---|---:|---:|---:|
| A1 | 0 | 17,135 | 10042,70 |
| B1 | 3 | 17,277 | 10039,00 |
| B2 | 3 | 17,206 | 9699,25 |
| A2 | 0 | 17,595 | 9600,77 |

Медианы запусков: **17,365 → 17,242 ток/с (−0,71%)**, prefill
**9821,74 → 9869,13 мс (+0,48%)**. В A1/B1 первый повтор decode был
15,905/16,155 ток/с, второй — 18,365/18,399 при нулевом чтении H:.
Поэтому выполнена дополнительная серия с четырьмя повторами; ещё до её
запуска для сравнения выбраны последние два, а все четыре сохранены в JSON.

| Дополнительная серия | Новый router | Decode, последние 2, ток/с | Decode, все 4, ток/с | Prefill, мс |
|---|---:|---:|---:|---:|
| A1 | 0 | 19,454 | 18,699 | 10171,00 |
| B1 | 3 | 20,045 | 19,067 | 9667,20 |
| B2 | 3 | 20,219 | 19,379 | 9670,44 |
| A2 | 0 | 20,220 | 19,324 | 9714,01 |

Медианы последних двух: **19,837 → 20,132 ток/с (+1,49%)**; всех четырёх:
**19,011 → 19,223 (+1,12%)**. Prefill: **9942,51 → 9668,82 мс (−2,75%)**.
При этом контроль A1 → A2 сам изменился с 19,454 до 20,220 ток/с,
а его prefill — с 10171 до 9714 мс. В первой серии знак разницы был обратным.
**Устойчивое ускорение не подтверждено**: изменение между режимами меньше
наблюдаемого разброса контрольных запусков. Новый router остаётся выключенным.

Во всех восьми запусках совпали 32 выходных token IDs decode и три token IDs
prefill, включая все cached repeats. Все **24 повтора decode и 8 повторных
полных prefill** показали 0 байт физического чтения H:. Первые запросы могли
читать SSD; счётчик относится ко всему PhysicalDrive6.

В дополнительной серии медианы CPU процесса на активных фазах A1/B1/B2/A2:
**4,80 / 4,86 / 4,86 / 4,81%** мощности всей системы; максимумы —
6,39 / 6,46 / 6,39 / 6,20%. Общий CPU достигал 10,4 / 12,1 / 9,3 / 11,1%.
Выборочные пики общей VRAM: 28841 / 28738 / 28796 / 28808 МиБ.
Аудит модели: 1 запись без DSpark, 337 с ним, везде **`cpu_compute_nodes=0`**.
Копирование и управление GPU по-прежнему требуют CPU; вычисление модели
на CPU не переносилось.

## Следующий шаг

1. Проверить фиксированный MMQ отдельно на shared gate/up и down с их
   реальными формами, FP64-эталоном и проверкой общего префикса.
2. Проверить всю цепь gate/up → SwiGLU clamp → down. Штатный CUDA backend
   умеет объединять gate/up/GLU на одном токене: новый dispatch должен
   учитывать этот путь, а не только отдельный MUL_MAT. Нужен контроль
   logits с наблюдением и без него.
3. Отдельно локализовать routed `MUL_MAT_ID` при уже одинаковом router.
   Текущий `@weight:` probe выбирает только обычный MUL_MAT; для routed
   матриц потребуется отдельная проверка ID/формы/входа.

Сырые результаты: `bench/results/ds4-router-shared-20261011-*`.
Профили, команды и архивные движки:
`build-local/deepseek4/router-shared-20261011`.
