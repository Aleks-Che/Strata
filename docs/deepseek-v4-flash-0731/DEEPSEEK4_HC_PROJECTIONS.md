# F32-проекции HC с арифметикой одиночного токена

11 октября 2026. Продолжение [выходных проекций attention](DEEPSEEK4_OUTPUT_PROJECTIONS.md).
Windows, Ryzen 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, CUDA 13.0,
драйвер 581.80. Модель DeepSeek V4 Flash 0731 UD-Q3_K_XL на H:;
llama.cpp закреплён на `3cf03257f219afbe7334045ff7c6a06ac68c627d`.

Эксперимент устраняет найденное расхождение двух F32-матриц коэффициентов
HC. На проверенных исторических позициях теперь точно совпадает весь участок
первого слоя до нормализованного входа FFN. Полная численная эквивалентность
ещё не достигнута: конечные logits различаются сильнее прежнего, а первый
greedy-токен полного/поэтапного prefill остаётся разным. Это диагностический
режим, выключенный в обычной сборке.

## Реализация

Для `hc_attn_fn` и `hc_ffn_fn`, обе **F32 16384×24**, добавлен
`STRATA_DS4_HC_MMVF`. Он действует только при
`STRATA_DEEPSEEK_PROJECTION_EXPERIMENT=ON`:

| Значение | Выполнение |
|---|---|
| 0 или не задано | Штатный выбор MMVF/cuBLAS |
| 1 | Один столбец на sample, все токены одним запуском MMVF |
| 2 | По четыре столбца на sample, хвост отдельным запуском |
| 3 | По восемь столбцов на sample, хвост отдельным запуском |

Меняются только временные копии метаданных тензоров: `[K,N,1,1]`
представляется как `[K,C,1,N/C]`, веса транслируются на все samples.
Данные остаются на прежних адресах. Штатный CUDA MMVF уже поддерживает
эти strides, трансляцию весов и 1–8 столбцов. Полный набор групп выполняется
одним kernel launch, остаток — вторым; цикла запусков по отдельным токенам,
нового device kernel, буфера упаковки и копирования данных нет.

Допуск ограничен NVIDIA, точными именами/формами, F32 весами, входом и выходом,
contiguous layout, одним исходным каналом/sample и batch **1–4096**.
Неподдержанные случаи сохраняют штатный путь. HC head сюда не включён.
Проверка SHA-256 исходного `mmvf.cu` требует пересмотра адаптера при изменении
закреплённой зависимости. Изменения изолированы в backend DeepSeek.

Код: [dispatch](../../backends/deepseek4/projection_dispatch.inc),
[проверка закреплённого MMVF](../../backends/deepseek4/ProjectionPatches.cmake),
[GPU-тест](../../backends/deepseek4/test_hc_projection.cpp).

## Изолированные проверки и подбор групп

Первый вариант с одним столбцом прошёл **30 сочетаний и 12 защитных проверок**
с TF32 off и с обычной настройкой TF32. После добавления групп набор расширен
до **38 сочетаний для каждого из трёх режимов**: обе HC-матрицы и batch
1/2/3/4/5/6/7/8/9/15/16/17/32/128/371/409/512/1024/4096.
Неполные группы проверены отдельно от кратных размеров.

Выбранные строки сравниваются с обычным одиночным MMVF и независимым FP64
dot product из F32-весов и активаций. Максимальная ошибка относительно FP64
на этих синтетических данных — **2,90493e-6** при заданном допуске 4e-5.
Все выбранные результаты трёх вариантов побитово совпали с одиночным MMVF.
Общий prefix 371/409 сравнивается целиком: штатно различаются **8374 из 8904**
значений, max Δ **1,19209e-5**; у всех трёх фиксированных вариантов — **0**.

Защитные проверки охватывают чужое имя и лишний суффикс, неподходящие K/M,
Q8_0 вместо F32, разреженные strides входа/весов и batch 4097. Результат
fallback должен побитово совпадать с выключенным режимом. Обнуление одного
токена рядом с ненулевыми не меняет соседние выходы ни в штатном, ни в новом пути.

Микрозамер одной `hc_attn_fn`, мкс/операцию: медиана трёх серий по 80 операций
после восьми прогревов. CUDA graphs и трассировка выключены, TF32 off.
Измеряется вызов графа с ожиданием завершения, не чистое время kernel.

| Batch | 1 столбец/sample | 4 столбца/sample | 8 столбцов/sample | Штатный контроль в серии 8 |
|---|---:|---:|---:|---:|
| 1 | 29,67 | 27,71 | 27,68 | 30,88 |
| 4 | 30,54 | 32,92 | 32,28 | 86,34 |
| 371 | 195,58 | 145,89 | 157,75 | 52,88 |
| 409 | 209,67 | 151,62 | 159,14 | 56,87 |
| 4096 | 1815,23 | 1011,68 | 854,88 | 227,89 |

Вариант 8 выбран для итогового модельного сравнения: он уменьшает стоимость
HC на полном prefill 4096 в 2,12 раза относительно варианта 1, сохраняя
проверенную арифметику. Но он всё ещё медленнее штатного cuBLAS для длинного
пакета. Эти числа не являются ускорением всей модели.

## Фиксированная история модели

Используются прежние 410 token IDs: prefix 409 сразу против prefix 371,
одиночных 371–403 и пакета 404–408; токен 409 отдельно в обоих путях.
Остальные исследовательские настройки одинаковы: MMQ=5, J64/4, FA=4,
HCA=1, router=1, MMVQ=2, TF32 off. Первый контроль с HC=0 на новой сборке
точно повторил logits предыдущего этапа.

У позиции 371 до изменения вход `hc_attn_fn` совпадал, но её выход различался
до **0,00006103515625**. С HC=1 на обеих исторических позициях 282 и 371
точно совпали входы/выходы `hc_attn_fn` и `hc_ffn_fn`, коэффициенты смешивания,
результат HC после attention, HC перед FFN и нормализованный вход FFN.
Q, K, attention, wo_a и wo_b сохраняют нулевое расхождение.

Далее при одинаковом входе FFN наблюдаются:

| Узел / max Δ | Позиция 282 | Позиция 371 |
|---|---:|---:|
| Router BF16 4096×256, F32 precision | 7,74860e-7 | 8,34465e-7 |
| Top-k IDs | 0 | 0 |
| Веса выбранных экспертов | 1,19209e-7 | 1,78814e-7 |
| Routed MoE | 5,96046e-8 | 0,044727396 |
| Shared expert | 2,38419e-7 | 0,001514137 |
| Выход слоя 0 | 5,96046e-8 | 0,022314670 |

У текущего токена 409 перечисленные узлы первого слоя совпадают. Это не
означает одинаковости исторических выходов слоя. Роутер теперь выделен при
одинаковом входе; routed MoE ещё получает разные веса маршрутов. У shared
expert остаются собственные матрицы и нелинейность, которые нужно проверить
по отдельности. Следующий этап — фиксированный порядок вычисления router
для длинного prefill и локализация gate/up/down shared expert.

| Режим | Max Δ конечных logits | RMS Δ | Argmax full / segmented |
|---|---:|---:|---|
| HC=0, предыдущий контроль | 2,995472074 | 0,571712750 | 112496 / 1 |
| HC=1 | 5,439953566 | 1,153730412 | 539 / 112496 |
| HC=3, группы по 8 | 5,439953566 | 1,153730412 | 539 / 112496 |

Повтор HC=3 дал полностью одинаковые JSON-трассы с HC=1 на обеих исторических
позициях и текущем токене. Во всех семи модельных probes нулевыми остались
контроли observer, snapshot/restore и replay. Чтение активаций синхронизирует
GPU, поэтому времена этих диагностических прогонов не являются замером скорости.

Улучшение локального совпадения **не уменьшило расхождение всей модели**.
Оценка качества ответов на корпусе этим сравнением не выполняется.

Сырые прогоны: `bench/results/ds4-hc-projection-20261011-*`.

## Проверки модели и сессий

Итоговая экспериментальная сборка прошла **28/28 CTest за 103,04 с**.
Включены все три режима HC, прежние тесты проекций и attention, передача
экспертов, GPU-only контракт и проверки состояния. Финальный тест плотных
проекций отдельно прошёл с обычной настройкой TF32.

Проверки модели без DSpark и с ним прошли за **59,07 / 75,98 с**.
Совпали greedy token IDs между этими режимами в восьми сценариях: две сессии,
восстановление, продолжение активной/восстановленной сессии, полный prefill
продолжения, один токен и генерация после отмены. Проверены отмена prefill,
отмена decode и повтор с фиксированным seed.
**29 проверок причинности DSpark дали max Δ logits = 0**.
Аудит: 1 запись без DSpark, 333 с ним; везде `cpu_compute_nodes=0`.

В обоих режимах **`full_prefill_identical=false`**: продолжение из 16 токенов
после полного prefill отличается от поэтапного, начиная с шестого токена.
Восстановление сессии воспроизводит её собственный результат точно.
Этот флаг отслеживается отдельно и не является assert в существующем
валидаторе: успешный выход скрипта не означает равенства всех способов prefill.
На предыдущем этапе в этом сценарии было `true`; локальное исправление HC
не сохранило это частное совпадение. Рабочий профиль этим экспериментом
не заменяется. Linux, другие GPU и качество ответов на корпусе не проверялись.

## Полная скорость и ресурсы

A/B/B/A использует один `grouped.exe`, HC=0 против HC=3, без DSpark.
Все прочие исследовательские параметры равны: MMQ=5, J64/4, FA=4, HCA=1,
router=1, TF32 off, MMVQ=2, контекст 8192, batch 4096, expert-кэш 15360 МиБ,
staging 16 МиБ. Это сравнение с предыдущим численным экспериментом, а не
с рабочим профилем. Decode — медиана двух прогретых повторов по 32 токена;
повторный полный prefill 4096 использует новую сессию и сохранённый кэш весов.
Файловый кэш ОС не очищался.

| Порядок | HC | Decode, ток/с | Повторный prefill 4096, мс | Чтение H: в прогретых фазах |
|---|---:|---:|---:|---:|
| A1 | 0 | 18,986 | 9474,67 | 0 |
| B1 | 3 | 18,767 | 9489,25 | 0 |
| B2 | 3 | 18,815 | 9498,15 | 0 |
| A2 | 0 | 18,873 | 9439,61 | 0 |

Медианы запусков: **18,929 → 18,791 ток/с (−0,73%)** и
**9457,14 → 9493,70 мс (+0,39%)**. Ускорение не подтверждено.
Все 32 выходных token IDs decode и три выходных token IDs prefill совпали
между режимами и повторами на этих запросах. Это отдельные последовательности
от численного probe и проверки продолжения сессии; их результаты не заменяют
проверку равенства всех logits.

Все восемь прогретых повторов decode и четыре повторных полных prefill
показали **0 байт физического чтения H:**. Счётчик `PhysicalDrive6` относится
ко всему устройству; первые запросы могли читать диск. Медианы CPU процесса
на активных фазах A1/B1/B2/A2 — **4,13 / 4,88 / 5,09 / 5,22%** мощности
всей системы, максимумы — **5,43 / 6,04 / 6,08 / 5,80%**. Общий CPU
достигал 9,7 / 9,3 / 9,1 / 8,3%. Выборочные пики общей VRAM по `nvidia-smi`:
**28697 / 28694 / 28688 / 28686 МиБ**; это память всей видеокарты.
В аудите графов модельных запусков вычислительных CPU-узлов нет.
Host-копирование и управление GPU по-прежнему выполняются на CPU.
