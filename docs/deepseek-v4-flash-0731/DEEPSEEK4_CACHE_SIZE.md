# Вытеснение матриц с учётом размера

5 октября 2026. Продолжение оптимизации
[частотного GPU-кэша DeepSeek](DEEPSEEK4_FREQUENCY_CACHE.md).

Следующий этап: [общий временный GPU-буфер с DSpark](DEEPSEEK4_SHARED_SCRATCH.md).

## Что изменено

В фиксированной арене VRAM матрицы разных размеров оставляют промежутки.
Чтобы добавить одну большую матрицу, строгий LRU может вытеснить несколько
полезных маленьких матриц, прежде чем образуется достаточно большой блок.

Добавлен параметр движка и `tools/setup_deepseek4.py`:

```text
--expert-cache-policy frequency --expert-cache-match-size 1
```

Когда свободного блока недостаточно, кэш ищет матрицу того же размера среди
64 самых давно использованных допустимых кандидатов. Если находит, освобождает
её место; иначе выбирает прежнего кандидата LRU. Защищённые текущим планом
матрицы пропускаются. Частотный допуск сравнивает новую матрицу именно
с выбранным кандидатом, поэтому горячая матрица может остаться в кэше.
В этом случае новые веса проходят через конвейер без сохранения в арене.

Общий default остаётся `0`. INFO сообщает `expert_cache_match_size`,
а About показывает настройку фиксированного кэша. Параметр относится к арене;
динамический кэш VRAM уже использовал поиск подходящего размера и не изменён.
Объём выделенной памяти не увеличивается. Маршрутизация, квантованные байты,
вычислительные ядра и backend Qwen не меняются.

В локальном рабочем профиле `strata-deepseek4-ud-q3-k-xl-dspark.json`
включено `--expert-cache-match-size 1`. Для возврата прежнего выбора достаточно
поставить `0`. При включении динамического управления VRAM вместо фиксированной
арены этот параметр не даёт дополнительного эффекта.

## Измерение

Windows, RTX 5090 32 ГиБ, Ryzen 9 9950X, RAM 128 ГиБ, CUDA 13.0.
DeepSeek V4 Flash 0731 UD-Q3_K_XL и DSpark Q8_0, `draft-max=2`.
Контекст 8192, batch 4096, один CPU-поток движка; фиксированный кэш основной
модели 15360 МиБ, draft 1024 МиБ, staging 16 МиБ, конвейер `auto`, два читателя.
Во всех проверенных графах `cpu_compute_nodes=0`.

Перед генерацией — отдельный prefill 256 токенов с коротким ответом.
Затем один запрос с temperature 0 и 128 выходными токенами, три повторения
с восстановлением prompt из RAM. Указана медиана этих трёх повторений.
Файловый кэш ОС не очищается. Это короткий прогретый decode, не измерение
ускорения длинного prefill.

| Запрос | Прежнее вытеснение, ток/с | С учётом размера, ток/с | Изменение |
|---|---:|---:|---:|
| Объяснение L1/L2/L3, 36 входных токенов | 19,95 | 20,81 | +4,3% |
| Python LRUCache и pytest-тесты, 81 входной токен | 16,56 | 17,09 | +3,3% |

Повторы L1/L2/L3: 15,89 / 19,95 / 20,40 и 16,43 / 20,81 / 21,48 ток/с.
Кэш продолжает обучаться, поэтому первый повтор медленнее последующих.
Все пять наборов выходных token IDs совпали. DSpark в каждой основной
генерации принял 78 из 98 предложенных токенов. В прогретых повторах физические
чтения диска H: — 0 байт. Счётчик относится ко всему устройству, включая
другие процессы; DSpark находится на другом диске.

Повторы генерации кода: 13,06 / 16,56 / 16,77 и 13,19 / 17,09 / 17,48 ток/с.
Все пять наборов token IDs также совпали; DSpark принял 79 из 95 токенов.
В контрольном первом decode были физические чтения H: (16,1 ГБ), поэтому
его скорость не сравнивается с первой генерацией нового режима. Во всех
трёх повторениях обоих режимов физические чтения H: — 0 байт.

Средняя CPU-нагрузка движка в прогретых генерациях кода — 4,03% и 3,99%
суммарной мощности 32 логических CPU. Это обслуживание памяти, очередей
и sampling; модельные операции на CPU не выполнялись. В сравнении L1/L2/L3
свободная VRAM была около 634–635 МиБ у контроля и 478 МиБ у нового режима.
Фоновая нагрузка не полностью изолирована; небольшой процент ускорения
нельзя переносить на любые запросы и состояние рабочего стола.

Счётчики основной модели за весь запуск, включая prefill и первую генерацию:

| Счётчик | Прежнее вытеснение | С учётом размера |
|---|---:|---:|
| H2D, байт | 459 542 685 696 | 438 500 913 664 |
| D2D, байт | 1 264 330 481 664 | 1 258 751 176 192 |
| Вытеснения | 8 571 | 6 636 |
| Попадания | 208 818 | 213 878 |

H2D уменьшился на 4,6%, вытеснения — на 22,6%. Это суммарный объём передачи,
не разложение времени CUDA по операциям. Размеры матриц draft одинаковы,
его счётчики в этом сравнении не изменились. Результат зависит от запроса,
истории частот, квантования и фактической доступности VRAM.

На генерации кода суммарный H2D основной модели также уменьшился на 4,6%:
583 602 724 864 → 556 880 331 264 байт; вытеснения — 10 321 → 8 617.

## Проверки

GPU-тест дополнен матрицами разных размеров. Проверяются одно вытеснение
вместо двух, сохранение остальных попаданий, защита матрицы текущего плана
и передача в обход кэша, когда фрагментация не позволяет выделить блок.
Копируемые байты сравниваются с исходными, включая padding границы эксперта.
Проверки выполняются с конвейером и без него; защита общего плана применяется
в конвейерном режиме. Существующие проверки частотного допуска, динамического
лимита VRAM, отмены плана и GPU-only также сохранены.

Прошли 7 CTest, 25 Python-тестов (`tools.test_deepseek4`, `serve.test_deepseek`,
`serve.test_vram_settings`), проверка синтаксиса Python и JavaScript.

Итоговая сборка прошла проверку реальной модели с DSpark: A/B/A, продолжение
и восстановление сессии, одиночный токен, отмена prefill/decode, восстановление
после отмены, sampling с seed 123. Результат
`bench/results/cache-size-validation.json`: `passed=true`.
Во всех сравнениях и в этой проверке `pipeline_fallbacks=0`.
Сохраняется ранее известное отличие полного prefill от инкрементального
продолжения (`full_prefill_identical=false`), описанное в
[DEEPSEEK4_DSPARK.md](DEEPSEEK4_DSPARK.md); восстановленные сессии совпадают.

Локальные результаты: `bench/results/cache-size-control.json`,
`bench/results/cache-size-match.json`, `bench/results/cache-size-code-control.json`,
`bench/results/cache-size-code-match.json` и соседние `.log`.

В первой паре параметр передавался через `STRATA_EXPERT_CACHE_MATCH_SIZE`,
до добавления CLI. Пара генерации кода проверена уже с окончательным CLI;
INFO подтверждает `expert_cache_match_size=0/1`. Алгоритм между парами не менялся.
SHA-256 итоговой сборки:
`5307110863b3bc97c1eb865987c5cc6ceac8870f3d88a96417b62bee59a5f68c`.

## Отброшенный эксперимент с барьером

В этой же работе проверено удаление ожидания CPU перед копированием выбранных
экспертов, с сохранением порядка операций в CUDA stream. На том же запросе
одна сборка дала 19,76 ток/с с барьером и 17,36 ток/с без него. Выходные токены
совпали, но фоновые CPU-нагрузка и VRAM различались. Доказанного выигрыша нет.
Экспериментальный патч удалён из рабочих исходников; прежняя синхронизация
сохранена. Сборка и патч оставлены в `build-local/deepseek4/ordered-experiment`,
измерения — `bench/results/ordered-copy-after.json` и
`bench/results/ordered-copy-same-binary-barrier.json`.
