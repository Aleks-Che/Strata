# Прямой H2D из общего RAM-кэша

12 октября 2026. Продолжение [CPU lane: эксперименты](DEEPSEEK4_CPU_LANE_EXPERIMENTS.md).

## Реализация

Два независимых экспериментальных переключателя, оба выключены по умолчанию:

- `STRATA_DS4_RAM_DIRECT_H2D=1`: готовая pinned-матрица передаётся в GPU-кольцо прямо из HostCache. Lease удерживает исходный адрес до завершения DMA. Промах использует обычный путь чтения и staging. RAM-кэш выделяется через CUDA pinned allocator, в том числе при CPU threads=0.
- `STRATA_DS4_RAM_DROP_GPU=1`: после полной передачи матрицы и включения в GPU-кэш удаляются её готовые RAM-копии. Удерживаемые CPU/DMA блоки перестают выдаваться новым читателям, остаются в RAM-бюджете и освобождаются после последнего lease.

Оба режима требуют `STRATA_DS4_RAM_CACHE_MIB>0` и expert pipeline. Для совместного CPU lane используется `STRATA_DS4_CPU_SHARED_RAM=1`; частичное наличие gate/up/down сохраняет GPU fallback. Qwen использует прежний путь по умолчанию.

Drop — удаление готовых дубликатов в момент promotion. Это не реестр всех GPU-резидентов и не демоция VRAM→RAM: последующий независимый RAM-запрос может снова заполнить блок. Pipeline-чтения передаваемой матрицы должны быть завершены перед discard. Padding и части больших матриц учитываются по полным покрытым блокам и идентичности файла.

При ошибке после постановки H2D в очередь владелец исходного адреса остаётся в слоте до дренирования CUDA stream. Отмена незавершённого плана дренирует загруженный остаток. Prefill-hit не обучает частотную политику decode.

## Счётчики

`STRATA_RAM_H2D` сообщает число прямых H2D chunks и их байты отдельно для каждого backend. Эти байты исключены из file/mmap read counters и из stage_bytes финальной сборки; общий h2d_bytes сохраняет все передачи GPU. Попадания HostCache теперь видны в lease_hits/lease_bytes вместо обычных hits/hit_bytes.

В `STRATA_RAM_CACHE` добавлены retired_bytes (ещё занятые дубликаты), gpu_drop_bytes и gpu_drop_entries (уже освобождённые). bytes включает retired до фактического освобождения. Target и DSpark печатают статистику одного общего HostCache: складывать эти строки нельзя.

## Проверки

26/26 выбранных CTest прошли за 67,08 с. HostCache: 228 assertions, включая 1200 конкурентных чтений. Добавлены проверки удержания DMA-адреса, отмены, смены плана, wrap-around кольца, давления памяти, padding, другой идентичности файла и исключения после постановки H2D в очередь. Ошибка не освобождает занятую pinned-память.

## Методика измерений

Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, SSD H: Samsung 990 PRO. DeepSeek-V4-Flash-0731 UD-Q3_K_XL, DSpark Q8_0. Context 8192, batch 4096, target GPU-cache 15360 МиБ, draft 1024 МиБ, общий pinned RAM-cache 2048 МиБ, stage 16 МиБ, два reader, auto I/O, frequency policy. Файловый кэш ОС не сбрасывался.

Фиксированная история: target-only, 68 одинаковых IDs, prefix 36 и decode оставшихся 32 по одному или по три токена. Четыре прохода с очисткой KV и сохранением expert caches. Сравнение времени — среднее двух последних проходов. Физическое чтение PhysicalDrive6 за все проходы включает холодную подготовку и активность всего диска. Проверяются hashes полных logits каждого шага и префикса; это не доказательство serial/batch эквивалентности.

Артефакты и профили: `build-local/deepseek4/ram-direct-20261012`. Каталог игнорируется Git; experimental.exe и executables.json фиксируют использованную сборку. Финальная сборка дополнительно уточняет только счётчик stage_bytes и teardown тестового Gate.

Для GPU, staging, direct и direct+drop совпали hashes всех logits префикса и шагов в каждой из 12 фаз. У CPU-вариантов совпал только полный prefill (4 фазы), где CPU lane выключен. Внутренние маршруты гибридного decode могут отличаться даже при фиксированных входных IDs.

Прямой H2D пропустил 4000 копирований в staging, 14562958336 байт (около 3,9% H2D-трафика за весь тест). Число GPU hits/misses и полный H2D-трафик совпали с контролем. Среднее время относительно staging уменьшилось на 2,35% / 1,71%, но разброс двух поздних проходов сопоставим или больше. Устойчивого выигрыша относительно обычного GPU-only нет.

Drop увеличил прямые попадания до 5726 (20930797568 байт), но заполнение RAM выросло с 6614885376 до 26439826432 байт. Освобождено 16024827904 байт в 4416 promotion-событиях; к финалу retired_bytes=0, pending=0, OOM=0. Время decode выросло: дополнительная полезная ёмкость не окупила заполнение и освобождение блоков. Частную стоимость CUDA allocation/free эта серия не разделяет.

CPU force 12 выполнил 1151 expert/token rows без drop и 625 с drop, pack=0 в обоих случаях. Удаление копий ухудшило доступность готовых троек gate/up/down для CPU. Ни один гибридный вариант не ускорил этот workload относительно GPU-only. Проблема seeded repeat динамического CPU lane из предыдущей серии этим опытом не устранена.

## Длинный холодный prefill: ограничение серии

Контроль без RAM-кэша и без новых переключателей не завершил prefill 4096 за лимит 300 с. Перед остановкой: elapsed 300,375 с, CPU process time 13,125 с, PhysicalDrive6 read 33131429888 байт / 24857 операций. Из этих данных нельзя вывести скорость prefill или сравнить его с direct H2D: GPU timings отсутствуют. Одиночный дополнительный замер показал около 218 МБ физического чтения за 2 с при почти простаивающем GPU. Это наблюдение об ожидании данных, не изолированная диагностика причины низкой скорости SSD.

Ошибка stdin.close после принудительной остановки потеряла исходный JSON бенчмарка. Числа выше восстановлены из строки телеметрии bench-gpu.log; sample-массив не сохранён. Артефакт long-prefill-timeout.json явно отмечает это ограничение. В tools/benchmark_deepseek4.py добавлено сохранение результатов при OSError очистки, без подавления исходной ошибки запроса.

Следующая проверка DSpark использует отдельный короткий prefill 64 токена и тот же запрос 36→64 с четырьмя повторами. Она не заменяет проверку длинного контекста. Первый холодный короткий prefill контроля занял 49,562 с и прочитал 14,297 ГБ; начальная генерация прочитала ещё 16,814 ГБ. Cached repeats контроля не читали SSD.

## Решение по настройкам

Рабочий профиль остаётся GPU-only без дополнительного RAM-кэша. Direct H2D и drop сохранены как выключенные экспериментальные механизмы. Следующий опыт должен согласовать RAM admission с предстоящим размещением в VRAM: не создавать RAM-копию, которая сразу удалится после promotion, учитывать стоимость pinned allocation/free и доступность полной тройки для CPU. Переиспользование ограниченного пула свободных pinned-блоков — отдельная проверяемая гипотеза; в этой серии такой пул не реализован.
