# О3: выбор слотов по фактическим промахам

14 октября 2026. Продолжение [оптимизации окна кандидатов](DEEPSEEK4_TRANSFER_O3.md).

Позднейшее продолжение: [ранжирование target по частоте и цене вытеснения](DEEPSEEK4_TRANSFER_O3_TARGET.md)
снизило общий H2D ещё на 31,22% и ускорило decode на 20,44% в одной A/B/B/A.
Ниже сохранены замеры предыдущего, неранжированного demand-пути.

Выбор по фактическим промахам помог небольшому кэшу DSpark: в одной A/B/B/A
полной связки **decode +4,76%, полное время −2,98%, H2D −8,04%** относительно
предыдущей экспериментальной очереди. Включение для target ухудшило удержание
матриц. Рабочий GPU-only остаётся быстрее; О3 не закрыт.

## Реализация

`STRATA_DS4_GPU_FETCH_DEMAND_CACHE=1` включает экспериментальный выбор после
публикации GPU-маршрута. По умолчанию выключен, требует owner DMA. Старый
mapped transport продолжает использовать прежний выбор кандидатов.

Вместо предварительного извлечения восьми записей на матрицу GPU сначала
публикует реальные промахи с адресами scratch. Владелец DMA на уже существующем
барьере маршрута ищет для каждого промаха слот точного размера, учитывая padding,
частоту и защиту читателей. Просматривается до 64 позиций LRU на промах; количество
выданных слотов ограничено `GPU_FETCH_CACHE_SLOTS`, максимум восемь на матрицу.
При отсутствии подходящего слота сохраняется scratch. Новые свободные слоты
резервируются только под реальный запрос и в пределах прежнего бюджета VRAM.

Сервис получает отдельное разрешение с номером запроса после окончательной
записи адресов. Разрешение старого поколения не подходит новому. При early sources
владелец готовит все три уже опубликованные матрицы вместе: чтение следующих
матриц может перекрываться с вычислениями. Pointer table привязывается после DMA.
Дополнительного GPU→host барьера нет, но первая загрузка теперь ждёт решения
владельца на существующем барьере; стоимость этого ожидания входит в замеры.

Полный набор выбранных экспертов, включая CPU-only и смешанные назначения,
защищён от замещения. Сохраняются direct leases, другие контексты, отложенные
читатели и порядок D2H перед перезаписью. Отменённые запросы завершаются и без
разрешения, затем источники и записи кэша освобождаются по прежнему протоколу.

`STRATA_DS4_GPU_FETCH_DEMAND_MAX_CACHE_MIB` позволяет ограничить новый режим
контекстами с небольшим настроенным бюджетом кэша. Ноль или отсутствие значения
не ограничивает бюджет. Значение 1024 в этой конфигурации включает его только
для DSpark (1024 МиБ), оставляя target (15360 МиБ) на прежней политике. Это
явная экспериментальная настройка, а не автоматическое распознавание модели.

Телеметрия фаз: `demand_plans`, `demand_misses`, `demand_scanned`,
`fetch_offered`, `fetch_restored`, `fetch_prepare_us`. Последнее поле — суммарное
время подготовки кэша на владельце, не время GPU или чистое ожидание DMA.

Код: [выбор слотов](../../backends/deepseek4/gpu_fetch_cache.inc),
[протокол очереди](../../backends/deepseek4/gpu_fetch_queue.cuh),
[конфигурация и сервис](../../backends/deepseek4/gpu_fetch_lane.cuh),
[привязка pointer table](../../backends/deepseek4/cpu_lane_hooks.inc).

## Условия и первые пробы

Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows, CUDA 13, PCIe Gen3 x16.
Target UD-Q3_K_XL, DSpark Q8_0, контекст 8192, draft-max 2. Кэши target/draft
15360/1024 МиБ, RAM-кэш 2048 МиБ, staging 4 МиБ, depth 8, четыре сегмента,
reader `mapped`, early sources. `KEEP_RAM=0`, `RAM_DEMOTE=0`, context overlap
выключен. База — tail limit 1, cache slots 8, current victims 0.

Четыре fresh-запроса по 15 входных / 32 выходных токена, два первых — прогрев.
H2D, wall и CPU-seconds относятся к сумме двух последних запросов; decode —
64 выходных токена / суммарное decode-время. Кэш ОС не очищался. CPU-профиль
пересоздаётся для сборки, 12 потоков, бюджет 0,01 мкс; в скоростных пробах
фактические CPU jobs/rows равны нулю. Физические чтения H: в поздних запросах — 0.

## Проверки корректности

На финальной сборке прошли 17 запусков CTest, 14 разных тестов: разрешение
владельца и смена поколения, отмена до разрешения, ранняя публикация трёх
матриц, DMA window, графы on/off, context overlap, демоция, arena/managed,
IQ3_XXS/MXFP4/Q8_0, явное освобождение кэша. Отдельно проверены fallback без
DMA и исключение кэша по лимиту бюджета. Более ранняя сборка дополнительно
прошла 24 проверки, включая прежние current-victims и ring-cache сценарии.

Fixed-history сравнение с совместимым GPU-only: **6 префиксов, 86 шагов**,
совпали hash полного вектора logits и argmax. Здесь demand включён для обоих
кэшей, `KEEP_RAM=1`, демоция 16 МиБ, context overlap 1; фактически выполнено
**2554 CPU jobs / 3392 rows**, prefill CPU rows = 0. Таким образом проверялся
и настоящий CPU-путь, а не только нулевая очередь скоростного теста.

Lifecycle с demand для обоих кэшей и current victims 1 прошёл A→B→A,
restore/extension/full-prefill, отмену prefill/decode и seeded repeat.
**726 CPU jobs / 1344 rows**, runtime profile generation **0→1**.
В восьми greedy-сравнениях совпали входные и выходные IDs с сохранённым
совместимым GPU-only контролем. Отдельный прежний вопрос lossless batch/serial
DSpark этим опытом не закрывается.

В каталоге артефактов сохранены EXE, профиль, конфигурации, запросы, JSON
замеров, trace и логи проверок, `source/`, `demand-only.diff` относительно
tail-эксперимента и SHA256 manifest. Прежние каталоги опытов не изменялись.

## Контроли и оставшаяся работа

Одиночные L0 и G на финальной сборке, тот же manifest и два прогрева:

| Режим | Decode, ток/с | Wall, с | CPU-seconds | H2D decode, ГиБ |
|---|---:|---:|---:|---:|
| L0: старый транспорт, CPU-инфраструктура, jobs=0 | 12,325 | 7,922 | 12,172 | 31,680345 |
| G: совместимый GPU-only | 14,231 | 7,266 | 9,594 | 31,680345 |

Новая комбинация всё ещё имеет **17,87% лишнего H2D** относительно L0 вместо
прежних 28,18%. Из оставшихся 5,660 ГиБ 4,983 ГиБ (88,05%) приходятся на target,
0,677 ГиБ — на DSpark. Политика target сохраняет предварительные предложения;
эксперимент с полным demand показал необходимость более строгого допуска и
удержания полезных матриц. Возвраты слотов на target пока не устранены.

Критерий О3 ≤5% лишнего H2D не выполнен. Следующий шаг — сравнить для target
ранжирование реальных промахов по частоте с ценой вытеснения, отдельно считая
повторные загрузки вытесненных матриц. Защита RAM по фактическому CPU-назначению
остаётся отдельным пунктом. Рабочий профиль не переключён: GPU-only быстрее.
Длинные 4096/8152-токенные сценарии, Linux и Qwen в этой серии не проверялись.
