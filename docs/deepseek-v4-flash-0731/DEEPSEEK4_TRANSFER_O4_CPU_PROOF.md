# О4: проверка CPU-бюджета и завершение пустых веток

14 октября 2026. Продолжение [переноса О3 в обычный GPU-путь](DEEPSEEK4_TRANSFER_O4_ORDINARY_CACHE.md).

Добавлены две независимые опции. Служебная работа уменьшилась, но устойчивого
прироста генерации во всех повторах нет. В трёх симметричных сериях N0 среднее
decode выросло **15,590 → 15,871 ток/с (+1,80%)**, wall снизился на **1,70%**,
CPU-seconds — на **2,08%**. Один повтор дал −0,59% decode. Обе опции по умолчанию
выключены; рабочий профиль сервера не переключён. Общий О4 остаётся открыт.

## Изменения

`STRATA_DS4_CPU_BUDGET_PROOF_CACHE=1` сохраняет результат консервативной проверки
для каждого из четырёх размеров короткого окна. Раньше перед каждой веткой
копировался профиль и просматривалась таблица стоимости. Теперь профиль
считывается по ссылке, а решение берётся из четырёх битов. Это проверка
возможности назначения, а не замена самого CPU/GPU-планировщика.

Для динамического профиля маска пересчитывается при успешной публикации
нового поколения под тем же mutex. Ошибка сохранения оставляет старые профиль
и маску. Проверка следующей ветки не перепривязывает наблюдатель ещё работающей
предыдущей ветки. Неизвестные, отключённые и некорректные профили сохраняют
консервативный путь; проверка не запрещает потенциально допустимое назначение.

`STRATA_DS4_CPU_EMPTY_CLEANUP_FAST=1` пропускает повторное обнуление пустой
CPU-ветки: в частности, два массива по 256×3 RAM leases. Ожидание отложенного
GPU-consumer выполняется до раннего возврата. При подготовленной, работающей
или ошибочной ветке остаётся полное завершение. Повторная попытка планирования
по host IDs не запускает лишний `finish_plan`, если текущий CPU-контекст пуст;
обычный GPU-план всё равно завершает все контексты перед использованием scratch
и кэша. Настройка также действует при полностью отключённом CPU lane.

Добавлены фазовые счётчики `cpu_budget_proof_checks`, `cpu_budget_proof_us`,
`cpu_empty_cleanup_skips`. Изменены только файлы отдельного backend DeepSeek:
`cpu_cost_model.hpp`, `cpu_cost_refresh.hpp/.cpp`, `cpu_expert_lane.cuh`,
`cpu_lane_hooks.inc`, `cuda_expert_transfer.inc`, `expert_transfer.h` и тесты.
Арифметика CPU/GPU, отбор матриц О3 и алгоритм DSpark не менялись.

## Условия

Ryzen 9 9950X, RAM 128 ГиБ, RTX 5090 32 ГиБ, Windows, PCIe Gen3 x16.
Target: DeepSeek-V4-Flash-0731 UD-Q3_K_XL с H:; DSpark Q8_0.
Контекст 8192, GPU-кэш target/draft 15360/1024 МиБ, draft-max=2.
Обычный отбор О3 включён в обеих сторонах сравнения.

N0: 12 потоков CPU, partitions=2, spin=0, RAM-кэш 2048 МиБ,
CPU budget=0,01 мкс, автоматическое обновление профиля выключено.
Нулевое назначение подтверждается jobs/rows, а не только настройкой бюджета.
Для новой сборки выполнена новая аппаратная калибровка.

В каждом коротком процессе четыре fresh-запроса по 15 входных / 32 выходных
токена. Первые два — прогрев. Скорость процесса: 64 токена / сумма времени
decode двух последних запросов; затем среднее по процессам. Wall и CPU-seconds
также суммируются по последним двум. Кэш ОС не очищался. Физическое чтение
считается по всему диску, включая другие процессы.

## Короткие замеры

Первый порядок: base / proof / cleanup / both / both / cleanup / proof / base.
Следом две отдельные A/B/B/A для base/both. В среднем по первой серии:

| Режим | Decode, ток/с |
|---|---:|
| Исходный N0 с обычным О3 | 15,816 |
| Только кэш проверки | 15,952 |
| Только пустая очистка | 15,823 |
| Оба изменения | 16,123 |

| Серия base/both | Исходный, ток/с | Оба изменения, ток/с | Изменение |
|---|---:|---:|---:|
| Первая, с промежуточными абляциями | 15,816 | 16,123 | +1,94% |
| Вторая | 14,892 | 15,524 | +4,24% |
| Третья | 16,061 | 15,965 | −0,59% |
| Среднее шести процессов на вариант | **15,590** | **15,871** | **+1,80%** |

Wall: **6,591 → 6,479 с**; CPU-seconds: **9,003 → 8,815**.
H2D decode: **24,447813 ГиБ в обоих вариантах**. На 64 выходных токена
1622 проверки бюджета занимали в среднем **2,540 → 0,366 мс (−85,60%)**.
3468 пустых очисток пропущено. Это малая доля полного decode; снижение
этого счётчика само по себе не объясняет весь разброс скорости.

Всего выполнено 28 коротких процессов, включая дополнительные контроли ниже.
Во всех совпали входные/выходные IDs и acceptance DSpark. В двух поздних
запросах каждого процесса чтение модели с H: равно нулю.

## GPU-only, смешанный режим и диагностические контроли

Одна GPU-only A/B/B/A с отключёнными CPU lane и экспертным RAM-кэшем:
исходный **16,809**, с быстрой очисткой **17,344 ток/с (+3,18%)**;
wall 6,367 → 6,1715 с. Однако два исходных процесса дали 17,241 и 16,376 ток/с,
а CPU-seconds выросли на 0,55%. Это недостаточное подтверждение отдельного
устойчивого GPU-only выигрыша; настройка не включена по умолчанию.

Смешанный auto, budget=1000 мкс, KEEP_RAM=2, demote=16 МиБ, замороженный профиль:

| Показатель | Исходный | Оба изменения |
|---|---:|---:|
| Decode, ток/с | 15,835 | 15,780 |
| Wall, с | 6,5235 | 6,5000 |
| CPU-seconds | 12,070 | 11,797 |
| CPU jobs / rows | 50 / 68 | 50 / 68 |
| H2D decode, ГиБ | 24,485 | 24,485 |

Decode −0,35%, wall −0,36%, CPU-seconds −2,27%: прирост скорости не подтверждён.
Раскладка CPU/GPU и работа модели одинаковы.

Дополнительно сравнивались включённые CPU-проверки без RAM-кэша и RAM-кэш
без CPU lane. Получено соответственно 16,048 и 15,993 ток/с. Это сравнение
двух разных наборов настроек, не полная факторная серия с одновременными
GPU-only/N0 контролями. Оно не доказывает, что единственная причина потерь — RAM
или CPU hooks. В этих режимах ранняя проверка бюджета не выполняется.

Две начальные диагностические конфигурации без RAM были отклонены при запуске:
сначала оставались RAM transfer tuning, затем CPU shared RAM. Они сохранены
в архиве, в 28 успешных процессов и результаты скорости не входят.

## Длинный контекст

Одна A/B/B/A N0, в каждом процессе fresh и restore для 4096 и 8152 входных,
по 32 выходных токена. Среднее двух процессов на вариант:

| Сценарий | Prefill, с, до → после | Decode, с, до → после | Wall, с, до → после | Чтение H:, ГиБ, до → после |
|---|---:|---:|---:|---:|
| 4096 fresh | 14,351 → 14,278 | 16,977 → 15,506 | 31,336 → 29,790 | 26,092 → 27,692 |
| 4096 restore | 0,0414 → 0,0404 | 2,396 → 2,305 | 2,4295 → 2,3510 | 0 → 0 |
| 8152 fresh | 32,624 → 31,340 | 5,935 → 5,472 | 38,5625 → 36,8050 | 111,038 → 104,938 |
| 8152 restore | 0,0642 → 0,0631 | 1,923 → 1,896 | 1,984 → 1,961 | 0 → 0 |

IDs и acceptance одинаковы во всех 16 запросах. H2D совпал побайтно
для каждого сценария отдельно в prefill и decode; CPU jobs/rows = 0 в обеих
фазах. Wall restore снизился на 3,23% и 1,16%, но это одна серия.

Fresh нельзя считать доказательством ускорения транспорта: состояние файлового
кэша различалось. Например, первая пара 8152 fresh дала 36,922 и 36,938 с,
а последний исходный запуск — 40,203 с при большем чтении H:.
Устойчивое ускорение полного prefill не установлено. Эти измерения не заменяют
открытую длинную приёмку GPU-only с О3 относительно старого рабочего профиля.

## Корректность и воспроизводимость

- Финальная сборка: 44 CTest прошли. Проверены CPU↔GPU, CUDA Graph on/off,
  перекрытие контекстов, кэш, DMA и отмена; тесты доказательства бюджета
  включают границы, NaN, неизвестные формы и невалидный профиль.
- Проверка обновления маски: публикация нового поколения, запрет изменения
  внутри запроса, ошибка записи и последующий возврат к CPU. GPU-тесты
  проверяют поколения 0/1/2 с переходом CPU/GPU/CPU.
- Полные logits на фиксированной истории: 6 префиксов, 86 шагов; хэши и argmax
  совпали с GPU-контролем для auto, fallback и принудительного CPU.
  В обычном fixed auto CPU jobs=0; отдельный force выполнил 86 jobs / 96 rows.
  Force — только численная проверка, не замер полезности CPU.
- Lifecycle: сессии, restore, продолжение, отмена и seeded repeat прошли;
  25 CPU jobs / 33 rows. Восемь greedy-сценариев совпали с GPU-эталоном.
- Восемь запросов с намеренно заниженной стоимостью CPU проверили живые
  поколения 0/1/2/3: 208 jobs / 285 rows, одинаковые IDs и acceptance.
  Этот искусственный профиль не участвовал в замерах скорости.
- При полном fallback mapped CPU queue так и не выделялась. Архивы четырёх
  предыдущих опытов О4 проверены по SHA-256 и не изменены.

`final-audit.json`, `validation-summary.json`, `short-audit.json`,

Следующий шаг О4 — измерять общую подготовку ветки, поиск веток в планировщике,
CPU hooks и операции RAM/residency отдельными интервалами на одинаковом GPU-пути.

и полная приёмка GPU-only с О3 остаются отдельными задачами.
