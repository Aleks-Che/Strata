# Подготовка следующей ветки после ответа CPU-service

Дата: 13 октября 2026. Продолжение этапа 2 CPU lane.

`STRATA_DS4_CPU_CONTEXT_OVERLAP=1` разрешает переиспользовать host-контекст
после ответа CPU-service, до завершения GPU-потребителя. По умолчанию выключено.
Это следующий шаг после [раннего снимка RAM](DEEPSEEK4_CPU_SNAPSHOT_OVERLAP.md):
перекрывается подготовка рабочей таблицы, CPU-параметров и источников GPU-fetch,
а не только отдельного CPU-снимка. Без GPU admissions до fence готовятся также
RAM reservations. При admissions выбор жертв и reservations идут после fence,
чтобы сохранить прежнюю политику размещения.

## Порядок и защита данных

1. Полная предыдущая ветка должна иметь записанный final event, а GPU-fetch —
   ранний copy fence. Последний подтверждает окончание публикации маршрутов.
2. I/O-service завершается по copy fence. Владелец получает все CPU replies;
   после release/acquire CPU-service больше не обращается к старым work/trace/leases.
3. Host-контекст освобождается и готовится для следующей ветки. Ответ CPU
   остаётся в mapped-слоте; reply не заменяет подтверждение его чтения GPU.
4. VRAM-ключи предыдущей ветки удерживаются отдельным набором. Если включены
   GPU admissions, перед выбором жертв владелец ждёт старый final event,
   проверяет consumed и GPU error, затем снимает удержание. Выбор жертв должен
   видеть тот же набор ключей, что и обычный путь; одной защиты от перезаписи мало.
5. Без admissions перед публикацией новой задачи владелец ждёт старый final event, проверяет
   consumed и GPU error. Только затем разрешены новая таблица, маршрут и
   переиспользование device packet/output. Старый набор защиты освобождается.

Следующая публикация всё ещё имеет host fence (с admissions — более ранний).
Здесь снимается ожидание
**перед подготовкой контекста**, но полностью асинхронного перехода между
ветками пока нет. Новые весовые буферы и VRAM не выделяются; добавлены несколько
полей состояния и host-набор защищённых ключей.

Неполная ветка, отмена без down, отсутствие copy fence и включённая GPU→RAM
демоция сохраняют прежний полный fence. Холодный слой без готовой RAM-тройки
также завершает отложенного потребителя перед fallback. Уничтожение контекста
и явное освобождение кэша обязаны завершить его потребителя.

Режим совместим с отдельным ранним снимком, но для оценки нового изменения
их следует проверять отдельно. `STRATA_CPU_CONTEXT_OVERLAP` сообщает число
отложенных ожиданий, число ещё незавершённых GPU-хвостов после CPU reply и
время финального ожидания перед публикацией. Это не оценка ускорения.

## Проверки первого варианта

Исходники до изменения, сборка, конфигурации и сырые результаты находятся в
`build-local/deepseek4/cpu-context-overlap-20261013/`.

Сборка CUDA 13 / MSVC, RTX 5090. Полная серия CTest: **64/64**, 272,44 с.
Ещё **25/25** конфигураций с компактными буферами, slabs 1 МиБ, одним copy block,
RAM_DROP_GPU и KEEP_RAM: 99,10 с. Отдельно прошли вариант без нового fetch RAM
fill и capture цепочки. Итого **91 native-проверка конфигураций**; начальный
smoke повторно не учитывается.

Новые цепочки сравнивают две зависимые MoE-ветки с разными весами, 12 входами,
тремя форматами и окнами 1/3/8 — 108 точных полных выходов на конфигурацию.
Проверены ранний режим, полный fence, демоция и сочетание с ранним снимком,
каждый с graphs и без них. Проверяются также счётчики фактического перехода
на новый путь, а не только равенство выходов при возможном fallback.

Протокольный тест дополнен 80 детерминированными случаями: GPU-потребитель
вообще не публикуется до смены host-контекста. После CPU reply проверка
отсутствующего consumed обязана отклонить переиспользование; после join GPU
получает исходный ответ. Существующие 1500 graph replay, полное кольцо,
ошибка CPU, отмена и timeout также прошли.

Восемь сохранённых заданий обеих веток воспроизведены по пять раз на 12 и
16 потоках — **80 побитно точных сравнений**. Диагностический capture удерживает
веса до записи, даже при включённом раннем освобождении CPU-матриц.

## Обнаруженное изменение политики admissions

Первый вариант проверял final event только перед публикацией. Пока следующий
план строился, предыдущие VRAM-ключи исключались из списка жертв. Это сохраняло
время жизни матриц, но меняло политику кэша, а вслед за ней — размещение CPU/GPU.

Дополнительная fixed-history пара с четырьмя предлагаемыми GPU-слотами выявила
**5/12** одинаковых signatures. Выключено/включено: 5051/5200 fetch-веток,
945/900 CPU jobs, 7545/8035 GPU admissions. Входные token IDs одинаковы, так что
различие здесь нельзя объяснить уже разошедшимися сгенерированными ответами.
Прогоны сохранены как `cache4-off` / `cache4-overlap`; они не являются успешной
численной приёмкой и их времена не используются как доказательство ускорения.

В DSpark с четырьмя слотами все восемь greedy input/output сценариев совпали,
но обе seeded-последовательности различались между режимами. Строгий restore
падал в контроле с индекса 6, с первой реализацией — с индекса 5, по 24 токена.
При отключённых новых GPU admissions оба режима снова дали одинаковые seeded
последовательности между собой, хотя restore в обоих падал с индекса 3.
Эти четыре validator запуска сохранили exit 1. Таймаутов очереди не было.

Исправление: при admissions завершать старого GPU-потребителя **до выбора
жертв**, уже после подготовки CPU-контекста. Без admissions остаётся поздний
fence перед публикацией. Первые исходники и binary сохранены в `source-candidate/`
и `candidate.exe`; окончательная сборка и результаты имеют префикс `guard`.

## Приёмка исправления

Итоговая сборка:
`674fafa9ba8b6d3052608614e7bb2c3d7e1d09f4a5a0b76496acb63fd2ffc2c3`.

На итоговом коде повторена полная native-регрессия: **66/66**, 282,08 с.
Добавлены варианты цепочки с четырьмя слотами admissions при graphs on/off.
После сборки менялись только поясняющие комментарии и документация;
все итоговые модельные прогоны используют один указанный executable.

Повтор fixed-history с четырьмя слотами дал **12/12** одинаковых signatures.
Теперь в обоих режимах 5051 fetch-ветка, 945 CPU jobs / 1092 rows,
60 241 предложенный слот, 7545 admissions / 52 696 возвратов. Новый путь
задействован 4903 раза, во всех случаях хвост GPU ещё был незавершённым.
Контроль / включено: 49,328 / 48,985 с, SSD 0 / 13 564 928 байт.
Это численная проверка исправления, не отдельное подтверждение ускорения.

Финальная пара DSpark использует CPU12, target/draft GPU-кэши 15/1 ГиБ,
общий RAM-кэш 2 ГиБ, общую scratch-память, draft до двух токенов и четыре
предлагаемых GPU-слота. Включены KEEP_RAM, PRUNE, RELEASE_RAM, EARLY_RETIRE,
ASYNC_PARK, CPU_RELEASE_WEIGHTS; отдельный SNAPSHOT_OVERLAP выключен.

Greedy A→B→A, продолжение и повторное восстановление, полный prefill,
одиночный токен без draft, отмена prefill/decode и ответ после отмены прошли.
Все восемь greedy input/output последовательностей совпали между режимами.
Обе seeded-последовательности также совпали с соответствующими контрольными.
Размещение одинаковое: target 1374 fetch-ветки, 299 CPU jobs / 484 rows,
1851 GPU admission; draft — 10 веток, 1 job / 2 rows, 45 admissions.
Ранних подготовок контекста 1324 / 10, каждый раз GPU ещё работал.
Итоговые RAM `oom`, `pending`, `retired_bytes` равны нулю в обоих режимах;
счётчики заполнений, вытеснений и попаданий совпали.

При этом оба validator вернули **exit 1** на строгом seeded restore: первое
различие с индекса 6 (седьмой токен), по 24 токена. Это прежнее незакрытое
ограничение; ошибку не отключали и не превращали в успешный результат.
Таймаут очереди в этой серии не повторился. Сопоставимого холодного/нагруженного
I/O A/B не проводилось; прежний DSpark timeout из отчёта раннего снимка не закрыт.

Итоговая прогретая A/B/B/A на target повторена на той же сборке:
`guard-off-b`, `guard-overlap-c`, `guard-overlap-d`, `guard-off-c`.
Параметры и правила усреднения те же, что в первой серии без новых GPU admissions.
Во всех четырёх чтений SSD — 0 байт; все **12/12 signatures** совпадают.
Одинаковы 3425 fetch-веток, 1139 CPU jobs / 1430 rows и 698 RAM fills.

и провести приёмку холодного I/O. Рабочий профиль остаётся прежним;
новый флаг выключен по умолчанию, Qwen не менялся.

## Продолжение

Дополнительная опция [CONSUMER_HANDOFF](DEEPSEEK4_CPU_CONSUMER_HANDOFF.md)
снимает отдельное ожидание final event перед следующей GPU-fetch публикацией:
статус старого GPU-потребителя сохраняется в stream и проверяется на следующем
copy fence. Без этой опции описанный выше протокол остаётся прежним.
