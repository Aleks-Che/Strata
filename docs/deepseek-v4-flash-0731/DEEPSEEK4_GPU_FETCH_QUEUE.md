# GPU-запросы подкачки матриц

12 октября 2026. Продолжение [этапа 2 CPU lane](DEEPSEEK4_CPU_LANE_IMPLEMENTATION_PLAN.md)
и [очереди CPU-заданий](DEEPSEEK4_CPU_GPU_QUEUE.md). Новый путь экспериментальный,
по умолчанию выключен. Он убирает получение маршрутов основным host-потоком
для подходящих коротких MoE-веток. Это ещё не законченный перенос архитектуры Maya.

Этот отчёт фиксирует первый вариант без admissions. Продолжение —
[заполнение RAM и обучение кэшей](DEEPSEEK4_GPU_FETCH_RAM.md): отдельный opt-in,
который использует уже выделенные блоки по фактическому запросу GPU.

## Передача и владение

До публикации CPU-работы backend удерживает снимок трёх матриц слоя: GPU-адреса
защищены от вытеснения, RAM-адреса удерживаются leases, для отсутствующих матриц
сохранены файловые handles и смещения. Снимок живёт до завершения GPU-потребителей
и остановки обоих сервисов. Target и DSpark имеют отдельные очереди.

Для up/gate/down предусмотрены три слота. GPU убирает повторные expert IDs,
пропускает CPU-only экспертов и записывает GPU-hits прямо в таблицу MMVQ.
Отсутствующие матрицы публикуются с эпохой, ID и проверяемым адресом назначения.
Основной поток сразу переходит к отправке вычислительного графа: старые
`tensor_get_async(ids)` и `synchronize(ids_backend)` этой ветки не исполняются.

Постоянный I/O-service проверяет запрос и читает отсутствующие матрицы по native
файловым смещениям. При RAM-hit используется удерживаемый pinned-адрес. Сервис
не вызывает CUDA, не выделяет pinned RAM и не изменяет кэши. Для чтения файлов
есть два заранее выделенных буфера по 2 МиБ; чтение следующего блока может
перекрываться с переносом предыдущего. CPU-service независимо считает экспертов.

Перенос из mapped RAM выполняет CUDA-ядро. На устройствах с cooperative launch
используются до 16 блоков, с гарантированной резидентностью для grid barrier.
Без этой возможности остаётся один блок. Подтверждение блока выдаётся после
окончания всех чтений и записей; слот нельзя повторно использовать до ответа
сервиса и GPU-подтверждения. Обычные и компактные рабочие буферы поддерживаются.
Дополнительное место — 4 МиБ staging RAM и небольшие таблицы на backend.

Этот прототип использует SM для переноса, а не copy engine. Попытка выполнять
`cudaMemcpyAsync` из I/O-service прошла изолированный тест, но во встроенном
тесте получила 500-мс тайм-аут уже на первой матрице, с графами и без них.
Вероятная причина — синхронные CUDA allocations GGML при ожидающем GPU-потребителе;
точка блокировки драйвера отдельно не трассировалась. В принятом варианте сервис
вообще не зависит от CUDA API. Тест включает allocation после публикации запроса.

## Включение и ограничения

К тестовому профилю с `STRATA_DS4_CPU_GPU_QUEUE=1`, shared RAM, pipeline, direct cache,
ordered experts и CPU threads > 0 добавить:

```text
STRATA_DS4_GPU_FETCH_QUEUE=1
```

`STRATA_DS4_GPU_FETCH_BLOCKS=1` оставляет одиночный блок для диагностики;
по умолчанию запрашиваются 16, максимум — 16. Режим относится только к backend
DeepSeek, не к Qwen. Длинный prefill остаётся на прежнем GPU-пути.
При `STRATA_DS4_ROUTE_TRACE` новая подкачка отключается: полная запись маршрутов
сохраняет прежний путь вместо неполной диагностической трассы. CPU trace и
scheduler profile поддерживают новую очередь.

Для включения ветки требуется хотя бы одна готовая и подходящая RAM-тройка.
Первый вариант запускал очередь и для совершенно холодного слоя: поскольку
новый путь пока не добавляет матрицы в кэши, RAM оставалась пустой и CPU получал
ноль заданий. Этот вариант отклонён. Холодные слои теперь прогреваются прежним путём.

Первые hash-слои, неподходящие формы/операции и ветки без готовой RAM-тройки
сохраняют старый scheduler. На остальных ветках записи кэшей удерживаются,
но новые admissions и обучение GPU frequency/LRU пока не перенесены.
Поэтому скорость нельзя интерпретировать как изолированную стоимость очереди.
Следующий необходимый шаг — безопасное заполнение кэшей и освобождение снимков.

На границе ветки остаётся ожидание завершения для освобождения leases. Это
не межслойный конвейер. Счётчик `gpu_fetch` в scheduler trace означает число
пропущенных host-копирований матриц; `route_get` и `route_wait` отдельно показывают
оставшийся старый путь. Лог `STRATA_GPU_FETCH_QUEUE` содержит RAM/file/H2D bytes.
Файловые байты включают чтение через файловый кэш Windows и не равны SSD-трафику.
Общий H2D/file учёт включает новую очередь, а прежние счётчики GPU-cache hits,
direct hits и пропущенных CPU-байтов ещё не учитывают её полностью. Их нельзя
использовать для расчёта полной доли попаданий в этом эксперименте.

Ошибка публикации, чтения или тайм-аут завершают запрос с ошибкой; после выдачи
CPU-назначения нельзя незаметно повторять работу на GPU. Тайм-аут GPU — 500 мс,
ожидание chunk acknowledgement на CPU — 2 с, drain — 10 с. Освобождение источников
идёт после завершения GPU-потока и сервиса. Это не расширяет поддержку прерывания
внутри одного уже отправленного CUDA kernel.

## Проверки и измерения

Артефакты текущего опыта: `build-local/deepseek4/gpu-fetch2-20261012/`.
Они содержат контрольную сборку, логи отклонённых вариантов, конфигурации,
точные входные token IDs, трассы и результаты. Условия: Ryzen 9 9950X,
RTX 5090 32 ГБ, RAM 128 ГБ, Samsung 990 PRO; DeepSeek UD-Q3_K_XL,
GPU-кэш 15 ГиБ, shared RAM 2 ГиБ, CPU12, force/cap1, CUDA Graphs.

До последнего изменения схемы переноса прошли 33 регрессионных теста.
Изолированный тест очереди проверяет 400 повторов CUDA Graph, новые номера
заданий, GPU-hit/CPU-only/повторяющиеся IDs, компактные адреса, ошибки и отмену,
перенос через обе staging-области и хвост нечётной длины. Встроенный тест
сравнивает CPU-строки с прежним CPU-ядром, GPU-строки — с GPU-only, побитно;
отдельная GPU-матрица читается из файла внутри уже прогретой CPU-ветки.

Первый, отклонённый вариант с пустым RAM-кэшем и одним CUDA-блоком дал
21 543,90 мс на decode1 и 13 939,71 мс на decode3. CPU-заданий — 0,
чтение SSD за все проходы — 13 672 415 232 байта. Это диагностический провал,
не результат оптимизации. Средние взяты по последним двум из четырёх повторов
фиксированного workload: 36 токенов префикса и 32 продолжения.

Вариант с готовыми RAM-тройками и 16 блоками, одна сборка с флагом fetch on/off:

| Режим | Prefill 68, мс | Decode1: 32 токена, мс | Decode3: 32 токена, мс |
|---|---:|---:|---:|
| Прежний путь подкачки, CPU-ring включён | 2398,13 | 1871,25 | 1290,89 |
| GPU fetch | 2394,20 | 2358,43 | 1764,49 |
| GPU fetch + trace/capture | 2381,14 | 2366,05 | 1792,63 |
| Прежний путь + trace/capture | 2397,97 | 1908,91 | 1213,98 |

Это одна исследовательская пара с отдельными диагностическими повторами,
не доверительный интервал. Decode стал дольше на **26,03% / 36,69%**.
Поэтому новый путь не включён в рабочем профиле и не записан в удачные оптимизации.
Trace/capture воспроизвёл все **12/12** полных logits signatures своего режима.
Между fetch и контролем совпали **4/12**, только prefill. Меняются история
кэшей и назначения CPU/GPU; побитное равенство итоговых logits между режимами
этим опытом не доказано.

Трасса обоих последних повторов показывает:

| Фаза | Host route_get/route_wait: контроль → fetch | Матрицы через GPU fetch |
|---|---:|---:|
| Decode1 | 1376 → 160 | 3648 |
| Decode3 | 473 → 55 | 1254 |

Это удаление **88,37%** прежних обращений на данном workload: 38 из 43 слоёв
на вызов. Оставшиеся пять слоёв продолжают обычный путь. `route_get` в decode1
занял 144,67/148,56 мс у контроля и 40,67/39,12 мс у fetch. Эти интервалы включают
ожидание предыдущей GPU-работы; уменьшение нельзя целиком считать чистой экономией.
Основной поток всё ещё ждёт завершения ветки при освобождении снимка.

За все проходы fetch обслужил 4642 ветки, 16 393 отсутствующие матрицы,
2 331 374 592 байта из pinned RAM и 57 711 916 032 файловых байта.
CPU-ring получил 336 заданий / 346 строк против 885 / 1018 у контроля.
Отсутствие новых admissions меняет использование CPU и GPU-кэша; эту часть
нужно перенести до следующего сравнения скорости. SSD прочитал 5 320 814 592 байта
в первом fetch-прогоне и 59 551 744 в контроле; в диагностическом fetch — 4096.
Эти счётчики охватывают все проходы после загрузки модели, не только прогретую
фазу, и учитывают другую активность диска. Минимально доступная RAM в этих
target-прогонах — 69,96 ГиБ; это не замер запаса памяти с DSpark.

После перехода на cooperative copy заново прошли **7 затронутых native-тестов**.
После исправления генератора заново прошли **4 проверки** очереди и встроенного
пути с графами/без графов, включая обход при shadow route trace; прочитано 6099
корректных JSON-записей маршрутов. Дополнительно прошли **4 проверки** с одним
блоком и компактными буферами.
Изолированный тест содержит 6 300 814 проверок, включая сравнение каждого байта
большого переноса; это не столько независимых сценариев. Два сохранённых
CPU-задания воспроизвелись побитно: по пять раз на 12 и 16 потоках.

Модель с DSpark Q8_0, draft max2 и общим scratch прошла A→B→A, extension/restore,
fresh prefill, одиночный токен, отмену prefill/decode и greedy restore после
отмены. Работали обе очереди: target 1530 fetch-веток и 190 CPU-заданий,
draft 90 fetch-веток и 5 CPU-заданий. `HostCache` завершился с `oom=0`,
`pending=0`, `retired_bytes=0`.

Полная проверка **не пройдена**: `seeded` и `seeded_repeat` дали по 24 токена,
первое различие — седьмой токен. Проверка не ослаблялась. Ранее проблема
воспроизводилась и в shared CPU-режиме до нового fetch; этот запуск не доказывает
её конкретную причину и не подтверждает полную корректность восстановления.

Финальная измеренная сборка: SHA-256
`c063f607707c5953bcdc0568d516944f1df9fabbdd2d1007d4a909e812a9eeeb`
(`final.exe`). Проверка shadow recorder обнаружила повторную подготовку CPU
при fallback: CMake заменял слишком общий anchor также внутри нового хука.
Порядок вставок исправлен, повторная подготовка пустого снимка исключена,
регрессионная проверка добавлена в CTest. Таблица выше и файлы `*-final*`
относятся уже к исправленной сборке. Промежуточные `*-v4*` сохранены отдельно.
Финальные исходники, их SHA, бинарник и логи — в `final-manifest.json` и `source-final/`.
