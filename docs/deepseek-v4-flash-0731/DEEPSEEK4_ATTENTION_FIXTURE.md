# Изолированный attention и граница расхождения в MoE

10 октября 2026. Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090
32607 МиБ, CUDA 13. Продолжение [трассировки активаций](DEEPSEEK4_ATTENTION_PROBE.md).

**Уплотнение видимых ключей устранило расхождение первого attention на
проверенных запросах модели. Полная эквивалентность batch/serial пока не
достигнута.** Следующая найденная граница — маршрутизируемая ветка MoE
первого слоя. Это результат диагностики, не подтверждённое ускорение модели.
Рабочий профиль сохранён; эксперимент не входит в обычную сборку.

## Независимый тест

Добавлен [test_attention_batch.cpp](../../backends/deepseek4/test_attention_batch.cpp).
Он создаёт граф только с Flash Attention и запускает его непосредственно на
CUDA backend. Модель, эксперты, DSpark и SSD в этом тесте не участвуют.

Q хранится в F32, K/V/маска — F16, sinks — F32. Размер головы 512,
64 query-heads, одна KV-head. Проверяются:

- batch 1–5, KV padding 256/512/4096/8192;
- короткий префикс, sliding window 128 и переход позиции 255 → 256;
- разреженная маска с конечными ненулевыми смещениями;
- K=V и разные K/V, sinks и отсутствие sinks;
- обычный и переставленный Q со strides как у реальной модели;
- повышенная амплитуда Q и аналитический случай Q=0, V=0,25.

Значения задаются по индексам: смена padding не меняет видимые данные.
Скалярный эталон вычисляет stable softmax и взвешенную сумму в FP64 по
**фактически округлённым входным F16 K/V/маске**. Sink добавляется в
знаменатель, но не в сумму V. Для аналитического случая результат независимо
проверяется как `0.25 * visible / (visible + 1)` с точностью 1e-14.
CPU используется только для этого небольшого эталона; граф attention и
инференс модели исполняются на GPU.

Отдельно рассчитан эталон с округлением Q и scale по схеме штатного MMA:
`half(half(Q) * half(scale))`. Это помогает отличать ошибку представления
входа от последующих округлений. Даже при Q=0 ошибка штатного attention
достигает 3,5153e-5: она не объясняется одним округлением Q.

В каждой серии **182 сочетания**. Максимальная абсолютная ошибка штатного
выхода относительно FP64 — **0,000974103**. Это измерение на данном наборе,
не оценка качества модели. Тест проверяет конечность, повторяемость, грубую
границу ошибки 0,02 на этих ограниченных входах и сохраняет все ошибки.
Для второго экспериментального режима дополнительно требуется точное
совпадение с serial и независимость от padding на поддерживаемых случаях.

## Два варианта уплотнения

[AttentionBatchPatches.cmake](../../backends/deepseek4/AttentionBatchPatches.cmake)
создаёт частные копии закреплённых исходников. SHA-256 проверяется до патча;
файлы зависимости и backend Qwen не меняются.

Патч собирается только с `STRATA_DEEPSEEK_ATTENTION_EXPERIMENT=ON`, default
**OFF**. В такой сборке переменная `STRATA_DS4_FA_COMPACT` выбирает:

| Режим | Поведение |
|---|---|
| 0 или отсутствует | Штатный dispatch |
| 1 | Разрешить существующее sparse MMA для короткого batch независимо от порога KV=4096 |
| 2 | То же, но отдельный CUDA-вызов attention для каждого query |

Условия: NVIDIA с поддержкой Turing MMA, F32 Q, F16 K/V/маска, D=512,
64 query-heads, одна KV-head и последовательность, batch ≤4, корректная
положительная граница `n_kv_max`, без ALiBi и softcap. Иные случаи идут
штатным путём. Режим задаётся до запуска; тест отключает CUDA graphs.

В графе DeepSeek при включённом эксперименте raw sliding-window attention
получает проверяемую границу `hparams.n_swa`, только для batch ≤4. Для HCA
новая граница не выдумывается. Sparse-уплотнение сохраняет все видимые ключи
в их физическом порядке; оно не меняет роутинг экспертов и не сокращает окно.

Из 182 случаев 84 соответствуют экспериментальным условиям. Для остальных
98 контрольные суммы выходов совпали со штатным режимом в обеих сериях.

| Режим | Совпадение с serial, одинаковый padding | Serial с естественным padding | Независимость от padding |
|---|---:|---:|---:|
| Штатный | 63/84 | 39/84 | 51/84 |
| Уплотнение, batch | 78/84 | 78/84 | 84/84 |
| Уплотнение, отдельные query | 84/84 | 84/84 | 84/84 |

Для малого bound 128/260 пакетный вариант совпал с serial. При bound 2048
порядок stream-K редукции снова зависит от batch: максимальная разница
0,000121724. Поэтому малый набор не доказывает общей детерминированности
пакетного sparse MMA. Отдельные query устраняют эту зависимость в проверенных
случаях, но сохраняют округления самого FP16-ядра относительно FP64.

Цена видна в локальном микротесте: boundary, batch=3, KV=512 —
**50,41 / 49,99 / 91,00 мкс** для режимов 0/1/2 в серии `final`.
При sparse bound=2048, batch=3, KV=4096 — **61,56 / 116,45 / 295,28 мкс**.
Это wall time операции с GPU-синхронизацией после 50 запусков, 5 warmup,
данные уже на GPU, CUDA graphs выключены. Числа включают накладные расходы
host dispatch, зависят от условий запуска и не являются скоростью модели.

## Проверка на DeepSeek Q3 + DSpark

Модель `H:\deepseek-v4-flash-0731\UD-Q3_K_XL`, DSpark Q8_0, draft-max=2,
контекст 8192, кэши target/draft 15360/1024 МиБ. Prefill 256 токенов,
отдельный запрос 36 токенов, генерация 4 токена и повтор. Включены serial
diagnostic и точечный activation probe; такие запуски не годятся для замера
производительности.

Режим 1 без экспериментального MMVQ: **21/21 строки** первого attention
имеют нулевую разницу batch/serial, включая разный размер K=512/256.
Q совпадает, видимые K/V/маска побайтово одинаковы. Эффект трассировки на
batch и serial равен 0, replay также 0. Полные logits всё ещё расходятся
до 4,58317.

При добавлении `--mmvq-token-batch 2` и проверке следующих узлов:

| Узел слоя 0 | Максимальная разница batch/serial, 21 строка |
|---|---:|
| Attention, обратный RoPE, обе выходные проекции | 0 |
| Hyperconnection после attention и нормализованный вход FFN | 0 |
| Общий эксперт `ffn_shexp` | 0 |
| Маршрутизируемые эксперты `ffn_moe_out` | 0,000952244 |
| Выход слоя `l_last` | 0,000604868 |
| Итоговые logits всей модели | 5,15790 |

Эффект трассировки и replay — 0. В каждой из трёх диагностических серий
29 аудитов, везде `cpu_compute_nodes=0`. Разные режимы могут менять
траекторию генерации; величины выше — внутренние сравнения одного batch
с serial из того же состояния, не сравнение качества режимов между собой.

## Проверки и воспроизведение

Обычная сборка прошла 17 CTest и 25 Python-тестов. Настройки и сервер не
переключены на эксперимент. Реальные проверки сессий/отмены предыдущего
этапа остаются применимы к прежнему рабочему пути; для нового attention
полной проверки сессий, длинного контекста и производительности ещё нет.

Существующее окружение сборки VS/CUDA/Ninja:

```powershell
cmake -S backends/deepseek4 -B build-deepseek4 -DSTRATA_DEEPSEEK_ATTENTION_EXPERIMENT=ON
cmake --build build-deepseek4 --target strata-deepseek4 deepseek4_attention_batch_test -j 2
$env:STRATA_DS4_FA_COMPACT = '2'
ctest --test-dir build-deepseek4 -R deepseek4_attention_compact --output-on-failure
```

Вернуть обычную сборку: убрать переменную, сконфигурировать с
`-DSTRATA_DEEPSEEK_ATTENTION_EXPERIMENT=OFF` и пересобрать. Для проверки модели
нужны также `STRATA_SPEC_CHECK_SERIAL=1` и activation probe из предыдущего
отчёта. Итоговый локальный CMake-кэш оставлен с **OFF**.

Сырые материалы в `bench/results`:

- `ds4-attention-fixture-20261010-final{0,1,2}.{json,log}` — 182 случая,
  численные ошибки, контрольные суммы и времена;
- `ds4-attention-fixture-20261010-verified{0,1,2}.{json,log}` — повтор с явным
  `memcmp` результатов вместо одного численного сравнения;
- `ds4-attention-fixture-20261010-default.{json,log}` — итоговая обычная сборка:
  эксперимент не скомпилирован, все 182 контрольные суммы совпали с режимом 0;
- `ds4-attention-fixture-20261010-model1.{json,jsonl,log}` — первый attention;
- `ds4-attention-fixture-20261010-next.{json,jsonl,log}` — участок до FFN;
- `ds4-attention-fixture-20261010-ffn.{json,jsonl,log}` — разделение routed/shared.

Профили, команды, журналы сборки и экспериментальный бинарник сохранены в
`build-local/deepseek4/attention-fixture-20261010`. SHA-256 бинарника модели
для последней серии `ffn`:
`23c218ec7035f06ef333f367ff379a3f71cbd82cdd6e81557eeb6438b76394ec`.
SHA-256 итогового обычного движка:
`d2df927b969d7f70b8fab61a25faf9fcd0235b5f782b80e2424162e737a66e57`.

Следующий шаг — проверить router IDs, веса маршрутов и вход/выход выбранных
экспертных матриц при одинаковом `ffn_norm`, включая fused gate/up, который
экспериментальный MMVQ пока обходит. Сначала нужно различить влияние
роутинга, fused matvec и суммирования экспертов. Лишь после устранения
расхождений имеет смысл выбирать быстрый единый запуск attention и снова
измерять DSpark на коротком и длинном контексте.
