# CPU lane v2: оставшиеся отличия от project-maya

12 октября 2026. Повторный аудит после [CPU lane v2](DEEPSEEK4_CPU_LANE_V2.md). Сравнивались текущие локальные исходники Strata и соседнего project-maya. Новые модели и GPU-бенчмарки в этом аудите не запускались. Числа ниже взяты из сохранённых запусков h1/i1/g1/j1; Maya на этом ПК не измерялась.

Целый эксперт, асинхронное исполнение и совместимость с CUDA Graphs уже перенесены. Но организация RAM и принятие решений остались другими. Отрицательный результат v2 не доказывает бесполезность CPU lane Maya на этой машине: перенесён вычислительный блок, а его снабжение весами и планировщик ещё заметно отличаются.

## 1. Главные измеренные затраты — создание CPU-копии, которой у Maya на этом пути нет

Maya выбирает CPU-эксперта только при наличии готового адреса в RAM-таблице: `tab[key] == 0 && rtab[key] != 0`. Service thread передаёт уже принадлежащий RAM-tier blob в `fast_cpu_experts`; веса удерживаются до границы токена. Перед каждым CPU-экспертом не надо проверять mmap-страницы и собирать новый blob. См. [GPU-выбор](../../../project-maya/src/kernels/cuda/glm_fast.cu), строки 3063–3097, и [service](../../../project-maya/src/core/glm_fast_path.cu), 3425–3467.

У нас [cpu_lane_hooks.inc](../../backends/deepseek4/cpu_lane_hooks.inc), 138–141, проверяет резидентность трёх mmap-областей через QueryWorkingSetEx. Затем [cpu_expert_lane.cuh](../../backends/deepseek4/cpu_expert_lane.cuh), 75–89 и 111–115, выделяет/переиспользует отдельный pinned blob и копирует в него gate/up/down перед вычислением. Это дополнительные чтение и запись всех весов; фактический DRAM-трафик зависит также от CPU-кэшей.

Target, весь процесс h1: Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, UD-Q3_K_XL + DSpark Q8_0, 8 CPU-потоков, cap 1, CPU RAM 256 МиБ:

| Счётчик | Значение |
|---|---:|
| CPU-заданий | 5310 |
| CPU compute | 2,028 с |
| Заполнение CPU-кэша | 4,246 с |
| Выбор и калибровка | 3,258 с |
| Попадания / промахи CPU-кэша | 2 / 5308 |
| Доля попаданий | 0,038% |

Это суммы счётчиков за весь процесс; часть работы перекрывается с GPU. Нельзя вычесть 7,504 с из времени запроса и объявить такой прирост.

В i1 увеличение кэша до 2048 МиБ подняло долю попаданий до 10,734% (570/5310), но оставило 3,934 с заполнения и не ускорило последний повтор. Значит, простое увеличение нашего дополнительного кэша не воспроизводит RAM-tier Maya.

Ранее добавленный [HostCache](../../backends/deepseek4/host_cache.hpp) тоже не решает это автоматически: он хранит pageable-матрицы для pipeline и выдаёт их копированием в destination (строки 169–209). CPU lane не берёт из него защищённые адреса. Его текущий интерфейс не даёт pinned lease для CPU и H2D.

**Следующее изменение:** единое ограниченное хранилище матриц, которое предоставляет CPU и GPU-передачам адреса с удержанием времени жизни. Gate/up/down могут оставаться тремя отдельными матрицами; для CPU не обязательно собирать их в новый непрерывный blob. Нужны опубликованная готовность, запрет вытеснения на время CPU/H2D, общий бюджет RAM и защита горячих записей от большого prefill.

## 2. Лимит CPU у нас относится ко всему speculative window, у Maya — к отдельному токену

В [нашем планировщике](../../backends/deepseek4/cpu_lane_hooks.inc), 119–145, кандидаты всех токенов сначала объединяются по expert ID, затем общий список ограничивается cap. При cap=1 выбирается один уникальный эксперт на весь batch. Маска `packet.mask[id]` действует на все его вхождения; это не маска `token × expert`.

Maya принимает решение в `moe_route` для текущего токена (`cpu_plan[f_ram]`). [win_cpu_merged](../../../project-maya/src/core/glm_fast_path.cu), 1756–1774, уже после этого объединяет одинаковые веса выбранных CPU-экспертов нескольких токенов. Выбор и объединение вычислений — разные стадии.

Минимальный разбор текущего кода: все эксперты — допустимые RAM-промахи, частоты одинаковы, force, cap=1.

| Входные маршруты | Наш выбранный CPU-эксперт | CPU у первого токена |
|---|---|---|
| [10, 11] | 11 | 11 |
| [10, 11], [20, 21], [30, 31] | 31 | нет |

Причина — сортировка по более позднему первому вхождению и общий cap. Это пример из управляющей логики, не новый замер logits полной модели. Он доказывает, что добавление будущих маршрутов может менять устройство вычисления неизменённого раннего токена. При разной CPU/GPU-арифметике это источник зависимости численного результата от состава verification batch. Диагностический `TEST_FIXED` тоже использует этот общий список: он устраняет влияние резидентности/частоты, но не гарантирует неизменность назначения при изменении длины окна.

В h1 target получил 6147 CPU expert/token rows на 15497 входных токенов активных CPU-заданий: около 0,397 эксперта на токен, хотя cap равен 1. Число входных токенов вычислено как `input_bytes / (4096 * sizeof(float))`; это не количество выданных пользователю токенов.

**Следующее изменение:** причинный план для каждого токена, затем группировка одинаковых весов. Нужна маска отдельных вхождений и учёт смешанного случая: если один токен считает эксперта на CPU, а другой на GPU, передачу его матрицы на GPU отменять нельзя. Простое умножение cap на длину batch не исправит зависимость раннего назначения от будущего.

## 3. У нас host всё ещё участвует в выборе каждого маршрута

Сгенерированный `build-deepseek4/strata-ggml-backend.cpp`, 1934–1967, получает IDs через `ggml_backend_tensor_get_async`, затем вызывает `ggml_backend_synchronize(ids_backend)` и запускает CPU-планировщик. В CPU lane остаются host-сортировка, map lookups, запросы RAM, D2H входа, cudaLaunchHostFunc, H2D выхода и публикация маски. CUDA Graphs выполняют оставшиеся GPU-части, но не убирают эту границу.

Maya выбирает CPU/GPU внутри [GPU router](../../../project-maya/src/kernels/cuda/glm_fast.cu), 3059–3145. Он же пишет вход и адреса в mapped ring (3196–3229). Отдельный service thread читает уже готовое задание, GPU продолжает fetch и свои экспертные операции. CPU-ответ требуется после GPU down. Нет эквивалентного чтения IDs главным host-потоком перед каждым решением.

Это различие существует и без полного CUDA Graph: в Maya layer capture ограничен recurrent/KDA decode и дополнительными условиями. [Документ Maya](../../../project-maya/docs/GLM-KDA-GRAPHS.md) прямо указывает обход capture для других путей. Нельзя объяснять её результат якобы обязательным полным CUDA Graph всей модели.

В g1 наша калибровка границы D2H/callback/H2D дала примерно 108–158 мкс. Это стоимость отдельной пробы, не измеренная чистая потеря на критическом пути. В Maya коэффициент 0,04 мс в формуле плана — константа; сравнивать его с нашими пробами как два замера на одном ПК нельзя.

**Следующее изменение:** сначала готовые RAM-адреса и дешёвый план; затем проверить собственный service/ring и GPU-таблицы выбора. Переносить весь GLM-граф в DeepSeek не требуется. В выбранном протоколе должны сохраниться уже проверенные владение буферами, отмена и обработка ошибок.

## 4. Калибровка v2 слишком оптимистична для фактической работы

В [нашем calibrate](../../backends/deepseek4/cpu_expert_lane.cuh), 119–137, один blob заполняется и считается повторно: один прогрев плюс три измерения. Для этой модели blob около 10,9–13,4 МБ; такой опыт допускает сильное переиспользование CPU-кэша. Калибровка также запускается при первом подходящем маршруте, а не отдельной стадией подготовки.

Maya [вращает до 64 готовых RAM-экспертов](../../../project-maya/src/core/glm_fast_path.cu), 2171–2189, считает до четырёх за вызов, прогревает CPU работой, делает пять серий по 16 измерений и использует лучшую медиану (2291–2328). Поэтому тест меньше похож на повторное чтение одного веса из L3. Это не гарантия, что её оценка идеальна на нашем ПК.

Есть и конкретная ошибка модели стоимости: у нас `cost.compute_us * uses / work.tokens` (cpu_lane_hooks.inc:155). Если blob измерен на трёх активациях, а реальный эксперт используется в одной, делится всё время, включая фиксированную подготовку и запуск двух пакетов пула. Реальный вызов всё равно квантует вход всего окна. Стоимость одной активации не обязана быть третью стоимости трёх.

Кроме того, расчёт `max(cpu, remaining_h2d)` не включает host-выбор/residency и влияние решения на будущее содержимое кэшей. В h1 только выбор в среднем занял около 523 мкс на распознанную ветку; по всему процессу он больше CPU compute. Часть включает начальную подготовку, это не оценка каждой ветки отдельно.

Maya дополнительно имеет [tools/calibrate_glm.py](../../../project-maya/tools/calibrate_glm.py): настройку числа потоков и доли PCIe по новым запросам в одном движке, с чередующимися перепроверками и порогом выигрыша 3%. У нас серия бенчмарков уже отвергает невыгодный профиль, но сам runtime auto такой обратной связи не имеет.

**Следующее изменение:** измерять фактические комбинации уникальных экспертов и числа использующих их токенов; отделять фиксированную стоимость вызова, чтение DRAM, дополнительные dot products и обмены. Вращать веса, включать планирование в оценку, затем подтверждать выбор полными запросами и разрешать GPU-only.

## 5. Политика хранения у Maya общая для RAM и VRAM

Maya использует [exclusive tiers](../../../project-maya/src/core/glm_fast_state.hpp), 345–369. После продвижения эксперта в VRAM его RAM-копия освобождается на безопасной границе. При вытеснении из VRAM возможна демоция в RAM; RAM-victim выбирается с учётом частоты и защиты недавно использованных записей. См. [fast_boundary](../../../project-maya/src/core/glm_fast_path.cu), 3660–3792. Это не обещание полного отсутствия временных копий: во время передач они необходимы.

Наш CPU-кэш — отдельный LRU. Он не освобождает запись по продвижению матриц в VRAM и не получает обратно вытесненные GPU-матрицы. Частоты выбирают холодного кандидата на CPU, но не образуют общую политику хранения. При включённом HostCache могут существовать ещё и его независимые копии.

Maya также прогревает RAM/VRAM из expert prior при загрузке. Гарантия «всё без SSD» у неё зависит от вместимости tiers и режима RAM-resident. Её модель, кванты и объёмы хранения отличаются от нашего DeepSeek; одинаковых ток/с по одному сходству алгоритма ожидать нельзя.

Матрицы GPU-кэша Strata не надо объединять обратно в целые эксперты ради переноса. Общая RAM-политика может удерживать три раздельных lease. Выбор CPU по всем трём VRAM-промахам у нас консервативен; возможность CPU при частичной VRAM-резидентности надо оценивать по реально отменённым байтам передачи, а не по размеру целого blob.

## 6. Пул и численная воспроизводимость — разные вопросы

Наш пул теперь правильно ждёт выполненные задания, но каждый пакет будит condition_variable и создаёт Batch. Между gate/up и down есть новое пробуждение. Maya держит workers в spin до 20 мс и использует постоянно работающий service; для обычного CPU-эксперта дробит работу примерно на 48 частей, а merged-window балансирует её по числу активаций на строку. У нас обычно около двух частей на поток с одинаковым числом строк на группу. Это кандидаты для дальнейшего замера; их вклад ещё не отделён от RAM-копирования. Увеличение до 12/16 потоков эти архитектурные затраты не устраняет.

Численные различия CPU/GPU не являются отсутствующей гарантией Maya. Её native CPU path также использует ggml-cpu from_float/vec_dot, а проверка `CPU_LANE_CHECK` выводит ошибки относительно double-эталона. Выбор CPU зависит от динамических RAM/VRAM-таблиц, и отдельная CPU-сумма добавляется к GPU-сумме. [SETTINGS.md](../../../project-maya/docs/SETTINGS.md), строка 83, указывает полное совпадение токенов multi-bench при CPU_LANE=0; этот текст не доказывает точность всех гибридных режимов.

Наша вставка отдельных down-строк сохраняет порядок общей редукции и должна остаться. Успех fixed в 8/8 прошлых сценариях — полезная проверка состояния, но не доказательство CPU/GPU-эквивалентности на всех входах или причинности общего window-плана.

## Порядок исправлений и критерии проверки

1. Убрать зависимость CPU-назначения раннего токена от будущих маршрутов. Проверить неизменный префикс при добавлении/замене draft-токенов, сначала маски, затем logits. Проверить смешанные CPU/GPU-вхождения одного эксперта.
2. Объединить снабжение CPU и H2D общими защищёнными RAM-матрицами. Проверить время жизни при отмене/вытеснении, общий бюджет с ОС, отсутствие повторного pack при попадании и сохранение горячих записей при prefill.
3. Исправить калибровку и cost model на реальных формах, затем подобрать число CPU-экспертов на токен. 12/16 потоков перепроверять после этих изменений.
4. Измерить service/ring и более дешёвую GPU-публикацию; spin/sleep настраивать отдельно, после устранения лишней работы с весами.
5. Разделять проверку состояния, численную погрешность и скорость. Для скорости нужны и фиксированная история, и новые запросы; отдельно SSD, acceptance, время prefill/decode. Прежний strict restore нельзя объявлять пройденным через ослабление сравнения.

Текущий рабочий профиль остаётся GPU-only. Сам аудит изменил только документацию. Последующая реализация и замеры ведутся в [плане испытаний](DEEPSEEK4_CPU_LANE_EXPERIMENTS.md).
