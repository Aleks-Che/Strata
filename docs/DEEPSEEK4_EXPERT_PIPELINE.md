# Конвейер загрузки матриц DeepSeek и DSpark

Дата: 3 октября 2026. Реализация в отдельном backend DeepSeek, на закреплённом
llama.cpp `3cf03257f219afbe7334045ff7c6a06ac68c627d`. Движок Qwen не изменён.

## Как работает

После получения router IDs планировщик собирает выбранные матрицы gate/up/down
текущего слоя. ID и квантованные байты остаются исходными. Планирование касается
только матриц с тем же тензором маршрутизации: эксперты следующего слоя ещё
неизвестны. Для target и DSpark используются отдельные конвейеры и GPU-кэши.

Путь данных:

```text
GGUF через mmap → pinned RAM → отдельный H2D stream → кольцо в VRAM
                                                        ↓ ready event
                                    compute stream: D2D → matmul на GPU
                                                        ↓ used event
                                               слот можно заполнить снова
```

Один постоянный фоновый поток на backend читает страницы mmap в pinned RAM.
Промах файлового кэша обслуживает ОС с диска. Поток отправляет H2D и заполняет
следующие слоты, пока GPU работает с предыдущими матрицами. Это ограниченный
конвейер с четырьмя слотами; отдельного IOCP/io_uring-загрузчика здесь нет.
Размер слота задаёт `--expert-stage-mib`. Большая матрица разбивается на части.

CPU обслуживает память, очередь и sampling. Все вычислительные узлы модели,
включая маршрутизацию и матричные операции, проходят GPU-only audit.

Кольцо имеет собственную VRAM: заранее писать в рабочие тензоры GGML нельзя,
поскольку их память может ещё содержать используемые активации. Compute stream
ожидает `ready`, копирует матрицу в её рабочую память и отмечает `used`.
Производитель ждёт `used` перед повторным заполнением слота. Событие готовности
публикуется только после записи в CUDA stream.

Попадания в GPU-кэш не читаются из RAM повторно. Уже закэшированные матрицы,
нужные текущему плану, защищены от вытеснения. Записи в кэш и чтения из него
упорядочены compute stream. Динамическое управление VRAM сохраняется; при
нехватке места матрица проходит через кольцо без добавления в кэш. Prefill
с числом входных токенов больше восьми по-прежнему обходит LRU.

При завершении графа, ошибке или отмене неиспользованный хвост плана отменяется,
а фоновое чтение и H2D завершаются до освобождения mmap. Если реальная загрузка
не соответствует плану, backend отменяет его и использует прежний путь
копирования. Такой случай учитывается в `pipeline_fallbacks`.

## Включение и память

В аргументах DeepSeek backend или `tools/setup_deepseek4.py`:

```text
--expert-stage-mib 16 --expert-pipeline 1
```

`--expert-pipeline 0` оставляет прежний путь; это общий default. Параметр 1
требует ненулевого staging. Он применяется одновременно к основной модели
и DSpark, если их эксперты подгружаются из mmap.

При staging 16 МиБ на каждый backend добавляются 64 МиБ pinned RAM и 64 МиБ
VRAM. Прежние два pinned-буфера по 16 МиБ сохраняются для резервного пути:
итого 96 МиБ pinned RAM на backend. Для target + DSpark прирост — **128 МиБ
RAM и 128 МиБ VRAM**, всего 192 МиБ pinned RAM. Кэши экспертов и остальные
выделения модели считаются отдельно. Размер колец учитывается в стартовой
проверке свободной VRAM. INFO/About показывают включение и число слотов.

В локальных профилях `strata-deepseek4-ud-q3-k-xl.json` и
`strata-deepseek4-ud-q3-k-xl-dspark.json` конвейер включён. Их обычные launcher
скрипты применят его при следующем запуске. Чтобы вернуться к прежнему пути,
достаточно заменить значение `--expert-pipeline` на `0` в массиве `args`.

`STRATA_EXPERT_PIPELINE_TRACE=1` выводит число матриц и выбранных фрагментов
каждого плана. В проверенной модели это три матрицы на слой. Для замеров
производительности подробную трассировку следует выключать.

Итоговая строка `STRATA_EXPERT_TOTAL` содержит `pipeline_groups`,
`pipeline_chunks`, `pipeline_unused`, `pipeline_fallbacks`. Счётчик `stage_us`
включает чтение страниц и memcpy; `submit_us` измеряет отправку команд, а не
время исполнения GPU. `wait_us` суммирует ожидания производителя и потребителя,
которые могут перекрываться; это не доля общего времени запроса.

## Проверка

Шесть CTest-проверок покрывают GPU-only, DSpark, политику VRAM и загрузку матриц.
Отдельный тест блокирует compute stream и проверяет, что все четыре H2D-слота
уже готовы. Затем сравнивает байты, многократно использует кольцо, отменяет
непрочитанный хвост и запускает новый план. Тест кэша проверяет padding,
разбиение большой матрицы, попадания, вытеснения, отдельный draft-контекст,
изменение лимита матриц и внешнее давление на VRAM.
Также проверены ошибка создания конвейера и последующая успешная попытка
создания на том же backend.

```powershell
.venv\Scripts\ctest.exe --test-dir build-deepseek4 --output-on-failure
```

Прошли 6 CTest и 25 Python-проверок (`tools.test_deepseek4`,
`serve.test_deepseek`, `serve.test_vram_settings`), проверка синтаксиса JS.
На реальной Q3 прошли проверки с DSpark и без него: A/B/A, восстановление
продолжения, один выходной токен, отмена, восстановление после отмены и
повторяемый sampling с фиксированным seed. Данные —
`bench/results/deepseek4-pipeline-validation.json` и
`deepseek4-pipeline-plain-validation.json`.

Финальная сборка также прошла `deepseek4-pipeline-final-validation.json` с
DSpark, включая прямую отправку STOP во время prefill. Отмена вернула ноль
токенов, после неё сохранённая сессия восстановилась с теми же token IDs.
Отмена может ожидать завершения текущего графа: в этой проверке ответ пришёл
примерно через 3,1 секунды, несмотря на отправку STOP через 50 мс.
SHA-256 финального `strata-deepseek4.exe`:
`261d8233c94a1f4a2d7d00bfe14a64aaa587141a2404d952f6b8914dd6d48fbb`.

В проверке с DSpark полное повторное prefill продолжения дало другой ответ,
чем инкрементальное продолжение (`full_prefill_identical=false`). Точное
восстановление сохранённого состояния прошло. Это ранее известное ограничение
DSpark/квантованного target при разных формах batch; тест не объявляет полное
prefill и инкрементальный путь эквивалентными.

Результаты относятся к RTX 5090; поведение на других GPU и Linux отдельно
не измерялось. Транспорт не меняет вычислительные типы или правила DSpark.
Прежние ограничения совпадения полного prefill и инкрементальной генерации
описаны в [DEEPSEEK4_DSPARK.md](DEEPSEEK4_DSPARK.md).

## Первое сравнение

Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ, Samsung 990 Pro,
CUDA 13.0, драйвер 581.80. Target `UD-Q3_K_XL`, DSpark Q8_0, два draft-токена,
GPU-кэши target/draft 15/1 ГиБ, контекст 8192, batch 4096, CPU threads 1,
staging 16 МиБ, confidence-фильтр выключен.

После отдельного prompt на 256 токенов: русский запрос про кэши L1/L2/L3,
36 входных и 128 выходных токенов, temperature 0, три повтора с восстановлением
prompt из RAM. Файловый кэш ОС не очищался.

| Путь загрузки | Медиана, ток/с | Диапазон трёх повторов |
|---|---:|---:|
| Прежний | 15,19 | 14,91–15,19 |
| Конвейер, с диагностической трассировкой | 18,01 | 17,89–18,31 |

В этом сравнении прирост медианы **18,6%**. Token IDs совпали для prefill,
первой генерации и всех повторов. DSpark принял 78 из 98 предложенных токенов,
в обоих режимах было 50 раундов. Ни у target, ни у draft не было fallback
или неиспользованных фрагментов конвейера.

Исходные данные: `bench/results/deepseek4-pipeline-before.json` и
`deepseek4-pipeline-after.json`, журналы рядом. Первый холодный decode и prefill
не используются для вывода об ускорении: резидентность файловых страниц
между запусками различается.

## Повторный контроль с prompt 4096

Без подробной трассировки, с теми же настройками и тем же отдельным запросом
на 128 токенов после проверки длинного prompt:

| Путь загрузки | Медиана decode, ток/с | Диапазон трёх повторов | Prefill 4096, с |
|---|---:|---:|---:|
| Прежний | 15,28 | 15,24–15,29 | 44,91 |
| Конвейер | 18,32 | 17,71–18,33 | 22,12 |

Прирост медианы decode — **19,9%**. Все пять наборов token IDs снова совпали
между вариантами. Замеры decode в этой таблице относятся к короткому запросу
про L1/L2/L3, а не к генерации на контексте 4096. Время prefill приведено как
наблюдение: это одиночные последовательные запуски без очистки файлового кэша,
поэтому устойчивое двукратное ускорение prefill не заявляется.

В выборках прогретой генерации процесс занимал примерно 4,1–4,4% всей мощности
32 логических CPU, GPU показывал преимущественно 60–69% загрузки. Во время
prefill CPU занимал около 3,1–3,4%. Это память и обслуживание конвейера;
во всех выполненных графах `cpu_compute_nodes=0`.

Оба конвейера закончили без fallback и неиспользованных фрагментов. Данные:
`bench/results/deepseek4-pipeline-before-4k.json` и
`deepseek4-pipeline-after-4k.json`, журналы рядом.
