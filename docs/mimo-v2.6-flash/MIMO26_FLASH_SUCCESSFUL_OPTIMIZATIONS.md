# Удачные оптимизации MiMo-V2.6-Flash в Strata

Сводка на **2026-10-07**, `Asia/Yekaterinburg`, по сохранённым измерениям
MIMO-04–MIMO-18. Новых замеров при составлении этого файла не проводилось.

Стенд: **Windows, Ryzen 9 9950X, RTX 5090 32 ГБ, 128 ГБ RAM**,
CUDA 13.0.48, sm120, MSVC 19.44, NVIDIA 581.80.
Модель: `H:/models/mimo-v2.6-flash/MiMo-V2.6-Flash-RL-GSQ-RCO-3.5bit.gguf`,
134 982 426 368 байт. Dependency: Unsloth `86ebfef2`.
Матрицы модели вычисляются на GPU; CPU обслуживает чтение весов, передачи,
метаданные кеша, токенизацию и выбор следующего токена.

**Проценты разных серий не складываются.** У каждого опыта свой контроль,
прогрев и фактический объём кеша. Ниже различаются ускорение полной генерации,
ускорение отдельной CPU-операции и выигрыш только при некоторых условиях.

## 2. Фичи, включённые в обычный engine

### 2.1. GPU-кеш экспертов и сохранение горячих весов — MIMO-04

Выбранные router матрицы Q2_K/Q3_K/MXFP4 сохраняются в VRAM. Попадание
обслуживается копией из GPU-кеша; из RAM загружаются промахи. Ключ включает
поколение модели, тензор и expert ID. Подходящие allocations переиспользуются,
публикация записи происходит после завершения копии. Prefill использует hits,
но по умолчанию не заполняет кеш и не меняет его LRU.

Раннее сравнение на одном prompt 24, по 3 запроса с 32 выходными токенами:
native mmap/cache 0 **3,122**, cache 12 **4,445**, cache 14 с live clamp
**4,563 ток/с** по сумме 93 шагов, включая первый запрос. Decode H2D:
**3,578 → 1,191 ГиБ на шаг**. Последние два запроса cache 14 дали 5,508/5,737
против 3,409/3,437 у native. Порядок был последовательным, OS file cache
не сбрасывался: это наблюдаемый выигрыш конфигурации, не изолированный
процент для mmap, prefill policy или увеличения cap по отдельности.

Настройки: `--expert-cache-mib 14336 --expert-reader mmap --expert-cache-prefill off`.
Число 14336 — запрошенный предел, а не гарантированное выделение 14 ГиБ.
Код: [expert_cache.hpp](../../backends/mimo2/expert_cache.hpp),
[sync_runtime.inc](../../backends/mimo2/sync_runtime.inc).
[Измерения](MIMO26_FLASH_CACHE_BENCHMARK.json),
[проверки полной модели](MIMO26_FLASH_CACHE_MODEL_VALIDATION.json).

### 2.2. Асинхронная подготовка и загрузка экспертов — MIMO-05

После получения реальных router IDs планируются gate/up/down текущего слоя.
Один reader читает mmap в ограниченный pinned ring; отдельный H2D stream
копирует данные в device ring. События ready/used защищают повторное
использование слотов. Producer не пишет живой scheduler scratch;
resident weights защищаются от вытеснения до завершения потребления.

Один prompt 24, четыре запроса по 32 токена на процесс, первый — прогрев.
Порядок sync → reader 1 → reader 2 → sync: **5,103 /7,053 /6,914 /5,160 ток/с**.
У reader 1 прирост **36,7–38,2%**, warm TTFT 2,554–2,654 с вместо 3,469–3,738 с
у двух sync-контролей. Два reader оказались медленнее одного.

Настройки: `--expert-readers 1 --expert-chunk-mib 8`. Ring занимает 32 МиБ
pinned RAM и 32 МиБ VRAM. Chunks 4/16 проходили correctness fixtures, но не
ранжировались по скорости полной модели. Значительного перекрытия H2D
с вычислением kernels trace пока не доказал; прирост нельзя целиком
приписывать одновременной занятости GPU и PCIe.

Код: [pipeline_runtime.inc](../../backends/mimo2/pipeline_runtime.inc),
[pipeline_sched.inc](../../backends/mimo2/pipeline_sched.inc),
[общий transport](../../backends/common/expert_pipeline.hpp).
[Измерения](MIMO26_FLASH_PIPELINE_BENCHMARK.json),
[проверки](MIMO26_FLASH_PIPELINE_MODEL_VALIDATION.json).

### 2.3. Несколько экспертных матриц в одном блоке VRAM — MIMO-07

Отдельные cudaMalloc с округлением каждой матрицы до 2 МиБ заменены slots
в общих блоках с целевым размером 16 МиБ. Slots выравниваются до 256 байт,
физический блок — до 2 МиБ; последний блок уменьшается под остаток бюджета.
Allocator индексирует неполные блоки, освобождает пустые и не перемещает
живые указатели.

**6,434 → 6,952 ток/с, +8,1%** в ABBA. При примерно одинаковом reserved
бюджете 12,9 ГиБ полезные веса выросли **9,855 → 12,370 ГиБ**, decode H2D
уменьшился **на 16,7%**. Все сохранённые IDs и logits сравнения bit-exact.
У индекса неполных блоков нет отдельного итогового A/B: весь результат
относится к окончательному allocator, а не к каждому его элементу.

Настройка: `STRATA_MIMO_CACHE_SLAB_MIB=16`.
Код: [expert_slab.hpp](../../backends/mimo2/expert_slab.hpp).
[Описание](MIMO26_FLASH_SLAB_CACHE.md), [измерения](MIMO26_FLASH_SLAB_BENCHMARK.json).

### 2.4. Одна группа доставки на входной тензор — MIMO-08

Вместо ожидания scratch перед каждым диапазоном и завершения копии каждой
матрицы все выбранные эксперты одного scheduler input доставляются до общей
fence. Порядок LRU и cache fills сохранён; fills остаются синхронными.
Pins удерживают источники и служебные хвосты до окончания доставки.

**6,591 → 7,299 ток/с** по ABBA; последний контроль 6,933, поэтому более
осторожная оценка — **+5,3%** к нему. Host fences доставки/fills сократились
на 74,92%, дополнительные scratch fences — на 90,41%; счётчики включают
prefill и decode. Decode H2D отличался менее чем на 0,1%: выигрыш получен
при почти прежнем объёме передачи весов. IDs/logits bit-exact.

Настройка: `STRATA_MIMO_PIPELINE_BATCH=1`.
Код: [pipeline_runtime.inc](../../backends/mimo2/pipeline_runtime.inc).
[Описание](MIMO26_FLASH_TENSOR_BATCH.md), [измерения](MIMO26_FLASH_TENSOR_BATCH_BENCHMARK.json).

### 2.5. Частотный допуск с забыванием истории — MIMO-09

При заполненном кеше частота новой матрицы сравнивается с частотой
кандидата на вытеснение среди 64 старых незакреплённых записей. Редкий miss
может пройти через staging, сохранив горячую запись в VRAM. История учитывает
hits, misses и отказанные admissions; каждые 65536 наблюдений частоты
лениво уменьшаются вдвое. Все выбранные моделью эксперты вычисляются.

**6,923 → 7,692 ток/с**, +11,1% по ABBA и **+8,2% к быстрейшему контролю**.
На прогретых запросах decode H2D уменьшился на 11,8%, объём D2D-заполнений
кеша — на 82,9%, host fences — на 58,9%. Reserved cache почти одинаков:
12,708/12,711 ГиБ. Все IDs/logits bit-exact.

Есть цена обучения: первые запросы новых тем в этой серии передали больше
весов, 251,799 → 347,100 ГиБ H2D. Прирост относится к прогретому корпусу,
а 65536 — число наблюдений матриц, не число токенов или миллисекунд.

Настройка: `STRATA_MIMO_CACHE_DECAY=65536`.
Код: [expert_cache.hpp](../../backends/mimo2/expert_cache.hpp),
[общая история](../../backends/common/expert_frequency.hpp).
[Описание](MIMO26_FLASH_FREQUENCY_CACHE.md), [измерения](MIMO26_FLASH_FREQUENCY_BENCHMARK.json).

### 2.6. Проверки logits без выделения временных строк — MIMO-10

Перегрузка `require(bool, const char *)` убирает создание `std::string`
на каждой успешной проверке значения logits. NaN/Inf checks и ошибки
сохранены. Это оптимизация служебной CPU-работы, а не матричной арифметики.

**7,721 → 7,933 ток/с, +2,74%** в отдельном binary ABBA, +2,63% к быстрейшему
контролю. В CPU microbenchmark число allocations на строку 152576 logits
снизилось **152576 → 0**, время 3,21–3,22 → 0,055–0,059 мс. Полный forward
практически не изменился; IDs/logits полной модели совпали.

Включено в коде без отдельного флага:
[contract.hpp](../../backends/mimo2/contract.hpp).
[Описание](MIMO26_FLASH_FILL_AND_GUARDS.md),
[измерения](MIMO26_FLASH_LITERAL_GUARDS_BENCHMARK.json).

### 2.7. Пакетная передача служебных хвостов — MIMO-13

Нужные CUDA 512-байтовые хвосты соседних экспертов раньше проходили через
reader, H2D ring и ожидания как отдельные маленькие задания. Теперь
отсутствующие хвосты известного маршрута собираются в pinned RAM и
отправляются одним H2D. Затем те же байты доставляются в scratch.
Дополнительная память ограничена 2 МиБ RAM +2 МиБ VRAM.

Процессы ABBA: **8,334 /10,300 /10,372 /7,275 ток/с**. Новый агрегат 10,336,
основной вывод — **+24,02% к быстрейшему контролю 8,334**. Среднее ABBA даёт
+33,05%, но завышено замедлившимся последним контролем.
Число H2D submissions, включая prefill, уменьшилось **935088 → 476626
(−49,03%)**; decode H2D остался почти прежним, 594,088 → 594,201 ГиБ.
IDs/logits bit-exact; runtime проверил отмену, ошибку и восстановление.

Настройка: `STRATA_MIMO_PACK_GUARDS=1`, применяется к mmap +tensor delivery.
В этом A/B запрашивалось 12800 МиБ cache; рабочий default 14336 не менялся.
Код: [pipeline_runtime.inc](../../backends/mimo2/pipeline_runtime.inc).
[Описание](MIMO26_FLASH_HOST_PIPELINE.md), [измерения](MIMO26_FLASH_HOST_PIPELINE_BENCHMARK.json).

## 3. Измеренные ускорения экспериментального MTP

### 3.1. Выходная BF16-голова без полной F32-копии — MIMO-17

Матрица `output.weight` имеет 4096×152576 элементов BF16. В прежнем batched
пути создавалось полное F32-представление размером **2,328125 ГиБ**.
Для 2–8 столбцов добавлена отдельная GPU-проекция каждого столбца обычным
single-column dispatch. Это убирает большую конверсию; MTP depth 1 обычно
проверяет только 2 токена за вызов. All-logit warmup выполняется до заполнения кеша.

Серия A B C C B A на Q4 MTP, первая обученная голова, depth 1/cutoff 0.7:

| Режим | Ток/с | Средний expert cache, ГиБ | H2D, ГиБ/выходной шаг |
|---|---:|---:|---:|
| Без MTP | 10,615 | 12,729 | 1,038 |
| Q4 MTP, прежняя голова | 9,880 | 9,797 | 1,199 |
| Q4 MTP, голова по столбцам | **10,929** | **11,882** | **1,025** |

Прирост **10,62% к прежнему Q4 MTP**, 2,95% к no-draft агрегату и 1,89%
к быстрейшему no-draft процессу. Это сравнение полных режимов с live clamp;
в эффект входят освободившаяся VRAM и увеличение expert cache.
Все 90 ответов совпали по токенам; logits MTP не bit-exact. Исторический
oracle mismatch на 18-м токене этим изменением не устранён.

Отдельная проверка настоящей головы дала bit-exact результат относительно
одиночных CUDA проекций; при 2 столбцах 1,531–1,534 мс против 4,204–4,373 мс.
При 8 столбцах новый путь медленнее; эти времена не равны скорости полной модели.

Опция offline probe: `--target-head-columns 1`. Обычный engine MTP не включает.
Код: [target_head.hpp](../../backends/mimo2/target_head.hpp),
[SpeculativePatches.cmake](../../backends/mimo2/SpeculativePatches.cmake).
[Описание](MIMO26_FLASH_TARGET_HEAD.md), [измерения](MIMO26_FLASH_TARGET_HEAD_BENCHMARK.json).

### 3.2. Одиночная арифметика короткого verification batch — MIMO-18

Совместно включены dense weight matmul по столбцам, quantized routed matmul
по токенам и существующий FA kernel с одной query в tile для MiMo 192/128,
GQA 8/16 на Blackwell. Пакет проверки ограничен на границе 256 позиций KV,
чтобы ранние queries не получали другую геометрию attention. Prefill сохраняет
прежнюю арифметику. Отдельная head-columns проекция здесь не требуется.

В новой A B C C B A серии: **9,878 → 10,447 ток/с, +5,76% к прежнему Q4**.
No-draft 9,525; его быстрейший процесс 9,921, прирост к нему **5,30%**.
Cache почти одинаков: 10,520/10,541 ГиБ. Это результат совместного режима,
не три независимо измеренных ускорения. KV boundary cap исправляет
корректность; собственного speedup для него не измеряли.

Все проверенные oracle logits на corpus и границах 127/255 exact. У реального
Q4 в performance серии 960 IDs и 930 decode строк logits совпали; первая
prefill строка пока отличается до 0,000195. Полное время короткого запроса
с prefill почти прежнее: 6220,69 → 6214,92 мс. Прибавка относится к decode.

Опции probe: `--tokenwise-matmul 7 --target-head-columns 0`.
В launcher 10,93 этот режим **не включён**. Default 0 и отсутствие MTP serving
сохранены. Числа 10,447 и 10,929 из разных серий не определяют общий ranking.
Код: [TokenwisePatches.cmake](../../backends/mimo2/TokenwisePatches.cmake),
[TokenwiseAttention.cmake](../../backends/mimo2/TokenwiseAttention.cmake),
[spec_verify.hpp](../../backends/mimo2/spec_verify.hpp).
[Описание](MIMO26_FLASH_TOKENWISE.md), [измерения](MIMO26_FLASH_TOKENWISE_BENCHMARK.json).

## 4. Выигрыш, который зависит от условий: scatter-copy — MIMO-15

Собственное CUDA-ядро объединяет до 32 диапазонов cache/guard → scratch
в один launch. Descriptors передаются в arguments, дополнительные device
allocations не нужны. Route pins и прежние fences сохраняются.

Основной ABBA: **9,567 → 10,259 ток/с, +7,23%**, к быстрейшему контролю+5,48%.
Copy microbenchmark: 118,027 → 63,163 мкс. Но отдельный русский ABBA
при одинаковом физическом cache 8 ГиБ и точных traffic counters дал
**9,131 → 8,035 ток/с, −12,01%**. Все сравниваемые IDs/logits exact.

Поэтому `STRATA_MIMO_D2D_BATCH=2` доступен только явно, **default 0**.
В сохранённом профиле 10,93 scatter-copy выключен. Это полезный кандидат
для определённых нагрузок, не универсальная удачная настройка.
Код: [scatter_copy.cu](../../backends/mimo2/scatter_copy.cu).
[Описание](MIMO26_FLASH_SCATTER_COPY.md), [измерения](MIMO26_FLASH_SCATTER_COPY_BENCHMARK.json).

## 5. Ускорения CPU-метаданных без доказанного прироста decode

Оба изменения включены в коде и входят в сохранённый MIMO-17. Они не
переносят модельные матрицы на CPU и не дают отдельного гарантированного
процента к токенам в секунду.

| Фича | Что изменено | Подтверждённый результат | Ограничение |
|---|---|---|---|
| MIMO-11: хеш частотной истории | Generation/tensor/expert перемешиваются во всех битах; исчезает концентрация разных слоёв в одних корзинах MSVC | CPU microbenchmark примерно **44× быстрее**; занятые корзины 256 → 27650, максимальная цепочка 141 → 7 | Два full-model ABBA дали средние +5,89% и +4,13%, но второй кандидат уступил быстрейшему контролю; устойчивый прирост decode не доказан |
| MIMO-12: индекс резидентных записей | `unordered_map`, LRU по стабильным указателям, pin count внутри записи; меньше повторных lookup | CPU replay 144000 обращений **63,330 → 32,505 мс, −48,67%** | Новое среднее 8,390 против прогретого контроля 8,401 ток/с; decode практически прежний |

Код обеих фич: [expert_cache.hpp](../../backends/mimo2/expert_cache.hpp).
[Хеш: описание](MIMO26_FLASH_HASH_CACHE.md), [проверки и microbenchmark](MIMO26_FLASH_HASH_VALIDATION.json),
[full-model ABBA](MIMO26_FLASH_HASH_FIXED_BENCHMARK.json).
[Индекс: описание](MIMO26_FLASH_CACHE_INDEX.md), [измерения](MIMO26_FLASH_CACHE_INDEX_BENCHMARK.json).

## 6. Что сохранять вместе с ускорениями

Это рабочая основа, но для каждого пункта нет самостоятельного процента speedup:

- Передача только выбранных router экспертов; веса и quant formats не меняются.
- Mmap и ограниченный pinned/device ring вместо полного закрепления GGUF в RAM.
- Учёт физического VRAM allocation, live clamp, резервы для CUDA workspace
  и global 95% RAM/VRAM. Рост cap не означает принудительное заполнение памяти.
- Route pins, ready/used events, защита scratch, завершение fills до публикации,
  drain при ошибке/отмене и освобождение ресурсов. Удалять эти fences ради
  скорости без новой проверки lifetimes нельзя.
- Повторное использование подходящих allocations и индексы свободных slots
  входят в проверенные cache/slab реализации; отдельный full-model прирост
  каждого элемента не выделен.
- GPU-only audit и локальные precision/stride исправления для BF16/Q2_K/Q3_K/MXFP4.
  Это условия корректной работы, а не дополнительные заявленные ускорения.

Контексты выше 512, длинная работа под внешним memory pressure, HTTP/streaming
с MTP и существенный H2D/compute overlap ещё требуют проверки. Успешные
full-model серии не закрывают исторические F32/mixed synthetic diagnostics,
сохранённые в [статусе](MIMO26_FLASH_IMPLEMENTATION_STATUS.md).
