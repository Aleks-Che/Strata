# GLM-5.3-Flash: загрузка RAM и mmap только для экспертов

Проверка 2026-10-05, Windows / Ryzen 9 9950X / RTX 5090 32 ГиБ / RAM 128 ГиБ.
Модель — `GLM-5.3-Flash-Uncensored-IQ3_XXS.gguf`, 112,31 ГиБ. MTP off,
ctx2048/batch16/threads4, targets95, events2, slabs16, chunk4, main decay131072.
Ревизия `5f57f844e393e7bdbad38d055791523468e41869` + рабочие изменения.

## Реализация

В исходном загрузчике CPU overrides с mmap сопровождаются рекомендацией
попробовать `LLAMA_LOAD_MODE_NONE`. Добавлен опциональный
`STRATA_GLM_EXPERT_LOAD_RAM=1`: загрузка обычных CPU buffers вместо mmap.
`no_host` запрещает попытку закрепить через CUDA весь набор экспертов.
Небольшой pinned ring асинхронного конвейера сохраняется.

Полная загрузка на этом ПК не прошла. Первая попытка без `no_host` пыталась
выделить 104 778 МиБ pinned memory; после его добавления не хватило commit
для следующего CUDA buffer 7 541,55 МиБ. Перед проверкой Windows сообщала
около 99,8 ГиБ доступного commit при 109,2 ГиБ свободной физической RAM;
сами CPU experts требуют 102,322 ГиБ. Файл подкачки и чужие процессы не менялись.
Это ограничение полной private allocation, а не отсутствие достаточной
физической RAM для работающего mmap-профиля.

Поэтому добавлен `STRATA_GLM_EXPERT_RAM_LAYERS=N`, только вместе с load RAM=1:
индексы слоёв `<N` используют private buffers, остальные routed expert tensors
остаются в mmap через существующий lazy loader. Значение — граница индекса,
не количество MoE-слоёв: при N=24 на этой модели private payload равен
51,521 ГиБ, mapped payload — 50,801 ГиБ. Без этой опции private загружаются все.

При N=0 все эксперты остаются mapped, а GPU tensors читаются через staging
без обращения к их file mapping. На Windows сам view файла остаётся целым;
новый режим **не выполняет частичный UnmapViewOfFile**. Он предотвращает
включение GPU-only весов в рабочий набор через mmap при загрузке.

Патч применяется только к GLM в отдельной генерируемой копии loader с проверкой
SHA-256 исходника. Архив и арифметика графа не меняются. Указатели и offsets
экспертов принадлежат модели до завершения конвейера. Windows `VirtualQuery`
проверяет ожидаемый тип backing каждого expert tensor. Native file read modes
1/2 с новой стратегией запрещены; memcpy читает private или mapped источник.

Лимит working set вынесен в RAII guard и применяется перед новой загрузкой,
затем обновляется прежней runtime policy. Вложенные guards восстанавливают
предыдущие ограничения, включая выход при ошибке. Добавлены счётчики private
commit процесса, private/mapped expert payload и `host_memcpy_bytes`.
Старый `pipeline.mmap_bytes` оставлен как совместимый alias для host memcpy;
в private режиме его имя не означает файловое происхождение bytes.

## Измерения

Пять последовательных процессов на одном бинарнике, по шесть warmup и шесть
timed запросов, A/B чередуются: A — 39 prompt + 64 generated, B — 49 + 64.
В каждом столбце медиана трёх timed ответов. Файловый кэш ОС не очищался.

| Режим, в порядке запуска | A, ток/с | B, ток/с | A, полный ответ, с | B, полный ответ, с |
|---|---:|---:|---:|---:|
| Private до слоя 24, reader1 | 8,050 | 9,111 | 10,104 | 9,775 |
| Обычный mmap, reader1 | 7,698 | 7,131 | 11,481 | 13,103 |
| Mmap только для экспертов, reader1 | 7,129 | 7,743 | 11,123 | 11,479 |
| Повтор обычного mmap, reader1 | **9,402** | **9,646** | **8,825** | **9,083** |
| Mmap только для экспертов, reader2 | 8,837 | 9,375 | 9,207 | 9,191 |

Все **60 ответов** совпали с reference token IDs; процессы завершились с exit0.
Это не подтверждает ускорение новой стратегии. Первое сравнение с обычным
mmap выглядело лучше для private RAM, но повтор контроля дал более высокую
скорость. Выбирать настройки по одному медленному контрольному запуску нельзя.

В первой контрольной серии один timed ответ упал до **1,477 ток/с**:
1 544 206 process page faults, 45,580 с суммарного worker read time и 4,437 ГиБ
системного disk read I/O. В новых режимах после прогрева обычно 450–700 faults
на ответ. Но повторный обычный mmap также дал 455–2 666 faults при большем
доступном working-set budget. PDH counters системные, они включают другие
процессы; это не точная атрибуция hard faults движку.

При mmap только для экспертов медиана working set составила **103,187 ГиБ**,
при повторном обычном mmap — **106,624 ГиБ**: разница **3,437 ГиБ** в этих
сериях. Private commit процесса почти одинаков — около 30,9 ГиБ. С private
слоями 0–23 commit вырос до 82,4 ГиБ. Таким образом, N=0 уменьшает резидентный
след загрузки без дополнительной копии 51,5 ГиБ; это отдельный результат по
памяти, а не доказательство прироста ток/с.

Targets95 сохранены. Это реактивные лимиты процесса/кэша, а не жёсткий потолок
для всей ОС: в первом mmap-контроле системная RAM достигала 97,46% при изменении
внешней нагрузки между обновлениями бюджета; максимум VRAM в пяти сериях —
95,26%. В JSON сохранены реальные значения и рассчитанные caps. Не следует
называть targets95 гарантией, что все процессы вместе никогда не превысят 95%.

## Решение

Рабочий профиль остаётся **обычный mmap / reader1 / MTP off**, targets95.
Новые варианты доступны для диагностики и ограниченного RAM budget, но не
включены по умолчанию. Обновлён только backend patch identity локального профиля.

После устранения массовых faults время подготовки порядка 115–126 ГиБ весов
на запрос всё ещё менялось примерно от 7 до 12 с. Это суммарный CPU wall time
reader, а не отдельный таймер PCIe. Следующий эксперимент должен отдельно
измерить CPU memcpy в pinned ring и H2D при одинаковом состоянии памяти,
включая размещение reader threads и вариант записи без заполнения CPU cache.
Увеличение reader count само по себе ускорения не дало.

## Проверки

**26 candidate CTest** и **83 Python tests** прошли. Новые fixtures проверяют
полную private загрузку, mapped экспертов с прямой загрузкой GPU weights,
смешанные private main / mapped MTP buffers, точность конвейера и MTP,
вложенное восстановление Windows working-set limits. Проверяется фактическое
наличие обоих типов buffers в смешанном MTP fixture.

На полной модели с N=0 все **9 912 320 сохранённых F32 logits** совпали
бит-в-бит. Checker загружает NextN weights и rollback slots, но эта проверка
генерирует baseline без MTP. **9 native pipe cases** прошли: две точные
генерации, invalid token, seeded sampling/repeat, cancel prefill/decode и
чистое восстановление после каждой отмены; exit0. Собственные процессы
завершены, после проверки GPU 2 128 МиБ / utilization0.

Полный HTTP, длинный контекст, Linux/HIP и полные Qwen/DeepSeek в этой работе
повторно не проверялись. Полная private загрузка реальной GGUF не дошла до READY;
это не успешный benchmark. Две ошибки загрузки сохранены в manifest.
