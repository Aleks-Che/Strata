# GLM: конвейер и native MTP

Стенд: Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ.
Модель: `GLM-5.3-Flash-Uncensored-IQ3_XXS.gguf`, 112,310 ГиБ.
Зависимость: Unsloth `86ebfef2c6a0f3359a2a07d2c215d61b0fa885c9`.

## Что подключено

`runtime_memory.cpp` использует общий `StrataExpertPipeline`, `ExpertTransport`
и `ExpertDispatch`. После получения router IDs scheduler собирает gate/up/down
с теми же IDs в порядке будущего потребления. Cache hits удерживаются leases;
только misses поступают в ограниченный кольцевой буфер. Четыре pinned slots,
отдельный H2D stream и CUDA events защищают переиспользование slots. Producer
может читать и загружать следующие матрицы во время текущего GPU split.
Неизвестные маршруты следующего слоя не предсказываются. Все выбранные эксперты
и исходные квантованные байты сохраняются.

`mtp.hpp` запускает native NextN-блок из того же GGUF, с общими model/embedding/
output weights. Глубина — 1, 2 или 3 draft-токена. Проверка основной моделью
использует пакет carry + drafts; при отказе откатываются KDA, attention KV и
pooled indexer. Draft history восстанавливается с target features. Первый
draft-step уже использует правильную feature и повторно не исполняется.
STOP дожидается текущего GPU-вызова, затем очищает оба контекста.

Алгоритм sampling — target sample-and-match: sampler основной модели вызывается
ровно один раз на выходной токен. Greedy draft принимается только при совпадении
с этой выборкой. Лишних RNG draws нет; p/q rejection sampling здесь не используется.
Обычные penalties применяются к принятой последовательности.

Main/MTP имеют разные cache keys и историю частот. MTP ceiling входит в общий
VRAM budget. Контроллер по-прежнему использует global NVML и учитывает систему,
чужие процессы, state, scratch и allocator overhead. RAM/VRAM targets 95% —
целевые пределы контроллера, а не резервирование ровно 95% в каждый момент.

## Исправление арифметики короткой проверки

Первый реальный MTP-тест не прошёл. На первых 16 токенах IDs совпали, но max abs
logits был 1,8882; NMSE — 0,0029501. На 64 токенах разошлись и IDs.
[Отчёт до исправления](GLM53_FLASH_MTP_BEFORE_MATVEC_FIX.json).

Послойная проверка одиночного токена и первого токена пакета выявила разницу
между CUDA matvec и batched matmul. На IQ3 эти погрешности накапливались и меняли
маршрутизацию. В generated copy CUDA dispatch короткие пакеты 2–4 теперь
исполняют MUL_MAT по колонкам через тот же путь, что одиночный decode;
для MUL_MAT_ID этот режим применяется только к квантованным expert weights.
Условия CUDA graph synchronization согласованы с этим dispatch. Runtime задаёт
`STRATA_GLM_TOKENWISE_MATMUL=1` и при MTP off, чтобы precision policy была общей.
Оригинальный архив не меняется; перед патчем проверяется SHA-256 исходника.

Повтор CTest обнаружил нестабильный BF16 routed fixture при применении нового
пути к неквантованным экспертам. Для них восстановлен исходный CUDA dispatch.
В тестируемом IQ3_XXS routed weights квантованы, их путь не изменился.
[Регрессия коротких пакетов](GLM53_FLASH_TOKENWISE_QUANT.json): 108 сравнений,
из них 90 бит-в-бит (81 quantized и 9 dense F32/F16/BF16), 18 original routed
F32/F16/BF16 с прежними численными порогами. После исправления полный CTest
прошёл 14/14, затем этот тест прошёл восемь последовательных повторов.

[Полная проверка](GLM53_FLASH_MTP_CHECK.json): 39 prompt + 64 generated, F16 KV,
ctx2048/batch16, TF32/FA off, pipeline on, RAM/VRAM 95%. Все logits MTP-1/2/3
совпали с обычным decode бит-в-бит. Forced reject-first/reject-middle/accept-all,
seeded sampling, отмена draft и следующий чистый запрос также прошли.
Этот checker держит три rollback slots во всех вариантах; его скорости не
используются для выбора глубины по умолчанию.

## Проверка конвейера и протокола

[CUDA trace](GLM53_FLASH_PIPELINE_GPU_TRACE.json) содержит шесть target graphs:
три prefill и три decode. Сумма объединённых H2D-интервалов — 1853,812 мс,
compute-split spans — 775,289 мс, их пересечение — **2,166 мс**. Это небольшое
перекрытие интервалов на фактических CUDA streams. Compute span включает
зависимости/ожидания и не равен времени занятых SM; данные не доказывают
значительное одновременное исполнение H2D и вычислительных kernels.
Оптимизация степени перекрытия остаётся отдельной задачей.

Тот же диагностический запуск подтвердил бит-в-бит все **9 912 320** baseline
F32 logits из P1 и все варианты MTP/rollback/sampling/cancel. Скорости этого
запуска не используются в таблицах: trace синхронизирует границы графов.

Рабочий профиль MTP 1 прошёл [9 native pipe сценариев](GLM53_FLASH_PIPELINE_MTP_PIPE.json)
и [8 HTTP сценариев](GLM53_FLASH_PIPELINE_MTP_API.json): OpenAI/Anthropic JSON/SSE,

## P3.3c: ожидания доставки экспертов

Дополнительный эксперимент 2026-10-04 заменяет host waits в scheduler и runtime
цепочкой CUDA events: предыдущий compute освобождает scratch, copy stream ждёт
это событие, затем compute stream ждёт готовности доставленных весов. User-input
copies и остальные scheduler dependencies сохраняют исходную синхронизацию.
При ошибке/отмене недоставленный остаток дренируется до очистки контекста.

Проверены три режима `STRATA_GLM_COPY_EVENTS`: `0` — исходные host waits,
`1` — пара событий на каждый выбранный диапазон экспертов, `2` — одна пара
на все диапазоны одной экспертной матрицы. Scheduler копирует эти диапазоны
подряд до отправки compute split; переиспользование scratch остаётся защищено.
В последнем запросе предварительной серии число пар событий снизилось
с 69 969 до 4608. Это счётчик за prefill и decode вместе.

Первый sweep показал продолжающийся прогрев после одного warmup request,
поэтому итоговый контроль использует **четыре warmup + пять измеряемых запросов**
на процесс. [Все результаты и конфигурации](GLM53_FLASH_COPY_EVENTS_BENCHMARK.json).

| Режим | MTP | Медиана, ток/с | Диапазон пяти повторов |
|---|---:|---:|---:|
| Исходные host waits | 1 | 8,510 | 8,489–8,661 |
| Events на матрицу | 1 | **9,586** | **9,553–9,655** |
| Events на матрицу | off | 8,978 | 8,887–9,389 |

Рост при MTP 1 — **12,64%** относительно исходных ожиданий в новой контрольной
серии. Дополнительный выигрыш MTP с новым транспортом — **6,76%** относительно
off. Эти проценты получены из этой серии; прежние замеры с одним warmup не
используются как контроль. Все IDs совпали с reference, все процессы завершились
с exit 0. Как и раньше, это один 39-token prompt / 64 output, RAM/VRAM 95%,
ctx2048/batch16/threads4, cache512/chunk4; файловый кэш ОС не очищался.
Скорости MTP 2/3 после этой оптимизации заново не подбирались.

Окончательный режим 2 прошёл 11 full-model проверок: baseline равен сохранённым
9 912 320 F32 logits из P1 бит-в-бит; MTP 1/2/3, forced acceptance 0/1/2/3,
seeded sampling и cancel/clean-next также дали max abs = 0 и NMSE = 0 там,
где сравнивались logits. Добавлены два CTest с режимом 2: native MTP и
streamed/resident/cache/bypass parity; полный набор прошёл 16/16.

В новой диагностике шести target graphs H2D spans составили 1935,988 мс,
compute spans — 1066,873 мс, пересечение — 55,698 мс. Предыдущий диагностический
запуск дал 2,166 мс пересечения. Это отдельные инструментированные запуски
с разным состоянием кэша, а spans включают ожидания: это не измерение занятости
SM и не самостоятельная оценка ускорения. Скорость берётся из таблицы выше.

На этапе P3.3c локальный профиль сохранял MTP 1/cache512/chunk4 и RAM/VRAM 95%; в `env`
установлен `STRATA_GLM_COPY_EVENTS=2`. Значение `0` возвращает исходные ожидания
для A/B. CLI без этой переменной сохраняет исходный режим.
Рабочий профиль прошёл [9 pipe](GLM53_FLASH_COPY_EVENTS_PIPE.json) и
[8 HTTP](GLM53_FLASH_COPY_EVENTS_API.json) сценариев, включая отмену, recovery
и unload; server/engine exit 0. [Точность и trace](GLM53_FLASH_COPY_EVENTS_CHECK.json),
[manifest с командами и hashes](GLM53_FLASH_COPY_EVENTS_VALIDATION.json).

## P3.3d: подача весов, история кэша и allocator

На том же IQ3_XXS / RTX 5090 / Ryzen 9950X проверены дополнительные настройки.
В каждом процессе четыре warmup requests и пять измеряемых запросов, 39 prompt
tokens / 64 output, MTP 1, chunk4/cache512, ctx2048/batch16/threads4, targets 95%.
Это несколько последовательных серий; разные сборки не считаются одним A/B.
[Исходные отчёты, конфигурации и hashes](GLM53_FLASH_STAGING_CACHE_BENCHMARK.json).

| Подача весов | Медиана, ток/с |
|---|---:|
| Один decode reader, обычный pinned ring | **9,198** |
| Один reader, write-combined | 9,020 |
| Два readers, обычный ring | 8,982 |
| Два readers, write-combined | 8,909 |
| Четыре readers, write-combined | 8,343 |

Увеличение числа потоков не помогло этому запросу. Размер ring остаётся
16 МиБ pinned + 16 МиБ device. Общий pipeline сохраняет прежний default одного
decode reader; opt-in GLM параметры не меняют настройки Qwen/DeepSeek.
Byte/guard/cancel/restart fixtures дополнительно проверяют несколько readers
и write-combined в mmap/native/auto режимах.

Новая диагностика CUDA pool показывает reserved/used/unused bytes. В серии
с main decay 32768 без reclaim после одного из запросов pool удерживал 15,28 ГиБ,

Синхронизация copy stream и `cudaMemPoolTrimTo` перед фактическим budget sample
не устранили все такие резервы. Эти вызовы проверялись отдельно, с частотой
контроллера 500 мс при decode, без возврата ожидания на каждый copy range.

Проверен отдельный период старения main history; MTP history сохраняет 4096.
В серии с pool/reclaim main decay 131072 сократил средние вытеснения с примерно
50 тысяч до 1568 за запрос и source/H2D payload с 145,62 до 126,32 ГиБ.
Счётчики охватывают prefill и decode вместе. Медиана выросла с 8,935
(decay4096/reclaim0) до 9,669 ток/с (decay131072/reclaim1) на одной сборке.

Прогрев RAM теперь останавливается также за один 32 МиБ scan chunk до жёсткого
Windows working-set limit: дальнейшее чтение при достигнутом лимите вытесняет
ранее прогретые страницы. В snapshot записывается причина остановки. Ускорение
старта от этой проверки отдельно не измерено; throughput исключает startup.

Полная модель с native allocator / decay131072 прошла **11 проверок**:
MTP 1/2/3, forced acceptance 0/1/2/3, seeded sampling, cancel/recovery.
Все сравниваемые logits точны, а 9 912 320 baseline F32 значений совпали

Новый профиль дал **+4,71%** к медиане прежнего профиля в этом финальном сравнении.
Разница между MTP off и MTP 1 на новых настройках лишь **0,60%**, диапазоны
перекрываются: измеримого полезного выигрыша от MTP здесь нет. По предпочтению
пользователя выбираем off: без draft-вычислений, с примерно **1,50 ГиБ**
дополнительного main cache относительно нового MTP 1. Общая занятая память
почти не падает, поскольку освобождённое место занимает основной кэш.
Электропотребление не измерялось. Один короткий prompt и последовательные серии
не устанавливают универсальный оптимум для всех запросов и контекстов.

Выбранный профиль прошёл [8 HTTP сценариев](GLM53_FLASH_STAGING_CACHE_API.json):
OpenAI/Anthropic JSON/SSE, disconnect во время prefill/decode и clean next request.
INFO подтвердил `spec=0`, native allocator и decay131072; unload и server exit 0.
[Manifest: команды, исходники, бинарники и профиль](GLM53_FLASH_STAGING_CACHE_VALIDATION.json).

Следующий вариант оптимизации базового decode — управляемый GPU arena для
плотного размещения cache entries: и pool, и отдельные CUDA allocations имеют
расходы сверх полезных весов. Для MTP отдельная задача — совместные verify kernels
на 2–4 токена с сохранением порядка вычислений n1. Простое отключение tokenwise
пути уже давало расхождение logits, поэтому для ускорения его не отключали.

## P3.3e: размещение экспертного кэша в общих блоках

`expert_slab.hpp` размещает несколько матриц одинакового размера в одной CUDA
аллокации. Адреса матриц не перемещаются; размеры slots выровнены на 256 байт,
overlap padding остаётся частью загружаемых данных. Заполняется наиболее полный
совместимый блок, чтобы остальные было легче освободить. Новый слот использует
обычный путь `ExpertCache`, включая ready/consumer events и защиту plan pins.
Пустой блок немедленно освобождается; частично свободные блоки видны в telemetry
и учитываются глобальным NVML budget как расходы сверх полезных весов.

Перед выделением нового блока runtime проверяет глобальную свободную VRAM
и оставляет заданный резерв плюс 2 МиБ на округление аллокации/задержку sample.
Тот же дополнительный резерв включён в логический бюджет контроллера. Последний
блок уменьшается до целого числа slots, помещающихся в доступный остаток.
Отказ или недоступный sample возвращает allocation bypass: выбранная матрица
доставляется через существующий uncached pipeline. Это не резервирование памяти
против других процессов. Существующие slots можно переиспользовать без роста
физического объёма. Математика GPU и выбранные эксперты не меняются.

Опция `STRATA_GLM_CACHE_SLAB_MIB=0` сохраняет прежний allocator; значения 4–256
включают blocks указанного целевого размера и имеют приоритет над async pool.
Большая матрица получает отдельный блок, если она не помещается в целевой размер.
Фактический размер блока — целое число slots; верхний предел 4096 slots ограничивает
метаданные на маленьких fixtures.

## P3.3f: прогрев по сохранённым expert IDs

Добавлен необязательный файл подсказок для размещения экспертных матриц. После
завершённого запроса движок сохраняет IDs резидентных экспертов с повторными
обращениями и их frequency scores. При следующей загрузке наиболее частые
матрицы первыми занимают доступный VRAM cache; оставшееся место заполняет
прежний обход слоёв. Веса всегда читаются из текущего GGUF. Роутер, вычисления
модели и KV/hybrid state не меняются; это не P4 session reuse.

Файл содержит только IDs, scores и описание модели/тензоров, без текста запросов,
token IDs или сохранённых состояний. Проверяются путь, размер и время изменения
GGUF, имена/формы/типы тензоров, границы expert IDs и отсутствие дубликатов.
Несовместимый или повреждённый файл отключает подсказки и не перезаписывается;
отсутствующий файл начинает обучение. Запись заменяет файл атомарно. Размер
ограничен 8 МиБ, число записей — 131072. Восстановленный admission score
ограничен 8: обращения нового запроса могут вытеснять старые подсказки.

`tools/benchmark_glm5next_warm.py` отдельно измеряет загрузку, первый токен,
полный ответ и прогретый decode. После девяти обучающих запросов список
замораживается; чередуются перезапуски с подсказками и без них, затем проверяется
новый prompt. Сохранение после запроса находится вне `DONE.decode_ms`, но входит
в измеренное полное время запроса. Без `STRATA_GLM_EXPERT_PROFILE` этот механизм
выключен.

## P3.3g: размещение страниц экспертов в RAM

Измерено 2026-10-04/05 на Windows / Ryzen 9950X / RTX 5090 32 ГиБ /
128 ГиБ RAM, IQ3_XXS 112,31 ГиБ, MTP off, slabs16, RAM/VRAM targets95.
Реализован опциональный прогрев `STRATA_GLM_RAM_WARM_MODE=1`: он пропускает
матрицы, уже находящиеся в GPU cache. Сначала оценивает резидентность CPU/GPU
групп и объём остальных данных процесса. Если по оценке необходимые CPU-веса помещаются
в текущий Windows working-set limit с запасом 256 МиБ, выполняет один полный
проход по ним, позволяя ОС замещать страницы. При изменении общей нагрузки RAM
переоценивает существующий предел; отдельного буфера весов не создаёт.
Если места недостаточно, останавливается на обычном лимите. Запросы после READY
не делают дополнительного RAM-прогрева. Без переменной остаётся прежний режим 0.

`STRATA_GLM_RAM_DIAGNOSTICS=1` добавляет замеры до/после прогрева. Это Windows
`QueryWorkingSetEx`, один адрес на не более чем 1 МиБ payload; запрос не читает
сами веса. Оценка показывает страницы в working set этого процесса. Отсутствующая
страница может оставаться в физическом standby cache. `process_page_faults`
объединяет soft/hard faults; ни один из этих счётчиков не измеряет дисковый I/O.
Диагностика в поисковой серии заняла около 0,1 с; в финальной серии выключена.

При обычном прогреве поисковая серия показала **17,45 ГиБ** резидентных CPU-копий
GPU-весов и только **73,04 из 84,88 ГиБ** нужных CPU-весов. Новый проход оставил
**15,19 ГиБ** копий GPU-весов и **75,73 из 85,13 ГиБ** CPU-весов. Состав GPU cache
слегка различается из-за общего свободного объёма VRAM. В этом сравнении резидентность
CPU-весов выше, но полного удержания нужных страниц нет.

Поисковая сборка: два warmup + три измерения A, затем два запроса B на каждый
из трёх режимов — всего 21 ответ по 64 токена. Разовый прогрев дал
**9,800 → 11,182 ток/с**, но это не окончательное сравнение. Повторный прогрев
перед каждым следующим запросом дал **6,748 ток/с**, медиану полного ответа
**26,03 с** и максимум **47,36 с**. Этот режим 2 удалён из итоговой сборки.
Ещё раньше прототип с `VirtualUnlock` был остановлен после нескольких минут
CPU-времени до READY; он также удалён. Сведения о неудачных опытах сохранены.

Финальная сборка сравнивает только 0/1: порядок сначала 1/0, затем 0/1 после
новых запусков. Первая пара — четыре warmup + пять повторов A и два B на режим;
вторая — один A на режим. Всего 24 запроса; файловый кэш ОС не очищался.
A содержит 39 входных токенов, B — 49; каждый ответ ограничен 64 токенами.
Все IDs совпали с сохранёнными references. Пять warm-повторов A:

| `--mtp 0..3` | Off / число native draft-токенов |

| `STRATA_GLM_POOL_RECLAIM=0/1` | Перед фактической проверкой VRAM budget завершить copy stream и вернуть свободные страницы cache pool драйверу; без переменной 0 для A/B |
| `STRATA_GLM_MEMORY_POOL=0/1` | Обычные cudaMalloc/cudaFree / async pool при поддержке GPU; без переменной pool включён |
| `STRATA_GLM_CACHE_SLAB_MIB=0/4..256` | 0: прежний allocator; иначе несколько матриц в одном CUDA block целевого размера в МиБ; имеет приоритет над MEMORY_POOL |

| `STRATA_GLM_EXPERT_PROFILE_READ_ONLY=0/1` | Обновлять список после завершённых запросов / только читать; без переменной 0, для сравнения используется 1 |
| `STRATA_GLM_RAM_WARM_MODE=0/1` | Прежний / разовый прогрев CPU-весов с пропуском GPU cache; Windows, без переменной 0 |
| `STRATA_GLM_RAM_DIAGNOSTICS=0/1` | Оценка резидентности CPU/GPU групп до/после прогрева; Windows, без переменной 0 |

| `--vram-target-percent 95` | Глобальная цель VRAM |

MTP требует `batch-size >= depth + 1`. Setup экспортирует эти параметры;
CLI без профиля сохраняет opt-in для MTP и pipeline. Рабочие настройки конкретного
ПК находятся в `strata-glm5next.json`.

`STRATA_GLM_TRACE_GRAPHS=1..128` включает отдельный диагностический захват CUDA
events на фактических compute/H2D streams. Он синхронизирует измеряемые графы и
не должен быть включён в throughput benchmarks. Без него CPU submit/wait timers
не выдаются за GPU execution time или доказательство overlap.

## Ограничения

Session snapshots/reuse (P4) ещё не реализованы; запросы начинают с чистого
hybrid state. Длинный sparse-контекст, другие prompts/кванты, Linux/HIP и полные
Qwen/DeepSeek модели в этой работе не проверялись.

В [официальном config](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/c54b8d1/config.json)
`index_share_for_mtp_iteration=true` (проверено 2026-10-04). Выбранный кандидат
пересчитывает draft indexer; повторное использование его выборки между draft
итерациями остаётся отдельной оптимизацией. Наличие флага не объявляется её реализацией.

## Чтение RAM и уплотнение кэша, 2026-10-05

Следующий эксперимент без MTP: [P3.3h](GLM53_FLASH_COMPACTION.md).
Native read, idle slab compaction и два decode readers проверены на IQ3_XXS;
новые опции оставлены выключенными, mmap/reader1 сохранены. Добавлены Windows
page/disk counters: задержки подготовки весов возникают и при малом дисковом I/O.
