# GLM: короткий пакет MMVQ с арифметикой одного токена

2026-10-05. Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ.
Полная модель: `GLM-5.3-Flash-Uncensored-IQ3_XXS.gguf`, 112,31 ГиБ.
Pin Unsloth `86ebfef2c6a0f3359a2a07d2c215d61b0fa885c9` сохранён.

## Изменение

Для численной эквивалентности обычному decode Strata разбивает короткую
проверку MTP на отдельные matrix-vector операции. Ранее каждая из них отдельно
выделяла временный буфер, квантовала вход в Q8_1 и запускала матричное CUDA-ядро.

Новый вариант квантует входы пакета вместе, затем запускает один matvec kernel
для всех 2–4 токенов. Токены становятся независимыми элементами третьего
измерения CUDA grid. Число warps, small-K dispatch, vec_dot и порядок редукции
остаются как при одном токене. Для routed matvec ID эксперта выбирается по
паре token/route. Поддержаны broadcast и отдельные входы для выбранных экспертов.

Это уменьшает число запусков и выделений временных буферов, но не превращает
проверку в GEMM и не гарантирует однократное чтение весов из VRAM. Общий результат
также зависит от CPU-подготовки и H2D экспертов.

[ShortBatchPatches.cmake](../../backends/glm5next/ShortBatchPatches.cmake)
проверяет SHA-256 исходного `mmvq.cu` и создаёт `strata-glm-mmvq.cu`.
Дополнен generated CUDA dispatcher. Оригинальный архив не меняется.
F32/F16/BF16, fused операции и неподдерживаемые размеры сохраняют прежний путь.
Основные условия выбора и преобразование strides вынесены в
[mmvq_token_batch.hpp](../../backends/glm5next/mmvq_token_batch.hpp) и
[mmvq_token_batch.inc](../../backends/glm5next/mmvq_token_batch.inc).

## Управление

`STRATA_GLM_MMVQ_TOKEN_BATCH=0` — прежние отдельные вызовы;
`STRATA_GLM_MMVQ_TOKEN_BATCH=1` — совместный запуск. Без переменной режим
выключен. Задавать до запуска engine: графы CUDA могут сохранять выбранный путь.
INFO возвращает `mmvq_token_batch`. Параметр применяется к подходящим коротким
пакетам, включая prefill, независимо от глубины MTP; одиночный decode не меняется.
`STRATA_GLM_TOKENWISE_MATMUL=1` и ограничения TF32 остаются включёнными.

В benchmark tool добавлен `--token-batch 0/1` с проверкой INFO.
В локальном профиле после проверок включён `STRATA_GLM_MMVQ_TOKEN_BATCH=1`;
сам MTP остаётся выключенным. Для опытов с MTP лучший из проверенных вариантов —
глубина 1, cache ceiling 512 МиБ, chunk4 МиБ. Глубины 2 и 3 оказались медленнее.

## Матрицы и регрессии

[check_mmvq_batch.cpp](../../backends/glm5next/check_mmvq_batch.cpp):
**486/486** случаев, **15 686 784** выходных значения — бит-в-бит с отдельными
одиночными matvec и прежним коротким пакетом. Проверены девять квантов:
Q8_0, Q6_K, IQ2_S, IQ3_S, IQ3_XXS, IQ4_XS, Q2_K, Q3_K, Q4_K;
размеры K×M 512×64, 4096×1536, 1536×4096; 2/3/4 токена;
обычная матрица, routed broadcast и routed per-expert; плотные и padded strides
для входов и IDs. IDs различаются между токенами.

В той же проверке веса постоянно находятся на GPU. CUDA graphs отключены,
порядок control/optimized чередуется четырежды. В каждой серии восемь warmup
и сто операций; время — host wall с синхронизацией, а не чистое kernel time.

| 4096×1536 | 3 | 101,8 | 66,7 |
| 4096×1536 | 4 | 128,2 | 77,7 |
| 1536×4096 | 2 | 90,6 | 75,1 |

На Q2_K, который присутствует в MTP этого GGUF, те же формы и глубины дали

Несмотря на имя файла модели, её основные routed weights имеют типы
IQ2_S/IQ3_S/IQ4_XS, MTP — Q2_K/Q3_K. Их точность также проверена; отдельные
тайминги всех этих типов пока не измерены.

Это измерения небольшого device-resident fixture, не скорость GLM в ток/с.
На итоговой сборке дополнительно прошли **26/26 остальных candidate CTest**
с включённым token batch и **83/83 Python tests**. Численные пороги не менялись.

## Полная модель

Сравнение: два сохранённых prompt A/B из 39/49 токенов, ответы 64 токена,
greedy, ctx2048/batch16/threads4, pipeline/slabs16/targets95. В каждом engine
8 warmup и 6 timed, prompts чередуются. Скорость — 63 / DONE.decode_seconds,
включает draft/verify/repair, sampling и pipe writes, исключает prefill/startup.
Файловый кэш ОС не очищается. Machine-wide paging/disk counters сохраняются
как сведения о внешних условиях, не как точные счётчики чтений данного процесса.

Порядок: исходный бинарник с MTP1; новая сборка с token batch и глубинами
1/2/3/0; та же новая сборка без token batch, глубины 1/0. Все **98 ответов**
совпали с сохранёнными references. Медиана и диапазон трёх timed повторов:

| Вариант | A, ток/с | B, ток/с |
|---|---:|---:|
| Исходный бинарник, MTP1 | 9,342 (8,675–9,401) | 9,508 (9,487–9,794) |
| Новый, token batch on, MTP1 | **9,654 (9,590–9,663)** | **10,187 (10,071–10,237)** |
| Новый, token batch on, MTP2 | 8,522 (7,759–8,778) | 9,433 (9,223–9,790) |
| Новый, token batch on, MTP3 | 7,730 (7,605–7,741) | 8,545 (8,423–8,840) |
| Новый, token batch on, MTP off | 7,301 (6,987–8,021) | 8,629 (7,437–9,666) |
| Новый, token batch off, MTP1 | 9,314 (9,061–9,520) | 9,202 (8,688–9,965) |
| Новый, token batch off, MTP off | 8,044 (7,986–8,089) | 9,550 (8,069–9,658) |

Оптимизированный MTP1 показал более высокую скорость, но контроль B замедлялся
от повтора к повтору. Общий прирост нельзя уверенно приписать только патчу:
ёмкость адаптивного GPU-кэша и нагрузка на RAM различались. Сам MTP off также
нестабилен; сравнение не доказывает его устойчивого отставания. Старые замеры
без MTP достигали 11,2–11,8 ток/с в иных условиях. Поэтому MTP по умолчанию
не включён. Новый матричный путь оставлен включённым в локальном профиле по
результатам изолированного A/B и проверок точности; глобальный default — off.

Для token batch + MTP1 медианы полного времени ответа A/B — 8,747/8,686 с,
TTFT — 2,231/2,535 с. Draft принимает 31/32 и 29/34 предложений.
Verify занимает 6003,6/5695,0 мс, draft 321,6/274,2 мс, repair 17,7/17,0 мс.
H2D за весь запрос, включая prefill: 126,28/122,55 ГиБ; сумма read time
работников — 7,46/7,58 с. Это параллельные таймеры, их нельзя складывать
с decode wall time. При MTP3 H2D возрастает до 157,61/146,14 ГиБ, а основной
GPU-кэш уменьшается: более длинный verify остаётся дорогим.

RAM/VRAM targets во всех сериях — 95%. Максимумы наблюдаемых снимков MTP1
с token batch: RAM 95,54%, VRAM 95,01%, working set 106,03 ГиБ.
В контроле без MTP общая RAM доходила до 99,12%; target — реактивный бюджет,
он пока не удерживает всю ОС строго ниже 95%. Это также ограничивает качество
сравнения скорости. Снимки сделаны на границах запросов, непрерывные пики
памяти не измерены.

Следующая полезная работа — разделить CPU memcpy в pinned ring и H2D,
затем уменьшить повторные переносы экспертов при verify. Одновременно нужен
контроль внешней RAM нагрузки и одинаковой ёмкости cache для A/B. Увеличивать
глубину MTP по одним лишь показателям acceptance здесь невыгодно.

Полный real-model checker прошёл **11 сценариев**: baseline, MTP1/2/3,
forced first-round accept0/1/2/3, seeded target sample-and-match, cancel during
draft и clean after cancel. Все сравниваемые logits совпали (`max_abs=0`,
`NMSE=0`), baseline — бит-в-бит с **9 912 320** сохранёнными F32 значениями.
Через production pipe с MTP1 и token batch on прошли **9 сценариев**, включая
invalid token, seeded repeat, отмену prefill/decode и чистые запросы после отмены;
процесс завершился с exit0. Скорость correctness checker не используется в
таблице: он удерживает MTP weights и три rollback slots даже для baseline.

Длинный контекст, другие модели и Linux/HIP не проверялись. Полный HTTP в этой
итерации не повторялся.
