# MTP в режиме повторяемого B с compaction

2026-10-05. Windows, Ryzen 9 9950X, 128 ГиБ RAM, RTX 5090 32 ГиБ.
Модель — `GLM-5.3-Flash-Uncensored-IQ3_XXS.gguf`, 112,31 ГиБ.

## База сравнения

По просьбе пользователя дальнейшие сравнения MTP в этой серии используют
режим пилота **12,748 ток/с** из [COMPACTION](GLM53_FLASH_COMPACTION.md):
один и тот же prompt B, 49 входных и 64 выходных токена, четыре warmup и
пять timed запросов. Greedy, без сохранения состояния разговора между запросами.
GPU-кэш экспертов и файловый кэш ОС между запросами сохраняются.

Настройки: ctx2048, batch16, threads4, RAM/VRAM targets95, mmap, reader1,
compaction on, slabs16 МиБ, copy events2, main cache decay131072, pool0,
chunk4 МиБ, обычная pinned memory. Бинарник P5.3c с optional token-batch MMVQ.
Модель, зависимости и код исполняемого файла в серии не менялись.

Повторный контроль без MTP дал **12,889 ток/с**, диапазон **12,823–12,939**,
медиана полного ответа **7,287 с**. Исходный быстрый режим воспроизведён.
Это не новое ускорение относительно исторических 12,748: процессы запущены
в разное время. Результаты A/B с чередованием разных prompts остаются отдельной
нагрузкой; их прежние 9–10 ток/с не служат базой для процентов этой серии.

Скорость — 63 / DONE.decode_seconds: включает draft, verify, repair, sampling
и запись в pipe, исключает загрузку и prefill. Полное время ответа и TTFT
сохраняются отдельно. Все варианты запускаются последовательно, кэш ОС
принудительно не очищается.

## Воспроизведение

Эталон B вынесен в отдельный [JSON](GLM53_FLASH_COMPACTION_B_REFERENCE.json).
Для локального `strata-glm5next.json` с указанными выше model/context/batch/threads:

```powershell
python tools/benchmark_glm5next_mtp.py --profile strata-glm5next.json --reference docs/GLM53/GLM53_FLASH_COMPACTION_B_REFERENCE.json --output build-local/glm-compaction-mtp-repeat.json --depths 0,1,2,3 --warmups 4 --repeats 5 --read-mode 0 --cache-compact 1 --decode-readers 1 --copy-events 2 --main-cache-decay 131072 --pool-reclaim 0 --memory-pool 0 --cache-slab-mib 16 --write-combined 0 --mtp-cache-mib 512 --chunk-mib 4 --token-batch 1 --paging-counters
```

Не добавлять `--second-reference` при воспроизведении этого режима.
Чередование A/B можно запускать отдельно для проверки переносимости результата.
JSON benchmark хранит фактический профиль каждого варианта и hash бинарника.

## Совместный временный GPU-буфер

Следующая оптимизация устраняет отдельное резервирование scratch для основной
модели и NextN. Они выполняются последовательно; KV, recurrent state и модельные
веса сохраняют независимые allocations. Опциональный `STRATA_GLM_MTP_SHARED_SCRATCH=1`
объединяет только freshly reserved CUDA0 compute buffers до первого выполнения.
Владение буфером учитывает обе стороны; освобождение одной не инвалидирует другую,
рост графа приводит к безопасному отдельному выделению. INFO показывает освобождённые
при настройке bytes, каждый MTP report — сохраняется ли sharing фактически.

Полная GGUF освобождает **993,553 МиБ VRAM**. Во всех 11 численных сценариях
sharing сохраняется, сравниваемые logits совпадают бит-в-бит; baseline также
совпал с **9 912 320** сохранёнными F32 значениями. Это проверка MTP1/2/3,
forced rejection, seeded sampling и восстановления. Она использует prompt A
и три recurrent rollback slots, поэтому не служит замером скорости режима B.

При реализации обнаружена и исправлена проблема резервирования: включение
NextN hidden outputs после первоначального reserve меняло liveness графа,
и первое выполнение снова выделяло отдельный буфер. Теперь после установки
output flags оба контекста завершают reserve до объединения. Численные тесты
и benchmark проверяют не только начальное освобождение памяти, но и сохранение
общего буфера после запросов. Рост графа по-прежнему безопасно отделяет буфер;
такой benchmark помечается ошибкой проверки sharing.

Синтетический allocator fixture чередует записи/вычисления в двух контекстах,
проверяет оба порядка освобождения, рост любой стороны и отказ для CPU buffers.
Флаг выключен по умолчанию. Контексты должны исполняться последовательно,
синхронизироваться и обновлять входы при переключении; этот режим не подходит
для одновременного draft/target execution.

## Проверки logits без временных строк

Общий `require(bool, const std::string &)` неявно создавал `std::string`
из диагностического литерала при каждом вызове. В проверках target/draft logits
это происходит внутри циклов по словарю. Добавлена перегрузка с `const char *`:
при успехе строка не создаётся, при ошибке по-прежнему выбрасывается
`std::runtime_error` с тем же сообщением. Динамические сообщения продолжают
использовать прежнюю перегрузку. Проверки конечности чисел сохранены.

Инструментированный CPU benchmark MSVC `/O2` для 154 880 × 64 значений
зафиксировал **9 912 320 → 0 allocations** на успешном пути. Этот отдельный
тест с подменённым `operator new` показывает устранённую работу, его времена
не являются оценкой ускорения полной модели. Изменение полезно также для
обычного decode, поэтому сравнение MTP проводится с новым MTP-off контролем.

## Полная генерация после изменений

Та же нагрузка B, четыре warmup и пять timed запросов. Последняя сборка:
`ae83ef59c5904fe911c0ab470fb720182851a6c1c8d56000bd8773b9f768be64`.

| Вариант | Медиана, ток/с | Диапазон | Полный ответ, с |
|---|---:|---:|---:|
| Shared scratch, до исправления `require` | 11,764 | 3,220–12,294 | 8,101 |
| Shared scratch + исправленный `require` | 10,644 | 1,835–12,949 | 12,469 |
| Раздельный scratch + исправленный `require` | 11,082 | 9,883–12,905 | 8,589 |
| MTP off, исправленный `require` | **13,373** | **13,019–13,637** | 7,528 |

Все **36 ответов** этих четырёх серий совпали с reference, exit0.
Вместе с первым подбором — **108 законченных benchmark responses**.
Отдельный ранний запуск остановлен после двух правильных warmup-ответов
0,406 и 5,582 ток/с для исследования задержек; он не включён в медианы.
Повторный запуск выполнен полностью. Все холодные результаты сохранены.

Медиана draft после исправления `require` — **133,7 мс** с раздельным scratch
и **135,8 мс** с общим; в первой серии с раздельным scratch было **256,6 мс**.
Но verify в новых сериях занимает **5 495 / 5 733 мс**, поэтому сокращение
CPU overhead не превратилось в выигрыш над обычным decode. Это последовательные
серии, а не чистая оценка процента ускорения одного изменения.

Общий буфер действительно увеличил основной GPU-кэш: **16,874 против 15,960 ГиБ**
на итоговой сборке. При этом передача весов за запрос составила **96,104 против
99,939 ГиБ**. Без MTP кэш — **17,733 ГиБ**, передача — **85,694 ГиБ**.
Эти объёмы включают prefill и не являются отдельным счётчиком decode.
Принятие MTP1 во всех завершённых запросах B — **29/34**, то есть высокая доля
принятия сама по себе не компенсирует переносы и стоимость verify.

В медленных timed запросах shared scratch были 0,85–0,94 млн machine-wide
transition faults, при этом дисковое чтение составляло лишь 0,5–5,3 МБ.
Это не объясняется большим чтением GGUF с диска. Working set находился у
hard cap, RAM — около 95%; точный вклад возврата страниц, CPU memcpy и GPU
ожиданий здесь ещё не разделён. Долгий первый warmup был и с раздельными
буферами. Называть shared scratch установленной причиной провалов нельзя.
Sampled maxima в итоговых сериях: RAM **95,24%**, VRAM **95,29%** при targets95;
эти targets не гарантируют точный потолок общего потребления всей ОС.

Исходные ответы, конфигурации, counters, временные ряды и hashes:
[benchmark](GLM53_FLASH_MTP_SHARED_SCRATCH_BENCHMARK.json).

## Решение и проверки

### Отдельный локальный запуск без MTP

В корне проекта создан `run-glm53-no-mtp-13_37.bat`. Двойной щелчок запускает
сервер и открывает интерфейс `http://127.0.0.1:8081` после загрузки модели.
Профиль — `strata-glm53-no-mtp-13_37.json`: MTP0, compaction1, mmap/reader1,
RAM/VRAM95, ctx2048/batch16/threads4 и остальные настройки итогового контроля.
Логи и статистика сохраняются отдельно от обычного профиля.

Движок скопирован в `build-local/glm53-no-mtp-13_37/strata-glm5next.exe`,
SHA-256 `ae83ef59c5904fe911c0ab470fb720182851a6c1c8d56000bd8773b9f768be64`.
Последующие сборки основного backend не перезаписывают эту копию. Рядом
сохранён `manifest.json` с происхождением замера. Скрипт и профиль локальные,
как остальные созданные setup файлы, и исключены из Git существующими правилами.
**13,373 ток/с** относится к указанному выше прогретому repeated-B тесту;
скорость произвольного диалога может отличаться.

### Итог итерации

Перегрузка `require` оставлена в обычном коде. MTP остаётся **off** в локальном
профиле; `STRATA_GLM_MTP_SHARED_SCRATCH` по умолчанию **off**. Экспериментальный
общий буфер корректно освобождает память, но устойчивого выигрыша скорости
не показал. Compaction включён в профилях этой серии; общий рабочий профиль
не меняется по результатам одного повторяемого prompt.

Итоговая сборка прошла **28 CTest** и **83 Python tests**. Неизменённые 486 MMVQ
matrix cases из P5.3c не запускались повторно. Full GGUF проверка 11 сценариев
и 9,9 млн сохранённых logits относится к shared scratch до добавления
перегрузки `require`; итоговые pipe/benchmark сравнения используют новую сборку.
Итоговый production pipe прошёл **9 сценариев**: два точных greedy-ответа,
неверный token ID, seeded sampling/repeat, cancel в prefill/decode и чистый
запрос после каждой отмены. Exit0, sharing сохранился во всех MTP reports.
Процессы завершены; после проверки GPU: 2 032 МиБ, utilization0.

[Численная проверка](GLM53_FLASH_MTP_SHARED_SCRATCH_CHECK.json),
[pipe](GLM53_FLASH_MTP_SHARED_SCRATCH_PIPE.json),
[manifest, команды и CPU benchmark](GLM53_FLASH_MTP_SHARED_SCRATCH_VALIDATION.json).

Для повторения итогового сравнения к команде выше добавить
`--shared-scratch 1` и выбрать `--depths 1,0`; отдельный контроль MTP1 —
`--shared-scratch 0 --depths 1`. Остальные параметры, reference B, четыре
warmup и пять timed запросов оставить теми же. Shared scratch действует
только при MTP; при `--mtp 0` INFO сообщает нулевую экономию.

Далее полезно отдельно измерить CPU memcpy, H2D и ожидания verify после prefill,
а также удержание нужных страниц RAM при hard working-set cap. Увеличение
глубины draft и cache ceiling в этой нагрузке уже не дало выигрыша.
Длинный контекст, полный HTTP, Linux/HIP и полные Qwen/DeepSeek в этой итерации
не проверялись.
