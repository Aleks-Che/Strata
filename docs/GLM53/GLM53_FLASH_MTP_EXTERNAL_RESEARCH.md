# GLM-5.3-Flash: внешние реализации MTP

Проверено **2026-10-05**. Исходный этап — исследование публичных результатов
и исходников, а также разбор прежних локальных логов. На этом этапе новые
inference-тесты не запускались и движок не менялся. Источники, SHA-256 скачанных
артефактов и локальные таймеры: [research evidence](GLM53_FLASH_MTP_EXTERNAL_RESEARCH.json).

Последующее внедрение и 114 сравнительных запросов описаны отдельно:
[cache-only catch-up](GLM53_FLASH_MTP_CACHE_ONLY.md). Оно сократило repair,
но устойчивый общий выигрыш MTP на RTX 5090 не подтвердился; default остаётся off.

Рабочие реализации с измеренным ускорением существуют. Для Strata полезнее
переносить отдельные изменения и проверять их на IQ3_XXS, чем заменять backend:
публичные результаты ниже получены на другом оборудовании и других квантах.

## Опубликованные сравнения

| Реализация / оборудование | Без MTP → с MTP, ток/с | Условия |
|---|---:|---|
| [Unsloth / llama.cpp](https://unsloth.ai/docs/models/glm-5.3-flash#faster-inference-and-mtp-support), 1× B200 | 58,6 → 86,5, **+47,6%** | UD-IQ1_S, MTP2; руководство обозначает контекст как 4096, исходный PR — как short |
| [SparkLab MTP-004](https://github.com/sixteen-miles-labs/sparklab/blob/main/benchmarks/gb10/results/GB10-GLM53-MTP-004.json), 1× DGX Spark 128 ГиБ | 5,516 → 7,232, **+31,1%** | NVFP4 target, FP8 MTP, эксперты подгружаются с диска; одинаковый кэш 6149 slots |
| [SGLang, опыт Stepan Mazurov](https://mazurov.dev/posts/glm-speculation-benchmark/), 2× GB10 | код: 14,74 → 25,75, **+74,7%**; проза: 14,66 → 23,51, **+60,4%** | NVFP4, TP2, native MTP3; 1 warmup + 3 повтора, ответы 512 токенов; скорость всей фазы, а не только steady decode |

У Unsloth заявленные 3,3× включают другие оптимизации длинного контекста.
Это не выигрыш только от MTP. Наш pin `86ebfef2c6a0f3359a2a07d2c215d61b0fa885c9`
уже относится к этой ветке [PR #27754](https://github.com/ggml-org/llama.cpp/pull/27754).
Повторное подключение той же реализации само по себе ничего не добавляет.

SparkLab ближе по задаче подгрузки экспертов, но у GB10 объединённая память,
Linux ARM64 и другой формат весов. MTP занимает около 7,25 ГиБ и сокращает
кэш с 6711 до 6149 slots. Против ранее опубликованного режима без MTP с большим
кэшем выигрыш составляет **15,3%**, не 31,1%. Проверен один math prompt:
54 входных / 256 выходных токенов, greedy, один замер на ширину и дополнительный
повтор MTP3. Исходное дерево содержало незакоммиченные изменения; широкие проверки
качества и длинного контекста не завершены. MTP2/3 совпали с контрольным output
hash, MTP1/4 — нет из-за порядка BF16-вычислений. Это ограниченное свидетельство
ускорения, не подтверждение полной численной эквивалентности всех режимов.

В опыте SGLang DFlash быстрее native MTP на коде, но это отдельная draft-модель
и другой расход памяти. Результаты DFlash не следует записывать как ускорение
встроенного NextN-блока GLM.

## Что можно перенести

### 1. Изменения графа в новом llama.cpp PR

[PR #29928](https://github.com/ggml-org/llama.cpp/pull/29928), открыт 3 октября,
проверенный head `1e24094d7`, ещё проходит review. Diff прочитан и сопоставлен
с локальным `glm5next.cpp`. Два отдельных изменения:

- Перестановка осей gathered DSA attention позволяет использовать batched GEMM
  и более быстрый transpose. Автор сообщает для 4-token verify: QK 35,2 → 2,9 мс,
  AV 57,2 → 3,4 мс, transpose 16,2 → 1,2 мс. В этом сообщении нет достаточного
  описания стенда, поэтому это ориентир для профилирования, не ожидаемый выигрыш.
- Режим `headless` при заполнении draft KV сохраняет необходимые записи кэша,
  исключая неиспользуемые query/attention/FFN/output вычисления. Заявлено
  6,9 → 0,33 мс для catch-up из четырёх токенов. На review запрошены отдельный PR
  и проверка realloc/reuse графа; считать изменение готовым upstream нельзя.

В обсуждении есть отдельный тест на **6× RTX 3090**, Q2_K/Q3_K 3,20 bpw:
+17% на контексте 8K/32K, практически ноль на пустом контексте. Это обычный
`llama-bench` PR-vs-base, **не MTP on/off**.

Применимость к Strata — вывод из локального кода:

- `Mtp::catch_up()` вызывает `draft_decode()`, который всегда запрашивает
  logits последней строки. Затем эти logits и draft hidden не используются:
  `pending` берётся из target. Кандидат всё равно исполняет полный NextN-блок.
  Здесь можно добавить отдельный режим заполнения KV без ненужных выходов.
- Одного `logits=false` недостаточно: нужен соответствующий граф с корректными
  cache writes, контрактом `embeddings_nextn_masked`, нулевым числом выходов и
  безопасным переиспользованием графа. Проверять prefill, полное принятие,
  rejection и границы kpool; обычный draft должен сохранить logits/hidden.
- Наш короткий профиль ctx2048 не включает scoring sparse indexer: порог
  `indexer_top_k + indexer_kpool - 1` равен 2051. У нового upstream другой
  attention graph. Его ускорение gathered DSA нельзя обещать для текущего
  короткого теста или применить копированием diff без адаптации.

Совместимость также изменилась: новый upstream использует `glm5-next`, наш GGUF —
`glm5next`. [Unsloth PR #239](https://github.com/unslothai/llama.cpp/pull/239)
добавляет загрузку старых имён архитектуры и metadata. Прямое обновление pin
без проверки loader/graph/state API и наших generated patches не подготовлено.

### 2. Приёмы SparkLab для подгрузки экспертов

[OPT-005](https://github.com/sixteen-miles-labs/sparklab/blob/main/benchmarks/gb10/results/GB10-GLM53-OPT-005.json)
объединяет специализированный skinny LM-head и перекрытие shared-expert compute
с загрузкой routed experts: MTP3 7,232 → 7,436 ток/с, **+2,82%**, два повтора.
Отдельная target-only пара для перекрытия дала +2,84%, но содержит лишь один
замер на режим. Идея применима к нашему pipeline после проверки фактической
зависимости графа и CUDA timeline. Это не доказательство отсутствия overlap у нас.

[OPT-006](https://github.com/sixteen-miles-labs/sparklab/blob/main/benchmarks/gb10/results/GB10-GLM53-OPT-006.json)
сохраняет KDA/conv-состояния для принятого префикса и убирает повторные проходы
target: 7,513 → 7,769 ток/с, **+3,40%**, медиана трёх процессов против одного
свежего control; дополнительно 0,547 ГиБ памяти. В Strata target уже откатывается
через `llama_memory_seq_rm`, без такого replay. Наш draft catch-up — другая
операция. Повторно реализовывать этот приём ради чужих +3,40% не требуется.

У SparkLab [Apache-2.0](https://github.com/sixteen-miles-labs/sparklab/blob/main/LICENSE).
В этом исследовании прочитаны benchmark/config/README; его runtime-код не
переносился и не исполнялся.

## Почему локальный MTP почти не ускорял генерацию

Прежний [сравнительный benchmark](GLM53_FLASH_STAGING_CACHE_MTP_BENCHMARK.json):
Windows / Ryzen 9950X / 128 ГиБ RAM / RTX 5090 32 ГиБ, IQ3_XXS,
39 prompt + 64 output, 4 warmup + 5 timed, RAM/VRAM targets95, **до slabs16**.

| Показатель | MTP off | MTP1 |
|---|---:|---:|
| Медиана decode, ток/с | 9,902 | 9,843 |
| Принятые / предложенные | — | 31 / 32, 96,875% |
| Основной expert cache, ГиБ | 12,744 | 11,246 |

Заново разобраны существующие `STRATA_GLM_MTP` записи пяти timed-запросов:
медиана draft **263,0 мс**, verify **5736,8 мс**, repair **156,6 мс** на ответ.
Verify занимает **93,31%** суммы трёх измеряемых участков. Это host wall time
с ожиданиями, не распределение времени CUDA kernels; некоторые операции
вне этих участков учитываются только общим decode timer.

При неизменных прочих затратах полное устранение timed repair даст около
**2,55%** ускорения: медиана `decode / (decode - repair) - 1` по пяти запросам.
Это не предел возможной пользы для другого контекста, MTP2/3 или cache traffic.
Но обещать +30–50% только от headless catch-up на данном тесте оснований нет.

Основные кандидаты на проверку:

- [CandidatePatches.cmake](../../backends/glm5next/CandidatePatches.cmake)
  разбивает короткие MUL_MAT и quantized MUL_MAT_ID на отдельные токены.
  Это уменьшает возможность совместного использования весов при verify.
  Режим введён ради точности: без него ранее расходились logits и затем IDs.
  Нужен быстрый short-batch kernel с проверенной арифметикой, а не простое
  отключение `STRATA_GLM_TOKENWISE_MATMUL`.
- MTP отнимает примерно 1,50 ГиБ основного кэша в прежнем сравнении. Нужно
  измерять фактические workspace/cache/H2D и размещение draft, не только
  процент принятия. Полностью резидентный FP8 MTP SparkLab слишком велик
  для прямого переноса его схемы на 32 ГиБ VRAM.
- После внедрения slabs16 отдельного сопоставимого MTP off/1/2/3 sweep
  в сохранённых отчётах нет. Поздние 11,2–11,8 ток/с без MTP нельзя напрямую
  сравнивать со старым MTP1 9,843.

## Следующий эксперимент

1. На текущей сборке и slabs16 повторить off/1/2/3, чередуя порядок; одинаковые
   prompts, greedy, warmup, output lengths и RAM/VRAM limits. Записать TTFT,
   decode, draft/verify/repair, H2D, cache sizes и реальные чтения диска.
2. Первым небольшим изменением отдельно проверить draft cache-only catch-up
   по идее PR #29928. Сохранить старый путь для A/B; проверить все cache writes,
   forced rejection и logits/IDs, включая продолжение после catch-up.
3. Основную работу по ускорению направить на verify: сначала профилировать
   токеновые matmul и копирование экспертов, затем отдельно менять short-batch
   kernels или планирование shared expert. Не смешивать это с обновлением
   upstream и изменением точности в одном эксперименте.
4. Gathered DSA и повторное использование MTP indexer проверять отдельным
   длинным контекстом после валидации sparse path. В ctx2048 они не являются
   обоснованной причиной низкого ускорения.

Ни один внешний прирост не записан как результат Strata. На этапе исследования
рабочий профиль оставлен MTP off; последующие локальные измерения приведены
в отдельном отчёте, указанном в начале файла.

## Проверка отдельного Q1 draft, 2026-10-05

В примере Unsloth IQ1 относится к полной основной модели. Чтобы проверить
состав её MTP, прочитан заголовок последнего шарда `UD-IQ1_S` на revision
`621d456e93e926e4b52f85cff5f634358c1828f9`: загружено только 16 МиБ через HTTP
Range, без скачивания всей модели. [Источник](https://huggingface.co/unsloth/GLM-5.3-Flash-GGUF/tree/621d456e93e926e4b52f85cff5f634358c1828f9/UD-IQ1_S),
[29 tensor descriptors и сравнение](GLM53_FLASH_MTP_IQ1_HEADER_CHECK.json).

| Встроенный MTP | Веса, байт | Routed experts |
|---|---:|---|
| Наш Uncensored-IQ3_XXS | 2 806 853 760 | down Q3_K, gate/up Q2_K |
| Unsloth UD-IQ1_S | 2 787 995 776 | down Q3_K, gate/up Q2_K |

Экономия — **17,984 МиБ, 0,672%** веса MTP. Разница приходится на несколько
dense/shared/indexer tensors; одноразрядных routed experts у этого MTP нет.
Сравнивались формы, типы и размеры, а не значения весов или acceptance.
Загрузка всей IQ1-модели ради замены только MTP не обоснована этим размером.

Найден [отдельный MTP Q4_K, 4,3 ГиБ](https://huggingface.co/neuralll/GLM-5.3-Flash-MTP-GGUF).
Его карточка требует другой fork с загрузчиком MTP-only и архитектурным именем
`glm5-next`; в текущем Strata такого загрузчика нет. Он больше нашего блока.
В просмотренных источниках готовый MTP-only IQ1 не найден. Отдельная
квантовка draft в IQ1 остаётся экспериментом: нужны подходящие исходные веса,
калибровка и измерение принятия/скорости при неизменной основной модели.

Реализация первого эксперимента со старым набором весов описана в
[cache-only catch-up](GLM53_FLASH_MTP_CACHE_ONLY.md).
